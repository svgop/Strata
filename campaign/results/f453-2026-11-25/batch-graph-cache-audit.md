# f453 — batch window-graph cache audit (read-only; 2026-11-25)

Scope: read-only audit of the batch-lane CUDA-graph cache. Nothing was built, run, signalled or modified; the only file written is this report. Labels: **[S]** UNCONFIRMED STATIC ANALYSIS (read from code, not measured); **[L]** derived from `logs/custom-iq3_s.log` with grep/awk (log lines, not an instrument); **[C]** CUDA-API claim, unconfirmed. Short names: `verify.cpp` = src/core/verify.cpp, `generate.cpp` = src/program/generate.cpp, `verify.hpp` = include/strata/core/verify.hpp.

## 0. The premise is a log-aggregation artifact — read this first [L]
- `logs/custom-iq3_s.log` (558,525 lines) holds **40 engine starts** (`engine started:` lines 9 … 551517; first 2026-11-22 15:59:10, the live one 2026-11-25 01:59:05 at line 551517; 39 of them print the `STRATA_COHORTS=2 on` banner). The graph maps are per-`Verifier` members (verify.hpp:397) and every process starts empty, so **the 1,254 captures / 95 layouts / 55-54-51-47-41 repeats are whole-file totals over 40 processes, not one boot.** All 95 strings already appear in the first segment (352 captures, lines 115-424628).
- The live boot (lines 551517-end): **30 captures over 28 distinct layouts** — 12 inside cohort rounds (6-row 4, 4-row 6, 2-row 2), 18 in the single-verifier path (≤ 3 active slots). It ran 1,528 cohort rounds, 1,466 of shape `A.S=6 B.S=6`, totalling 39.6 s of `cohorts: windows done` time. No VRAM eviction line in the whole file (0 × `no VRAM for a new window graph`); no `ar_off_` flip in the live boot (0 × `doorbell graph runs the windows` / `zero-doorbell graph`).
- Price of one in-round capture: the round's `windows done` minus the mean of the adjacent capture-free rounds of the same shape. `A.S=6 B.S=6`, one capture: **n=88, median +11.2 ms** (p25 9.3, p75 13.6, min 5.4, max 25.9 — all positive). Other shapes, one capture: +8.6 ms (n=246, one 238 ms outlier) and +9.4 ms (n=46); two captures: +12.1 (n=47), +16.0 (n=7). Confound: a capture round is also the first round after the active set changed. One printed capture = 1 window graph + up to 2 commit graphs (G4).
- Consequence: the cohort lane pays ≈ 12 × 10 ms ≈ **0.12 s per boot against 39.6 s of cohort window time (≤ 0.3%)**. Capture cost is an admission-time latency tax (one ~10 ms round per new layout), not a throughput lever of the size 1,254 suggested.

## G1. The layout key
- Key = `[hbase, rows[0], …, rows[S-1], ar_off]`. `batch_key` pushes `hbase` then every `rows[t]` (verify.hpp:407-413); `bkey` appends `ar_off_ ? 1 : 0` — "#871: the doorbell variant has its own graphs" (verify.hpp:402-406); the commit key is `bkey + [parity]` (verify.hpp:446-449). `rows[t]` is the **slot id owning row t**, S the row count. Nothing is derived: the rows are baked into the exec.
- `hbase` depends on the caller: `run_slot_rows` → `stage_batch(rows, S, 0, …)` (verify.cpp:4047); `batch_stage_rows` → `stage_batch(rows, S, rows[0], …)` (verify.cpp:4246). [S] On one GPU `hbase` reaches the recorded graph only as `hrow0` in the two hand-off sites, guarded by `if (lb_ > 0)` (:1301-1302) and `if (le_ < g.n_layers)` (:2402-2403); the cohort verifiers are `set_stage(0, -1, nullptr, nullptr)` (generate.cpp:9690) with `if (le_ < 0) le_ = g.n_layers` (verify.cpp:878). So without a layer split `hbase` changes no node and only splits the key space: cohort A's `1,1,2,2,0,0` is `[1,1,1,2,2,0,0,ar]` on `ver`, and the same rows through the single-verifier path are `[0,1,1,2,2,0,0,ar]` on the same `ver` — two execs for one graph. [L] Seen at lines 419388 (no `cohorts:` line before it) and 419404-419405 (`cohorts: round A.S=6 B.S=2`, same layout).
- Per window: with `n_active > o.batch / 2` (generate.cpp:12593) the cohort path runs `collect(lo, hi, …)` per cohort (:12614-12651): walk the span's active slots cyclically from `next_cur` while `w.S + (mtp_use ? 2 : 1) <= kVerifyMaxT` (:12623; 8, verify_kernels.hpp:21); `rows_b = mtp_use && bs[b].draft_ready ? 1 + std::min(bs[b].n_draft, batch_draft_depth) : 1` (:12631-12632); `next_cur = ((size_t) (w.active[w.A - 1] - lo) + 1) % span` (:12650). With ≤ 3 active slots the same walk covers all 6 slots on `ver` (:12977-13005).
- Two rows per slot: `batch_draft_depth = 1` unless STRATA_BATCH_DRAFT_DEPTH is set (generate.cpp:5593-5598; the launcher does not export it). `draft_launch` refuses `min_p <= 0.0f` (mtp.cpp:1907) and its readout starts `int n = 1;` — "the first proposal always" (mtp.cpp:2006-2013); the live argv has `--spec-min-p 0.5` (log line 551517). So the min_p walk only trims steps ≥ 2, which the depth cap already removes: n_draft ≥ 1 always. `draft_ready` is set at admission by `draft_first` (generate.cpp:17429-17436) and re-armed in every tail (:12918), so every active slot is 2 rows from its first window — hence the 2/4/6-only histogram; an odd S needs a slot whose draft failed.
- Steady 6-slot decode: all three slots of a cohort active pins `next_cur = 0`, so exactly **one layout per verifier** (`0,0,1,1,2,2` on ver, `3,3,4,4,5,5` on ver_b), ×2 if `ar_off_` flips (`refresh_ar`, verify.cpp:2542-2556), plus two commit execs per key. Over a whole probe run (solo and pair phases included) the single path can visit Σ C(6,k)·k for k=1..3 = **96 layouts on `ver`**, plus the 12 hbase twins of cohort A; ver_b has 12. The 95 strings observed are 95 of those 96 [L][S].

## G2. The print
- verify.cpp:3721-3723, after upload and sync: `std::fprintf(stderr, "strata verify: captured the batch window over slots %s\n", list.c_str());`. It is unconditional per successful `capture_batch`, which runs whenever `exec_bm_[bkey(rows, S, hbase)]` is null (:3696-3697) — so it prints on first capture **and on every re-capture** after LRU (:3862) or VRAM (:3884-3891) eviction. No timestamp, no verifier tag: A and B print identically.
- LRU eviction prints nothing (`evict_batch_graph`, :3845-3875). The VRAM path prints only after a successful free — "no VRAM for a new window graph: freed the graphs of %d older batch slot layouts, %zu kept (a larger --vram-reserve-mib keeps more)" (:3892-3894) — and never has in this log [L]. Commit captures never print (:3840-3842).

## G3. The LRU cap
- Enabled iff `batch_graph_limit_ > 0`: `if (batch_graph_limit_ > 0 && exec_bm_.find(key) == exec_bm_.end() && exec_bm_.size() >= batch_graph_limit_ && !evict_batch_graph(key, evicted, err))` (verify.cpp:3975-3977). Its only setter is `set_batch_graph_limit(64)` (verify.hpp:234) — **the literal 64 at generate.cpp:9539, :9620, :9691, :9713**, each under `if (batch_mtp)`. No flag and no env var configure it (grep for `graph.limit|GRAPH_LIMIT` finds only these).
- **In force under the env arm**: `const char* batch_mtp_env = std::getenv("STRATA_BATCH_MTP"); bool batch_mtp = o.batch_mtp || (batch_mtp_env != nullptr && batch_mtp_env[0] != '\0' && batch_mtp_env[0] != '0');` (generate.cpp:5565-5566; option at :750 `///< --batch-mtp / STRATA_BATCH_MTP=1 (opt-in)`, parsed :2836). The live argv carries no `--batch-mtp` and the boot prints "--batch-mtp: 6 slot drafters on CUDA0" (log line 551537) [L]. Value 64 **per verifier**, counting that verifier's window-graph keys (`exec_bm_.size()`; ar variants and hbase twins included); one eviction takes the window exec and both parity commit execs (:3864-3872).
- It can only bind in mixed traffic (ver's key space is up to 96 + 12 per ar value; the steady conc phase needs 1). [L] Live boot: 28 distinct layouts, 30 captures → the cap was not reached.

## G4. Cost path of one capture, serve thread, in order
1. `stage_batch`: if the cap binds, `evict_batch_graph` → `cudaStreamSynchronize(cs_)` (:3856), `cudaGraphExecDestroy` of the window exec (:3861) and its commit execs (:3869).
2. `capture_batch`: `cudaStreamBeginCapture(cs_, cudaStreamCaptureModeThreadLocal)` (:3698); `batch_rec_ = true; row_base_ = hbase; … brow_[t] = rows[t]` (:3702-3704); `record_window(S, cs_, rerr)` (:3706) — every launch of the window is recorded on the serve thread (≈ 2,660 nodes for 6 rows, SVG-CUSTOM.md:9388).
3. `cudaStreamEndCapture(cs_, &graph)` (:3710).
4. `instantiate_evicting(ex, graph, key, …)` (:3716) → `cudaGraphInstantiate(&ex, graph, 0)` (:3882), flags 0.
5. `cudaGraphDestroy(graph)` (:3717) — **the cudaGraph_t is not kept.**
6. `cudaGraphUpload(ex, cs_)` (:3719); `cudaStreamSynchronize(cs_)` (:3720) — this also joins the verifier's own previous async commit, which is stream-ordered on `cs_` (F-196, :4197-4201) [S].
7. The print (:3723).
8. Back in `stage_batch`: `capture_commit_batch(…, 0, err)` and `(…, 1, err)` (:3979-3981), each: begin capture (:3741), the commit's copies and launches (:3747-3824), end capture (:3830), `instantiate_evicting` with flags 0 (:3840 → :3882), destroy (:3841). No upload, no sync, no print.
- A cheaper re-capture does not exist: `cudaGraphExecUpdate` appears nowhere under src/ (grep), no cudaGraph_t or template is cached, and an evicted layout's commit graphs are re-instantiated from scratch.
- Counters and timing: none. `ms_host` starts after the captures — `const Clock::time_point t0 = Clock::now();` is verify.cpp:3982, `ms_host += ms_since(t0)` is :4030. No `STRATA_VERIFY_*TIMING` env exists (the verify envs in the code are ASYNC_LAUNCH :3117, DEVICE_LAUNCH :3904, PROFILE verify.hpp:460, TRACE :704).

## G5. Memory
- The code's only figure is the comment at verify.cpp:3879: "#997: every layout of active slots keeps its own graph pair (20-30 MiB each on an L40S), and with an expert cache sized to the reserve the next window graph … can find no VRAM left". Nothing measures the host side; flags-0 `cudaGraphInstantiate` allocates the exec's host structures inside the driver, invisible to the engine [C].
- `instantiate_evicting` (:3877-3900) has **no budget variable**: it instantiates, and while the result is `cudaErrorMemoryAllocation` it calls `evict_batch_graph(key, …)` — which destroys the least recently used layout **other than the key being made** (oldest `bm_used_` tick, :3849-3854): its window exec and both parity commit execs (:3861-3872) — then retries (:3884-3891). The budget is implicit: whatever the driver has left after the expert cache was sized against `--vram-reserve-mib 1800` (live argv) [L].
- Estimates, not measurements. Inputs: 20-30 MiB per layout (the comment), ≈ 2,660 nodes per 6-row window graph. **95 execs: 1,900-2,850 MiB (1.9-2.8 GiB). 64 execs: 1,280-1,920 MiB (1.25-1.9 GiB).** That is 7.8-11.7 KiB per node if the comment means one window exec; if it means the pair, the window is most of it (the commit graph is ≈ 2 launches per slot group per GDN layer plus 2 per row per QSA layer, :3768-3814, about a tenth of the window's nodes [S]). [C] Plain kernel-node exec structures are often quoted nearer 1-2 KiB/node, which would give 2.6-5.2 MiB per exec and 250-500 MiB for 95; the tree holds no measurement to choose. Live boot: ≤ ~34 keys ≈ 0.7-1.0 GiB by the comment's figure.

## G6. The launch sites
- All four are plain `cudaGraphLaunch`: verify.cpp:4048 `cudaGraphLaunch(exec_bm_[bkey(rows, S, 0)], cs_)`, :4253 `cudaGraphLaunch(exec_bm_[bkey(last_rows_, last_t_, row_base_)], cs_)`, :4190 and :4258 for the commit execs. `HostGraphLaunch` is constructed at one site only, the serial `run()`: `launch_o.emplace(ar_off_ ? exec_nr_[T] : exec_[T], cs_, device_, threaded_launch, …)` (:3126-3127), in the `else` of `if (const cudaGraphExec_t dev = dev_exec(T))` (:3121-3129), `threaded_launch` read from STRATA_VERIFY_ASYNC_LAUNCH (:3116-3119). **The batch sites do not go through it.** With STRATA_VERIFY_DEVICE_LAUNCH=1 (launcher:158) the serial site takes the device parent (:3124) — the live boot prints 8 × `device launch armed` [L] — so under the standing env HostGraphLaunch is on no hot path.
- Per cohort round: **2 window launches** (`ver.batch_go(err, false)` :12719, `ver_b.batch_go(err, false)` :12723 → :4253) and **2 commit launches** (`finish()` → `commit_slot_prefixes` :12856, called :12939-12940 → :4190). `with_commit` is false on this path, so :4258 is not taken. A single-verifier round: 1 + 1 (:4048, :4190).
- Yes: commit graphs are keyed by layout and parity — `commit_bm_[ckey(rows, S, hbase, parity)]` (:3730) — and `stage_batch` calls `capture_commit_batch` for both parities on every stage (:3979-3981: "F-196: both parities up front - no mid-serving capture when the parity flips"). Each miss is a full capture (G4 step 8).

## G7. While a capture runs
- The round is stage A → stage B → go A → go B → one poll loop over both → finish A → finish B (generate.cpp:12703-12730, :12764-12780, :12939-12940). Captures sit inside the stages, before either launch: "stage BOTH cohorts (a lazy capture happens while NO window is in flight - the standing flow's capture condition)" (:12703-12704); "its first-round lazy graph capture must happen while NO window is in flight (v1's capture-under-flight hung layer 0, #267)" (:12714-12715).
- So the stall is **additive to the cycle**: no window of this round is on the GPU yet, and the pool workers are fed only by `pool(user, …)` inside the poll loops (verify.cpp:4119-4121 inline, :4307-4309 `batch_poll`) — idle for the duration. What does overlap: the previous round's F-196 async commits already on the GPU; the other verifier's keeps running (ThreadLocal capture records only the capturing thread's calls, :3698 [C]); the capturing verifier's own is joined by the sync at :3720. Drafters were joined in the previous tail (:12924-12929). The standing→cohort transition is fenced once with `cudaDeviceSynchronize()` (:12594-12598) because "the last standing window's F-196 async commit may still be in flight while cohort B's stage CAPTURES its first layout".
- [L] Where it lands: 11 of the live boot's 1,528 cohort rounds carry a capture, +9-12 ms each (§0).

## G8. Fixes, ranked by (expected conc gain × confidence) / risk
Every item that only removes captures is capped at ≤ 0.3% of cohort time [L] — below the +4% adopt bar; none justifies a perf leg on its own.
1. **(e) Device-launch twin for the batch window graphs** — the only item not capped by the capture count. Precedent: F-452, "the window graph now launches from the device (ADOPTED, M1 +5.0% over 3 pairs)" (SVG-CUSTOM.md:13810). Change: in `capture_batch` keep `graph` until `make_dev_exec(dev, par, graph, …)` (verify.cpp:3914-3951) has built the twin — `cudaGraphInstantiateWithFlags(&dev, graph, cudaGraphInstantiateFlagDeviceLaunch)` (:3934) and the one-node parent (:3941-3946) — upload both (the :2762 pattern) and then destroy the graph; key twins by the same `bkey` in two sibling maps beside `exec_bm_`; `evict_batch_graph` destroys all four; launch `dev ? cudaGraphLaunch(par, cs_) : cudaGraphLaunch(exec_bm_[…], cs_)` at :4048 and :4253. **The existing decline lambda must not be reused as is**: it runs `dev_launch_ = false` (:3931), the per-verifier arm that `dev_exec(T)` reads (verify.hpp:598, :603) — `ver` is also the solo verifier, so one batch decline would silently send M1's windows back to host launch — and it destroys its `parent` argument (:3928), which for the batch twin must be a batch-owned slot, never `exec_devp_[T]`. Gain unpriced [S][C]: it removes the host's node-by-node submission of ~2,660 nodes per window; the live BT line leaves `run 13.17 − wait 0.31 − pool 3.43` = 9.4 ms/window unattributed [L], launch share unknown. Falsifier: time `cudaGraphLaunch` at :4253 in `A.S=6 B.S=6` rounds; a host submission under ~0.5 ms kills it.
2. **(b′) Boot-time pre-capture of every cohort layout** — the safe form of (b). After `init_slots`, with nothing in flight (the condition `ver.capture_all` already uses at boot, generate.cpp:9635), stage and capture the 12 layouts of each cohort span on its own verifier, both parities. Removes all 12 run-time cohort captures per boot [L] → ~0.12 s/boot, an admission-latency win only; costs ~24 × 10 ms of boot and, by the comment, 0.5-0.7 GiB of VRAM. The helper-thread form is **not safe as the code stands**: `capture_batch` ends in `cudaStreamSynchronize(cs_)` (:3720), which on a stream carrying a doorbell window waits for doorbells only the serve thread raises (#267 class); it writes `batch_rec_`, `row_base_`, `brow_` (:3702-3708) that `stage_batch`/`batch_go` read for the key (:4027, :4253); and `exec_bm_` is an unsynchronised `std::map`. Falsifier: capture lines inside cohort rounds must fall to 0; 6-conc t/s will not move beyond noise.
3. **(a) Cap knob + key normalization.** The cap is the literal 64 (G3): give it a name and an env (read at the four sites), default 64. Independently, pass `hbase = 0` (or drop it from the key) when `lb_ == 0 && le_ == g.n_layers` — merges the single/cohort twins on `ver` (G1) at zero VRAM cost. Gain ≈ 0 for conc; removes solo/pair re-captures in long mixed-traffic sessions. Falsifier: with the cap at 0 or 256 the per-boot capture count is unchanged → the cap was not binding (it was not in the live boot [L]).
4. **(c) `cudaGraphExecUpdate` retarget.** The code keeps only the exec (G4 step 5), so this needs a kept cudaGraph_t template per S and one mutable exec per S. [S] All-pairs layouts of equal S have identical topology: per row one K/V append, one indexer append and four attention nodes (:1895-1913, :1767-1772, :1989-1998); per slot group one conv and one recurrence node (:1586-1595, :1647-1656) — unless a slot has `kv_mode == 1` (:1926, :1936), differing kv_hybrid/q4/int8 flags (:1898-1913), or a 1-row group. [C] `cudaGraphExecUpdate` needs matching topology and is usually far cheaper than an instantiate — unconfirmed. Saves perhaps 6-8 ms × 12 per boot; medium risk (a failed update must fall back to instantiate). Not worth its risk at this rate.
5. **(d) Indirection table (row → slot read on device).** Sites in `record_window` that bake a slot pointer or a slot-derived row group: :1277 (`slot_ss` = `*slots_[brow_[t]]`, the root of every dereference), :1435 (`ple_hist`), :1588-1594 (GDN conv state), :1636-1644 (GDN groups, env-off), :1649-1655 (GDN state), :1754-1756 (indexer-tail snapshot: source pointer and slot-indexed destination), :1768-1772 (indexer buffers), :1896-1913 (K/V append: k_q, v_q, scales, page table, pools **and the host mirror `&st.host`**), :1943-1946 / :1966-1969 / :1991-1998 (attention: idx_pooled, idx_dead, pools, `qsa_kv_resolve(sx, …)`); record-time host decisions :1280, :1926, :1936; split-only :1302, :2403. Commit graph: :3771-3775, :3805-3813, :3822. That is about ten active launch sites across eight kernel families, several taking pointer arrays or host-pool structs as kernel arguments: each contract becomes (table, row), with a device-resident mirror for `&st.host`. Size: weeks. Hazards: every captured pointer becomes per-window data (a small upload before each window); per-slot K/V bases must stay stable inside a window (the elastic arenas are fixed VAs, log line 424560 [L]); the commit path must follow; outputs must be proven byte-identical by the diff-harness. Gain alone ≈ 0.3%; its value is that it makes (e) one twin per S instead of per layout. Do it only after (e) is priced positive.

## G9. The one measurement
For the capture question the log already prices it to ±2 ms — ~10 ms per capture, 12 per boot in the cohort lane — so no capture instrument is worth a leg. The measurement that still prices a real lever is the **host duration of `cudaGraphLaunch` at verify.cpp:4253 (and :4048) per round in `A.S=6 B.S=6` traffic**, i.e. the submission cost of the ~2,660-node exec on the serve thread, because it alone decides whether (e) can pay. No existing env exposes it, and none exposes capture time either: there is no `STRATA_VERIFY_*TIMING` (G4); `ms_host` starts after the captures (:3982); `STRATA_DECODE_TIMING`'s snapshot carries `wait, pool, host, plan, actq, jobs, run` (generate.cpp:16052-16059) with no capture or launch field. What does contain capture time, inseparably: the BT line's `run` term (`bt_run += msd2(w0c, w1c)`, :12947; printed :13243-13249), the WSTAT window histogram (`window_ms.push_back(msd2(w0c, w2c))` :12946 under STRATA_SERVE_TELEMETRY=1, launcher:33), and the per-round `cohorts: windows done in %.1f ms` line (:12781, every round) — the last is what §0 used. The cheapest instrument: one diagnostic env (default off) that steady-clocks `cudaGraphLaunch` at the two window sites into a new `ms_launch`, counts captures and sums stage-to-commit-capture time into `ms_capture`, both printed in the BT line.

## Verdict
[S][L] The cache works as designed and is not thrashing: under the env arm the cap is 64 per verifier, never reached in the live boot, and no VRAM eviction has ever printed. The lane pays ~12 captures of ~10 ms per boot (≤ 0.3% of cohort window time), all at active-set transitions. Capture-side fixes are latency hygiene; the only candidate with headroom is (e), and it needs the launch-time measurement of G9 before any leg.
