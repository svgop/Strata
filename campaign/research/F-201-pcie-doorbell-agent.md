# Deep brief 2: PCIe / doorbells / DMA (investigative-researcher, 2026-10-15) — 10 findings

**Quantified suspicions (all load-bearing figures from fully-read sources):**
- Device-side polls of host-mapped flags = UNCACHED non-posted PCIe reads, ~1-2µs RTT each (arXiv:2512.16056; CUDA docs: mapped sysmem not cached in GPU L2). At one poll/node: 1800 × 1-2µs = **1.8-3.6ms of our 17.1ms window**. FIX DIRECTION: invert the signaling — GPU polls its OWN device memory (L2 hit ~200-300ns) while the host posts doorbells as posted Memory Write TLPs (single posted TLP, sub-µs) via `cuStreamWriteValue64`/`cuStreamBatchMemOp` (driver posts as one MMIO write — CUDA Handbook ch6.10) or BAR-mapped buffers.
- `__threadfence_system()` on GPU = `MEMBAR.SC.SYS + ERRBAR + CCTL.IVALL` (SASS-verified, NVSHMEM thread) = full L1+L2 invalidate + PCIe drain → every subsequent access refills from DRAM. One per node = 0.2-1.8ms + refill storms. Budget: ONE sys-fence per producer per handoff, NEVER per poll iteration.
- Our 12.7GB/s DMA = latency-floor artifact: ~5-10µs fixed overhead per CE op (Diamos/GT + NVIDIA forums); 256KB chunks sit in the overhead regime. Gen5 pinned large-block native ~53GB/s (server platform) but AM5 desktop: ~24.5-26GB/s H2D, ~14.7GB/s bidirectional (5090D measurements). FIX: batch per-expert DMAs into **2.8-10MB phase-aligned megablobs** (optimal chunk 2.81MB), one direction per phase → ~3-4× of the DMA component (~1.2-1.6ms of the 4.9ms tail).
- Validated doorbell protocol (arXiv:2512.16056 "MMA" spin kernel + NCCL GIN 2511.15076): ONE warp polls (`__ldcg` L1-bypass + `__nanosleep(100)` backoff), results broadcast via smem; producer→consumer = fire-and-forget posted stores of 64B descriptors; CPU-proxy hop costs ~1.3µs (GIN measured). Armed-node signaling ~2-4µs total.
- AM5 reality: all PCIe off ONE IO die, single NUMA node; every DMA byte terminates in the same dual-channel DDR5 (~55-65GB/s real) the CPU pool reads. Mixed-traffic cap ≈ 15-25GB/s. Keep CUDA driver thread on CCD0 (V-cache), expert workers on CCD1 — manage DRAM contention, not GPU affinity.
- Write-combining: correct for host→device one-way staging (WC buffers → larger posted TLPs, sfence-bounded); WRONG for host-polled counters (WC uncached on CPU → polls go to DRAM). Device-written seq counters stay in plain WB pinned (coherent with PCIe snoops).
- 40GB pool: `cudaHostRegister` over THP/madvise(MADV_HUGEPAGE) 2MB-backed allocations (not cudaMallocHost's 4KB pinning): PTE count ÷512, TLB-walk tax off the DMA path.
- NVMe Gen5: QD1 ≈ 108µs/MB (9.2GB/s consumer); gains end at QD4. With 184GB RAM: page-cache-prefetch the whole 47GB model once at boot (~5.1s at QD1); keep O_DIRECT out of the hot path. Steady-state window NVMe time → 0.
- Node-spacing floor: kernel-launch ~5-11µs CPU/driver round trip if ANYTHING per-node escapes the graph (dynamically enqueued copy, host poke). `nsys` gap profile; replace CPU-mediated arming with `cuStreamBatchMemOp` IN-graph; target floor = wire time + L2-hit polling.
- Protocol rule: maximize posted writes, minimize non-posted reads, bound poll rate (N status words → one coalesced posted 64B write + ring indexing).

**Combined upper-bound recovery: ~4-7ms of the 17.1ms window + ~3-3.6ms of the 4.9ms expert tail.** OPEN: cuStreamBatchMemOp posting latency on Blackwell (10-line microbench); MSHR-merge behavior of N-warp sysmem polls (nsys).
