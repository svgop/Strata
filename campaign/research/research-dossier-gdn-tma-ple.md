# Research dossier: GDN kernels · TMA/L2 prefetch · SSD PLE readout
Scope: RTX 5090 (sm_120) CUDA 13.4 engine; Qwen3-Next-style 36 GDN + 12 attention layers; 47.75 GiB mmap'd n-gram embedding table (160 B/token random rows). All PR/issue numbers verified against the GitHub API on 2026-11-20; commits/papers cited inline.

## 1. Gated DeltaNet kernels

**Papers.** Delta rule origin: "Linear Transformers Are Secretly Fast Weight Programmers", arXiv:2102.11174 (Schlag et al.). Sequence-parallel form: "Parallelizing Linear Transformers with the Delta Rule over Sequence Length", arXiv:2406.06484 (Yang, Wang, Zhang, Su, Kautz) — derives the WY-representation chunkwise algorithm; paper states chunkwise cost O(LCd + Ld²) with chunk C (64–128 in practice) and only L/C sequential state steps vs L for the scan; their recurrent kernel alone was already 2× the original DeltaNet CUDA kernel of Schlag et al. (their footnote 4). GDN: "Gated Delta Networks: Improving Mamba2 with Delta Rule", arXiv:2412.06464 (ICLR'25, Yang/Kautz/Hatamizadeh) — adds per-head decay gate; chunked parallel training reaches "essentially the same throughput as DeltaNet"; 3:1 GDN:attention hybrid is the best throughput/quality trade (the ratio Qwen3-Next-80B-A3B ships). Related: Kimi Delta Attention arXiv:2510.26692 (Kimi Linear); GDN-2 arXiv:2605.22791 + github.com/NVlabs/GatedDeltaNet-2 (same WY chunk structure, decoupled erase/write).

**FLA kernels** (github.com/fla-org/flash-linear-attention, MIT, Songlin Yang & Yu Zhang). Chunked GDN forward = 3 Triton kernels: (1) WY kernel — build A = tril(diag(β)·KKᵀ), solve (I−A)⁻¹; (2) state-passing kernel chunk_gated_delta_rule_fwd_kernel_h_blockdim64 (fla/ops/common/chunk_delta_h.py), grid (cdiv(V,BV)·N·HV), walks chunks sequentially; (3) output kernel O = QSᵀ + masked intra-chunk attention. Default chunk_size = 64 (fla/ops/gated_delta_rule/chunk.py). On Blackwell the state kernel is pinned to num_warps=2 "until Triton 3.8 is released" (source comment in chunk_delta_h.py). SGLang fuses kernels 1+2 (3→2 launches) in commit c69844f0431cd2e696add537a0766f730f02a062 (python/sglang/srt/layers/attention/fla/chunk_fwd.py). NVIDIA Model Optimizer ships adapted copies with FP8 state fake-quant (needs fla-core 0.5.1). **Why it cuts TTFT:** prefill trades L memory-bound sequential steps for L/64 dense tensor-core phases + a short inter-chunk scan; decode stays O(1) recurrent.

## 2. TMA / L2 control

- **Instruction**: cp.async.bulk.prefetch.L2 — PTX ISA, "Data Movement and Conversion Instructions: cp.async.bulk.prefetch" (docs.nvidia.com/cuda/parallel-thread-execution). Fire-and-forget L2-only prefetch, no completion token; the ::cache_hint variant carries an evict policy.
- **FlashInfer, sm_120-native**: include/flashinfer/attention/sparse_mla_sm120/common/kv_cache_io.cuh defines io_bulk_prefetch_l2() (line 109) issuing cp_async_bulk_prefetch_l2_hint(src, PREFETCH_BYTES, cache_policy) (line 133) and cp_async_bulk_prefetch_l2(src, PREFETCH_BYTES) (line 135); prefill_swapab_kernel.cuh uses it to warm L2 one tile ahead of TMA KV gathers. Verified at commit 4510df441de67003be6505064756da890a364b3c ("Support compact FP8 cache rows for GLM NoPE attention"). Open fix #7584 (bound MIS next-tile prefetch by physical tile). Adjacent merged PRs: #8656 L2-prefetch mid-forward in cake_rmsnorm_silu_gate on SM107 (2026-11-04); #6857 evict-first L2 hint on FC2 weight loads (2026-10-20).
- **TensorRT-LLM**: PyTorch-backend KV Manager V2 exposes host/disk tiers + prefetch in KvCacheConfig (official docs); recent perf PR #18541 (batched page copy, storage manager) — no public cudaAccessPolicyWindow surface.
- **Measured**: arXiv:2504.06319 (Dong et al., Alibaba Cloud; AAAI'26 paper 39224) — async KV prefetch into L2 via cp.async.bulk.prefetch.L2 on H20: L2 hit up to 82%, warp-stall cycles −75–90%, up to 2.15× attention-kernel speedup, 1.97× e2e throughput vs XFormers, outperforming a FlashAttention-3 baseline. PRESERVE, arXiv:2501.08192: prefetch weights + KV into L2 overlapping allreduce; +1.25× performance/cost at optimal L2 size.
- **cudaAccessPolicyWindow**: set-aside via cudaDeviceSetLimit(cudaLimitPersistingL2CacheSize), window via cudaStreamSetAttribute; persisting maps to evict_last (NVIDIA patent US2022/0365882A1); hitRatio is a static address hash — keep hitRatio×window ≤ set-aside. Real-engine adoption is thin: the only vLLM search hit for accessPolicyWindow is open (unmerged) PR #46269 (RWKV7 Albatross); FlashInfer/TensorRT-LLM express policy in-kernel via PTX cache hints instead (#6857). For your engine: persist small hot structures (router/gate weights); stream KV via explicit bulk prefetch (2504.06319 shows misses in an oversized window thrash it).

## 3. Massive SSD-resident embedding readout (47.75 GiB PLE)

**Correction**: the n-gram table is not in the original Qwen3-Next-80B-A3B (Sept 2025, issue #15940). It ships in the successor Qwen3.8-Flash-Next (HF qwen4exp): llama.cpp PR #27742 (danielhanchen, merged 2026-08-27) — "per-layer embeddings, 97.7 GiB n-gram hash table" handled as host-side row indices in a set_input + ggml_get_rows over the mmap'd tensor; superseded draft #27739 (JJJYmmm). Tensor: per_layer_token_embd.weight 160 × 320,001,536 → 160 B/row (26.82 GiB IQ4_NL in ukasai GGUF shard 1; 28.8 GB NVFP4 / 32 GB INT4 / ~95 GB BF16). Access ≈16 rows ≈5 KiB/token, addresses fully determined by token IDs (Qiita analysis, 2026-08-26) — ideal prefetch shape.

**llama.cpp handling & latency record**: mmap + lazy mode loads tensors >4 GiB on demand (HF discussion ukisai/Swift-1.5-Qwen3.8-Flash-Next-GSQ-RCO-GGUF #10; --lazy-mode auto issues #31943/#31957; open PR #32515 adds read-ahead of offloaded tensors). No O_DIRECT/io_uring/async row prefetch as of 2026-08-27 (Qiita). Measured (Toolhalla, 2026-10-26): Optane P5800X (--ple-io direct) vs DDR5 (--ple-io ram): decode 112.9–120.5 vs 113.1–117.6 t/s; prefill 1527.5–4767.1 vs 1493.5–4785.3 t/s → ~zero single-client penalty; sparse 4 KiB random touches are absorbed by page cache + NVMe parallelism. The latency bugs that bit were host-side: #28011 (merged 2026-08-30) — n-gram prev-token lookup scanned all 256 sequence slots per used KV cell; fix gave 56.3→74.3 t/s @55k ctx and 33.6→50.9 @132k (RTX PRO 6000, UD-Q4_K_XL). #27992 (closed, unmerged) proposed an O(log n) (seq,pos) index; #27852 ngram-cache reuse bug (acceptance 86%→11%); #19167 (open) LongCat-Flash-Lite ngram embeddings.

**Techniques**: (a) madvise(2) MADV_RANDOM kills readahead for random row access; MADV_WILLNEED batches prefetch; page cache = free hot-row LRU (man7.org). Page math: 160 B rows share 4 KiB pages (25.6 rows/page) → 16 rows/token ⇒ up to 16 faults ≈64 KiB/token worst case. (b) io_uring: POMACS'26 DOI 10.1145/3788106 (25k-point design-space study: libaio vs io_uring interrupt/poll vs SPDK vs GDS over SATA/NVMe/Optane/PMem) — interrupt-driven io_uring is best for inference's small random I/O; GDS wins bulk throughput (pretrain/fine-tune). Foundational: Axboe, Vault'19 (kernel.dk/io_uring.pdf); hybrid polling kernel commit 01ee1941aba1 (v5.7). (c) GPU-direct: CUDA GDS (docs.nvidia.com/cuda/gpudirect-storage); LMCache×xPU-IO blog 2026-11-09 — Phoenix libphxfile batched io_uring + GDSContext DMA NVMe→GPU; Tutti arXiv:2605.03375 — GPU-side io_uring ("gio_uring") for SSD restore, saturates NVMe with near-zero GPU stalls; J.Supercomput. 2025 DOI 10.1007/s11227-025-07118-9 — SSD embeddings + prefetch/compute overlap. (d) Closest published analog: ESPN, ISMM'24, DOI 10.1145/3652024.3665515 — SSD-offloaded embedding tables + GPU software prefetcher; 3.1–3.9× faster than mmap when the table exceeds RAM.

**Fit**: keep mmap + get_rows; add MADV_RANDOM; optional 8–16 GiB pinned hot-row LRU keyed by n-gram frequency; if you need headroom, an io_uring worker doing batched preadv one ubatch ahead into pinned staging + cudaMemcpyAsync beats GDS complexity at 5 KiB/token volumes.
