# T33 prior art: seamless / delay-free resource elasticity for LLM serving

Date: 2026-10-22. Scope: mechanisms for dynamic session/memory allocation with zero-added-delay in LLM serving engines, and dynamic expert-cache elasticity for MoE, evaluated for a single-GPU (RTX 5090, 32 GB) Strata fork with statically-allocated slot sessions (~0.78 GiB each) competing with a runtime-shrinkable expert cache. Complements 2026-10-16 Strata memory/quant research (docs/research/2026-10-16-strata-moe-quant-memory-offload.md), which covers the expert-cache/quant landscape; this file covers serving-level elasticity and transition mechanics.

NOTE: the referenced spec `campaign/research/T33-dynamic-session-allocation.md` was NOT present in the workspace at research time (campaign/research/ contained only INDEX.md). This file was written against the design as described in the assignment: zero-added-delay arrivals on an existing fast lane; background shrink-cache → allocate-slot → CUDA-graph capture (~1-2 s) → hot-swap conversation (34-59 ms); idle sessions demote with hysteresis. When the spec lands, check the amendments section against it.

## Summary

Every production engine already solves the *arrival* half of T33: Orca's iteration-level scheduling (continuous batching) lets a new request join the running batch at the next decode-iteration boundary, so arrival delay is one iteration (~10-100 ms). Nobody ships T33's *capacity* half — adding a fully-provisioned, graph-captured session slot on demand without stalling the lane. The closest prior art decomposes into four reusable mechanisms: (1) **priority inversion of cache vs. sessions** (SGLang evicts all cached tokens in favor of running requests; Mooncake treats KV as the first-class schedulable resource); (2) **append-only pipelined state migration** (Llumnix copies KV while decoding and pays only a 20-30 ms tail-copy, nearly constant in sequence length — the direct precedent and target for T33's 34-59 ms hot-swap); (3) **graph persistence instead of recapture** (vLLM sleep mode now backs captured CUDA graphs to CPU and restores them in place on wake — "replayed, not recaptured" — which can collapse T33's 1-2 s capture to a page-in); (4) **stream-ordered allocation pools** (cudaMallocAsync with release-threshold = max makes shrink/grow of non-graph buffers a cheap pool op with no device sync). One cautionary precedent: vLLM explicitly **rejected** runtime lazy CUDA-graph capture (RFC #20098, closed not planned: "huge maintenance burden", OOM-mid-serving risk) — but T33's bounded, fixed-shape, background-captured slot set is a materially smaller problem than what they rejected; the rejection reasons define the invariants T33 must keep. On the MoE side, MoE-Infinity already lets KV growth shrink the expert buffer and documents the failure mode T33 prevents: at 2^17 context the buffer degrades to on-demand fetching at **+137 ms/token**. Nothing found in the literature disagrees with T33's structure; the amendments below are mostly cheap upgrades (graph persistence, swap-vs-recompute demotion, COW shared prefixes, pool-based resize) plus two hard invariants (expert-cache floor, bounded KV growth).

## Per-system notes

### Group 1 — dynamic allocation & scheduling

**Orca (OSDI'22, Yu et al.) — iteration-level scheduling.** [USENIX page](https://www.usenix.org/conference/osdi22/presentation/yu); corroborated by [Anyscale continuous-batching blog](https://www.anyscale.com/blog/continuous-batching-llm-inference) (OPT-13B/A100: 8x over static batching from continuous batching alone, up to 23x with PagedAttention-class memory management). Mechanism: the engine interacts with the scheduler per iteration; a completed sequence's seat is refilled by a queued request at the next boundary regardless of other sequences' progress; selective batching applies batched kernels only to batch-friendly ops. This is the founding "zero-added-delay arrival" mechanism: an arrival is servable within one decode iteration. *Delay hides:* in the iteration boundary. *Single-GPU:* yes — it is the standard. *Steal:* nothing new — it's our fast lane; but note its corollary: an arrival that needs *new capacity* must be decoupled from the join event, which is exactly T33's split.

**Llumnix (OSDI'24, arXiv 2406.03243)** — [abs](https://arxiv.org/abs/2406.03243), [HTML](https://arxiv.org/html/2406.03243v1), [code](https://github.com/AlibabaPAI/llumnix). Mechanism: live migration of a *decoding* request between engine instances: KV cache is append-only, so the source copies completed blocks to the destination while still decoding new tokens (stage 0→N pipelining); downtime is only the final tail copy of cache produced during one iteration. Measured **migration downtime ≈ 20-30 ms, nearly constant with sequence length** (recompute-from-scratch baseline: 3.5 s for an 8k LLaMA-30B sequence; blocking-copy baseline up to 111x worse). Migration overhead to co-resident requests ≤1% per step. Cross-node transfer is Gloo Send/Recv over CPU staging (NCCL rejected as unsafe concurrent with inference). Scheduler is hierarchical (global scheduler + per-instance "llumlets") because a centralized scheduler stalled iterations up to 40 ms at 64 instances. *Delay hides:* the copy of all-but-the-final block, overlapped with ongoing decode. *Single-GPU:* the multi-instance fabric doesn't exist, but the *re-seat pattern* transfers directly to any same-device handoff: when promoting a session onto a new slot/graph, decode on the old graph while pipelining KV to the new slot, then flip. *Steal:* make the 34-59 ms hot-swap a *tail flip*, not a stop-and-copy — pre-wire the new slot, stream KV across, decode until the last iteration, swap.

**vLLM allocator evolution (arXiv 2309.06180 SOSP'23 + v1 blog + docs).** [Paper HTML](https://arxiv.org/html/2309.06180), [v1 blog](https://vllm.ai/blog/2025-01-27-v1-alpha-release), [CUDA-graph design](https://docs.vllm.ai/en/latest/design/cuda_graphs.html), [sleep mode docs](https://docs.vllm.ai/en/latest/features/sleep_mode.html), [RFC #20098](https://github.com/vllm-project/vllm/issues/20098). Chain of mechanisms:
- *PagedAttention:* KV pool pre-divided into fixed physical blocks allocated on demand; measured that contiguous preallocation wastes 60-80% (only 20.4-38.2% of KV memory holds live states in Orca/FasterTransformer); paging caps waste at one partial block. Cost: attention kernels 20-26% slower from block-table indirection. *Single-GPU:* yes. *Steal:* the 0.78 GiB slot is the slot-level analog — the question T33 answers is the *slot-count* analog of their block-count question.
- *Copy-on-write:* shared physical blocks (parallel sampling/beam) carry refcounts; on divergence only one block is copied. Memory savings 6.1-9.8% (parallel sampling) to 37.6-66.3% (beam/ShareGPT). *Steal:* cross-session prefix sharing with COW would cut effective per-session footprint below 0.78 GiB for shared system prompts.
- *Preemption:* when blocks run out, evict running sequences; recover by **recompute** (default) or **swap-to-CPU**. Recompute overhead is constant in block size and "never higher than 20% of swapping's latency" (Fig. 19); swap wins only for long sequences with large blocks. *Steal:* demotion policy — forget-KV-and-recompute is *the cheap default*; store KV on demote only above a context-length threshold.
- *gpu_memory_utilization + profile run:* pool sized once at startup from a profiling pass; the watermark is a small reserved fraction (constant WATERMARK ≈ 0.01 of blocks; `preemption_mode` per request can override). *Lesson:* vLLM sizes **once, statically**; it does not resize the pool at runtime. T33's runtime resize is beyond vLLM's shipped design — closest shipped mechanism is sleep mode (below).
- *v1 scheduler:* unified persistent batch (schedule = map request→token budget), chunked prefill via fixed token budget, prefix caching default with O(1) eviction structures (<1% overhead at 0% hit rate), CPU overhead cut gives up to 1.7x throughput. *Lesson for resize:* the scheduling path must be diff-updated state (their persistent batch), so inserting/removing a session is metadata work, not reconstruction.
- *CUDA graphs:* captured at startup for a fixed ladder of padded batch sizes ("capture sizes"); ~67 graphs, 10+ s startup; ~50 ms per graph for an 8B model (RFC #20098). Batches are padded up to the nearest captured size. T33's 1-2 s/slot is in family (bigger model, warmup runs, per-slot buffers); the ladder/padding pattern is worth copying — capture one slot shape, run all slots at that shape, pad.
- *Sleep mode (the big one):* `sleep(level=1/2)` uses a cuMem (VMM) allocator to discard KV (L1, weights backed to CPU) or everything (L2) while **preserving virtual addresses**, so `wake_up()` maps physical pages back in place. With `sleep_mode_offload_cudagraph=True`, captured CUDA graphs are backed up to CPU and restored in place — docs state graphs are "**replayed, not recaptured**", at a stated cost of pinned host memory plus ~3% decode latency at batch size 1. *Steal:* promote/demote slot graphs via VMM unmap/map (or CPU-backup/restore) instead of capture every cycle — this converts the 1-2 s capture into a page-in and removes capture jitter from the promote path.

**SGLang (arXiv 2312.07104 + LMSYS v0.4 blog + docs).** [Paper HTML](https://arxiv.org/html/2312.07104v2), [v0.4 blog](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4), [server args docs](https://docs.sglang.ai). Mechanisms:
- *RadixAttention:* one memory pool shared by cached prefixes and running requests; leaf-first LRU with per-node refcounts; evicted prefixes recompute on demand. Critical sentence: under pressure the system "will evict all cached tokens in favor of a larger batch size" — allocation failure triggers evict-to-fit and retry. *This is the canonical precedent for T33's priority rule: live sessions outrank the cache, and the cache is the elastic victim.*
- *Cache-aware scheduling:* longest-shared-prefix-first (≈DFS on the radix tree) reaches ~96% of optimal hit rate; greedy can starve.
- *Overlap scheduler (v0.4, Dec 2024):* CPU schedules batch i+1 while GPU computes batch i; combined with mixed chunked prefill; cache-aware load balancing up to 1.9x throughput (blog). Decode retraction (their preemption analog) has policy options (`length`: retract short-output/long-input first) and has historically interacted badly with overlap scheduling (see their issues) — a caution for overlapping disruptive memory events with pipelined scheduling.
- *CUDA graphs:* captured at launch for padded batch sizes (`cuda_graph_max_bs`), like vLLM.
*Single-GPU:* yes, all of it. *Steal:* (a) grow-by-evict-retry as the resize primitive; (b) refcounted shared prefixes; (c) the warning that overlap scheduling + disruptive retraction has correctness/perf history — test T33's background resize under the same lens.

**Sarathi-Serve (OSDI'24, arXiv 2403.02310)** — [abs](https://arxiv.org/abs/2403.02310), [code](https://github.com/microsoft/sarathi-serve). Mechanism: chunk each prefill into near-equal chunks bounded by a per-step token budget tuned to TTFT/TPOT targets; co-schedule chunks with decodes so no iteration is a long prefill ("stall-free"). 2.6x serving capacity at equal tail latency on a *single* A100 (Mistral-7B); composes with PP for 180B-class. *Delay hides:* prefill work is spread across iterations instead of monopolizing one. *Single-GPU:* yes — the flagship result. *Steal:* token-budget the promoted session's initial prefill on the fast lane so lane latency stays bounded during the swap window; the budget is the knob that reconciles "serve the arrival now" with "don't stall the incumbents."

**SplitWise (ISCA'24, arXiv 2311.18677) / DistServe (OSDI'24, arXiv 2401.09670)** — [SplitWise abs](https://arxiv.org/abs/2311.18677), [DistServe abs](https://arxiv.org/abs/2401.09670), [MSR blog](https://www.microsoft.com/en-us/research/blog/splitwise-improves-gpu-usage-by-splitting-llm-inference-phases). Mechanism: prefill (compute-bound) and decode (bandwidth-bound) run on separate machine pools with per-phase parallelism; DistServe allocates per-phase plans against TTFT/TBT goodput (7.4x more requests or 12.6x tighter SLO). KV is shipped machine-to-machine at phase switch, overlapped layer-wise (Mooncake's and DistServe's versions). *Transition latency:* a per-request KV transfer, hidden behind pipelining; fundamentally requires a second machine/GPU pool. **Does not transfer to single-GPU as architecture.** The transferable insight: prefill and decode have different resource shapes, so a *slot graph set* might carry a decode-shaped graph plus an off-graph chunked-prefill path (which Sarathi already gives us in-process).

**Splitwiser (2025, arXiv 2505.03763)** — [HTML](https://arxiv.org/html/2505.03763v1). The single-GPU attempt at phase splitting: two processes (prompt / token-gen) time-share one GPU via MPS or multiprocessing; KV handed off via shared mapping; weights deduplicated via shared memory. Results: 1.42x (vLLM, MPS, 2 instances), ~18% latency reduction (HF+MPS), and *no gain* from MPS alone; per-batch latency is always worse; their in-scheduler process attempt **lost memory swapping and CUDA graphs entirely** (spawn-not-fork, pickling). *Honest negative:* process-level elasticity on one GPU is a dead end for a graph-captured engine. *Lesson:* T33's promotion must stay **in-process** — new graph capture into the same CUDA context — or it will silently forfeit graphs.

**Mooncake (FAST'25, arXiv 2407.00079)** — [HTML v3](https://arxiv.org/html/2407.00079v3). Mechanism: KVCache is the scheduling atom; a conductor picks prefill+decode pairs and streams KV layer-wise to the decode node during chunked prefill (load time overlaps compute; execution ≈ max(load, compute)). Under overload: **prediction-based early rejection** — system-level load forecast (uniform decode time t_d; not per-request output-length prediction, which they found costly/inaccurate), admit/reject up front (HTTP 429); rejected-request counts dropped 4183 → 3771 (plain) → 3589 (prediction-based) on a 23k-request trace, and it removed anti-phase oscillation between pools. Cache eviction: KV in CPU DRAM as paged blocks; policy comparison found **plain LRU best** (LRU 0.50 vs LFU 0.49 vs LengthAware 0.48 hit at 50k blocks); >50% of blocks never reused; max useful reuse ≈50% (up to ~90% for chat-like workloads). *Single-GPU:* architecture no; *Steal:* (a) admit/reject at the door with a load forecast instead of admitting then thrashing — pairs with T33's hysteresis; (b) KV/session as the unit of scheduling; (c) their output-length-avoidance trick (system-level t_d model) if we ever need queue prediction.

**ServerlessLLM (OSDI'24, arXiv 2401.14351)** — [HTML](https://arxiv.org/html/2401.14351v2), [OSDI PDF](https://www.usenix.org/system/files/osdi24-fu.pdf). Mechanisms: (1) loading-optimized checkpoint format (contiguous per-GPU chunks, direct tensor addressing, multi-thread pinned/O_DIRECT pipeline): 3.6-8.2x faster loading than PyTorch/safetensors; OPT-6.7B starts in ~0.8 s vs 12.1 s (Ray Serve); OPT-30B 7.5 s vs 213 s; (2) locality-aware scheduling: pick the server minimizing startup estimate q + n/b; (3) **live migration that moves tokens, not KV**: destination recomputes KV from the 10s-100s KB token backlog over multiple rounds, then inference continues seamlessly. *Delay hides:* model preload + state recompute at the destination, masked by routing. *Single-GPU:* the loading system no (it's about multi-server cold start), but the *tokens-not-KV* trick is a demotion option: drop KV entirely on demote, keep only the token log (KBs), and re-prefill on promotion. Viable only for short contexts (32K re-prefill is seconds); combine with the vLLM recompute-vs-swap threshold.

**AlpaServe (OSDI'23, arXiv 2302.11665)** — [HTML](https://arxiv.org/html/2302.11665v2), [USENIX](https://www.usenix.org/conference/osdi23/presentation/li-zhouhan), [code](https://github.com/alpa-projects/mms). Mechanism: colocate models on shared GPUs and use model parallelism so each model's compute/communication bubbles are filled by others (statistical multiplexing); placement via kinetic-span dynamic programming. Explicitly **argues against model swapping**: "it can take multiple seconds just to swap a large model into accelerator memory." High utilization (~90% class) reported for colocated serving. *Single-GPU:* parallelism-based multiplexing doesn't exist on one GPU, but the doctrine transfers: fill the GPU with colocated *sessions*, never swap *weights*; the only elastic things should be small state (our slots, our cache). *Steal:* confidence that T33's choice to make sessions (0.78 GiB) — not experts-as-whole-model — the elastic unit is right; expert-cache shrink is also "small state" relative to 65.4 GiB of experts.

**Clockwork (OSDI'20, arXiv 2006.02464)** — [HTML](https://arxiv.org/html/2006.02464), [USENIX](https://www.usenix.org/conference/osdi20/presentation/gujarati), [code](https://github.com/MachineLearningSystem/clockwork). Mechanism: *all* GPU memory preallocated at load into three pools (Workspace 512 MB transient, IOCache 512 MB async copies, PageCache = rest, 16 MB weight pages with static tensor→page maps); workers never allocate or lock during inference; controller queues per-batch-size, admits/drops requests that cannot meet deadlines; every action has earliest/latest timestamps and out-of-window work is aborted, not degraded. Deterministic `Load` (≈8 ms/ResNet50 over PCIe) is the only runtime memory op; 99.99th-pct latency within 0.03% of median isolated; 100 ms SLO for 99.9999% of 208M requests. *Single-GPU:* the principles are hardware-independent. *Steal:* (a) the entire contract — boot-time preallocation, bounded deterministic resize ops, abort-not-degrade — is the strictest formalization of what T33 asserts informally; (b) measure and publish the *deterministic cost* of promote/demote like Clockwork's Load; (c) their evidence that eliminating runtime allocation beats variance, which is T33's "static slots" instinct made rigorous.

### Group 2 — elastic MoE / expert offloading

**MoE-Infinity (OSDI'24, arXiv 2401.14361)** — [abs](https://arxiv.org/abs/2401.14361), [HTML](https://arxiv.org/html/2401.14361), [code](https://github.com/TerryX-666/MoE-Infinity). The closest published system to T33's competing-claims problem. Mechanisms: (1) Expert Activation Matrix Collection — request-level L×E trace of tokens routed per expert, kept separately for prefill/decode; on a miss with a full cache, PredictEAM matches the current iteration-level EAM to history by cosine distance with layer-proximity weighting, evicts lowest-priority expert; prefetch by predicted next-layer EAM overlapped on I/O threads (one thread saturates PCIe 4.0); EAMC of ~120 entries (3% of requests) suffices, query 21-226 µs (<1% latency). (2) **Dynamic expert-buffer resize:** dense/KV parts stay resident "without eviction"; the expert buffer *shrinks as context grows* — DeepSeek-V2-Lite needs ~3 GB/decoding-iteration, shrinking to 2 GB at 2^16 and 1 GB at 2^17 context, at which point it "forces fallback to on-demand fetching" with a measured **+137 ms** penalty. Evaluation: single RTX A5000 24 GB; TPOT 155 ms avg vs vLLM 485 ms (3.1-16.7x over baselines). *Delay hides:* prefetch against predicted EAM during compute. *Single-GPU:* yes — this is the closest published baseline for T33. *Steal:* (a) they prove the shrink-as-KV-grows design point exists and degrades exactly where T33's floor invariant should live; (b) their +137 ms on-demand penalty is the quantified cost of *not* having a zero-delay path — publish ours against it; (c) trace-guided EAM matching is a cheap upgrade path for deciding *which* sessions to demote first (demote the session whose predicted future expert set overlaps the hot set least).

**AdapMoE (ICCAD'24, arXiv 2408.10284)** — [HTML](https://arxiv.org/html/2408.10284v1), [code](https://github.com/PKU-SEC-Lab/AdapMoE). Mechanisms: (1) sensitivity-based gating — Fisher-information-approximated perturbation score decides whether a token activates 1 expert instead of top-2 (-25% activations, no finetuning); (2) prefetch — reuse next-layer gate on current hidden states (residual-stream similarity) to prefetch next 2-3 layers, plus a tiny auxiliary gate trained on last token's activations for layer 1; (3) **per-layer cache budgeting as a knapsack** — expected on-demand-load cost derived from gate probabilities/prefetch accuracy/hit probability, solved by DP; early/sensitive layers get more cache; LRU within layers; fine-grained CUDA streams + tile-wise load/compute overlap. 1.35x avg over a tuned Mixtral-offloading baseline on RTX 4090/A6000 (4-bit HQQ). *Single-GPU:* yes (consumer cards). *Steal:* when the expert cache is small (post-shrink), split it **per layer** by the DP/knapsack rather than a global LRU pool — cache need is provably non-uniform across layers.

**Pre-gated MoE (ISCA'24, arXiv 2308.12066)** — [HTML](https://arxiv.org/html/2308.12066). Mechanism: a trained pre-gate MLP per MoE block emits layer N+1's expert mask during block N, so expert transfer overlaps block-N compute (first block carries an extra gate; last has none). Requires *fine-tuning* (pre-gates trained alongside downstream fine-tune; pretrained weights untouched). Results: 1.7x avg (max 1.9x) vs on-demand loading, 42x vs naive prefetch; single A100 80 GB PCIe; peak GPU memory 4.2x lower than GPU-only; ~81% of GPU-only throughput. *Single-GPU:* hardware yes, but the model change is not available for our checkpoint. *Steal:* validation that *predict-then-overlap* is the only way to make PCIe-class expert movement invisible; our runtime predictor (DuoServe-style, already at 93% hit) is the inference-time substitute for their trained pre-gate. No new action.

**EdgeMoE (arXiv 2308.14352)** — [ResearchGate entry](https://www.researchgate.net/publication/373451252_EdgeMoE_Fast_On-Device_Inference_of_MoE-based_Large_Language_Models). Mechanisms: expert-wise non-uniform bitwidth adaptation (sensitivity-aware quantization per expert) + expert preloading of frequently-accessed experts with bitwise compression, for Jetson-class devices. *Single-GPU:* yes in spirit (it is the extreme of our hardware class). *Steal:* under sustained multi-session pressure, per-expert mixed-bit (drop cold experts to lower bpw before evicting them entirely) is a recognized elasticity axis that composes with our mixed-bit quality plan (protect ffn_down).

**Mixtral-offloading (Eliseev & Mazur 2023, arXiv 2312.17238)** — [HTML](https://arxiv.org/html/2312.17238v1), [code](https://github.com/dvmazur/mixtral-offloading). The founding consumer-GPU expert cache: LRU over experts with k=2 (12 GB) to k=4 (16 GB) experts/layer resident; **speculative prefetcher** applies the *next* layer's gating function to the *current* layer's hidden states (valid because residual streams change slowly), fetching 1-2 likely experts during current-layer compute, with 4 async pinned staging buffers shared across layers; experts "active in short sequences of 2-4 tokens" is the locality argument that makes LRU work at all. 2-3 tok/s batch-1 on T4/3060/3080-Mobile. *Single-GPU:* yes — this and llama.cpp PR #29887 are our direct lineage. *Steal:* the staging-buffer pattern (fixed shared async buffers, no per-transfer allocation) — same discipline Clockwork preaches, applied to expert DMA; also the reminder that our demoted-but-idle sessions can keep a *minimal* hot set (k=2/layer) alive at trivial cost instead of demoting to zero.

**Fiddler (ICLR 2025, arXiv 2402.07033)** — [abs](https://arxiv.org/abs/2402.07033), [code](https://github.com/efeslab/fiddler). Mechanism (per the arXiv v3/ICLR version): non-expert params always on GPU; experts split by *offline popularity profiling* (ShareGPT calibration); at runtime placement is **static** — the dynamic part is a per-batch execution decision per expert: predicted CPU-compute latency (linear in input size) vs GPU latency + PCIe copy; pick cheaper. 1.26x single-batch, 1.30x long-prefill, 11.57x beam-search vs offloading baselines; single Quadro RTX 6000 24 GB (56/256 experts on GPU) and RTX 6000 Ada. *Note:* a "uKV/TalleQ" version of this paper (FAST'25 framing with dynamic parameter re-assignment) could **not** be verified anywhere — see methods note; do not cite TalleQ. *Single-GPU:* yes. *Steal:* when the expert cache hits its floor and a miss occurs, compute-on-CPU (AMX/AVX512 path) is a legitimate fourth option before thrash — we hold 96%+ of experts in DDR5 already.

**Klotski (arXiv 2502.06888)** — [abs](https://arxiv.org/abs/2502.06888). Mechanism: expert-aware multi-batch pipeline — *stretch* the compute of the current layer (more micro-batches) to cover the I/O of the next layer's cold experts; constraint-sensitive I/O-compute planner + correlation-aware prefetcher; up to 85x vs naive offload baselines. *Single-GPU:* partly — needs batch > 1, which we only have with multiple active slots. *Steal:* during a promote burst (new session's first prefill), batch the misses across slots so cold-expert loads amortize over more compute.

### Group 3 — zero-delay techniques

**Stream-ordered allocation (CUDA 11.2+)** — [NVIDIA devblog](https://developer.nvidia.com/blog/using-cuda-stream-ordered-memory-allocator-part-1/), [Programming Guide chapter](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html). Mechanism: `cudaMallocAsync`/`cudaFreeAsync` are *stream-ordered* — they behave "as if allocation and free were kernels"; the CPU call does not synchronize with the GPU; memory is valid for work ordered after allocation in the stream. Contrast: `cudaMalloc`/`cudaFree` synchronize the device. Pools (`cudaMemPool_t`) reuse memory without "expensive calls into the OS"; **release threshold**: default 0 returns all unused pool memory to the OS at every sync point (causing expensive re-allocation each iteration in sync-heavy loops); set `cudaMemPoolAttrReleaseThreshold = UINT64_MAX` to retain freed memory in the pool; `cudaMemPoolTrimTo` gives explicit shrink control. Caveat: the driver may implicitly release pool memory to satisfy unrelated `cudaMalloc`/`cuMemCreate` in-process — relevant when the expert cache and session pools must not steal from each other; consider separate pools per class. *Single-GPU:* yes. *Steal:* implement cache-shrink's "free 0.78 GiB" and slot-buffer materialization as pool ops with max release threshold — no sync, no driver round-trips; trim explicitly only when returning memory to the OS matters (it doesn't, in our fixed 32 GB world).

**VMM (cuMem*) as the resize substrate — vLLM sleep mode + vAttention (arXiv 2405.04437).** Sleep mode docs (fetched, current 2026): level 1 discards KV, backs weights to CPU; level 2 discards all; cuMem allocator preserves virtual addresses so wake-up maps physical pages back *in place*; `sleep_mode_offload_cudagraph=True` backs captured graphs to CPU and restores them so they are "replayed, not recaptured" (~3% decode overhead at bs1, pinned-memory cost); fine-grained wake via tags (`["weights"]`, `["kv_cache"]`); `release_kv_cache_memory()` requires a full pause and resident executor memory (i.e., their release is *not* concurrent-safe — T33's concurrent background shrink is beyond this). vAttention (validated in our 2026-10-16 file) uses the same VMM primitives for KV-pool elasticity device-side. *Steal:* VMM gives both patterns: (a) shrink = unmap physical pages of demoted slots, leaving reservations intact → promote = map back, no cudaMalloc, no address churn; (b) graph+pool persistence across the cycle.

**Watermarks vs on-demand.** vLLM reserves a ~1% block watermark and a `gpu_memory_utilization` headroom at init so preemption is rare and graceful; SGLang evicts cache to satisfy allocation (grow-by-evict-retry); MoE-Infinity bounds KV by a max-output-length reservation then lets the expert buffer absorb the remainder. No major engine resizes its *primary* pools at runtime; elasticity is always emulated by *evicting a cache* (prefix cache, expert cache) that shares the arena. *Lesson:* T33's design is the natural next step only because our arena has a real elastic tenant (the expert cache); keep a watermark for the fast lane's decode growth inside the promoted slot so a promotion can never immediately starve.

**Copy-on-write / shared state.** vLLM: refcounted shared blocks, copy at most one block on divergence (numbers above). SGLang: radix-tree shared prefixes with refcounts, evictable at zero refs. *Steal:* if sessions share system prompts (typical for a campaign), cross-session shared KV blocks both shrink the 0.78 GiB and make demotion cheap (shared blocks survive; only private blocks are dropped).

**Request draining vs live handoff.** Draining (finish-then-remove) is what every autoscaler does at scale-in and what vLLM preemption-recompute effectively does to victims; live handoff exists in Llumnix (pipelined KV migration, 20-30 ms) and ServerlessLLM (token backlog + recompute). For a *demotion* (capacity shrinking), drain = let the idle session finish; T33's hysteresis demote of *idle* sessions needs no handoff at all — the Llumnix/ServerlessLLM mechanisms matter only if we ever demote a *busy* session under memory duress, where Llumnix's tail-flip is the mechanism to copy.

**Lazy/pre-staged CUDA graph capture.** vLLM RFC #20098 (fetched): startup captures ~67 graphs, 10+ s; lazy capture on first use was proposed (plus capture-at-runtime-start, largest-first, time-bound, by IBM's diegocastanibm) and **closed as not planned** — maintainers: "capturing cudagraph during runtime is very complicated, with huge maintenance burden"; commenters flagged OOM-mid-serving (users can't tune `gpu_memory_utilization` for memory they haven't spent yet) and unpredictable runtime stalls. Per-graph capture ≈50 ms (8B model) after optimization; warmup runs dominate the rest. vLLM instead ships capture-size ladders + padding, and (new) graph persistence via sleep mode. *Assessment for T33:* our design answers each stated objection — bounded fixed-shape capture set (no shape explosion), background capture off the serving path (no unpredictable stalls), budgeted memory arena (no OOM surprise) — but the RFC is the reason our capture must stay a *small, closed set*, and why graph *persistence* (sleep-mode pattern) is strictly better than repeated capture. Also: audit why our capture is 1-2 s where vLLM manages ~50 ms/graph at 8B — likely warmup-iteration count and graph-pool sizing; both are reducible, and torch.compile artifact caching (their "cache GPU memory utilization like compilation artifacts" suggestion) is an accepted-practice pointer.

## Contradictions and resolutions

1. **"Runtime graph capture is bad engineering" (vLLM maintainers) vs T33's background capture.** Resolution: the rejection targeted *lazy, shape-discovery-driven, on-the-serving-path* capture. T33 captures a closed set of shapes off the critical path with pre-budgeted memory. Treat the RFC's objections as a checklist (bounded shapes, off-path, pre-budgeted, abort-on-miss-deadline), not as a prohibition. Also adopt their escape hatch: if a promote misses its deadline, serve the session uncaptured (eager) rather than stalling — the graph then upgrades in background.
2. **Fiddler's identity.** The task framing expected "uKV/TalleQ dynamic parameter orchestration" (FAST'25 framing); the only verifiable Fiddler is ICLR 2025 / arXiv 2402.07033 with *static* placement + per-batch execution choice. Resolved: cite the verified version; TalleQ flagged unverified (methods note).
3. **HoME (hierarchical HBM/DRAM warm-cold expert tiering)** — could not be located under that name (multiple query formulations; arXiv 2408.13397 is an unrelated XAI paper; "HoME" hits are multi-task-recommendation MoE architectures). Closest real systems recorded instead: Klotski (2502.06888), fMoE (2502.05370), HOBBIT (2411.01433), DALI (2602.03495), MoE-Lightning (2411.11217). Recorded as an honest negative.
4. **Swap vs recompute for state recovery.** vLLM's data says recompute is ≤20% of swap latency in typical settings; Llumnix says recompute of an 8k sequence costs 3.5 s; ServerlessLLM migrates tokens precisely because KV copy is expensive *cross-machine*. Resolution: the answer is context-length-dependent and locality-dependent — for same-device, KV copy at ~1.8 TB/s is ~µs-class per 100 MB, so swap wins on-device for long contexts, recompute wins for short ones. Set the demote threshold empirically (vLLM leaves it "auto" for the same reason).
5. **MoE-Infinity's shrink-as-KV-grows vs our shrink-cache-for-sessions.** Same action, different victim and contract: they shrink the expert buffer to serve KV growth and accept the +137 ms degenerate mode; T33 shrinks to serve *new sessions* with a zero-delay guarantee. The published +137 ms is our baseline-to-beat and the reason a cache floor is needed on both axes (KV growth and session count).

## Open questions

- Does T33's 34-59 ms hot-swap include the KV copy, or only graph-pool wiring + lane flip? If stop-and-copy, the Llumnix tail-flip should collapse it to single-digit ms; measure the breakdown first.
- What exactly costs 1-2 s in per-slot capture (warmup iterations? pool alloc? torch.compile guard re-checks)? vLLM's ~50 ms/graph at 8B suggests 10-40x headroom; also test the sleep-mode pattern (capture once, persist) which removes the question entirely for stable shapes.
- Can captured graphs be *cloned* across identical slots (same shape, different static-buffer pointers) via CUDA graph exec-update APIs (`cudaGraphExecUpdate` / kernel-node param patch), rather than captured per slot? No production LLM engine found doing per-slot graph cloning — would make promotion O(update) not O(capture). (Searched: vLLM/SGLang issues and docs; only whole-graph capture + padding exists. Open.)
- Demotion hysteresis parameters: no LLM-serving prior art found for session-level demote hysteresis (closest analogs: Clockwork's controller LRU with deterministic Load; KEDA-style stabilization windows in autoscaling). We will need to tune from scratch; suggest logging Llumnix-style per-event costs to justify the window.
- Whether the expert cache should keep a per-layer minimal hot set (Mixtral-offloading k=2/layer) during demote windows to protect the 93% hit rate from cliff-drop on re-promotion.

## AMENDMENTS TO OUR DESIGN (ranked)

1. **Persist slot graphs + graph memory pool across demote/promote (vLLM sleep-mode pattern).** Capture each slot shape ONCE; on demote, either keep the graph (if arena allows) or back its pool to pinned CPU and unmap physical pages (cuMem), preserving virtual addresses; on promote, remap and replay. Expected effect: the 1-2 s capture disappears from steady-state promote cycles (becomes a page-in), capture jitter leaves the tail entirely. Cost: pinned host memory (~graph pool size) and a stated ~3% bs1 decode precedent in vLLM's shipping implementation. This is the single highest-value change; it also answers vLLM RFC #20098's objections by construction.
2. **Make the hot-swap a Llumnix-style tail flip, not a stop-and-copy.** Pre-wire the new slot's buffers/graph while the conversation still decodes on the old lane; copy KV pipelined (it is append-only); flip lanes at an iteration boundary carrying only the final partial block. Llumnix shows 20-30 ms *cross-machine* with this pattern and ~constant downtime in sequence length; same-device it should be ms-class. Directly attacks the 34-59 ms figure.
3. **Hybrid demote policy: forget-vs-park KV by context length (vLLM recompute-vs-swap rule).** Demote = drop KV + keep token log (KBs) for short contexts (re-prefill on promote is cheaper than parking); park KV to host RAM (or keep resident if arena allows) only past a length threshold. vLLM ships exactly this decision ("auto") and their data says recompute is never worse than 20% of swap latency in the small/medium regime.
4. **Resize via CUDA memory pools with release-threshold = UINT64_MAX; separate pools per memory class.** Cache-shrink frees and slot materialization become stream-ordered pool ops (no device sync, no driver calls); explicit `cudaMemPoolTrimTo` only where OS return is needed. Isolate the expert-cache pool from session pools so the driver's implicit-release behavior cannot silently trade one for the other.
5. **Cross-session shared-prefix blocks with COW (vLLM/SGLang pattern).** If sessions share system prompts, refcount shared KV blocks: shrinks effective per-session footprint below 0.78 GiB, makes demotion cheaper (shared blocks survive), and costs at most one block-copy on divergence.
6. **Enforce an expert-cache floor + a per-slot KV watermark (MoE-Infinity counterexample).** Their shrink-to-1-GB degenerate mode costs +137 ms/token on-demand fetch. Never shrink the expert cache below the point where predicted hit-rate collapses (our admission-control data from the 2026-10-16 file gives the curve); conversely, cap per-session KV growth (window/sink) so a long-running session cannot starve the next promotion. Reject-or-queue arrivals (Mooncake 429-style, with a system-level load forecast) rather than admitting into a guaranteed-thrash.
7. **Per-layer knapsack split of the shrunk expert cache (AdapMoE).** When the cache is small, distribute capacity across layers by expected-miss-cost DP instead of one global LRU pool; layers differ in sensitivity and prefetch difficulty, and a global pool over-invests in easy layers.
8. **Budget the promoted session's first prefill with a Sarathi token budget.** The arrival rides the fast lane, but its initial prefill must not monopolize an iteration; chunk it against the lane's TPOT budget (this is also the answer if prefill-time expert misses spike right after a cache shrink).
9. **Smaller, cheaper capture.** Audit warmup-iteration count and pool sizing against vLLM's ~50 ms/graph (8B) data point; cache compile/capture artifacts per shape (their accepted-practice direction) so re-capture after any engine restart is also cheap. Fallback: serve eager (uncaptured) on deadline miss and upgrade in background — never stall for a graph.
10. **Do NOT adopt:** process-level phase split (Splitwiser loses CUDA graphs; gains modest); weight/model swapping (AlpaServe: seconds); prefill/decode disaggregation (needs a second GPU pool); trained pre-gates (needs fine-tuning; runtime predictor already covers it); HoME-style tiering as cited (system unverifiable — the real alternatives are listed above).
