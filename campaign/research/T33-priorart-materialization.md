# T33 Prior Art — Making Session Materialization Cost Approach Zero

Date: 2026-10-22. Scope: dynamic slot-session allocation on one RTX 5090 (sm_120), CUDA 13.4, Strata fork (ggml-lineage MoE engine), CUDA-graph-captured decode windows. Goal of the survey: find prior art for (1) CUDA-graph capture under unknown future shapes, (2) near-free GPU buffer grow/shrink from pools, (3) live in-process GPU memory re-partitioning.

Note on inputs: the referenced spec `campaign/research/T33-dynamic-session-allocation.md` did not exist on disk when this research was written (campaign/research/ contained only INDEX.md). Context was taken from the assignment text: background materialization budget ~1-2 s = shrink expert cache -> allocate ~0.78 GiB session buffers -> capture the session's CUDA graphs -> hot-swap the conversation in, while the request is served on an existing lane.

## Findings by confidence

### HIGH confidence (primary source or direct measurement, uncontradicted)

**H1. Nobody captures per dynamic shape at runtime; everyone pads into a captured shape set.**
- vLLM: dispatch key is the `BatchDescriptor` (num_tokens, num_reqs, uniform, has_lora); batches are padded up to a captured size; non-matching runs eager. Capture list is config-driven (`cudagraph_capture_sizes`), 67 sizes by default (RFC #20098). Design doc: docs.vllm.ai/en/stable/design/cuda_graphs.
- TRT-LLM: 23 default sizes (1,2,4,8,16,...,128 dense, then 256/512/1024/2048); "the runtime pads it up to the nearest larger captured size, running the model over some empty slots". Padding waste up to 50% at high concurrency with the coarse list; finer lists trade KV cache for less waste (blog20).
- SGLang: decode pads to batch buckets; prefill pads two-dimensionally — token buckets plus FIXED request slots filled with zero-length "sentinel" requests whose metadata is refreshed per replay (LMSYS blog 2026-08-17, #27988).
- Cost of this choice, measured (TRT-LLM blog20, GB200, R1 TP4): 23 graphs = 10.77 s capture; 49 graphs = 25.9 s; each graph costs ~10 MB of non-pooled memory; finer capture lists regress throughput by squeezing KV cache (DeepSeek-V3.2 lost 17.2% of KV tokens for a step-8 list).
- Implication: a "capture the session's graphs" step inside a per-session materialization path is a design the whole industry moved away from. Capture amortization is the entire game.

**H2. CUDA graphs bake in addresses; the universal pattern is static buffers + copy-in, and graph-owned pools must outlive the graphs.**
- PyTorch CUDA notes: "Replays always use the same virtual addresses"; capture-time allocations go to a graph-private pool that "stays alive until its CUDAGraph object and all tensors created during capture go out of scope"; pools may be shared only if graphs replay in capture order and never concurrently. docs.pytorch.org/docs/stable/notes/cuda.html.
- vLLM/SGLang runners hold "captured shapes, static buffers, attention metadata, batch padding" and copy live tensors into them per step (LMSYS blog runner/backend refactor; vLLM design doc).
- Implication for us: if a session's buffers can appear at DIFFERENT addresses per materialization, every graph that referenced the old addresses is invalid or must be patched. The cheap design is a fixed-address slot arena: N slots allocated once at startup, forever.

**H3. Stream-ordered pools make buffer materialization nearly free once the pool is grown — but the default policy actively fights you.**
- Semantics (CUDA programming guide, stream-ordered allocation): free-to-pool then reuse is guaranteed same-stream, event-gated cross-stream; default release threshold is 0, i.e. "all unused memory in the pool is released back to the OS during every synchronization" (allocator blog part 1); setting `cudaMemPoolAttrReleaseThreshold = UINT64_MAX` retains memory across syncs; with a non-zero threshold "allocation becomes simple bookkeeping" and performance becomes "independent of the size of the allocation". `cudaMemPoolTrimTo(pool, minBytesToKeep)` shrinks explicitly. The driver may defragment pools by remapping rather than new OS allocations.
- vAttention (arXiv 2405.04437, Table 3) gives the raw VMM costs that bound the "fresh" path: 2 MB granule — cuMemAddressReserve 2 us, cuMemCreate 29 us, cuMemMap 2 us, cuMemSetAccess 38 us, cuMemUnmap 34 us, cuMemRelease 23 us. Doing that per-layer synchronously cost vAttention ~5 ms per iteration before they moved mapping to a background thread.
- Implication: 0.78 GiB from a pre-grown pool = microseconds of bookkeeping (+ your own memset/copy). 0.78 GiB via fresh VMM mapping at 2 MB = ~390 granules x ~70 us of API time ≈ 20-30 ms if done synchronously — acceptable as a background operation, not as the primary path. Fresh `cudaMalloc` (allocates virtual+physical together) is the worst option and can serialize.

**H4. Graph update/patch is cheap when few things change; instantiation is the fixed cost; launch is now O(1)-ish.**
- NVIDIA "Employing CUDA Graphs in a Dynamic Environment" (Nov 2021): `cudaGraphExecUpdate` cost is "roughly proportional to the number of changes"; instantiation is expensive; on an A100 workload with 2520-kernel graphs, save-and-recognize cut 1540 captures to 3 (24-26% end-to-end vs per-launch).
- NVIDIA "Constant Time Launch" blog (Sep 2024, CUDA 11.8 vs 12.6, RTX 3060): instantiate 1025-node graph 2143 -> 1526 us (~1.5 us/node); first launch 278 -> 175 us; repeat launch on Ampere+ becomes "2.5 us + (~1 ns per node)" for straight-line graphs (previously 2 us + 200 ns/node); upload can be prepaid via a separate upload operation (cudaGraphUpload).
- ggml/llama.cpp already does the patch-and-replay dance: capture on first eval, patch node params between replays when only pointers change, and DISABLE graphs after 4 consecutive "graph changed" updates (PR #6766 merged May 2024, +5-18%; fix #7302; PR #16548 refactors this into "graph plans" and notes a pathological "update 1-3 times then reuse once" pattern; typical steady state reuses ~once per 128 tokens).
- Implication: even the worst-case "capture a session's graph" for a fixed-topology decode window is dominated by instantiation (~1-5 ms for a few-thousand-node graph) plus one capture execution — IF you skip framework-style dummy/warmup runs. The 0.5-1.5 s/session in our budget is framework-style process, not a CUDA API floor.

**H5. Weight indirection decouples hot-swapping from capture validity (proven in our own lineage).**
- llama.cpp discussion #28248 (Sep 2026, "persistent expert slot pool for MoE CPU offload"): a persistent pool of N GPU expert slots; expert IDs remapped to slot IDs via a device-side map table consumed by get_rows; LRU eviction with H2D copy-in; cache hits = zero H2D per step. Measured: +12% (N=16) to +84% (N=64) decode on RTX 4090 (Qwen3.8-Flash-Next, experts on CPU), +34% on a real workload; prefill bypasses the pool when a ubatch could touch more experts than slots (protects the decode hot set). VRAM budget after field reports: free_at_load minus max-context KV minus ~1 GiB rail.
- The architectural lesson transfers verbatim: because graphs reference the SLOT POOL (stable addresses), evicting/refilling experts is invisible to CUDA graphs. Shrink/expand of the expert cache therefore never recaptures anything.
- S-LoRA is the same idea generalized: KV cache and adapter weights share ONE paged pool (page size = hidden dim) and custom gather kernels (Punica BGMV-style) read adapters from arbitrary pool offsets; 2000 concurrent adapters on one A100 (LMSYS blog 2023-11-15). dLoRA (OSDI'24) adds the policy layer: keep weights "merged" when request mass concentrates, "swapped" when spread; up to 1.8x lower average latency than S-LoRA.

### MEDIUM confidence (multiple independent credible sources)

**M1. The graph-update path in ggml is real but fragile at multi-slot shapes — and its end-to-end payoff on Linux at small batch is small.**
- PR #16548 (open, unmerged as of May 2026 activity): author's RTX 5090 + Win11 shows hybrid MoE TG up to 1.34x (n_cpu_moe=99) but CUDA-only TG only 1.0-1.1x and PP 0.88-0.93x; Linux testers saw smaller or mixed results (some regressions, one -8% TG on GLM-4.6); reviewer attributes Windows gains to WDDM2 launch overhead.
- Issue #27009 (Aug 2026, "CUDA graphs for multi-slot decode via shape-stable padding"): proposes always padding decode ubatches to fixed size B or buckets {1,2,4,8} with dummy tokens, -inf mask columns, reserved dummy KV row, fixed out_ids — exactly the SGLang sentinel technique. Closed not-planned (stale): a maintainer-adjacent tester measured only ~2-3% difference on a 4090 across 1/4/8 slots with `LLAMA_GRAPH_REUSE_DISABLE` toggled and could not reproduce graphs turning off at >=2 slots on master. A maintainer disputed the "graphs are bs=1 only" premise.
- Implication: if our decode windows mirror ggml's, per-session graph capture buys little raw speed on Linux; the case for graphs in materialization is architectural (stable lanes), not throughput. Do not pay capture per session for 2-3%.

**M2. torch.compile-style "shape-generic" capture exists but the compiler dominates its cost.**
- SGLang LMSYS blog (2026-08-17): torch.compile accounts for 78-86% of graph preparation time — up to 90 s on a 235B MoE; their compiler-free "Breakable CUDA Graph" (BCG) builds prefill graphs 3.8-5.2x faster and replays ~17% faster than the compiled path (1.70x vs 1.45x vs eager; full capture 1.93x on gpt-oss-120b TP4 GB300); BCG extracted into meta-pytorch/breakable-cuda-graphs. 42 shapes cost only 2.4 GB on a 78-layer MoE; capturing through the chunked-prefill size cuts peak prefill activation memory dramatically (0.56 GB -> 0.001 GB on gpt-oss-120b).
- Implication: a C++ engine with precompiled kernels skips the 78-86% entirely; our capture cost floor is instantiate + one real pass. Also: "piecewise" (close the graph around a dynamic op and resume) is a pattern we can copy without any compiler — SGLang's `@eager_on_graph` break markers are the mechanism, and vLLM's shared-graph-pool-across-segments trick (vLLM #9724, weak refs at breaks) is the memory companion.

**M3. Watermark + floor borrowing across subsystems exists, at small scale, in production systems.**
- S-LoRA: one unified pool, memory shifts dynamically between KV and adapters (explicitly contrasted with reserved partitions that "waste space or cap" capacity).
- TRT-LLM blog20: the graphs-vs-KV tradeoff is a live re-partition decision made per capture-list config (V3.2 lost 4.86 GB of KV to graphs).
- #28248: expert-slot budget explicitly carved out of "free minus KV minus rail" — a floor formula, refined after deep-context slowdowns.
- vAttention: reclamation of mapped pages triggers "when cached page-groups fall below ~10% of GPU memory" (a watermark) with deferred reclamation; synchronous mapping otherwise causes 5-15 ms decode latency spikes.
- PyTorch: `garbage_collection_threshold` (e.g. 0.8) reclaims old cached blocks preferentially to avoid full sync-and-reclaim stalls; `expandable_segments` grows one VA segment per stream by appending, eliminating "unusable free slices" across 50+ layers — the canonical fragmentation failure mode (docs.pytorch.org cuda notes).
- Implication: our expert-cache-shrink -> session-buffer borrow has direct precedent, and the recurring failure across all of them is the same: borrowing done synchronously on the critical path, or floors set wrong, show up as latency spikes or OOM weeks later.

### LOW confidence (single source or inference — treat as leads)

**L1. Our engine's true per-graph capture cost is likely 5-50 ms, not 0.5-1 s.** Inference: instantiation is ~1.5 us/node (measured, RTX 3060, CUDA 12.6) and a ggml decode graph is thousands of nodes; capture itself needs one real execution pass; framework numbers (vLLM ~50 ms/graph post-optimization for an 8B model; TRT-LLM ~0.5 s/graph including a mandatory dry run) are dominated by dummy runs, profiling, and allocator warmup, none of which are CUDA-mandated. Verify empirically before trusting.

**L2. Conditional nodes (CUDA 12.4 IF/WHILE; 12.8 adds IF-ELSE and SWITCH; `cudaStreamBeginCaptureToGraph` from 12.3) could express variable-activity decode windows in ONE graph**, e.g. IF per slot or WHILE over a device counter for multi-step windows, eliminating CPU round-trips. No LLM engine adopted them in any source we read; PyTorch has an open bug where conditional-node graphs never release their memory pool after reset() (pytorch/pytorch#201567); cooperative kernels are disallowed and all nodes must share one context. NVIDIA blogs (May 2024, CUDA 12.4/12.8).

**L3. cuBLAS/CUDA 13.x fragility around capture**: CUDA 13.4-era release notes record a cuBLAS bug (13.3) where `cublasLtMatmulAlgoGetHeuristic` "invalidated an in-flight CUDA graph capture", fixed in cuBLAS 13.4 Update 1/13.5.1; cuBLAS 13.4 U1 also moved workspace to a per-device pool that retains across stream syncs. We use our own kernels, but any vendor-library call near capture is a hazard class. (CUDA toolkit release notes.)

## Honest negatives (sounds relevant, does not transfer)

1. **"Capture-on-demand per shape" (lazy capture)** — vLLM RFC #20098 was explicitly rejected ("strong no", maintainer, Aug 2025; closed not-planned Dec 2025): OOMs surface at runtime days later, latency becomes unpredictable. Any design that captures inside the materialization path inherits this failure mode on a 1-2 s loop.
2. **Graph alloc/free nodes (cudaMallocAsync captured into a graph, CUDA 11.4+)** — allocations become graph-owned and tied to graph launches; they do not give per-session buffer grow/shrink and add pool-lifetime constraints (and per the programming guide addendum you cannot memset stream-ordered allocations directly). Useful only for graphs that genuinely allocate internally; not our tool.
3. **MPS / MIG / green contexts** — partitioning is multi-process or SM-scoped, not memory re-partitioning within one process. Out of scope for slot-session allocation.
4. **CUDAPluggableAllocator / PYTORCH_ALLOC_CONF** — PyTorch-only surface; a C++ engine just implements the same ideas directly against cudaMemPool/VMM.
5. **`cudaMemPoolTrimTo` as a shrink mechanism for live traffic** — works only on unused pool memory and (per docs) not for IPC pools; fine for releasing the expert cache's own pool headroom, useless for moving memory between subsystems that have live allocations. Real re-partitioning needs either fixed-slot design or VMM unmap/map.
6. **vLLM's exact FULL+PIECEWISE machinery** — exists because attention backends have dynamic shapes and torch.compile integration; a ggml-lineage engine with its own kernels has no attention-backend boundary problem to solve. Steal the pattern (graph the static 95%, run dynamic ops eager between graph segments), not the code.
7. **cudaMallocManaged / unified memory** — rejected by vAttention for our exact reasons: no partial freeing, no aliasing, 2 MB default pages fragment.

## Contradictions and resolution

- **Capture cost: ~50 ms (vLLM RFC thread) vs ~0.5 s (TRT-LLM) vs "graph creation must amortize over reuse" (ggml).** Resolved: the CUDA-level floor is instantiation (~1.5 us/node) + one capture execution; everything above that is framework ceremony (dry runs, profiling, compile). Our engine sits near the floor (L1, unverified). Do not copy framework startup numbers into per-session budgets, and do not copy the ceremony either.
- **Do CUDA graphs matter at all on our platform?** Reddit/PR #6766 claimed +5-18% (2024); #27009 benchmark says ~2-3% at 1-8 slots on Linux (2026); #16548 says 1.34x only for hybrid CPU-MoE on Windows/WDDM. Resolved position: graphs are cheap to keep for a fixed-shape lane, but they are NOT a per-session value proposition on Linux/sm_120 — the materialization design should not spend anything on them per session.
- **Pooling default behavior**: allocator blog says default threshold 0 (release every sync); CUDA 13-era cuBLAS notes show even NVIDIA libraries now explicitly configure retained pools because the default is hostile to steady-state serving. Resolution: never rely on defaults; set thresholds explicitly.

## Failure modes catalogued (with sources)

- Fragmentation slivers from slightly-different allocation sizes each iteration -> fix pattern: one growable VA segment (PyTorch expandable_segments) or VMM page mapping (vAttention).
- Graph cache growth/OOM leaks when shapes vary (llama.cpp #20315, #25082) -> avoid unbounded per-shape caches; bound slot count.
- Pools retained by graphs never released after reset (pytorch#201567) -> define pool/graph teardown order explicitly (ggml PR #16548 hit a destruction-order bug too: scheduler depending on backend lifetime).
- OOM at first-use instead of startup (vLLM RFC rejection rationale) -> pre-reserve max-session arena at startup; fail fast.
- Borrowing done synchronously on the decode path -> 5-15 ms spikes (vAttention); solution: background thread maps/copies, i.e., exactly our "materialize in background" design.
- Stream contention: #28248 started with synchronous H2D map-table uploads and moved to pool-owned device-table copies enqueued on the split stream; expert copy-in must ride a side stream with event gating, never the decode stream.
- VRAM pressure from over-reserved slots -> deep-context slowdowns in #28248 until budget = free - KV - rail. Our equivalent floor: session arena + expert slots + KV + fixed rail.
- Vendor libraries invalidating in-flight capture (cuBLAS 13.3, fixed 13.4 U1) -> no library calls inside capture regions.

## AMENDMENTS TO OUR DESIGN (ranked by value)

1. **Delete "capture the session's CUDA graphs" from the materialization path.** Capture ONCE per lane at startup at a fixed max shape (or 2-3 buckets), and make every session — including brand-new ones — replay into a padded lane (SGLang sentinel slots / TRT-LLM padding / #27009's exact padding recipe: dummy tokens, -inf mask columns, reserved dummy KV row, fixed out_ids). Expected effect: the dominant 1-2 s term drops to the cost of copying conversation state; the residual risk (eager fallback for overflow) is bounded by the same buckets everyone else uses. This single change is worth more than everything else combined.
2. **Make session buffers fixed-address slots from one pre-grown arena.** Allocate N x 0.78 GiB once (cudaMallocAsync pool with `ReleaseThreshold = UINT64_MAX`, or a plain arena; NEVER fresh cudaMalloc in the materialization path). Materialization = slot assignment + H2D of conversation state + memset of scratch: microseconds of allocator work plus DMA. Set the floor so the arena can never fragment (it never frees).
3. **Route expert weights through a device slot-map table (get_rows indirection) and put expert-cache shrink on a side stream.** Per #28248: graphs then reference stable slot addresses, so shrinking the expert cache — the "borrow" step of materialization — never invalidates a graph and never touches the decode stream. Adopt their guardrails: bypass the pool for prefill ubatches wider than the slot count; budget = free - session arena - KV - fixed rail.
4. **If real memory must be returned when shrinking (rather than slot reuse), use VMM unmap/map, not copies, for anything whose authoritative copy already lives in host RAM** (offloaded experts qualify: cuMemUnmap is ~34 us per 2 MB and no H2D/D2H is needed to drop pages; re-grow is cuMemCreate+Map ~70 us per 2 MB ≈ 25-30 ms per 0.78 GiB, run in the materialization background thread with vAttention-style one-iteration-ahead mapping).
5. **Keep a graph-update fallback (cudaGraphExecUpdate / per-node param patch) for topology-stable, address-changed cases only** — and prefer to design it away via amendment 2. If kept, mirror ggml's guard: a bounded consecutive-update counter before falling back, and instantiate-once with prepaid upload (`cudaGraphUpload`, constant-time relaunch on Ampere+).
6. **Do not build on conditional nodes or device graph launch, and do not lazily capture new shapes at runtime.** Both are documented dead ends for this workload (PyTorch pool leak; vLLM maintainer rejection). Revisit conditional nodes only if GPU-side looped multi-step windows become a goal.
