## Novel findings

**D1 (HIGH — primary source, fetched paper HTML, direct quotes). Llumnix's scheduler is a thresholded freeness band over a virtual-usage metric: the policy half of the migration story, absent from the dossier.**
Source: Llumnix, arXiv 2406.03243v1 (OSDI'24), https://arxiv.org/html/2406.03243v1, fetched 2026-10-23.
- Load metric: per-instance "freeness" **F = (M − ΣV)/B**, V = per-request *virtual usage*, B = batch size. Dividing by B is deliberate: "it determines the consumption speed, i.e., the number of new tokens per iteration" — F approximates the instance's remaining decode iterations, not its free GiB.
- Virtual-usage rules (CalcVirtualUsage): normal running request = its physical usage; **head-of-line queuing request = its real memory demand** (physical usage 0) — so an instance with a queued arrival reads as overloaded (negative F) and migration is pulled toward it to make contiguous space (de-fragmentation); non-head-of-line queuing = 0; high-priority running requests = physical + headroom (**~1,600 tokens of load, profiled on LLaMA-7B**, to preserve ideal decode speed, split among the instance's high-priority requests); an instance being drained advertises a **fake request with infinite virtual usage**, forcing every request to migrate away.
- Decision cadence: the migration policy triggers **periodically, not per event**. Source = freeness below a threshold, destination = above a threshold; it pairs the lowest-freeness and highest-freeness instances repeatedly; migration stops when an instance falls back inside the band — **implicit hysteresis by construction**.
- Arrival-time decision: dispatch to the freest instance. Queued requests are **not** eagerly re-dispatched — they inflate virtual usage so migration comes to them ("queuing delay can dominate the end-to-end latency and worth such preference").
- Migration request selection: lower scheduling priority and **shorter sequences first**.
- Autoscaling: keep average cluster freeness within a band **[x, y] = [10, 60]** in their experiments, sustained "for a period" (temporal damping); scale-in picks the instance with fewest running requests.
- Transfers to us: our idle-demote/promote design (T33-dynamic-session-allocation.md §3) is a single-GPU freeness band in disguise. Steal the shape, not the fabric: (a) express our watermark in *remaining-decode-iterations* units (their /B insight), not raw GiB; (b) two thresholds + state that unsets inside the band is the canonical hysteresis shape the dossier says must be tuned from scratch (demote below x, allow promotion above y, no action between); (c) virtual-usage accounting lets a QUEUED arrival pull slot materialization toward itself without eager allocation — a queued client books its 0.78 GiB demand against the pool so the policy sees the need before the slot exists (the accounting form of "instant admission, background promotion"); (d) drain-by-infinite-virtual-usage is the bookkeeping mechanism behind our "never demote mid-conversation" (a session being parked advertises infinity so nothing new stages into it).

**D2 (HIGH, same source). Llumnix migration duty cycle: migration is active only ~10% of the time per instance on average, so its ≤1%-per-step overhead compounds to far less; victims are chosen as lower-priority + shorter first.** The duty-cycle figure is the new bit (the dossier carries 20-30 ms downtime, ≤1%/step, 3.5 s recompute already). For us: it says a policy that fires often is cheap if every event is a tail-flip — the spec v2 cap of one promotion per ~2 s is conservative, not load-bearing.
