# Decode-Loop Research Dossier: Overlap Scheduling, CUDA Graphs, MTP Speculation, Chunked Prefill, Determinism, RTX 5090 MoE Records
Context: single RTX 5090, 671-node CUDA-graph decode loop, MTP fork/join, batch-1. All claims cite primary sources I fetched this session.

## 1. vLLM overlap / zero-overhead scheduling
- Design doc: vLLM V1 alpha blog (2025-01-27) — https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2025-01-27-v1-alpha-release.md. V1 goals: "high performance with near-zero CPU overhead"; §5 "Efficient Input Preparation": persistent-batch technique (caches input tensors, applies per-step diffs; NumPy instead of Python ops) borrowed from LMDeploy; §2 scheduler treats prompt/output tokens uniformly via `{request_id: num_tokens}`, which subsumes chunked prefill and speculative decoding.
- V0 zero-overhead scheduler: PR #15801 "[Feature] Zero overhead schedule support" (lizhigong1988) — https://github.com/vllm-project/vllm/pull/15801. Removes sync points in sampling (`samples.tolist()`, `.cpu()`); CPU cannot see decode results immediately, so the next step's inputs (async H2D from pinned host buffers) are prepared while the current forward runs, with a background thread + semaphore pipeline.
- V1 async scheduling: PR #19970 "Implement Async Scheduling" (WoosukKwon) — https://github.com/vllm-project/vllm/pull/19970. Scheduler runs one step ahead ("output placeholder" = tokens scheduled but not yet generated); `--async-scheduling` flag. Measured: **+3–15% throughput; speedup larger for smaller models / larger batches; "No significant latency improvement is observed for batch size 1"**; reduces TPOT, slightly increases TTFT. Follow-up PR #23569 "[Perf][V1] Fully overlap model execution" makes the model runner async (prepare_inputs overlapped with forward) — https://github.com/vllm-project/vllm/pull/23569.
- Batch-1 takeaway: scheduler overlap mainly buys throughput; at batch 1 the win is TPOT consistency, not step-time reduction — your graph-replay loop already removes most of that overhead.

## 2. SGLang overlap scheduler
- PR #1738 "Faster overlap mode scheduler" (merrymercy) — https://github.com/sgl-project/sglang/pull/1738: "the overlap scheduler can bring 10% throughput improvement even when radix cache is turned off" (Llama-3.1-8B, 3000 prompts, 51.03 req/s with `--enable-overlap`).
- Overlap mode was default-on through v0.4.x–v0.5.x; disable path is `--disable-overlap-schedule` (flag still referenced in 2026-era PR #25464, https://github.com/sgl-project/sglang/pull/25464, which made speculative decoding always driven by overlap scheduling).
- Related: PR #2158 "Fix mixed chunked prefill in overlap mode" (v0.4.0 changelog). TensorRT-LLM's independent overlap scheduler measured **1.03x average latency** in a min-latency (bs=1) DeepSeek-R1 case — see §4 source; again: overlap ≈ throughput feature, near-neutral at batch 1.

## 3. CUDA graph batching strategies
- vLLM: V1 piecewise CUDA graphs (blog §6). Implementation: `vllm/v1/worker/gpu_model_runner.py` (verified in v0.8.5) uses `compilation_config.cudagraph_capture_sizes` (ascending `cudagraph_batch_sizes`); runtime replays the smallest captured size ≥ current token count, padding the batch up to that bucket (tunable via `--cudagraph-capture-sizes`; historically 1…512, dense at small sizes — exact default list per release is in config; treat "51 graphs" claims as version-specific). Decoupling attention (dynamic shapes) from the graphed regions is what makes piecewise capture possible.
- TensorRT-LLM batch-1 graphs: the official MTP/min-latency benchmark recipe captures graphs for bs=1: `cuda_graph_config: {}`, `max_batch_size 1`, `TRTLLM_ENABLE_PDL=1` (programmatic dependent launch) — https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog02_DeepSeek_R1_MTP_Implementation_and_Optimization.html. Same blog: "both the verification and draft stages can be captured in one graph" for MTP, and **CUDA graph alone gives 7.22x average speedup in min-latency mode** (vs eager, DeepSeek-R1-FP4, B200×8).
- cudaGraphExecUpdate for dynamic shapes: CUDA Runtime API (11.2+)`cudaGraphExecKernelNodeSetParams` etc. update an instantiated exec "as though node had contained the given params at instantiation" — https://docs.nvidia.com/cuda/archive/11.2.1/pdf/CUDA_Runtime_API.pdf. Real-world caveat: llama.cpp PR #31284 — https://github.com/ggml-org/llama.cpp/pull/31284 — shows `cudaGraphExecUpdate` returning cudaSuccess while silently keeping stale cluster dims (Hopper cuBLAS cluster shapes differ per shape → illegal instruction); llama.cpp re-instantiates graphs when cluster dims change. For your 671-node loop: prefer re-capture per shape class over update unless you validate grid/cluster params.

## 4. MTP speculative decoding (DeepSeek-V3 / TRT-LLM) + EAGLE-3
- DeepSeek-V3 (arXiv 2412.19437, §5.4.3): one MTP module predicts next-2 tokens; with speculative decoding "the acceptance rate of the second token prediction ranges between 85% and 90% ... delivering 1.8 times TPS". Checkpoint ships exactly one MTP layer → chain draft only.
- TensorRT-LLM: tech blog above. MTP-Eagle variant reuses one MTP module repeatedly sharing the target KV cache (vs MTP-Vanilla multi-module). Optimal draft length: **nextn=3 is best at bs=1: 2.16x** vs nextn=0; relaxed acceptance (top-10 candidates, delta=0.6, thinking phase only) → **2.33x** with slight accuracy drop. PRs: #9045 MTP>1 for DS-v3.2 (https://github.com/NVIDIA/TensorRT-LLM/pull/9045); #12353 merges Eagle3 & MTP-Eagle workers (https://github.com/NVIDIA/TensorRT-LLM/pull/12353); #12555 MTP+PP fix.
- Acceptance math (derived, Leviathan et al. 2023 chain framework): E[accepted per verify] = (1−β^(k+1))/(1−β). With β=0.87: k=1→1.87; k=2→2.50; k=3→2.99; k=4→3.36 tokens/step. Diminishing returns past k≈3 while draft+verify cost grows ~linearly → matches TRT-LLM's measured optimum at nextn=3. Your fork/join engine should sweep k∈{1..4} and measure β on your workload; effective speedup ≈ E[accepted]/(1+c·k) with c = marginal draft cost per token (small when the MTP head shares embeddings/output head, as DeepSeek does).
- EAGLE-3: arXiv **2503.01840** ("EAGLE-3: Scaling up Inference Acceleration of LLMs via Training-Time Test"). Abandons feature prediction for direct token prediction with multi-layer feature fusion; **speedup up to 6.5x, ~1.4x over EAGLE-2** (batch-1 style latency on single-GPU setups); 1.38x throughput @bs=64 in SGLang. Requires a trained draft head — for DeepSeek-V3/R1 the shipped MTP head is the zero-training-cost alternative (TRT-LLM blog confirms an Eagle3 head for DeepSeek is future work).

## 5. Chunked prefill: Sarathi-Serve & vLLM
- Sarathi-Serve (arXiv 2308.16369, OSDI'24 — https://www.usenix.net/conference/osdi24/presentation/agrawal): chunked prefills + decode-maximal ("piggyback") batching → stall-free schedules. Measured: **2.6x higher serving capacity (Mistral-7B, 1×A100) and up to 3.7x (Yi-34B, 2×A100) vs vLLM; 5.6x for Falcon-180B with pipeline parallelism**. Chunk-size guidance from the paper: Llama-13B on A6000 peaks at chunk ≥512 tokens; chunk 256 costs only 12.5% of peak prefill throughput — i.e., chunk ≈ compute-saturation knee, larger chunks buy little TTFT throughput but inflate per-step time and thus decode ITL/TBT tail.
- vLLM: V1 makes chunked prefill default via a token budget (`--max-num-batched-tokens`); the V1 scheduler combines one prefill chunk with decodes per step ("SplitFuse"-style: long prompts split across iterations, decode prioritized, short prompts packed) — see V1 blog §2 and vLLM docs/tutorials (e.g. vllm-ascend docs: "V1 scheduler splits long prefill inputs into chunks, with each step processing at most --max-num-batched-tokens"). SGLang v0.4.1 exposes `--chunked-prefill-size` (default None=auto; `max_prefill_tokens=16384`) — https://github.com/sgl-project/sglang/blob/v0.4.1/python/sglang/srt/server_args.py.
- Tradeoff for your batch-1 engine: every chunked prefill step inserted between decode steps creates an ITL spike ∝ chunk time. p99 ITL data point: TRT-LLM's benchmark guidance uses ISL/OSL 1K/2K; Sarathi's thesis is exactly that capping chunk size caps the per-step time, keeping TBT SLOs while sacrificing some TTFT. For latency-critical single-user decode, cap chunks near the 512-token knee.

## 6. Deterministic boot & warmup
- Clock pinning: `nvidia-smi -lgc <min>,<max>` (`--lock-gpu-clocks`) + `-lmc` (`--lock-memory-clocks`) defeats DVFS idle-downclocking, the main source of step-time variance. Documented pattern for 50-series: `nvidia-smi --lock-gpu-clocks=2500,3090 && nvidia-smi --lock-memory-clocks=9801,10001` (NVIDIA forum, RTX 50-series thread — https://forums.developer.nvidia.com/t/seconds-of-latency-on-50-series-gpu/362978/9); industrial precedent: Zivid KB "unstable capture time" prescribes locking GPU+memory clocks to fixed values because idle gaps let the driver drop clocks (https://support.zivid.com/latest/camera/support/unstable-capture-time-windows.html). Failure mode without pinning: headless GPUs stuck at 180 MHz (vLLM forum — https://discuss.vllm.ai/t/sm120-rtx-pro-4000-6-5x-throughput-gain-and-v0-18-1-regression-findings/2525).
- First-token latency variance: first request after boot pays weight load, kernel JIT (PyTorch/Triton autotune) and graph capture; subsequent requests reuse it (vLLM forum benchmark thread — https://discuss.vllm.ai/t/topic/814). Mitigations engines use: vLLM fires a dummy warmup request at engine init + captures all CUDA graphs before serving (V1 boot sequence), and has a sampler warm-up phase that pre-compiles graph variants for representative batch-size/sampling-param combos so "the first real user requests avoid extra compilation" (vLLM warm-up docs — https://docs.vllm.ai/projects/gaudi/en/0.13.0/configuration/warm-up/sampler_warm-up.html). TRT-LLM equivalents: build-time engine warmup + `trtllm-bench` warmup iterations; SGLang: `--warmups` factor + graph capture at boot.
- For your engine: boot sequence = load → capture 671-node graph(s) → replay N warmup iterations → then `nvidia-smi -lgc` pinned clocks; measure only after warmup steady state.

## 7. Batch-1 decode tok/s records on RTX 5090 (MoE, llama.cpp)
- llama.cpp discussion #17621 "Optimizing Token Generation in llama.cpp's CUDA Backend" (am17an, Nov 30 2025) — https://github.com/ggml-org/llama.cpp/discussions/17621. CUDA backend, tg128, -fa 1, fused+concurrent-stream opts (`GGML_CUDA_GRAPH_OPT=1`, explicitly NOT CUDA graphs):
  • gpt-oss-20b MXFP4 (20.91B, 11.27 GiB): **419.14 ± 0.89 t/s** (baseline 329.23; est. speed-of-light ~520 t/s ≈ 80%).
  • Qwen3-30B-A3B Q4_K_M (17.28 GiB): **352.06 ± 1.76 t/s** (baseline 246.96; +42%).
- Qwen3-Next-80B-A3B (hybrid linear attention): PR #17996 "Qwen3 next autoregressive pass" — https://github.com/ggml-org/llama.cpp/pull/17996 — dedicated n_seq_tokens==1 delta-net path, ~40% TG gain. On RTX 5090 (Vulkan, Q2_K_L, 27.23 GiB): tg128 **74.65 → 94.36 t/s**; pp512 ≈ 3072 t/s.
- gpt-oss-120b (117B, MXFP4, doesn't fit): via `--n-cpu-moe 20` ≈ **47 tok/s generation, 473 tok/s prefill** on a single 5090 (witcheer rtx-5090-benchmarks, 2026-06 — https://huggingface.co/datasets/witcheer/rtx-5090-benchmarks).
- Relevance: at batch 1, MoE decode is HBM-bandwidth-bound on active params; 5090's ~1.8 TB/s gives these ceilings. Your MTP k=3 with β≈0.87 on a ~3B-active MoE could multiply effective t/s ~2.2x if the fork/join stays inside the captured graph (TRT-LLM's 7.22x graph speedup shows eager-mode CPU dispatch is otherwise the dominant cost).
