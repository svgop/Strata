## 1. The donor's mechanism, walked (basalt @ fb0944c7)

### 1.1 What dm is

`dec_moe.hpp:1-11` states the contract: per layer, the verify window's MoE tail runs without host handshakes — one route kernel sorts routed entries into tiers from device residency tables, builds the VRAM group plan, quantizes the FFN input, publishes mapped rings and rings two doorbells; the peer GPU (we have none) and the CPU pool are served from those rings; CUDA0 computes its own entries immediately and waits on a tier only when the layer has entries there; the combine reads each tier's rows from where the tier left them. Every row is the same arithmetic as the grouped kernels it replaces ("a tier gives the same bits as before; only the PCIe share is gone"). `kDmCap = 128` entries/window (`dec_moe.hpp:22`; `kVerifyMaxT = 8` tokens × top-10 = 80 on our geometry — fits).

### 1.2 The route kernel — `dm_route_kernel` (`dec_moe.cuh:149-299`)

- **Launch shape:** `kDmThreads = 256` (`:10`); grid = `1 + ceil(n_tok·n_embd/256)` blocks (`dec_moe_route_blocks`, `:1714`; 8×2560 ⇒ 81 blocks). Host entry `dec_moe_route` hard-fails `n_tok·k > 128` or `n_embd % 256` (`:1716-1720`).
- **Work split:** block 0 plans (`dm_group`, `:43-79`); every other block quantizes its 256-value slice of the FFN input into `block_q8_1` rows (`q8_1_store`, `:250-256`) and, only if the CPU pool has entries, mirrors the fp32 x into mapped memory (`:255-256`); only if the peer has entries (or warm-up) does it copy the 288-byte q8_1 image per token to mapped memory, 16 B/thread (`:272-281`). A block also folds the **shared expert's gate partial sums** when wired (`sh_gw`/`sh_part`, `:258-271`) — the router-adjacent GEMV partial, warp-summed in fixed order.
- **Plan algebra (`DmPlan`, `dec_moe.hpp:32-39`):** `counts[4]` (VRAM groups, VRAM entries, peer, CPU), `start[129]`, `dst[128]`, `tok[128]`, `kind[128]`, `ptr[128]`. Grouping = distinct ids in routing order (first-occurrence order), entries ranked within group by entry order — `dm_group` computes `first`/`rank`/`cnt` per entry with an O(n²) shared-memory pass (n ≤ 80) and a 32-thread prefix scan variant `dm_group_keys` (`:83-144`). Tier assignment: id valid, not repeated within its token, and `res0[e] >= 0` ⇒ VRAM (kind 0); else peer (kind 2, `res1`); else CPU pool (kind −1) (`:159-171`). `ptr[g] = cache_base + slot_off[slot]` (`:224-228`) — the plan is built from the SAME inputs our `resident_plan` uses (residency row + slot table + blob stride).
- **Doorbell protocol:** after `__threadfence_system()`, each block's thread 0 does `atomicAdd(ctr)`; the last of `gridDim.x` writes the ring word to the peer (`ring | n_tok<<16 | has-peer<<28 | rows-published<<29`) and the host flag (`ring`), once, through mapped memory (`:283-298`). One PCIe doorbell round per layer, from inside the kernel.
- **PDL:** `pdl_trigger()` before the wait when the shared gate is folded (`:153`), `pdl_wait()` at entry (`:155`) — launched during the router's tail.

### 1.3 The glue — plan built inside the gate/up launch (the default path)

- **Gating:** `dec_moe_glue_ok` (`dec_moe.cuh:1726-1739`): gate/up ∈ {16,17,18,21,22,42} (or 40 via the gu1 variant), down with `kSplit`, `n_ff == 640`, `g_gu2 >= 2` (default 2, `iq_kernels.cu:2542`), `!g_old_kernels && !g_grouped_v1 && g_exp_phase == 0`. Dispatch: `verify.cpp:1866-1869` requires the hc read to produce the q8_1 rows (`hc_fused_q8_rows_ok`) — the glue's `xq` input comes from the hc read (`DmGlueArgs::xq`, `dec_moe.hpp:84-85`), which is why glue_on collapses without it.
- **`dm_glue_gu_kernel`** (`dec_moe.cuh:422-525`): `__launch_bounds__(256, 2)` — two blocks/SM by register budget. Per-block plan build from a 1024-expert × 16-token bit mask in shared memory (`kDmGlueExperts/kDmGlueTokens`, `:418-419`): each entry `atomicOr`s its token bit into `s_tab[e]`; a repeat within a token sets `s_dup`; group order/starts come from two warp-scan rounds (`:467-497`) — algebraically identical ordering to `dm_group` (first occurrence in entry order = earliest token; position = group start + popcount of earlier tokens' bits, `:500-503`). Block 0 writes `DmPlan` (dst/tok/ptr/start/counts) and then `pdl_trigger()`s (`:498-514`); non-lead blocks triggered at entry (`:433`). Every block then loops (row-block, group) items stride `gridDim.x`, computing grouped gate/up via `gu2::pair<TG>` (`:515-524`).
- **The ring block:** with `ring_on`, the LAST block is the route kernel's mode-2 remainder — reads ids, tiers them against `res0`/`res1`, writes the ring header + mapped q8_1/fp32 rows, rings both doorbells (`dm_glue_ring`, `:333-408`) — i.e. the doorbell launch is eliminated entirely; it hides inside the gu launch. It L2-prefetches the layer's residency rows and ptab first (`:436-439`).
- **`gu2::pair`** (`gu2.cuh:304-329` + `rows2` `:254-300`): grouped gate/up at TWO ROWS PER WARP. A row is 80 dot-calls (n_embd 2560 / 32); the first two passes of 32 calls run both rows (A/B) per warp; the half-idle third pass runs row A on lanes 0-15 and row B on 16-31, B's scale/sum shuffled to lane−16 before its add (`:282-299`). Weights via aligned 32-bit loads + `__funnelshift_r` (`int_at/int2_at`, `:19-30`), sign masks via `prmt` sign-replication (`:33-48`), grid table staged in shared memory per format (`:240-250`). **Bitwise `native_gu_multi_kernel`'s** by construction (same per-lane call order, same `warp_sum`; `gu2.cuh:5-11`). Entries consumed in sub-groups of 1/2/3/6 (`:312-328`). `gu2_usable` = n_embd 2560, even n_ff, 4-byte-aligned rows (`:360-362`) — ours qualifies.
- **The chain:** gu → `swiglu_q8_1_entries_pdl_kernel` (PDL dependent, triggers at entry, `gu2.cuh:376-390`) → `launch_down<T>` (`launch_dependent`, `gu2.cuh:392-405`; `dec_moe.cuh:1770-1784`). Down rows per item: 32 (IQ4_NL/Q4_K-class, `kDown40`), 16 (Q2_0), 8 else (`dm_down_rows`, `:744`) — same as our `iq_kernels.cu:4951`. The down kernel reads the plan the gu launch wrote; the SwiGLU/down launches start while gu's blocks are still arriving, and down blocks prefetch their weight rows to L2 before waiting (`gu2.cuh:364-368` header note).

### 1.4 The in-kernel tier wait and the folded combine

- **`dm_wait_kernel`** (`dec_moe.cuh:314-328`, launcher `:1787-1792`): ONE block, ONE thread, launched with `launch_pdl` (a programmatic dependent of the down kernel — it launches during down's tail). Order: optional `pdl_trigger()` at entry (`:316`) so the combine may start; stats clock; poll BOTH tier words together (`dm_poll_tiers`, `:302-312`, `__nanosleep(32)`); `pdl_wait()` — i.e. "the down kernel's rows are complete once this returns" (`:327`). Tier words are the SAME mapped doorbells the pool already rings (host_flag) — for us `m_flag_` (`verify.cpp:2105` passes `m_flag_`). `skip_peer` variant lets the combine poll the peer's per-row tags itself.
- **`dec_moe_combine`** (`native_moe.cu:202-239`): default form `dm_combine4_kernel<10, DEP, TAG>` — grid `((2560/4+127)/128, n_tok)`, 128 threads, **four columns a thread**; loads ALL final-on-wait data first (the VRAM `parts` rows with `__fadd_rn(0.0f, p)` to reproduce the old zero-add hit bits, the weights, the shared row), THEN `pdl_wait()`, THEN issues the mapped-tier row loads (`:147-166`); sum order j = 0..9 in order, first product rounded, one FMA per expert (`:187-195`) — the T-column contract. The DEP variant `pdl_launch_dependents()` at entry (`:134`) — the next layer's hc read starts its blocks while this combine waits. The TAG variant per-row-polls the peer's arrival word and restores it (`:167-186`) — peer-only, dead for us.

### 1.5 What runs per layer, and what a host-planned path pays that dm does not

Default glue path per layer, CUDA0 stream: hc read (1-2 launches, produces q8_1 + router) → glue gu (1, includes ring + plan) → swiglu (1) → down (1) → wait (1) → combine (1) ≈ **6-7 launches**. Non-glue layers (e.g. a gate/up format outside glue_ok): `dec_moe_route` (1) → `native_expert_grouped` on the dm plan (3: gu/swiglu/down, `verify.cpp:2050`) → wait (1) → combine (1) ≈ 6-7.

Per-token/per-window work a host-planned path pays that dm deletes, in donor terms:
1. the host plan round trip (wait-flag kernel + mapped plan copy per group) — the plan is built on device inside the gu launch;
2. the always-published x copy — only published when the CPU tier actually has entries (`:255-256`, `dm_glue_ring :394-397`);
3. the separate q8_1 quantize launch — folded into route/hc;
4. the PCIe staging tier wholesale (fetch_blobs + pointer rebase + second grouped launch + waitB) — "only the PCIe share is gone (those entries go to the CPU pool)" (`dec_moe.hpp:11`);
5. `copy_rows_from_mapped` + `moe_hit_add` — the down kernel scatters rows DIRECTLY into `parts` at `plan->dst[e]` (`dm_experts` `:1013-1018`), and the combine reads each entry's row from its tier by `plan->kind` (`dm_combine_kernel :110-115`);
6. the wait/combine serialization — combine pre-loads weights/shared under the wait (PDL), and both are 1-thread/1-block-class launches overlapping the down tail.

**Parked relatives (do not port):** `pk_moe` persistent MoE and `dec_shx` one-launch shared expert have NO call sites at the pin (T25-1 §5, re-verified by reading `dec_moe.cuh` — the shipped shared path is the side-stream fork, basalt `verify.cpp:1976-1990`); `dec_moe_vram` TMA kernels are built but `d->vram = -1` is the only assignment (`verify.cpp:515`) — unreachable; the peer persistent kernel + L2 warm-up (`dm_peer_kernel`, `dec_moe.cuh:1253-1376`; `dm_warm` `:1098-1245`) is peer-tier machinery we do not have.

**Total ≈ 12-14 nodes per (layer, group) on the critical stream, ×2 groups ×48 layers** — against the donor's ~6-7 per layer. The wait kernels are 1-block spins (`verify_kernels.cu:1190,1500-1514`); our own comment prices a dependent launch at ~2.4 µs (`verify.cpp:295`). The plan lists are algebraically identical to the donor's (`resident_plan_par_kernel`, `verify_kernels.cu:1438-1499`: first-occurrence groups in routing order, `dst`/`tok`/`ptr[start]` layout = `DmPlan`'s up to field order).

**Formats:** `native_experts.txt` (read-only) gives 48 layers = 14×(18,20), 3×(18,42), 9×(21,20), 1×(21,42), 15×(22,20), 5×(22,42), **1×(23,20)** — ALL in `DM_PAIRS` (`dec_moe.cuh:1024-1027`). n_ff = 640 (`ED_HB=20`, `iq_kernels.cu:2142-2143`; shexp rows 640×2560). The (23,20) layer fails `dec_moe_glue_ok` (23 ∉ {16,17,18,21,22,42}, `dec_moe.cuh:1727-1728`) but passes `dec_moe_formats_ok` (23 ∈ `DM_GU_FMTS` `:1022`) ⇒ dm stays ON for the whole model; that one layer takes the route+grouped form. **Arithmetic:** unchanged by construction — the dm row math calls the same `row_dot_multi`/`row_dot_40_sub8`/`row_dot_20_sub16` family both trees share from v0.2.1 (our `iq_kernels.cu` is byte-identical to upstream v0.2.1.4 per T25-1 §1); GRP_NC 4 (ours) vs 6 (donor, `iq_kernels.cu:1367` vs ours `:1801`) changes only entry batching, not any (row, entry) sum order. The combine contract also matches: `dm_combine4_kernel`'s sums = our `combine_k10_vec4[_hits]` (`native_moe.cu:66-140` vs donor `:127-198`), with `+0.0f` standing in for our zeroed-row hit add — bitwise equal including the ±0 edge.

## 4. The +5-12% M1 band, re-derived

Node math (estimates, marked): at G=2, the tail costs ~24-28 nodes/layer vs the donor's ~6-7; delta ≈ 17-21 nodes/layer-group. But not all delta-nodes are equal:
- **Pure-overhead nodes** (2.4 µs class — launch + dispatch + trivial body): plan copy (1), doorbell (1), quantize (1), PCIe grouped-empty (≤1), copy_rows (1, plus ~0.9 µs of 1.6 MB traffic) ≈ 5/layer-group ≈ 0.24 ms/window per G=1 pass… ×2 groups ×48 layers is wrong arithmetic — per LAYER-GROUP: 5 × 2.4 µs = 12 µs; × 48 layers × (1 + G2 fractional presence ~0.7 at mean n 2.47) ≈ **0.7-0.9 ms/window** (estimate).
- **waitA, the host-plan round trip** (device_plan_ OFF in the live config): a mapped-memory RTT + host wakeup per group — this is the core of T13A's 3d (0.83 ms). dm deletes it entirely; credit **0.4-0.7 ms/window** (estimate; the DM_WAIT_STATS-class instrument would price it exactly — our STRATA_DECODE_TIMING is the cruder proxy).
- **waitCPU (3h, 0.4-0.8 ms)**: NOT recoverable — the pool's compute latency is real and dm waits for it too (in-kernel instead of as a node; the combine's prefetch hides a few µs of it). Anyone claiming the full 3h as win is overcounting.
- **What the donor gets that we do not, at Phase A:** the PDL substrate (early triggers, down-rows prefetch, combine-under-wait) and the hc-fused router/q8_1 fold — donor-specific, priced separately (T23 #3).
Credible total at Phase A, M1: **−0.6..−1.2 ms/window on a ~11.5 ms window ⇒ +5..10% M1** (estimate) — the top of T25-1's band is reachable only because our live config pays the plan RTT every group (their published windows ran with the dm path always on, so their +5-12% analog was measured INTO their number, not stacked on it). Conc (6 windows, G=2 always) should scale at least as well; pair (n=2, G=1) gets roughly half the node savings. Donor-specific residue (PDL, hc fold, peer warm-up) is excluded from the band and is where their remaining ~1.5× lives (T23 calibration).
