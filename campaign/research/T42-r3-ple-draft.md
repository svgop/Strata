## External-doc claims: right / wrong

**(a) "The engram is designed to live in host RAM and be gathered per token" — WRONG on residency, right on gather.** The design statement is explicit: the table "is never held in RAM: every row comes from an unbuffered 4 KiB read" (`ple_reader.hpp:3-4`); default mode keeps it on the SSD, `mmap` only page-caches touched pages, and host-RAM residency is the opt-in `--ple-io ram` (28.8 GB mlock, `ngram.hpp:156-159`). "Gathered per token" is correct: 16 rows/token from a host hash (`ngram.hpp:103-111`).

**(b) "A single page fault at layer 1 stalls the whole forward — pagefile hazard" — MOSTLY WRONG.** In default Direct mode there are no page faults at all (unbuffered reads; `ngram.hpp:141-147`); a slow row read blocks `collect` on the host thread before layer 1 — a real but different hazard (the SSD-stall watchdog #1425/#1629 exists for it). In our mmap mode a cold page fault during the layer-1 gather does block the host feed of that token's forward — but the faulting file is the model's PLE shard on the data disk, not the OS pagefile; the row cache (82% corpus hit) and prefetching mitigate.

**(c) "The draft shares the 248k lm_head and reads ~521 MB per draft step at Q6" — WRONG for this deployment.** 248,320 x 2100 B = 521.5 MB is the FULL head, read only under `STRATA_MTP_FULL_HEAD=1` (`mtp.cpp:541-544,728`). Our draft head is the 40,525-token subset: 81.2 MiB native Q6_K, **55.7 MiB/step at Q4_0** after `--mtp-q4 all`.

**(d) "Draft never touches DDR" — WRONG as stated, right about weights.** The draft's own tensors (dense.bin 111 MB, 512 experts 675 MB, head subset) are fully VRAM-resident and never offloaded. But every draft round touches host memory: the PLE prefetch path reads the mapped shard into the host row cache (`mtp.cpp:1657-1666,1899-1904`), and the round runs through pinned mapped staging (`h_tok_/h_out_/h_prob_`).

**(e) "PLE disabled in draft" — MISLEADING.** True only vacuously (the 1-layer draft has no PLE block of its own). The engine wires the draft into the PLE path the OPPOSITE of "disabled": it prefetches rows for the seed and each drafted token (`do_ple` gate) so the verifier's layer-1 gathers hit the row cache — the LongCat draft→verify reuse pattern, already built. There is no `no_ple` branch anywhere in the draft code.

## Notable adjacent facts

- Prefill gathers a whole chunk's rows in one `gather_batch` (page-deduped, queue-depth-sorted); per-token budget ~0.35 GiB of touched rows assumed for the file tier (`generate.cpp:7896`).
- `--no-ple` is a diagnostic ablation only; without `--ple-gguf` layer 1's PLE is silently skipped (`generate.cpp:1033,3339-3341`).
- Boot probe: Direct mode measures rows/s at startup and can auto-suggest mmap; slow-probe auto-switch off by default since 0.1.43+ (`generate.cpp:4099-4128`).
- Image cells: the PLE hash reads `qwen4exp.ple.image_token_id` = 248,056 for vision cells (`generate.cpp:11396`).
