# Keeping live traffic off a cold path: what comparable servers do, and what it buys here (F-467, 2026-11-25)

Question (operator): identify this architecture, find how it is warmed elsewhere, and make the model never run
cold; a wait of two to three minutes before serving is acceptable.  Every quotation below was read from the
primary document on 2026-11-25; the Strata numbers are this campaign's own measurements.

## 1. What the architecture is

A tiered mixture-of-experts offload engine behind a Python API server.  Qwen3.8-Flash-Next's 46.8 GiB of expert
tensors are split three ways (18.8 GiB in GPU caches, a 37.86 GiB page-locked RAM copy, the rest reached through
the page cache), an adaptive tier swaps experts between RAM and GPU by observed routing, K/V beyond 32,768 cells
streams from RAM, a speculative drafter runs with an n-gram lookup, concurrent requests share batch windows whose
CUDA graphs are captured per slot count on first use, and finished conversations persist in a RAM cache and on
NVMe.  The server (`serve/server.py`, class `Prewarm`) owns the start-up: a file sweep, the engine load, a
post-pin sweep, then a replay of real requests.

The closest peer in component class is the llama.cpp server with CPU MoE experts (`--cpu-moe`, `--moe-cache-mib`
"GPU cache size in MiB for the MoE experts kept in the CPU") and a RAM prompt cache (`--cache-ram`).  The
vLLM / SGLang / TensorRT-LLM / Triton family solves the same start-up problem on different hardware.

## 2. What the peers do (primary sources)

| System | Mechanism, in its own words | Source |
|---|---|---|
| Triton | "the first (few) inference requests can be significantly slower due to deferred initialization"; "Triton will not show the model as being ready for inference until model warmup has completed"; the settings "define a series of inference requests that Triton will create to warm-up each model instance"; "the effect of warming up models varies depending on the framework backend" | [Model Warmup, Model Configuration](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/model_configuration.md#model-warmup) |
| SGLang | `--skip-server-warmup` (default off: warm-up runs); `--warmups` names "custom warmup functions (csv) to run before server starts ... before the server starts listening for requests"; `--cuda-graph-max-bs` "will extend the cuda graph capture batch size to this value" | [Server Arguments](https://sgl-project.github.io/advanced_features/server_arguments.html) |
| vLLM | a start-up contract that "makes their required specializations available during startup, before the first request, by warming the kernel's compile-key space without dummy runtime launches"; it "warms only the wrappers selected by the current engine configuration" | [JIT Kernel Warmup](https://docs.vllm.ai/en/latest/contributing/jit_kernel_warmup/) |
| TensorRT-LLM | graphs are captured for configured sizes (`cuda_graph_config: max_batch_size`, `enable_padding`); the benchmark method says "Warm up and ramp to steady state - send enough concurrent requests that the engine is consistently at or near max_batch_size" | [Run benchmarking with trtllm-serve](https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/commands/trtllm-serve/run-benchmark-with-trtllm-serve.md) |
| llama.cpp | `--warmup, --no-warmup`: "whether to perform warmup with an empty run (default: enabled)"; `--cache-ram N`: "set the maximum cache size in MiB (default: 8192)"; `--cache-idle-slots`: "save idle slots to the prompt cache on new task"; `--load-mode mmap+mlock` | [tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) |
| CUDA | lazy loading is the default: "do at least one warmup iteration prior to measurement", "preload the benchmarked kernel prior to launching it", "preload all kernels that will be used in the program before trying to initialize the allocator", or `CUDA_MODULE_LOADING=EAGER` | [Lazy Loading, CUDA Programming Guide 4.9](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html) |

## 3. The principles, and whether Strata already keeps them

1. **Warm the set the configuration can reach, not a guess.** (vLLM: specializations selected by the engine
   configuration.  TensorRT-LLM and SGLang: graph sizes from configuration.)  Here: the replay sends ~1.1k-token
   prompts and one six-way burst; it reaches one slot count, never a tool call, never a read past the K/V window.
2. **Gate the door: warm up before serving, and say so in readiness.** (Triton: not ready until warm-up completes.
   SGLang: before the server listens.)  Here: the opposite - the first live request pre-empts the warm-in
   (`_external()`), which is right for a shared server and wrong for a single-user restart.
3. **Populate memory, not only code.** (CUDA: preload kernels; llama.cpp: mlock.)  Here: kept - the file sweep
   (80.1 GiB) before and after the pin, and the engine's own warm-up pass.
4. **Restore state as part of start-up.** (llama.cpp: the prompt cache.)  Here: kept - the conversation cache
   is restored at boot; its deferral keys on free VRAM for the copy stream, not on host memory.
5. **Converge, then prove it with a reading.** (TensorRT-LLM: warm up and ramp to steady state.)  Here: the
   corpus at temperature 0 makes the start state deterministic (F-400), but nothing said whether the warm-in had
   converged.  Now the first short's rate is compared with a settled reading and printed.
6. **Measure the cold cost by shape before building.**  New instrument: `campaign/cold-cost-probe.py`.

## 4. What was cold after the old warm-in (two boots, 17:38 and 17:47, the standing at 8 GiB)

| Tool call, two calls | 142 / 163 t/s decode | 189 / 209 t/s | tier hit 85.6 % / 87.8 % against 92.8 % / 93.7 % |
| Bursts of 2, 3, 4, 5, 6 | within +-4 % of again | | one -8.7 % reading on burst 2 in boot 1, +3.1 % in boot 2: noise |
| Three ~97.5k-token cold reads | 14.37, 14.68, 14.58 s | | 6,849 / 6,745 / 6,693 tok/s: no first-use cost |
| Agent turns on the deep read | 761 ms, 1,164 ms | | |

Mechanism of the one repeatable cost: the adaptive expert tier fits a new traffic's routing during its first
request; a miss is a RAM-to-GPU swap on the window's path (8.5 ms a window against 5.3).  The corpus shows the
tier prose; nothing showed it a tool call.  In absolute terms the cost is small: 0.4-0.7 s on the first long
generation of an unusual text, about 0.1 s on the first tool call.  In the production boot the first twelve
requests decoded at 205 t/s against 184 later: no cold penalty visible at the operator's shapes.

The hole that remained is structural, not a shape: a request arriving while the warm-in runs ends it.  An
operator who restarts and sends within the first minute met an engine warmed only as far as the corpus.

## 5. What changed (serve/server.py, `Prewarm`)

- `prewarm.hold_s` (standing: 180): an inference request arriving during the warm-in waits at the HTTP door - no
  lock, no admission slot - until the warm-in ends or the hold expires; `X-Strata-Wait: 0` never waits (the
  warm-in's own requests carry it).  The hold is released on every exit path: warm-in done, failed, refused,
  engine down, expiry.
- `prewarm.replay.tools` (standing: on): a tool call and its result, so the first live tool call does not pay the
  tier's fit.
- A settled reading: the first short's whole-request rate against one more of the same shape at the end, printed
  with the verdict ("NOT CONVERGED" when the last is below 90 % of the first); every stage's seconds and tokens
  on /v1/status (`prewarm.stages`); /health carries `hold_s`, the wait a request would face now.
- Not built, with the pricing recorded: a burst per slot count and a deep-read stage.  Two boots measured no
  first-use cost for either (table above), so by the campaign's law 15 they are not run.
