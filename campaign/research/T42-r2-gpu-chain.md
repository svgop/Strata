## Verdicts on external-doc claims

**(a) "GDN decode uses one CTA per head = 48 CTAs = 28% of SMs" — RIGHT (for the production path).** The engine's decode-window recurrence is `g1(h_v)=48` CTAs of 512 threads, one per head (verify_kernels.cu:1215, 441); 48/170 = 28.2%. Caveats: the opt-in `--native-gdn` kernel column-splits to 1536 CTAs (native_gdn.cu:119), `STRATA_GDN_SPLIT` gives 192, and the commit kernel is 192 — "one CTA per head" describes only the default window kernel.

**(b) "GDN state is fp32, 108 MiB per stream, 216 MiB/token DRAM traffic" — RIGHT with one qualifier.** fp32 (session.cpp:106, kernel signatures) and 108 MiB/stream (36 x 3 MiB, session.cpp:43-45) verified; 216 MiB/token is the correct read+write *access volume* (36 x (3+3) MiB). Whether all of it hits DRAM depends on L2 — which is exactly why the opt-in `STRATA_L2_SETASIDE_MIB` persisting window over the state exists (generate.cpp:9300-9305); treat 216 MiB as the uncached upper bound, not a measured DRAM figure.

**(c) "HC adds two small kernels per layer = ~96/forward" — WRONG (undercounts ~3x).** Two HC read *call-sites* per layer is right (96 reads/forward), but each read (`fused_gr_read_multi`) is 3 kernel launches — norm, down, up (fused_gr.cu:1338-1475) — so ~288/forward plus the head read and final write. Writes are not extra (folded into the next read, verify.cpp:1306-1308). ~96 would require one kernel per read, which no config does (STRATA_GR_V3 gets 2/read).

**(d) "QSA is pure overhead below ~2051 context" — PARTLY RIGHT.** The 2051 bound is the codebase's own (`idx_top_k + idx_block - 1`, qsa.hpp:128-136), and below it the selection degenerates to an identity copy inside `block_topk_kernel` (qsa_select.cu:74). But the indexer *kernels still launch every step* — append, query, block scores, identity top-k, attention (verify.cpp:1870-1980) — there is no host-side short-circuit; and below budget attention is dense regardless, so what the indexer adds is launch/scan overhead, not selection work. "Pure overhead" overstates: it is fixed launch cost plus degenerate kernels.

**(e) "verify pays K+1 sequential passes over GDN state" — WRONG.** The window recurrence is one kernel per layer that runs all K+1 tokens sequentially *inside* the kernel with the state in registers — one state read at entry, one write only on commit paths (verify_kernels.cu:334-335, 336, 433-435); verify windows pass `n_keep=nullptr` so state isn't even written. There is no WY/UT chunk transform, but also no per-token DRAM round-trip. The real second pass is the commit's replay of the accepted prefix over the live state (default) or the F-216 snapshot promote (`STRATA_GDN_SLOTS`) — sequential in m, one launch per layer or one batched (48,4,36) launch (verify_kernels.cu:1115).
