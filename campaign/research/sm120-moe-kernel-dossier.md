# Dossier: Fastest MoE Grouped GEMM/GEMV on Consumer Blackwell (RTX 5090, sm_120, CUDA 13.4)

Compiled 2026-11-20. All citations verified against primary sources unless flagged "community".

## 0. Executive summary

sm_120 is **not** a cut-down sm_100 — it is a "chimera": Ampere-style warp-level `mma.sync` tensor cores with sm_100-style block-scaled FP4/FP8 MMA modifiers, Hopper-style TMA, **no TMEM, no tcgen05/UMMA, no cluster multicast, 99–100 KB smem/SM** (vs 228 KB on sm_100). Any kernel or cubin built for the sm_100 tcgen05 path fails on 5090. The practical state of the art for MoE on sm_120 today: **Marlin-style W4A16 for decode (bandwidth-bound)** + FlashInfer/CUTLASS SM12x grouped GEMM for prefill + cuBLASLt NVFP4 for dense. For your batch-1 GEMV: **do not chase tensor cores; build a bandwidth-saturating vectorized dequant-GEMV** (details §8).

## 1. vLLM fused_moe on sm_120

- **Marlin** is the workhorse fallback on sm_120 for W4A16 (AWQ/GPTQ INT4, MXFP4 W4A16, NVFP4 W4A16). Measured correct and fastest decode in community reports: 50.5 tok/s sustained decode, Qwen3.5-397B-A17B-NVFP4, 4× RTX PRO 6000 TP=4 ([vLLM forum thread 2536](https://discuss.vllm.ai/t/sm120-rtx-pro-6000-nvfp4-moe-performance-report-qwen3-5-397b/2536)); gpt-oss-120b MXFP4: 183 tok/s (RTX PRO 6000, Marlin MoE backend) and Qwen3-32B NVFP4 dense: 340 tok/s on 5090 ([fakoli/anvil-serving sm_120 lab notebook](https://github.com/fakoli/anvil-serving/blob/main/docs/findings/blackwell-sm120-lab-notebook.md), community).
- **Marlin NVFP4 correctness on SM120/121 is shaky**: issue [#54666](https://github.com/vllm-project/vllm/issues/54666) lists Marlin illegal-memory-access reports #49926, #50934, #52225, #49070 on this device class (GB10/SM121) and proposes auto-selecting the **B12X** backend (merged in vLLM PR #52018) ahead of Marlin; PR #47577 (open) auto-selects FlashInfer B12X on SM120.
- **vLLM CUTLASS MoE on sm_120**: PR [#43814](https://github.com/vllm-project/vllm/pull/43814) (open) fixes two silent gates: a Python capability check `>= 110` that disabled the path on SM120/121, and the missing `grouped_mm_c3x_sm120.cu` (FP8 grouped GEMM, tile 128×128×128, cluster 1×1×1, `KernelPtrArrayTmaWarpSpecializedCooperativeSm120`), which depends on upstream **NVIDIA/cutlass#3280** (`MainloopSm120ArrayTmaWarpSpecialized`, in review). Issue [#51525](https://github.com/vllm-project/vllm/issues/51525): explicit `VLLM_CUTLASS` NVFP4 MoE on SM_120 silently returns empty completions (auto selects FLASHINFER_CUTLASS).
- **Machete**: Hopper-only, deliberately — PR [#20830](https://github.com/vllm-project/vllm/pull/20830) "[Bugfix] Restrict Machete to only run on Hopper"; the Blackwell W4A8 gap is tracked in issue [#35439](https://github.com/vllm-project/vllm/issues/35439).
- **gpt-oss (MXFP4 MoE) on sm_120**: vLLM runs gpt-oss via Marlin by default; PR [#58877](https://github.com/vllm-project/vllm/pull/58877) (merged 2026-09-27, wtdcode) enables the OpenAI Triton MXFP4 MoE kernel on SM12x. RTX 5090 measurements: **decode speed identical to Marlin; Triton prefill 10% slower** ("smem is too small for a larger tile" — 99 KB opt-in smem vs 228 KB on SM100; block_m=128 pipeline stage 66.5 KB + 67.5 KB f32 accumulator overflows smem → num_stages=0; fix pins block_m≤32, `is_persistent`, `epilogue_subtile=1`; +8% KV cache headroom). Follow-up to #41028 and #52850. gpt-oss-20b MXFP4 on 5090: ~298 tok/s decode ([smeltcore recipe](https://smeltcore.com/recipes/gpt-oss-20b-on-rtx-5090-mxfp4-chat-at-298-tok-s-via-ollama-or-vllm/), community).
- **FP8 linears on sm_120**: PR [#49936](https://github.com/vllm-project/vllm/pull/49936) documents kernel selection (FlashInfer/DeepGEMM hybrid is Hopper-only; candidate order DeepGEMM → CUTLASS → Marlin → Triton); issue #46619: RTX 5080 FP8 silent hang, workaround `VLLM_USE_DEEP_GEMM=0`.

## 2. TensorRT-LLM trtllm-gen on consumer Blackwell

- trtllm-gen = TRT-LLM's low-bit grouped-GEMM kernel family. **On sm_120 the fit is partial**: SGLang PR [#49015](https://github.com/sgl-project/sglang/pull/49015) (2026-11-07) quotes the runtime error: *"The trtllm-gen batched GEMM cubin manifest contains no kernels runnable on sm120; this backend currently ships cubins for sm100, sm103 and sm107."* FlashInfer's own MoE API pins `_TRTLLM_ROUTED_ARCHS = (100, 103, 107)` and comments that FP8 kernels "compile for major 12 as well, but those cubins fail at runtime on SM120/121" ([flashinfer/fused_moe/api.py](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/fused_moe/api.py)).
- TRT-LLM itself targets datacenter Blackwell for these paths; its tech blog "MoE as Dense GEMM" (DenseGEMM, NVFP4 MoE on SM100/SM103) reports the low-latency regime (num_tokens 64–208) speedup up to 1.12× over trtllm-gen grouped GEMM on B200 ([blog24](https://nvidia.github.io/TensorRT-LLM/1.4.0rc4/blogs/tech_blog/blog24_MoE_as_Dense_GEMM.html)) — evidence that even NVIDIA treats low-token MoE as memory-bound and schedule-overhead-dominated. TRT-LLM v1.1.0 lacked qwen3_5_moe support entirely (forum 2536 above).
- **Licensing/extractability**: TensorRT-LLM is **Apache-2.0** ([LICENSE](https://github.com/NVIDIA/TensorRT-LLM/blob/main/LICENSE)); FlashInfer (also Apache-2.0) already vendors/redistributes trtllm-gen MoE kernels + cubin manifests, which is the proven extraction path for a standalone C++ engine. Caveat: the cubins you actually need (sm_120 NVFP4/FP8 grouped GEMM) largely don't exist yet — see quote above.

## 3. CUTLASS grouped GEMM on sm_120 vs sm_100 — the "SM120 Chimera"

Best single reference (community but technically detailed and consistent with NVIDIA's examples): [lna-lab/blackwell-geforce-nvfp4-gemm](https://github.com/lna-lab/blackwell-geforce-nvfp4-gemm):

| Feature | Source gen | SM120 reality |
|---|---|---|
| MMA | SM80 | `mma.sync.aligned.m16n8k32`, warp-level, register-to-register, **no tcgen05/UMMA** (`sm_120a` rejects `tcgen05.*` at ptxas; `sm_100f` cubins fail to load) |
| TMEM | SM100 only | **does not exist** |
| TMA | SM90 | available (async bulk GMEM→SMEM) |
| FP4/FP8 block scaling | SM100 | `…block_scale` modifier on mma.sync |
| Shared memory | unique | **99 KB/SM usable** (vs 228 KB sm_100) |
| Cluster multicast | SM100 | not supported, cluster 1×1×1 only |

Corroborated by NVIDIA's own CUTLASS example 79 ("Blackwell GeForce GEMM", optimized for RTX 50 series): *"The Blackwell SM120 CUTLASS kernel uses the new Block Scaled Tensor Core MMA Instructions (mma.sync.aligned.block_scale)"*, cluster shape must be 1×1×1 ([examples/79_blackwell_geforce_gemm/79a…cu](https://github.com/NVIDIA/cutlass/blob/main/examples/79_blackwell_geforce_gemm/79a_blackwell_geforce_nvfp4_nvfp4_gemm.cu); siblings: 79b NVFP4×NVFP4, 79c MXFP8/MXFP6/FP8×BF16). Also by [gau-nernst/gn-kernels](https://github.com/gau-nernst/gn-kernels): "SM100 (TMA + tcgen05)… SM120 (TMA + mma.sync)". So the 1-SM vs 2-SM question dissolves: **cta_group::2 (2-SM cooperative UMMA) is an sm_100-family feature; sm_120 has no tcgen05 at all**, warp-level mma only (a lone HN commenter argues tcgen05 "exists" under other SASS encodings — [news.ycombinator.com 46463475](https://news.ycombinator.com/item?id=46463475) — but every compilable code path uses mma.sync).
- **What works on 5090 today**: dense NVFP4×BF16, NVFP4×NVFP4, MXFP8/MXFP6/FP8×BF16 GEMM (example 79) via TMA + mma.sync.block_scale; grouped (ptr-array) FP8 GEMM once cutlass#3280 lands (vLLM PR #43814); grouped block-scaled NVFP4 MoE was producing garbage output — CUTLASS issue [#3096](https://github.com/NVIDIA/cutlass/issues/3096) documents the full debugging journey on RTX PRO 6000 (dense FP4 fine, grouped path wrong; `compute_120a` forced-compile segfaulted; fixed via FlashInfer SM120 patches + `compute_120f` under CUDA 13.0, reaching 39 tok/s native FP4 vs Marlin 46–49 tok/s). Build note for CUDA 13.x: use the family-conditional target `120f` (`FLASHINFER_CUDA_ARCH_LIST=12.0f` in practice, anvil notebook).

## 4. FlashInfer fused MoE / grouped GEMM

From [flashinfer/fused_moe/api.py](https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/fused_moe/api.py): trtllm-gen routed kernels = SM100/103/107 only (fail at runtime on SM120/121); CuteDSL MXFP8×MXFP4 grouped GEMM supports major 10/11/12 **including SM120/121**; dedicated **SM12xNvfp4Config / SM12xNvfp4Bf16Config** (CUTLASS NVFP4 W4A4 and W4A16 MoE for sm_120); **B12xNvfp4Config / B12xW4A16Config** — the "B12X" kernel family surfaced in vLLM #52018/#54666; **CudnnFrost*Config** (BF16/MXFP8/NVFP4/MXFP8×MXFP4) `supported(arch) in (107, 120)`; **FrostLowLatencyConfig**: low-token routed MoE on SM80/90/100/103/107/**120**. Takeaway: FlashInfer is currently the most sm_120-complete MoE kernel hub; trtllm-gen routes are the exception, not the rule.

## 5. DeepGEMM (DeepSeek)

Upstream README still says "SM90 or SM100" as the requirement ([deepseek-ai/DeepGEMM](https://github.com/deepseek-ai/DeepGEMM)), but SM120 kernels have landed upstream: vLLM PR [#51959](https://github.com/vllm-project/vllm/pull/51959) re-pins vLLM from DeepGEMM `e21c821` (arch dispatch 9/10 only, aborts on SM12x) to **`a6b593d`**, which adds `sm120_bf16_gemm`, `sm120_bmk_bnk_mn`, `sm120_fp8_fp4_gemm_1d1d`, `sm120_tf32_hc_prenorm_gemm` and the `arch_major == 12` dispatch; verified serving DeepSeek-V4-Flash on 2× GB10 (SM121, CUDA 13.2). FP8 1D1D grouped GEMM + FP8×FP4 are the relevant MoE primitives. Community port: [lmxxf/Consumer-DeepGEMM](https://github.com/lmxxf/Consumer-DeepGEMM) (CUTLASS SM120 grouped GEMM templates replacing Marlin FP4 on GB10/5090).

## 6. Credible 5090 GEMM/MoE benchmarks

[gau-nernst/gn-kernels](https://github.com/gau-nernst/gn-kernels) (Triton/CuteDSL, torch 2.12): RTX 5090 realistic-SOL large-matmul TFLOPS @600W — BF16 245.8, INT8 726, FP8 480, MXFP8 660, **NVFP4 1306** (memcpy 1509 GB/s; PRO 6000: NVFP4 1426; B200: 6242). @400W cuBLAS-path numbers: BF16 203, FP8 379, INT8 583, MXFP8 531, **NVFP4 1140** (SOL 1676). MoE decode tok/s: see §1 (50.5 tok/s 397B TP4 Marlin; 183 tok/s gpt-oss-120b; 298 tok/s gpt-oss-20b; lna-lab 175 tok/s Qwen3.6-35B-A3B NVFP4 on PRO 6000). GPU MODE runs a Blackwell NVFP4 track (GEMM **and GEMV** problems, B200, speed-of-light = max(TC throughput, DRAM BW)) — [gpu-mode/reference-kernels](https://deepwiki.com/gpu-mode/reference-kernels/3-nvidia-blackwell-nvfp4-track), [gpumode.com/news/nvidia-blackwell-competition](https://www.gpumode.com/news/nvidia-blackwell-competition); leaderboard write-ups of the `nvfp4_gemv` problem exist (Chinese community walkthroughs). Pattern: NVFP4 ≈ 2.6–3× FP8 ≈ 5–6× BF16 in FLOPs, but **decode tok/s tracks bandwidth, not TFLOPS**.

## 7. cuBLASLt NVFP4 on sm_120

Works and is fast: PyTorch's cuBLAS NVFP4 path on 5090 hits 1140 TFLOPS (gn-kernels above); cuBLAS docs: block scaling supported for FP8- and FP4-precision tensors (no mixing) ([cuBLAS](https://docs.nvidia.com/cuda/pdf/CUBLAS_Library.pdf)); TransformerEngine drives the same path (`use_fp4` NVFP4 GEMM in [cublaslt_gemm.cu](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/common/gemm/cublaslt_gemm.cu)). Caveats: CUDA release notes flag "FP8 matmuls may fail to launch on multi-device Blackwell GeForce systems"; one community reverse-engineering report claims intermittent wrong results from a cuBLASLt codegen path on 5090, bypassed via explicit `mxf4nvf4` PTX ([zhihu p/2037812230222246386](https://zhuanlan.zhihu.com/p/2037812230222246386), unverified). cuBLASLt has no grouped/MoE API — dense only.

## 8. Critical sub-question: M=1 decode, tensor cores vs dequant-GEMV

**A bandwidth-optimal vectorized dequant-GEMV is the right tool at M=1; tensor cores buy you nothing there.** Evidence:
1. Arithmetic intensity at M=1 is ~1 FLOP per weight element vs the 5090's flop:byte ratio of >400 (Marlin README: modern GPUs are 100–200 even before Blackwell; "as long as we perform less than 25–50 MACs per 4-bit weight… near-ideal speedup" — [IST-DASLab/marlin](https://github.com/IST-DASLab/marlin/blob/master/README.md), paper at PPoPP'25, DOI 10.1145/3710848.3710871). Marlin's own design notes: it sustains near-ideal 4× only up to batch 16–32 precisely by saturating bandwidth (async global loads with evict-first policy, L2-resident activations, double-buffered smem, interleaved dequant/MMA pipelines).
2. GPU MODE's NVFP4 track explicitly defines speed-of-light for the GEMV problem as **DRAM bandwidth**, not tensor throughput (reference-kernels link above).
3. Measured on sm_120: W4A16 Marlin (dequant + FMA path) **beats** native W4A4 tensor-core CUTLASS at decode — 46–49 vs 39 tok/s (CUTLASS #3096); gpt-oss decode on 5090: Marlin = Triton MXFP4 exactly (vLLM #58877). The tensor-core NVFP4 advantage (1140 vs ~200 TFLOPS) never materializes at M=1 because both sit at ~99% memory-bound.

What your scalar loop is missing vs a correct GEMV kernel: 128-bit (`int4`-packed) vector loads of 8×FP4, LUT/PRMT-based dequant, per-16-element e4m3 scale application, split-K across SMs with atomic or two-pass reduction, `cp.async`/TMA double buffering, and enough CTAs to saturate 1.5 TB/s (measured memcpy 1509 GB/s of 1792 spec). Marlin's sm_120 kernels (Apache-2.0 via vLLM) and FlashInfer's B12X W4A16 family are the best templates; lookup-table approaches for low-bit GEMV are analyzed in arXiv:2407.10960 (Frantar et al., "Fast Matrix Multiplications for Lookup Table-Quantized LLMs").

**Recommended plan**: hybrid — vectorized dequant-GEMV for M≤8 decode (your kernel, Marlin-ized), CUTLASS sm_120 grouped GEMM (mma.sync.block_scale, ≤99 KB tiles, cluster 1×1×1) or cuBLASLt-per-expert-batch for prefill; NVFP4 weights with W4A16 at decode and W4A4 only in the prefill kernel.
