## (a) FRONTIER MAP — what is genuinely new, with sources and dates

### A1. MoE decode kernels (fused route+plan+combine, in-kernel waits, expert-tier fusion)

1. **SGLang low-latency mode + sgl-nvidia-mega plugin (LMSYS blog, 2026-10-18)** — [https://www.lmsys.org/blog/2026-10-18-sglang-low-latency-mode](https://www.lmsys.org/blog/2026-10-18-sglang-low-latency-mode) [sourced]. DeepSeek-V4.1-Flash + DSpark spec decode on 4x GB300 / MI355X. Four mechanisms, each mapped to something we already have or are porting:
   - **MoE routing overlap:** expert GEMMs (8-row tiles) launch BEFORE routing finishes, using a **bitmap + population counts** instead of scan/sort; all-zero padded tiles skipped. MoE window 44.4 → 36.5 µs (−18%, donor-reported, GB300, EP). This is a *stronger* form of our empty-PCIe-group skip (our node always launches: verify.cpp:1709, prior-dossier anchor).
   - **Early dependency release inside PDL:** "the MoE reduction releases the next layer's first projection as soon as it starts polling for peers" — the trigger-at-start-of-wait pattern our dm_combine4 DEP variant has (basalt dec_moe.cuh:134-137, prior-dossier anchor). External confirmation the industry converged on the same trick.
   - **(AMD side, sgl-amd-mono/FlyDSL) Tag-based in-kernel waits:** values carry a monotonically increasing decode-step tag; consumers start as soon as tags match — "no flags/resets". Our doorbell protocol is already `wait_flag_ge` (verify.cpp:2105-2140, prior-dossier anchor) — i.e. ge-compared monotone flags ARE tags. Confirmation, not a gap. Weights load early (routed-expert weights after routing) — same as dm's down-rows L2 prefetch pre-wait.
   - **Fused draft sampling:** DSpark's five sequential Markov-head proposals become ONE kernel launch per GPU, head weights in registers; 85.1 → 34.2 µs (donor-reported, GB300). Directly the class of our one-launch draft-head item (T26-1 §5 row 4).
   - Measured whole-stack: median decoder layer 96.8 → 68.4 µs, attention region 33.4 → 18.3 µs, verify graph 1,205 → 1,189 kernels, 12-38% decode speedup at 1-8 concurrent (donor-reported, 4x GB300, 8K in/1K out).
2. **FlashInfer release train, Jul-Oct 2026** — [https://flashinfer.ai/releases](https://flashinfer.ai/releases) [sourced]:
   - **v0.6.15 (2026-07-17): "Fused FP8 blockwise MoE megakernel for BS ≤ 8"** (PR #3424) — a low-latency fused-MoE megakernel specialized to OUR batch regime (decode windows are T ≤ 8 tokens; our kVerifyMaxT = 8, top-10 = 80 entries). Exists; the class is shipping.
   - **v0.7.0 (2026-09-22): PrimTS** — "TRT-LLM Gen MoE kernels as Python source with PrimTS" (PR #4361): NVIDIA's trtllm-gen Blackwell MoE kernels **open-sourced in readable CUTLASS-DSL form**. This is the first time the reference implementation of small-batch fused MoE on Blackwell is *readable source* rather than a binary.
   - **v0.7.2 (2026-10-15): PrimTS fused-epilogue GEMMs** — fused SwiGLU epilogue, fused QKV+norm+RoPE epilogues (PRs #5758/#6255/#6286); plus **SM120 W4A8 EP MoE** and cuDNN speculative-decode verification.
   - **Shared-expert fusion** shipped as a first-class feature (FP8 v0.6.15 #2625, FP4 v0.6.17 #4239, unified API v0.6.18 #4326) — the industry treats shared-expert fold-in as standard, exactly what basalt's route kernel does with `sh_gw`/`sh_part` (dec_moe.cuh:258-271, prior-dossier anchor).
   - **v0.6.16 (2026-07-31): XQA decode kernel on SM120/121** — ragged Q + per-row sliding-window masking for speculative decode (#4137). Small-batch decode attention is being specialized per-architecture on OUR silicon.
   - **v0.7.1 (2026-10-09): DGX Spark Marlin 1.36x** (W4A16/W4A4 canonical-layout backends) — consumer-Blackwell mixed-input GEMM still moving.
   - API surface: [https://docs.flashinfer.ai/api/fused_moe.html](https://docs.flashinfer.ai/api/fused_moe.html) [sourced] — `trtllm_gen_routing` standalone routing kernel, routed variants taking precomputed topk_ids, `MoELayer` unified API with per-token-count-bucket autotuned backend selection, `enable_pdl` execution flag.
3. **FlashMoE (NeurIPS 2025; arXiv 2506.04667, Jun 2025)** — [https://arxiv.org/abs/2506.04667](https://arxiv.org/abs/2506.04667), [https://github.com/osayamenja/FlashMoE](https://github.com/osayamenja/FlashMoE) [sourced, paper landing only]. Fully-fused distributed MoE (dispatch+compute+combine) in ONE tile-pipelined persistent kernel with device-initiated comm and grid-wide sync, up to 9x vs non-fused (donor-reported, distributed training/inference context). Academic existence proof for the "one kernel per MoE layer" end-state — the same end-state basalt reaches without persistence (route/glue/wait/combine as 6-7 PDL-chained launches).
4. **NVIDIA "Boosting MoE training throughput with advanced fusion kernels" (developer blog, 2026)** — [https://developer.nvidia.com/blog/boosting-moe-training-throughput-with-advanced-fusion-kernels](https://developer.nvidia.com/blog/boosting-moe-training-throughput-with-advanced-fusion-kernels) [sourced via search summary; landing not deep-read]. Up to 1.3x forward-pass from MoE fusion kernels. Training-side, class-confirmatory only.
5. **Numerics caution:** Fireworks.ai, "When faster is not identical: MoE numerics" — [https://fireworks.ai/blog/when-faster-not-identical-moe-numerics](https://fireworks.ai/blog/when-faster-not-identical-moe-numerics) [sourced via search summary]. Fused MoE kernels introduce numerical drift vs the training graph — supports our bit-identity/T-column contract and the KL-gate-first stance for anything that moves bits.

### A2. CUDA graph / launch-overhead elimination

1. **TensorRT-LLM perf-optimization-casebook, PDL reference (NVIDIA, current main, 2026)** — [https://github.com/NVIDIA/TensorRT-LLM/blob/main/.claude/skills/perf-optimization-casebook/references/runtime-execution/pdl.md](https://github.com/NVIDIA/TensorRT-LLM/blob/main/.claude/skills/perf-optimization-casebook/references/runtime-execution/pdl.md) [sourced]. PDL is **default-on** since PR #9695 (commit 8462cf6c96f1), env `TRTLLM_ENABLE_PDL`, gated SM ≥ 90. Two things we had not priced:
   - **Per-kernel WAR disables exist for accuracy**: quant kernels, TinyGEMM, trtllm-gen routing (NaN), dsv3 MoE, Qwen3-235B ATP were turned OFF per-kernel after real regressions. PDL is not uniformly safe — it needs a per-kernel accuracy record and rollback. Our STRATA_DF_PDL is a single global switch (verify_kernels.cu:1720) with no per-pair kill switch.
   - **Per-kernel verification protocol**: nsys inter-kernel-gap measurement + parity eval vs PDL=0 + on-disk accuracy record. Matches our parity/canary laws but is worth encoding per pair, not per boot.
2. **NVIDIA, "Pushing latency boundaries: DeepSeek-R1 on B200" (TensorRT-LLM tech blog)** — [https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog1_Pushing_Latency_Boundaries_Optimizing_DeepSeek-R1_Performance_on_NVIDIA_B200_GPUs.html](https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog1_Pushing_Latency_Boundaries_Optimizing_DeepSeek-R1_Performance_on_NVIDIA_B200_GPUs.html) [sourced via search summary]. PDL named as the launch-latency-hiding lever in NVIDIA's own low-latency decode stack. Class confirmation.
3. **CUDA Graphs conditional nodes (NVIDIA blog 2024-05-10, CUDA 12.4+; docs current through 2026)** — [https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes](https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes), [https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) [sourced]. Condition evaluated on device when dependencies are met; IF/WHILE/SWITCH subgraphs. Production adoption now visible: vLLM issue #33341 "Support full CUDA Graph for the drafter" (2026-01-29) — [https://github.com/vllm-project/vllm/issues/33341](https://github.com/vllm-project/vllm/issues/33341) [sourced]; SGLang "Advanced CUDA Graph Techniques" (LMSYS, 2026-08) — unified decode/prefill/spec-decode graph runners — [https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph](https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph) [sourced via search summary]; HIP porting of conditional handles requested upstream (ROCm issue #3905, Jul 2026). The device-conditional draft graph we have queued (F-253, +0.3-0.9% est.) is the same primitive these stacks are standardizing on.
4. **Device-side graph launch (CUDA 12.4+; tooling matured in CUDA 13.1, 2025-12-04)** — CUDA 13.1 announcement: [https://developer.nvidia.com/blog/nvidia-cuda-13-1-powers-next-gen-gpu-programming-with-nvidia-cuda-tile-and-performance-gains](https://developer.nvidia.com/blog/nvidia-cuda-13-1-powers-next-gen-gpu-programming-with-nvidia-cuda-tile-and-performance-gains) [sourced]. Nsight Systems 2025.6.1 adds profiling of device-launched graph nodes and `cudaLaunchHostFunc` traces; cuBLAS adds grouped GEMM with "host-synchronization-free implementation with device-side shapes" + CUDA-graph support, "up to 4x over multi-stream GEMM in MoE workloads" on Blackwell (donor-reported). Our per-window loop is host-paced (graph launches at verify.cpp:2765/2840/3309, prior-dossier anchors) — device launch is the primitive that could chain draft→verify→commit with no host between.
5. **`cudaGraphInstantiateFlagUseNodePriority` (= 8)** — official semantics: "the graph was instantiated with UseNodePriority: the priority attribute of each node is used instead of the priority of the stream the graph is launched into" — [https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__GRAPH.html](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__GRAPH.html) [sourced]. Node priorities enter via capture from priority streams. Our instantiate passes flags=0 (verify.cpp:2628, :3588, :3595 — re-verified this session); our priority streams exist (verify.cpp:929, prior-dossier anchor). XS arm stands, now with exact documented semantics.
6. **Event Tensor: a unified abstraction for compiling dynamic megakernels (MLSys 2026, arXiv 2604.13327)** — [https://arxiv.org/abs/2604.13327](https://arxiv.org/abs/2604.13327) [sourced]. Quantifies the enemy outside graphs: kernel boundaries ~5-10 µs, fastest decode kernels 1-2 µs, so launch/sync dominates non-graph decode. Our window is already graph-captured with a measured marginal of 0.48-0.95 µs/node (R1 §1, prior-dossier anchor) — the paper's numbers bound what NOT capturing costs and validate that the remaining lever inside graphs is node count + overlap, not graphs-vs-streams.
7. **TaxBreak (arXiv 2603.12465, 2026)** — [https://arxiv.org/html/2603.12465](https://arxiv.org/html/2603.12465) [sourced via search summary]. Trace-driven decomposition of host-side LLM inference overhead — methodology cousin of our DRAFT_TIMING/nsys audits; nothing to port.
8. **llama.cpp (our parent) still pays this:** PR #26802 reportedly +13% decode from extended CUDA-graph capture (Turin Tech analysis, Aug 2026) — [https://www.turintech.ai/blog/inside-llama-cpp-pr-26802](https://www.turintech.ai/blog/inside-llama-cpp-pr-26802) [donor-reported; the underlying PR not independently read]. Base CUDA-graph work: NVIDIA blog 2024-08-07 [https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs) [sourced]. Confirms our window architecture is far ahead of the parent and that launch overhead is the binding constraint for everyone at small batch.
9. **Breakable CUDA Graphs (SGLang, default prefill path since v0.5.15, 2026-08/09)** — [https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph](https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph), [https://sgl-project.github.io/advanced_features/piecewise_cuda_graph.html](https://sgl-project.github.io/advanced_features/piecewise_cuda_graph.html), release notes via [https://github.com/sgl-project/sglang/releases](https://github.com/sgl-project/sglang/releases) [sourced via search summaries]. Builds prefill graphs 3.8-5.2x faster, prefill +39.5-40.9% in some MoE configs (donor-reported). Mechanism: piecewise capture to kill host-side Python dispatch + re-capture cost in a *serving framework*. Our prefill is C++ stream-launched with <1.5% launch overhead (T26-3 (b)) — nothing to win; see (d) N5.

### A3. sm_120 / Blackwell-specific hardware facts

1. **tcgen05 / TMEM do NOT exist on sm_120** — tcgen05 is sm_100a/sm_101a (datacenter Blackwell); GeForce Blackwell programs its 5th-gen tensor cores through classic `mma.sync` paths plus sm_120a-gated FP4/FP6 block-scaled variants. Sources: [https://gau-nernst.github.io/tcgen05](https://gau-nernst.github.io/tcgen05) (2025-12-21) [sourced]; PTX ISA target-ISA notes [https://docs.nvidia.com/cuda/parallel-thread-execution/index.html](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html) [sourced]; real breakage example [https://github.com/modular/modular/issues/5707](https://github.com/modular/modular/issues/5707) [sourced]. Also **wgmma is absent on sm_120** (Ada-style mma.sync only) — [https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor](https://newsletter.semianalysis.com/p/dissecting-nvidia-blackwell-tensor) [sourced via search summary]. Consequence: any donor kernel using tcgen05/wgmma (all SM100 megakernels, FA4) **cannot port to our card**.
2. **Thread-block clusters + DSMEM ARE supported on sm_120** — NVIDIA forum (2025-01-17): [https://forums.developer.nvidia.com/t/thread-block-clustering-in-blackwell-gpus/320471](https://forums.developer.nvidia.com/t/thread-block-clustering-in-blackwell-gpus/320471); CUDA compute-capability table: [https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html) [both sourced]. Basalt already proves it on our exact card: their CMake hard-fails arch ≠ 120 and the cluster dec_gdn_rec ships on an RTX 5090 (T23-basalt.md:15,23). The one Colfax caveat — "CTA cluster paths not supported on SM120" in their NVFP4 GEMM tutorial — is about CUTLASS's 2-SM cluster-MMA GEMM path, not cluster absence: [https://research.colfax-intl.com/optimizing-an-nvfp4-blockscaled-gemm-on-rtx-pro-6000-blackwell-gpu-sm120](https://research.colfax-intl.com/optimizing-an-nvfp4-blockscaled-gemm-on-rtx-pro-6000-blackwell-gpu-sm120) [sourced via search summary]. **The dec_gdn_rec rung's cluster+DSMEM construction is hardware-safe on our card.**
3. **TMA / cp.async.bulk:** usable on sm_120; basalt's CONTRIBUTING rule "never `cp.async.bulk.shared::cluster`" (T23-basalt.md:15) is a known consumer-Blackwell sharp edge (cluster-scoped bulk copies). Nothing new this sweep changes that discipline.
4. **F-252 (the fp32-accumulate half-rate lock) — no Blackwell unlock exists.** Searched 2026-10-21: no FMLA32-style unlock module for GB202; the only Blackwell unlock-class project found is vGPU ([https://github.com/bird/vgpu-unlock-blackwell](https://github.com/bird/vgpu-unlock-blackwell)) and it is **"Hardware-blocked"** [sourced]. The 2:1 remains documented spec in the RTX Blackwell whitepaper (209.5/419 TFLOPS for the 5090): [https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf](https://images.nvidia.com/aem-dam/Solutions/geforce/blackwell/nvidia-rtx-blackwell-gpu-architecture.pdf) [sourced]. Adjacent find, different pipe: a cuBLAS FP32-SGEMM 60%-utilization dispatch bug on RTX 5090 (Cloudrift, Apr 2026) — [https://www.cloudrift.ai/blog/beating-cublas-on-rtx-5090](https://www.cloudrift.ai/blog/beating-cublas-on-rtx-5090) [donor-reported] — CUDA-core FP32, not our F-252 pipe, but it is vendor-stack-bug evidence supporting an offline cuBLASLt algo sweep (candidate C4).
5. **Consumer-Blackwell support is now first-class in the big frameworks:** SGLang v0.5.17 release notes list "feat: SM120 (Blackwell Desktop) support" ([https://github.com/sgl-project/sglang/releases](https://github.com/sgl-project/sglang/releases) [sourced via search summary]); vLLM v0.12.0 added SM120-family NVFP4 + Marlin W4A8 (search-summary sourced); FlashInfer SM120 items per A1.2. None of it beats what we run today on this model — but SM120 now has maintained kernel paths to mine (XQA decode, W4A16 persistent launches, sparse MLA, GDN CuTe-DSL rewrite v0.6.14).
6. **PDL platform caveat:** a no-overlap report on GB10 (integrated sm_121-class) — [https://forums.developer.nvidia.com/t/issue-with-programmatic-dependent-launch-pdl-no-overlapping-execution-observed-on-gb10/359590](https://forums.developer.nvidia.com/t/issue-with-programmatic-dependent-launch-pdl-no-overlapping-execution-observed-on-gb10/359590) [sourced via search summary]. PDL behavior is per-chip; the nsys overlap probe stays mandatory per pair (our T-1 falsifier already requires it).
7. **No new sm_120 ALU-cap/f16x2 data beyond F-252** was found this sweep; the F-252 measurement (476/238, ratio 1.99/1.97, campaign/mma-accum-ratelock.cu) remains our only on-card instrument, consistent with the whitepaper's documented 2:1.
