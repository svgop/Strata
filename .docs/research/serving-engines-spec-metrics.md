# How four production serving engines define and gate the speculative-decoding depth/acceptance trade

Research date: 2026-10-12. Question under study: MAGMA v2 lowers the provisional-chain gate `--spec-min-p`
from 0.7 to 0.5, which buys 8-11% single-stream decode throughput and costs ~4 points of "acceptance rate"
(91% → 87%). The standing law lists acceptance rate (M3, MTP draft acceptance) among six metrics that may
never regress. This file records what vLLM, NVIDIA TensorRT-LLM, SGLang and HuggingFace Text Generation
Inference actually do with this exact trade.

Scope note: every claim below carries a URL. Claims that are my own reading rather than a source's own
statement are marked **(inference)**.

## 2. Per-system detail

### vLLM

- **What it does differently**: vLLM has no drafter-probability gate analogous to `--spec-min-p`. Chain depth is a fixed integer per configuration, and §"dynamic speculative decoding control" of the config carries the comment "dynamic speculative decoding control" over the field `num_speculative_tokens_per_batch_size`. So vLLM's answer to "the deeper chain wastes work" is *depth as a function of batch size*, never depth as a function of confidence at draft time.
- **Approach**: `SpeculativeConfig.num_speculative_tokens` is the depth (`--spec-tokens` on the CLI). `num_speculative_tokens_per_batch_size: list[tuple[int, int, int]]` is documented as "Batch-size schedule used to dynamically choose speculative-token count. Each entry is `(range_start, range_end, num_speculative_tokens)` with an inclusive batch-size range." A second, narrower mechanism exists: `enable_adaptive_verification: bool = False` — "Whether to adaptively size the draft-verification budget from per-request confidence. Currently only supported for method='dspark'." That is the closest thing in vLLM to a confidence-driven gate, and it is off by default and gated to one method.
- **Key tradeoff**: vLLM buys depth predictability (one depth per batch-size band, CUDA-graph friendly) at the cost of per-sequence adaptivity. `enable_adaptive_verification` cannot coexist with `use_local_argmax_reduction`: the validator raises "Adaptive verification estimates per-position acceptance from the draft logits, which use_local_argmax_reduction never materializes. Disable one of." Confidence-driven depth and a communication optimisation are mutually exclusive here.
- **What it got right that we have not**: two things. (a) `vllm:spec_decode_num_accepted_tokens_per_pos` is a counter labelled `position`, documented "Accepted tokens per draft position", with the PromQL to read it: `vllm:spec_decode_num_accepted_tokens_per_pos[$interval] / vllm:spec_decode_num_drafts[$interval]`. This tells you *where the chain should be cut*, which a single accept-rate number cannot. (b) vLLM states the acceptance→depth conversion explicitly: `_acceptance_length_to_rates(length, n)` converts a target mean acceptance length into per-position unconditional rates, using "the minimum-variance schedule" (`num_drafts = length - 1`). **(inference)** That is exactly the reverse of our gate: instead of shrinking depth until the draft confidence drops below `--spec-min-p`, start from the acceptance length you want and derive the per-position rates it implies.
- **Metric it publishes**: `vllm:spec_decode_num_drafts` ("Number of spec decoding drafts"), `vllm:spec_decode_num_draft_tokens` ("Number of draft tokens"), `vllm:spec_decode_num_accepted_tokens` ("Number of accepted tokens"), all counters, plus `vllm:spec_decode_num_accepted_tokens_per_pos` with a `position` label. The engine publishes counts only; the header comment documents the rates as PromQL: acceptance rate = `rate(...num_accepted_tokens_total)/rate(...num_draft_tokens_total)`, mean acceptance length = `1 + rate(num_accepted_tokens)/rate(num_drafts)`. The log line prints "Mean acceptance length: %.2f", "Avg Draft acceptance rate: %.1f%%" and "Per-position acceptance rate: %s". Mean acceptance length is explicitly "conventionally including bonus tokens".
- **Sources**: https://github.com/vllm-project/vllm/blob/main/vllm/v1/spec_decode/metrics.py · https://github.com/vllm-project/vllm/blob/main/vllm/config/speculative.py · https://github.com/vllm-project/vllm/blob/main/vllm/engine/arg_utils.py · https://github.com/vllm-project/vllm/blob/main/docs/usage/metrics.md · https://docs.vllm.ai/en/latest/features/speculative_decoding/

### NVIDIA TensorRT-LLM

- **What it does differently**: depth is authored in a typed config object **per algorithm** (`DraftTargetDecodingConfig`, `Eagle3DecodingConfig`, `MTPDecodingConfig`, `PARDDecodingConfig`, `DFlashDecodingConfig`, `NGramDecodingConfig`, `SADecodingConfig`, `UserProvidedDecodingConfig`), all inheriting `DecodingBaseConfig`. None of them takes a probability floor. Acceptance quality is traded against depth through the *shape* of the draft tree, not through a stop rule.
- **Approach**: `DecodingBaseConfig` defines `max_draft_len` ("The maximum number of draft tokens") and `max_total_draft_tokens` ("The number of draft tokens in the draft tokens tree… If it's a linear tree, each draft layer will only generate one draft token. In this case, `max_draft_len == max_total_draft_tokens`"). EAGLE 3 adds dynamic tree mode: `use_dynamic_tree=True`, `dynamic_tree_max_topK`, with the constraint `max_draft_len <= max_total_draft_tokens <= dynamic_tree_max_topK * max_draft_len`. MTP carries a partial-acceptance rule that is the nearest analogue to our "typical acceptance" rescue: `use_relaxed_acceptance_for_thinking`, `relaxed_topk`, and `relaxed_delta` — "We remove tokens `t` for which `log(P(top 1 token)) - log(P(t)) > relaxed_delta`". Batch-size-dependent depth exists as `draft_len_schedule`, "mapping batch-size thresholds to draft lengths", e.g. `{100:4, 200:3, 300:2}`, whose keys are merged into the CUDA-graph batch sizes. For `trtllm-bench`/`trtllm-serve` these are set via `--config config.yaml` under `speculative_config:` with `decoding_type` ∈ {MTP, Eagle3, NGram, DraftTarget, PARD, DFlash, SA}.
- **Key tradeoff**: TRT-LLM's docs state the boundary condition without hedging: "For all speculation algorithms, when speculation is enabled, a single sequence of draft tokens with length `max_draft_len` is created for every request. There is currently no way to dynamically disable speculation, thus speed ups are only observable at low batch sizes." Its performance section adds that effectiveness "is highly dependent on the specific task at hand" — code completion vs. article summarisation. Dynamic tree mode likewise "can improve acceptance rates compared to linear drafting at the cost of additional compute per generation step", and is "not supported" for sliding-window/MLA models such as DeepSeek and gpt-oss.
- **What it got right that we have not**: acceptance is reported as a **percentile distribution over requests**, weighted by decoding iterations, and throughput is reported alongside it in the same artifact. The reporting code weights per-request acceptance rate and acceptance length "by the number of decoding iterations the request ran", because "An equally-weighted mean would bias the result toward short requests" — and notes this makes `acceptance_length_percentiles.average` equal the global `sum(output_tokens) / total_decoding_iterations`. **(inference)** Our "acceptance rate" is a flat ratio over tested drafts; a long generation and a short one contribute equally to the noise in it, whereas TRT-LLM's iteration weighting makes the number converge to what it actually governs (tokens per forward).
- **Metric it publishes**: `trtllm-bench` emits a `decoding_stats` block containing `num_draft_tokens_percentiles`, `num_accepted_draft_tokens_percentiles`, `draft_acceptance_rate_percentiles`, `acceptance_length_percentiles` — each rendered with minimum/maximum/average/p50/p90/p95/p99 under the tags `[DT]`, `[ADT]`, `[DAR]`, `[AL]`. It also emits `acceptance_length` globally (`sum(output_tokens) / total_decoding_iterations`), and alongside it the throughput block: `request_throughput_req_s`, `system_output_throughput_tok_s`, `batch_full_output_throughput_tok_s` ("Estimated output throughput while active requests fill a batch"), `output_throughput_per_user_tok_s`, `output_throughput_per_gpu_tok_s`.
- **Sources**: https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/bench/dataclasses/reporting.py · https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/features/speculative-decoding.md · https://github.com/NVIDIA/TensorRT-LLM/blob/main/tensorrt_llm/llmapi/llm_args.py

### SGLang

- **What it does differently**: SGLang is the only one of the four that closes the loop in production. Adaptive speculative decoding "lets SGLang adjust `speculative_num_steps/speculative_num_draft_tokens` at runtime instead of keeping a single fixed value for the whole server lifetime. It is designed for workloads whose accept length changes over time, where one static step count is rarely optimal." The stated rationale is precisely our trade, in SGLang's words: "If `num_steps` is too large, the draft model produces many candidate tokens that the target model rejects, so extra draft work is wasted", and "At high batch sizes, the cost of each wasted draft step is multiplied across all sequences in the batch, so the optimal step count is often lower than at low batch sizes."
- **Approach**: three objects — `AdaptiveSpeculativeParams` (the EMA policy), `SpecRuntimeState` (per-tier runtime state bundle, owning its own `CudaGraphRunner` and attention backend per tier), and `AdaptiveController` (queries the policy for the current batch size and activates the matching state). Flow per decode round: ⓪ `activate_step_by_batch(batch_size)` → ① `draft(batch)` → ② `verify(batch, spec_info)` → ③ `forward_draft_extend_after_decode(batch)` → ④ `adaptive_controller.on_verify_complete(num_correct_drafts_per_req, batch_size)` → `worker.apply_runtime_state(state)`. Policy config keys: `candidate_steps` (required per BS slot), `down_hysteresis` (default −0.25), `up_hysteresis` (0.0), `ceiling_coeff` (0 = disabled), and globally `ema_alpha` (0.2), `update_interval` (5 verify batches), `warmup_batches` (10). Ladder examples ship as JSON presets: conservative `{"1": [1,3,7], "8": [1,3], "32": [1]}`; aggressive `{"1": [1,3,7], "8": [1,3,7] ceiling 3.0, "64": [1,3] ceiling 1.67, "128": [1,3] ceiling 1.2}`.
- **Key tradeoff**: adaptive mode is restricted — "Only `--speculative-algorithm EAGLE` or `EAGLE3`", "Only `--speculative-eagle-topk 1`"; "If either condition is not met, SGLang falls back to static speculative settings." It also requires pre-captured CUDA graphs per candidate tier (memory cost at startup), and the docs concede "If your workload is already stable and one static setting is well tuned, adaptive mode may not help much." The decision logic is deliberately damped (`warmup_batches`, `update_interval`, `down_hysteresis`/`up_hysteresis`) because switching is expensive.
- **What it got right that we have not**: the control variable is **accept length**, not accept rate. SGLang reads "the accepted draft length per request, computes the batch average, smooths it with an exponential moving average (EMA), and switches among the candidate tiers", with the policy `target_steps ≈ clamp(round(ema_accept_len) + 1, min(candidate_steps), max(candidate_steps))`. It also keeps **independent EMA trackers per batch-size range**, "so observations at small BS don't pollute the large BS signal", and it publishes the currently active tier as a gauge (`sglang:spec_num_steps`, `sglang:spec_num_draft_tokens`) so a throughput change can be attributed to a deliberate tier change rather than noise. **(inference)** That last point is the one our six-metric law is missing: SGLang can tell whether a metric moved because the policy moved or because the workload moved.
- **Metric it publishes**: `sglang:spec_accept_length` — "Mean acceptance length of speculative decoding (accepted drafts + bonus token per forward)"; `sglang:spec_accept_rate` — "Speculative acceptance rate (`accepted drafts / proposed drafts` in batch)"; `sglang:spec_cap_length` — "Mean DSpark confidence-scheduled verify window per verify step, incl the bonus slot (0 when no cap is scheduled)"; `sglang:spec_block_accept_length` — "Mean uncapped full-block accept length per verify step"; `sglang:spec_num_steps` — "Currently active speculative_num_steps"; `sglang:spec_num_draft_tokens` — "Currently active speculative_num_draft_tokens (decouples from steps under topk>1)". All are gauges. `/server_info` exposes `speculative_num_steps` and `avg_spec_accept_length`.
- **Sources**: https://docs.sglang.io/docs/advanced_features/adaptive_speculative_decoding · https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/observability/metrics_collector.py · https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/speculative/spec_info.py

### HuggingFace Text Generation Inference

- **What it does differently**: TGI models depth as the count of **speculated input tokens**, not as a chain of forward draft steps. The single knob is `--speculate <N>`, documented in the launcher's own clap help as "The number of input_ids to speculate on — If using a medusa model, the heads will be picked up automatically; Other wise, it will use n-gram speculation which is relatively free in terms of compute, but the speedup heavily depends on the task." Method selection is by checkpoint, not by flag: "In order to use medusa models in TGI, simply point to a medusa enabled model, and everything will load automatically."
- **Approach**: two methods, no feedback loop. Medusa is "a simple method to create many tokens in a single pass using fine-tuned LM heads in addition to your existing models" (arXiv 2401.10774). N-gram "works by trying to find matching tokens in the previous sequence, and use those as speculation for generating new tokens" — the docs' own example is `np.mean` reappearing in a sequence. Depth is static for the process lifetime; the user is told to set it and accept the consequence: n-gram "works best for code, or highly repetitive text. This might not be beneficial, if the speculation misses too much."
- **Key tradeoff**: TGI's conceptual framing names the failure mode directly — "So you are making *more* computations on your LLM, but if you are correct you produce 1, 2, 3 etc.. tokens on a single LLM pass. Since LLMs are usually memory bound (and not compute bound), provided your guesses are correct enough, this is a 2-3x faster inference." The qualifying clause "provided your guesses are correct enough" is the trade, and TGI leaves the judgement to the operator rather than encoding it as a threshold. Its n-gram path is explicitly cheaper per draft ("relatively free in terms of compute") but its payoff is task-dependent.
- **What it got right that we have not**: TGI publishes **speculated tokens** (`tgi_request_skipped_tokens`) and no acceptance rate at all — and still ships speculation as a production feature. **(inference)** That is the strongest available evidence that acceptance rate is not a universal non-regression metric: a widely deployed serving engine treats speculated-token volume as the observable, and lets throughput be the objective. Its metric list is otherwise entirely latency/throughput/queue telemetry (`tgi_request_mean_time_per_token_duration`, `tgi_batch_forward_duration`, `tgi_queue_size`, `tgi_request_duration`), which is consistent with optimization being aimed at the latency numbers, not the speculation efficiency ratio.
- **Metric it publishes**: on the `/metrics` Prometheus endpoint, exactly one speculation metric — `tgi_request_skipped_tokens`, described "Speculated tokens per request", type Histogram, unit Count. There is no `tgi_*accept*` metric, no acceptance-length metric, and no per-position breakdown anywhere in the exported list.
- **Sources**: https://huggingface.co/docs/text-generation-inference/main/en/reference/metrics · https://github.com/huggingface/text-generation-inference/blob/main/launcher/src/main.rs · https://huggingface.co/docs/text-generation-inference/main/en/conceptual/speculation

## 3. Cross-cutting

- **No engine in this set gates depth on a drafter-probability floor.** vLLM's depth is an integer config value (plus a batch-size schedule); TRT-LLM's is `max_draft_len` plus tree width; SGLang's is an EMA-driven tier; TGI's is `--speculate N`. `--spec-min-p` has no direct analogue in any of the four. The nearest published relatives are TRT-LLM's `relaxed_topk`/`relaxed_delta` partial-acceptance rule for thinking phases (https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/features/speculative-decoding.md) and vLLM's opt-in, method-restricted `enable_adaptive_verification` (https://github.com/vllm-project/vllm/blob/main/vllm/config/speculative.py).
- **They share a metric definition, and it is accept *counts*, not a rate.** vLLM publishes `vllm:spec_decode_num_accepted_tokens` and `vllm:spec_decode_num_draft_tokens` as counters and documents the rate as a PromQL division the operator performs; SGLang publishes `sglang:spec_accept_rate` with the definition written out as "`accepted drafts / proposed drafts` in batch"; TRT-LLM computes `draft_acceptance_rate` as `num_accepted_draft_tokens / num_draft_tokens` per request before taking percentiles; TGI publishes only `tgi_request_skipped_tokens`. The shared quantity is **counts of accepted drafts per verify step**; the ratio is a derived view.
- **The primary published metric is acceptance LENGTH (tokens per forward), not acceptance rate.** vLLM logs "Mean acceptance length" and defines it as `1 + (num_accepted_tokens / num_drafts)` — "conventionally including bonus tokens". SGLang's headline gauge is `sglang:spec_accept_length`, "accepted drafts + bonus token per forward". TRT-LLM reports `acceptance_length` globally as `sum(output_tokens) / total_decoding_iterations` and in percentiles. All three treat length (equivalently tokens per window) as the number that multiplies throughput; the rate is the diagnostic. This matches the metric we already log as "tokens/window".
- **Three of four already make depth a function of batch size, and one makes it a function of acceptance.** vLLM: `num_speculative_tokens_per_batch_size`, entries `(range_start, range_end, num_speculative_tokens)`, inclusive ranges. TRT-LLM: `draft_len_schedule` mapping batch-size thresholds to draft lengths, e.g. `{100:4, 200:3, 300:2}`. SGLang: integer BS-slot keys `"1"`, `"8"`, `"32"`, `"64"`, `"128"` in the adaptive config, each with its own `candidate_steps` and hysteresis. Only SGLang additionally feeds measured accept length back into the choice, and its docs give the reason: "At high batch sizes, the cost of each wasted draft step is multiplied across all sequences in the batch, so the optimal step count is often lower than at low batch sizes."
- **Acceptance is treated as position-dependent in the two engines that instrument it, and the instrumentation is what tells them where to cut.** vLLM exposes a `position`-labelled counter `vllm:spec_decode_num_accepted_tokens_per_pos` ("Accepted tokens per draft position") with the per-position rate documented as `num_accepted_tokens_per_pos[$interval] / num_drafts[$interval]`, and it logs a `Per-position acceptance rate` vector. SGLang publishes `sglang:spec_cap_length` ("Mean DSpark confidence-scheduled verify window per verify step, incl the bonus slot") and `sglang:spec_block_accept_length` ("Mean uncapped full-block accept length per verify step") — a scheduled window versus an uncapped block, which is the same depth-versus-quality comparison our chain-depth-4 window makes. Our logs carry "drafts accepted N of M" and "avg T" but not a per-position acceptance vector **(inference)**.
- **Throughput is the stated objective in every source; acceptance is reported beside it.** TRT-LLM's `trtllm-bench` prints `request_throughput_req_s`, `system_output_throughput_tok_s`, `batch_full_output_throughput_tok_s` and `output_throughput_per_user_tok_s` in the same report as `[DAR]` and `[AL]`, and its docs scope the whole technique: "speed ups are only observable at low batch sizes." vLLM documents spec-decode metrics as "Mean acceptance length… Accepted throughput: %.2f tokens/s, Drafted throughput: %.2f tokens/s". SGLang's adaptive guide optimises step count, and states the failure mode of a fixed setting as wasted compute and under-speculation — never as an acceptance-rate floor. **(inference)** Across all four, no source states a minimum acceptance rate that must be defended; the regressions they guard against are throughput and latency.
