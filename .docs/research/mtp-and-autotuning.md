# MTP acceptance, draft depth, and auto-tuning of the acceptance tradeoff

Primary-source research for the Strata / MAGMA v2 decision on lowering the MTP draft probability floor
from 0.7 to 0.5 (measured effect on this engine: throughput +8–11%, acceptance rate 91% → 87%,
tokens banked per verify window 2.2 → 2.5, with acceptance rate protected by the six-metric non-regression law).

Scope: (a) how the model side designs and reports MTP acceptance — the published numbers and the depth
they were measured over; (b) how production stacks auto-tune draft depth or the acceptance tradeoff, and
what objective those auto-tuners optimise.

Two questions the research had to answer, stated up front:

- **(a) Is a falling acceptance *rate* with rising *tokens per window* a defect or the normal shape of the curve?**
  Every primary source found says it is the normal shape. Acceptance per position decays with depth by
  construction, and the systems that report both publish them side by side rather than trading one for the other
  ([vLLM adaptive-verification docs](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/adaptive_verification.md),
  [vLLM DSpark blog](https://vllm.ai/blog/2026-08-14-dspark-adaptive-verification),
  [ReDrafter paper Table 2](https://arxiv.org/html/2403.09919v5)).
- **(b) What objective do production auto-tuners maximise?** Every mechanism found in (b) optimises
  **throughput or latency** (or an explicit proxy for them: expected accepted tokens per unit step time,
  goodput, end-to-end runtime). Not one optimises acceptance rate as its objective; acceptance is used as a
  *control signal* or published as a *diagnostic*. Detail in the final section.

Measurement vocabulary, fixed once here so the rest of the document is unambiguous:

- **acceptance rate** = accepted draft tokens ÷ proposed draft tokens (vLLM's `draft_acceptance_rate`,
  [acceptance_metrics.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/acceptance_metrics.md)).
- **acceptance length** = tokens emitted per verification step, `1 + accepted/steps` (vLLM's
  `mean_acceptance_length`; this is Strata's "tokens banked per verify window").
- **depth / draft length** = K, the maximum number of chained draft tokens per verification
  (`max_draft_len`, `num_speculative_tokens`, `num_nextn_predict_layers`, `beam_length`,
  `speculative_num_draft_tokens` depending on the stack).

## 2. System sections

### 1) DeepSeek-V3 / V3.2 MTP

- **What it does differently**: DeepSeek keeps the full causal chain across prediction depths — each MTP module consumes the previous module's hidden state plus the embedding of the token shifted by exactly k positions — so depth-k prediction is a trained sequential objective rather than k independent heads ([report §2.2](https://arxiv.org/html/2412.19437v2#S2.SS2)); the released 685B checkpoint is 671B main weights plus a 14B MTP module ([DeepSeek-V3 README](https://raw.githubusercontent.com/deepseek-ai/DeepSeek-V3/main/README.md)).
- **Approach**: Each depth carries its own cross-entropy loss, summed into one auxiliary training objective, with the embedding layer and output head shared between the main model and the MTP modules; at inference the released checkpoint exposes one module, and prediction of the next two tokens is used for speculative decoding, where the second token's acceptance rate is 85–90% and the combined speedup is 1.8× TPS ([report §2.2](https://arxiv.org/abs/2412.19437), quoted in the same terms by a technical walkthrough of that section at [juejin.cn](https://juejin.cn/post/7491199420693774363)).
- **Key tradeoff**: Acceptance is workload-bound, not a model constant — the same checkpoint measures ~83% at k=1 on ShareGPT chat data ([ROCm/ATOM #609](https://api.github.com/repos/ROCm/ATOM/issues/609)) against the paper's 85–90%, and a serving bug dropped it to 14.93% at k=1 (acceptance length 1.15) without changing any model weights ([vLLM #33497](https://api.github.com/repos/vllm-project/vllm/issues/33497)); TensorRT-LLM's own field guide says a real dataset is required for min-latency MTP benchmarking "since the MTP accept rate is affected by the dataset" ([best-practice doc](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/Best_perf_practice_on_DeepSeek-R1_in_TensorRT-LLM.md)).
- **What it got right that we have not**: It reports acceptance **at a stated depth, on a stated workload**, and it treats acceptance as a knob with a price — the relaxed-acceptance path explicitly buys acceptance (and therefore speed) by widening the verification candidate set to top-10 with `relaxed_delta 0.6`, and reports the accuracy cost alongside the 2.16× → 2.33× latency gain ([TRT-LLM MTP blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog02_DeepSeek_R1_MTP_Implementation_and_Optimization.md)).
- **Metric it publishes**: the acceptance rate of the second predicted token (85–90%), the TPS speedup (1.8×), the MTP module parameter count (14B), and in TensorRT-LLM the min-latency speedup per `num_nextn_predict_layers` setting (2.16× at nextn=3 vs nextn=0 baseline, 2.33× with relaxed acceptance, on 8×B200 with DeepSeek-R1-FP4, batch 1, ISL/OSL 1K/2K).
- **Sources**: [DeepSeek-V3 Technical Report §2.2](https://arxiv.org/abs/2412.19437) · [report HTML anchor](https://arxiv.org/html/2412.19437v2#S2.SS2) · [DeepSeek-V3 repo README](https://raw.githubusercontent.com/deepseek-ai/DeepSeek-V3/main/README.md) · [TensorRT-LLM MTP blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog02_DeepSeek_R1_MTP_Implementation_and_Optimization.md) · [TRT-LLM speculative-decoding docs](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/features/speculative-decoding.md) · [vLLM issue #33497](https://api.github.com/repos/vllm-project/vllm/issues/33497) · [ROCm/ATOM issue #609](https://api.github.com/repos/ROCm/ATOM/issues/609) · [nebius MTP-DeepSeek-V3-0324](https://huggingface.co/nebius/MTP-DeepSeek-V3-0324)

### 2) Qwen3-Next and Qwen3.8-Flash-Next style MTP heads

- **What it does differently**: Qwen's MTP module is trained with **multiple steps under inference-consistent conditions** — the announced purpose is to keep the acceptance rate high in real scenarios by removing the train/inference mismatch that makes later draft positions collapse ([Qwen3-Next blog](https://www.alibabacloud.com/blog/602580), [Qwen3.8-Flash-Next blog](https://www.alibabacloud.com/blog/qwen3-8-flash-next-a-new-architecture-towards-ultimate-cost-efficiency_603501)).
- **Approach**: The head is one prediction layer that takes the verifier's hidden states plus ground-truth token embeddings, normalises and concatenates them, projects back to the model dimension and passes a decoder layer; only the MTP layers are trainable while `embed_tokens` and `lm_head` stay frozen and shared, and per-depth losses are weighted with exponential decay (`beta=0.6` → weights [0.51, 0.31, 0.18] for 3 steps) so the first speculative token dominates the gradient ([vLLM Speculators MTP guide](https://raw.githubusercontent.com/vllm-project/speculators/main/docs/user_guide/algorithms/mtp.md)); the same guide records the fine-tuning recipe as Tencent's FastMTP ([arXiv 2509.18362](https://arxiv.org/html/2509.18362v1)).
- **Key tradeoff**: The published per-depth decay is steep and is the whole reason training must be multi-step: reusing one vanilla head recursively gives 70% / 11% / 2% acceptance at depths 1 / 2 / 3, and multi-step fine-tuning lifts that to 81% / 56% / 36% — a 3-token chain is only viable because positions 2 and 3 were trained ([FastMTP §1, §3](https://arxiv.org/html/2509.18362v1)); the cost side is visible in TensorRT-LLM's Qwen3.8-Flash-Next numbers, where MTP3 changes GSM8K from 95.72 (BF16, no MTP) to 95.11 ([TRT-LLM Qwen3.8-Flash-Next guide](https://nvidia.github.io/TensorRT-LLM/deployment-guide/deployment-guide-for-qwen3.8-flash-next-on-trtllm.html)).
- **What it got right that we have not**: It ships the depth that its head was trained for, states the supported ceiling (the recurrent MTP module supports `max_draft_len` up to 3, and the guide requires the draft length be configured identically on every rank), and warns in the deployment guide that acceptance "depends on the prompt distribution, sampling parameters, checkpoint, and batch shape; a rate measured on one workload is not a model constant" ([TRT-LLM Qwen3.8-Flash-Next guide](https://nvidia.github.io/TensorRT-LLM/deployment-guide/deployment-guide-for-qwen3.8-flash-next-on-trtllm.html)).
- **Metric it publishes**: per-depth acceptance rate and speedup in the FastMTP line (70/11/2% → 81/56/36%, 2.03× average speedup vs 1.21× for vanilla reuse, on an A10 24GB with MiMo-7B-RL), plus served-depth recipes: SGLang `--speculative-algo NEXTN --speculative-num-steps 3 --speculative-num-draft-tokens 4` and vLLM `{"method":"qwen3_next_mtp","num_speculative_tokens":2}` ([Qwen3-Next blog](https://www.alibabacloud.com/blog/602580)).
- **Sources**: [Qwen3-Next blog](https://www.alibabacloud.com/blog/602580) · [Qwen3.8-Flash-Next blog](https://www.alibabacloud.com/blog/qwen3-8-flash-next-a-new-architecture-towards-ultimate-cost-efficiency_603501) · [TRT-LLM Qwen3.8-Flash-Next deployment guide](https://nvidia.github.io/TensorRT-LLM/deployment-guide/deployment-guide-for-qwen3.8-flash-next-on-trtllm.html) · [vLLM Speculators MTP guide](https://raw.githubusercontent.com/vllm-project/speculators/main/docs/user_guide/algorithms/mtp.md) · [FastMTP (Tencent)](https://arxiv.org/html/2509.18362v1)

### 3) Apple ReDrafter

- **What it does differently**: The draft head is a small RNN conditioned on the target model's last hidden state and on the embedding of the previously drafted token, so the head is recurrent across draft positions while its parameters stay constant no matter how many tokens it is trained to predict; beam search over the head produces candidates, and a dynamic tree attention mask de-duplicates shared prefixes before verification ([paper §3.1–3.3](https://arxiv.org/html/2403.09919v5)).
- **Approach**: Training is knowledge distillation from the target with the target frozen — the objective is `min KL(p_llm(y_1:T) || p_draft(y_1:T))` over the T-token prediction range, backpropagating only through the draft head ([paper §3.5](https://arxiv.org/html/2403.09919v5)); the reference training run takes about 1.5 hours on 8×H100 with the ShareGPT dataset ([repo README](https://raw.githubusercontent.com/apple/ml-recurrent-drafter/main/README.md)).
- **Key tradeoff**: Depth is cheap to raise but verification is not — with beam length fixed at 4, raising beam width from 1 to 3 on M2 Ultra raises tokens/step from 2.15 to 2.44 while speedup moves 1.43× → 1.52×, and beam width 4 keeps tokens/step at 2.44 while speedup **falls to 0.75×**; on M1 Max the best speedup is at beam width 1, and the paper attributes the difference to the verification FLOPs the weaker GPU cannot absorb ([Table 2 and §4.2](https://arxiv.org/html/2403.09919v5)).
- **What it got right that we have not**: It publishes tokens-per-step and speedup as a **paired** result across a sweep, and it reports the throughput/latency split explicitly (per-request tokens/s vs tokens/s × batch size) so that "more accepted tokens" can never be mistaken for "faster" ([Table 3](https://arxiv.org/html/2403.09919v5)).
- **Metric it publishes**: speedup and tokens/step (MT-Bench, Vicuna 7B/13B/33B, H100: 2.80×/4.20, 2.80×/4.21, 2.61×/3.87), the MLX beam-width sweep with TPS (M1 Max and M2 Ultra), and the beam-width × batch-size grid of TPS and TPS×BSZ on H100.
- **Sources**: [ReDrafter paper (arXiv 2403.09919)](https://arxiv.org/abs/2403.09919) · [full HTML incl. Tables 1–3](https://arxiv.org/html/2403.09919v5) · [apple/ml-recurrent-drafter README](https://raw.githubusercontent.com/apple/ml-recurrent-drafter/main/README.md)

### 4) Prompt-lookup decoding (NVIDIA TensorRT-LLM NGram and vLLM n-gram/suffix)

- **What it does differently**: There is no trained drafter at all — draft tokens are copied from a match of the last k tokens anywhere in the prompt plus previously generated text, so depth costs nothing to train and nothing to keep in memory ([PLD repo](https://raw.githubusercontent.com/apoorvumang/prompt-lookup-decoding/main/README.md)); TensorRT-LLM keeps a (key, value) n-gram pool with `is_public_pool` (one pool for all requests), `is_keep_all`, `is_use_oldest`, and looks up the last k tokens to propose up to v draft tokens ([NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md)).
- **Approach**: Depth is chosen by configuration and by the *batch shape*: TensorRT-LLM's measurements show `k=3, v=5` best at batch 1 and 4, but `k=5, v=3` best at batch 32 "since the verification batch size is smaller and the overhead is less", and the shipped policy is a batch-aware heuristic behind `spec_decode_algo=AUTO` that keeps iteration overhead under 15% while delivering double-digit end-to-end speedups ([NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md)); vLLM exposes the same knobs as `num_speculative_tokens`, `prompt_lookup_min`, `prompt_lookup_max` ([vLLM n_gram.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/n_gram.md), [README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md)).
- **Key tradeoff**: Accepted length is a property of the workload, not of the configuration — generic chat gives ~1.3–1.4 accepted length while a translation workload reaches 4.73 at `k=5, v=23`, and the depth that pays depends on how much verification the batch can absorb ([NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md)); vLLM's suffix variant solves the same problem by speculating a dynamic number of tokens per request per step, which is why its `num_speculative_tokens` is documented as a *maximum* to be set high (16 or 32) rather than as a target depth ([suffix.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/suffix.md)).
- **What it got right that we have not**: It adapts the drafter to load — the (k, v) pair is a function of batch size and the enablement heuristic is written as a policy rather than a constant — and it reports accepted length split by workload class (chat vs translation) instead of a single blended figure ([NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md)).
- **Metric it publishes**: accepted length (AL) per dataset and per (k, v), end-to-end runtime speedup percentages, the AL distribution over requests, and for the original PLD the speedup on summarization/context-QA (~2.4×) and MT-Bench; vLLM's suffix path publishes the adaptive-depth controls `suffix_decoding_max_tree_depth` (24), `suffix_decoding_max_spec_factor` (1.0) and `suffix_decoding_min_token_prob` (0.1).
- **Sources**: [TensorRT-LLM NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md) · [TRT-LLM speculative-decoding docs](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/features/speculative-decoding.md) · [vLLM n-gram](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/n_gram.md) · [vLLM suffix decoding](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/suffix.md) · [original PLD repo](https://raw.githubusercontent.com/apoorvumang/prompt-lookup-decoding/main/README.md)

### 5) Auto-tuning and benchmarking practice for draft depth

- **What it does differently**: Instead of choosing K once, the production stacks derive K from a measured cost model — vLLM's adaptive verification profiles step cost at startup across CUDA-graph shapes and spends a token budget where survival probability is highest, and SGLang keeps independent accept-length EMA trackers per batch-size tier and switches tiers only after hysteresis gates pass ([adaptive_verification.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/adaptive_verification.md), [SGLang adaptive guide](https://raw.githubusercontent.com/bojieli/ai-infra-book/b069b6971faf6c4701b57a8b025462b9f2694b8f/references/framework-history/2026-09-08/speculative-execution/sglang-adaptive-guide.mdx)).
- **Approach**: `trtllm-bench` takes depth through the `--config` YAML (`speculative_config.num_nextn_predict_layers`, `max_draft_len`, `decoding_type`) for both throughput and latency subcommands, so a depth sweep is a loop over YAMLs rather than a flag ([trtllm-bench](https://nvidia.github.io/TensorRT-LLM/commands/trtllm-bench.html), [MTP blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog02_DeepSeek_R1_MTP_Implementation_and_Optimization.md)); vLLM's equivalent flag is `num_speculative_tokens` inside `--speculative-config`, and the tuning loop is documented in the same page that documents the adaptive alternatives ([README](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/README.md)).
- **Key tradeoff**: The measurements say a static K is wrong across concurrencies and that chasing acceptance costs throughput — the Adaptive K* proposal measured fixed K=5 at 75.2 tok/s with acceptance 1.88, adaptive K at 75.9 tok/s with acceptance 1.86, and an oracle K=12 at 60.8 tok/s with the *highest* acceptance of the three at 2.27, concluding "the cost model correctly penalizes over-speculation" ([PR #44336](https://api.github.com/repos/vllm-project/vllm/pulls/44336)); vLLM's own adaptive-verification page states the same crossover moves with load, so "no static `num_speculative_tokens` is right across concurrencies" ([adaptive_verification.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/adaptive_verification.md)).
- **What it got right that we have not**: They instrument first and tune second — vLLM exposes the exact two-sided view of the decision through `--per-request-spec-decode-metrics summary|detailed`, returning `mean_acceptance_length`, `draft_acceptance_rate`, `acceptance_histogram`, `num_spec_steps`, `num_accepted_draft_tokens`, `num_draft_tokens` and `num_spec_tokens` per request, reconciled against the `vllm:spec_decode_num_accepted_tokens_total` / `vllm:spec_decode_num_draft_tokens_total` / `vllm:spec_decode_num_drafts_total` counters ([acceptance_metrics.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/acceptance_metrics.md)); SGLang exposes the live tier and the acceptance signal through `/server_info` as `speculative_num_steps` and `avg_spec_accept_length` ([SGLang adaptive guide](https://raw.githubusercontent.com/bojieli/ai-infra-book/b069b6971faf6c4701b57a8b025462b9f2694b8f/references/framework-history/2026-09-08/speculative-execution/sglang-adaptive-guide.mdx)).
- **Metric it publishes**: per-request acceptance length and acceptance rate with the draft-length distribution; per-position survival probability (on DeepSeek-V4-Pro-0813, TP=8 on 8×B300, FP8 KV cache, the first of a 7-token block survives >70% of the time and the last <10%); aggregate throughput vs interactivity across concurrency 1–256; and the cost tables themselves (median of 5 profiled runs per shape, `VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN` default 8192) ([DSpark blog](https://vllm.ai/blog/2026-08-14-dspark-adaptive-verification), [adaptive_verification.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/adaptive_verification.md)).

## 3. Auto-tuning the acceptance tradeoff — every concrete mechanism found

Each entry names the exact flag, tool or policy, and states what it optimises. "Mixture" means the
mechanism's own control signal is an acceptance quantity but its stopping rule or budget is a cost/throughput
term.

### What the mechanisms agree on

1. **Depth is a load- and hardware-dependent quantity, not a model constant.** vLLM: "no static
   `num_speculative_tokens` is right across concurrencies"; TensorRT-LLM n-gram: best (k, v) moves from
   `k=3, v=5` at batch 1–4 to `k=5, v=3` at batch 32; ReDrafter: the optimal beam width is 3 on M2 Ultra
   and 1 on M1 Max for the same model ([adaptive_verification.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/adaptive_verification.md),
   [NGram blog](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog07_NGram_performance_Analysis_And_Auto_Enablement.md),
   [ReDrafter Table 2](https://arxiv.org/html/2403.09919v5)).
2. **Acceptance per position decays, and the decay is designed for, not discovered.** DeepSeek's head is
   trained sequentially so depth 2 exists at all ([report §2.2](https://arxiv.org/html/2412.19437v2#S2.SS2));
   FastMTP shows 70/11/2% collapsing to 81/56/36% once later positions are trained
   ([FastMTP](https://arxiv.org/html/2509.18362v1)); vLLM measures >70% → <10% across a 7-token block on
   DeepSeek-V4-Pro-0813 ([DSpark blog](https://vllm.ai/blog/2026-08-14-dspark-adaptive-verification)).
3. **No production auto-tuner found optimises acceptance rate as its objective.** The objectives are
   throughput/latency (1, 2, 4, 8, 9, 14), acceptance-at-fixed-budget (5), or acceptance-as-control-signal
   under a cost rule (3, 6, 10, 12, 13). The closest thing to "acceptance as the goal" is relaxed acceptance
   (3), and even there the stated payoff is latency with an acknowledged accuracy cost.

### Reading for the floor decision (inference)

Marked as inference, because it is this document's own reasoning over the sources above rather than a quoted claim:

- Strata's observation — floor 0.5, acceptance rate 91% → 87%, tokens banked per window 2.2 → 2.5,
  throughput +8–11% — is the same shape as ReDrafter's beam-width 1→3 result (tokens/step up, speedup up
  until verification saturates) and the same shape as the Adaptive K* failure mode in reverse (higher
  acceptance 2.27 with lower throughput 60.8 tok/s vs 1.88/75.2 tok/s). Acceptance rate and tokens per
  verify window are not two readings of one quantity when the floor moves: the floor changes *which
  proposals are admitted*, so the denominator changes too. (inference)
- On the sources found, acceptance rate is a diagnostic that no production stack protects as a
  non-regression metric; the metric that appears in every tuner's stopping rule is a throughput term
  (tok/s, tok/s/user, expected accepted tokens per unit step time, or goodput). (inference)
- The one measurement that would make the Strata decision comparable to these systems is the paired one:
  acceptance rate **and** tokens banked per verify window **and** ms per window **and** tok/s, per depth,
  on a fixed workload class — which vLLM's `--per-request-spec-decode-metrics detailed` shape
  (`per_step_drafted`, `per_step_accepted`) already models ([acceptance_metrics.md](https://raw.githubusercontent.com/vllm-project/vllm/main/docs/features/speculative_decoding/acceptance_metrics.md)).
  (inference)
