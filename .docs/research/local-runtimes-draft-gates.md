# Draft gates, depth control and the acceptance metric in four local runtimes

Research note for the Strata / MAGMA v2 decision on lowering `--spec-min-p` from 0.7 to 0.5.
Question asked of the sources: **how do local runtimes that expose a per-token draft gate choose it,
what do they log, do they adapt depth automatically, and which number do they treat as the objective?**

Method: primary sources only — repository files read at `master`/`main` on 2026-10-12 (raw file URLs are
cited per claim), plus the merged pull requests and the one upstream discussion where the floor value is
argued about. Where a project documents *why* a default was chosen, the text is quoted verbatim.
Everything I concluded myself is marked **(inference)**.

## 2. System sections

### llama.cpp

- **What it does differently** — It is the only one of the four whose floor is a first-class, per-token probability gate *and* is left disabled by default: `--spec-draft-p-min, --draft-p-min P  minimum speculative decoding probability (greedy) (default: 0.00)` (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md), with the struct field `float p_min = 0.0f; // minimum speculative decoding probability (greedy)` (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.h).
- **Approach** — Drafting walks the chain one token at a time and stops the chain the moment the top candidate's probability falls under the floor: `// only collect very high-confidence draft tokens` / `// (configurable via --spec-draft-p-min, set to 0.0 to disable early-stop)` / `if (cur_p->data[0].p < params.p_min) { drafting[seq_id] = false; … }` (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/speculative.cpp). The same flag means three different quantities depending on the implementation: top-1 sampler probability for draft-simple/MTP/DFlash, a draft **confidence head** for DSpark (`const float * conf = params.p_min > 0.0f ? llama_get_embeddings_nextn(ctx_dft) : nullptr;` … `if (conf && conf[idx * n_embd_dec] < params.p_min) break;`), and a softmax-derived `1.0f / sum` for DFlash2 (same file). Depth is separately bounded by `--spec-draft-n-max` (3) and flushed by `--spec-draft-n-min` (0): `if (dp.result->size() < (size_t) params.n_min) dp.result->clear();`.
- **Key tradeoff** — The default is the no-floor arm, and the project's own argument for turning the floor on is stated in acceptance terms: "if we increase the p-min from the default 0.0 to say 0.8, and bump the n-max to a higher number, say 16, we could get the best of both worlds" (https://github.com/ggml-org/llama.cpp/discussions/25198). The measured cost is exactly our 0.7→0.5 shape: "Avg Acceptance is lower for the Benchmark (58% vs 72 %) … But the Benchmark is actually ~15 % faster: because the Benchmark is allowed to guess up to 16 tokens, when it is right, it gets a huge head start. This is reflected in the Avg Draft Len (5.8 vs 3.8)." The counter-report on the same discussion, dated 2026-09-23 (three weeks before this note), finds the floor *losing* on novel reasoning text: "On this workload the 0.70 floor brought acceptance back to the n-max 3 level or above, yet it was the slowest arm on both files: 17 % and 21 % slower than n-max 3 with no floor."
- **What it got right that we have not** — (inference) It reports the chain's death position, not just a scalar: `#gen tokens` vs `#acc tokens` per implementation and `n_accepted_per_pos_total{position="N"}`, so a floor change is read as "where did the chain start dying" rather than as one aggregate ratio. It also keeps the two depth knobs (`n-max`, `n-min`) *separate* from the floor, so the floor can be raised without changing the maximum window — the opposite of our single `--spec-min-p` doing both jobs.
- **Metric it publishes** — Console `draft acceptance rate = 0.57576 (  171 accepted /   297 generated)` plus `statistics <type>: #calls(b,g,a) = …, #gen drafts = …, #acc drafts = …, #gen tokens = …, #acc tokens = …, dur(b,g,a) = … ms` (https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md); server-side Prometheus counters `llamacpp:spec_decode_num_draft_tokens_total`, `llamacpp:spec_decode_num_accepted_tokens_total`, `llamacpp:spec_decode_num_drafts_total`, `llamacpp:spec_decode_num_accepted_tokens_per_pos_total{position="N"}` and JSON fields `n_draft_tokens_total` / `n_draft_accepted_total` / `n_draft_verif_steps_total` / `n_accepted_per_pos_total`, merged in PR "server: Adding spec-decode counters to /metrics endpoint" on 2026-08-05 (https://github.com/ggml-org/llama.cpp/pull/26389).
- **Sources** — https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/speculative.md · https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.h · https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/speculative.cpp · https://github.com/ggml-org/llama.cpp/discussions/25198 · https://github.com/ggml-org/llama.cpp/pull/26389 · history check: `common/common.h` at tag b4000 (2024) has `int32_t n_draft = 5;` and **no** `p_min` field at all (https://raw.githubusercontent.com/ggml-org/llama.cpp/b4000/common/common.h), so the floor is a later addition whose default was chosen as "off".

### ExLlamaV2

- **What it does differently** — It runs a nonzero probability floor on the draft chain by default and never exposes it as a flag: `self.speculative_prob_threshold = 0.25` set in `ExLlamaV2StreamingGenerator.__init__` (https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/streaming.py). It is also the only project of the four that gives the throughput-side number its own name.
- **Approach** — Greedy drafting with an early break: `if prob < self.speculative_prob_threshold: self.draft_cache.current_seq_len -= 1; break` inside the `for k in range(self.num_speculative_tokens)` loop; verification then continues token-by-token, counting `accepted_draft_tokens` while `self.future_tokens[0, 0] == token[0, 0]` (https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/streaming.py). Depth defaults differ per generator: `num_speculative_tokens = 5` in the streaming constructor, `num_draft_tokens: int = 4` in `ExLlamaV2DynamicGenerator` (https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/dynamic.py). The dynamic generator's draft loop is `torch.argmax` on the draft logits with **no** probability test (same file) — (inference) so the floor survives only in the older streaming path.
- **Key tradeoff** — The n-gram path documents the depth/acceptance tension directly on its own knob, `speculative_ngram_threshold` (default 1) being incremented per predicted token, i.e. progressively raising the evidence bar as the chain gets longer (same file). For the draft-model path the trade is simply accepted: 0.25 is a low floor that keeps chains long, and the project publishes both the resulting length and the resulting ratio rather than a single verdict.
- **What it got right that we have not** — (inference) The naming. `get_sd_stats()` returns `efficiency = self.accepted_draft_tokens / self.total_tokens` **and** `accuracy = self.accepted_draft_tokens / self.total_draft_tokens` (https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/streaming.py) — `efficiency` is our "tokens/window"-style number, `accuracy` is our "acceptance rate". Their vocabulary lets both move in opposite directions without either being called a regression. Our six-metric law binds the `accuracy`-shaped number while the decision is justified by the `efficiency`-shaped one.
- **Metric it publishes** — `(efficiency, accuracy, total_tokens, total_draft_tokens, accepted_draft_tokens)` from `get_sd_stats()`, resettable with `reset_sd_stats()`; per-job `"accepted_draft_tokens"` / `"rejected_draft_tokens"` in the dynamic generator's result dict; the shipped example measures only end-to-end speed (`speed, -SD: … tokens/second` vs `speed, +SD: … tokens/second`) (https://raw.githubusercontent.com/turboderp-org/exllamav2/master/examples/inference_speculative.py).
- **Sources** — https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/streaming.py · https://raw.githubusercontent.com/turboderp-org/exllamav2/master/exllamav2/generator/dynamic.py · https://raw.githubusercontent.com/turboderp-org/exllamav2/master/examples/inference_speculative.py

### LMDeploy

- **What it does differently** — It has no confidence gate at all. The draft length is a fixed per-request integer set at launch: `--speculative-num-draft-tokens` **default 1**, "The number of speculative tokens to generate per step" (https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/cli/utils.py). The only runtime-shaped override is the DFlash block size: "Overrides `--speculative-num-draft-tokens` with `block_size - 1` proposed tokens and must not exceed the DFlash checkpoint block_size" (same file).
- **Approach** — A proposer/verifier split with standard rejection sampling: `RejectionSampler.forward` asserts "target logits must contain each draft position plus one bonus" and routes greedy requests to `forward_greedy` and stochastic ones to `forward(...)` with `bonus_token_ids` (https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/spec_decode/reject_sampler.py). Depth is decided once by config: `self.num_spec_tokens = specdecode_config.num_speculative_tokens` (https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/spec_decode/base.py). The documented way to buy acceptance back is not a floor but masking the draft with the grammar: "Speculative decoding (MTP) can be combined with structured output … This significantly improves the acceptance rate compared to running spec decoding without grammar masks" (https://raw.githubusercontent.com/InternLM/lmdeploy/main/docs/en/advance/spec_decoding.md).
- **Key tradeoff** — It reports the trade instead of taking a side. The counters comment in the metrics logger states the intended reading: "Acceptance rate and mean acceptance length are derived in PromQL from these raw counters. `rate(accepted_tokens) / rate(draft_tokens)`; `1 + rate(accepted_tokens) / rate(drafts)`" (https://github.com/InternLM/lmdeploy/pull/4625/files). With no floor, depth is a memory/verification-budget choice, and the docs note the feature is still "experimental" (https://raw.githubusercontent.com/InternLM/lmdeploy/main/docs/en/advance/spec_decoding.md).
- **What it got right that we have not** — (inference) It publishes **per-position** acceptance (`lmdeploy:spec_decode_per_position_accept_rate{position="N"}` and `num_accepted_tokens_per_pos_total`) *and* the aggregate, so raising the floor is evaluated at the position where it starts cutting. It also derives both aggregates from raw counters, which means the acceptance ratio and the mean acceptance length can never drift apart — one is not "the" number, both are re-derivable from `num_drafts` / `num_draft_tokens` / `num_accepted_tokens`. Our per-request log lines ("drafts accepted N of M", "tokens/window", "ms/window") already carry the raw material; what is missing is the published per-position series.
- **Metric it publishes** — `lmdeploy:spec_decode_mean_accept_rate` ("Mean speculative decoding acceptance rate. 1 means 100 percent accepted."), `lmdeploy:spec_decode_mean_accept_length` ("Mean speculative decoding acceptance length, including the bonus token."), the three counters plus `lmdeploy:spec_decode_num_accepted_tokens_per_pos_total{position}` and `lmdeploy:spec_decode_per_position_accept_rate{position}`; `SpeculativeDecodingStats.__repr__` prints `draft_acceptance_rate=…%, mean_acceptance_length=…, per_position_acceptance_rate=…` with the comment "conventionally, mean acceptance length includes the bonus token" (https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/metrics/stats.py; PR merged 2026-05-29, https://github.com/InternLM/lmdeploy/pull/4625).
- **Sources** — https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/cli/utils.py · https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/metrics/stats.py · https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/spec_decode/base.py · https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/spec_decode/reject_sampler.py · https://raw.githubusercontent.com/InternLM/lmdeploy/main/docs/en/advance/spec_decoding.md · https://github.com/InternLM/lmdeploy/pull/4625

### MLC-LLM

- **What it does differently** — It adapts the draft length automatically, but on **batch size**, not on drafter confidence, and it says so in a comment: "Right now we use the fixed table to select the draft length (only based on the batch size). We will follow up to adopt powerful draft length selection." — `num_running_rsentries < 10 → 4`, `< 20 → 3`, `< 30 → 2`, else `0` (no speculation), with `spec_draft_length` forced to 0 when `num_running_rsentries * (draft_length + 1) > max_num_sequence` (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/engine_actions/auto_spec_decode.cc).
- **Approach** — `EngineConfig.speculative_mode` defaults to `"disable"`; `spec_draft_length: int = 0` is documented as "Being 0 means to enable adaptive speculative mode, where the draft length will be automatically adjusted based on engine state", and `spec_tree_width: int = 1` sets tree width (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/python/mlc_llm/serve/config.py). The CLI exposes `--speculative-mode {disable,small_draft,eagle,medusa}` (default `disable`) and routes the rest through `--overrides "…;spec_draft_length=N;spec_tree_width=N"` (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/python/mlc_llm/cli/serve.py). The computed value lives on the engine state as `int spec_draft_length = 0;` with the comment "The length may change across time under the auto speculative decoding mode" (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/engine_state.h). No per-token probability floor exists in the config surface at all.
- **Key tradeoff** — It resolves the acceptance-vs-throughput tension by publishing the *cumulative* length and treating the per-position rate as a diagnostic: `accept_prob{step=i} = accept_count[i]/draft_count[i]`, `accept_rate{step=i} = accept_count[i]/accept_count[i-1]`, `accept_len{step=i} = Σ accept_prob` (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/metrics.cc). (inference) A drop in the per-position rate at step 3 while `accept_len` rises is exactly the pattern our 0.7→0.5 arm shows, and MLC-LLM's schema makes that pattern readable rather than contradictory.
- **What it got right that we have not** — (inference) Two things. First, the depth decision is *automatic and stated in code* — the pipeline never asks an operator to hand-tune a threshold against a metric law. Second, its metric update is position-indexed by construction: `SpecDecodeMetrics::Update(int draft_length, int accept_length)` increments `accept_count[j]` and `draft_count[j]` for every `j < accept_length`, which is the same shape as llama.cpp's and LMDeploy's per-position counters and is the one shape none of our three per-request log lines produce (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/metrics.h).
- **Metric it publishes** — `EngineMetrics.spec_decode` in the engine metrics JSON: raw `draft_count[]` / `accept_count[]` plus `accept_prob{step=i}`, `accept_rate{step=i}`, `accept_len{step=i}`; engine metrics also carry `draft_time_by_batch_size` and `verify_time_by_batch_size` as `mean{batch_size=N}` / `count{batch_size=N}` (https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/metrics.cc).
- **Sources** — https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/python/mlc_llm/serve/config.py · https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/engine_actions/auto_spec_decode.cc · https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/metrics.h · https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/metrics.cc · https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/cpp/serve/engine_state.h · https://raw.githubusercontent.com/mlc-ai/mlc-llm/main/python/mlc_llm/cli/serve.py

## 3. The probability floor, compared

Every floor/threshold found in these four projects that gates how far a draft chain extends, with its
default and what the project says about choosing it:

| system | flag / symbol | default | what the project says about choosing it |
|---|---|---|---|
| llama.cpp | `--spec-draft-p-min`, alias `--draft-p-min` (`common_params_speculative_draft::p_min`) | **0.00 — disabled** | Help text: "minimum speculative decoding probability (greedy) (default: 0.00)". Code comment: "only collect very high-confidence draft tokens (configurable via --spec-draft-p-min, set to 0.0 to disable early-stop)". The discussion's recommended value is 0.8 paired with `--spec-draft-n-max 16`, justified purely by the length/acceptance trade: acceptance 67.8 % → 55.7 %, avg draft length 3.71 → 5.20, TPS +20.4 %; a dissenting report at 0.70 on reasoning text found 17–21 % *slower* than no floor, and another commenter settled on 0.6 ("0.7 and 0.8 both performed worse. 0.6 really seems to be the ticket") |
| llama.cpp (DSpark only) | `--spec-draft-conf-min P` | **0 — disabled** | "`--spec-draft-conf-min P` truncates each drafted block at the first position whose predicted acceptance (from the draft's confidence head, if present) falls below `P` (default 0 = disabled)." — the same design decision as `p_min`, but gating on a *predicted acceptance* head instead of a token probability |
| llama.cpp (n-gram mod) | low-acceptance streak reset, `f_acc < 0.25` for `n_low >= 5` | **hard-coded 0.25 over 5 rounds** | Not a chain gate but the only adaptive use of an acceptance threshold in the file: "compute acceptance fraction if we have a recorded draft length … if (f_acc < 0.25) { sinfo.n_low++; if (sinfo.n_low >= 5) { … mod.reset(); } }" — acceptance is used as a *health signal that throws away state*, never as a reason to shorten the window |
| ExLlamaV2 | `speculative_prob_threshold` (member of `ExLlamaV2StreamingGenerator`) | **0.25 — on by default, not configurable** | No comment, no docs, no CLI flag; the only statement is the code itself: `if prob < self.speculative_prob_threshold: self.draft_cache.current_seq_len -= 1; break`. It is the lowest floor of any project here, and the only one left switched on (inference: consistent with a project that optimises tokens/second and reports ratio separately) |
| ExLlamaV2 (n-gram path) | `speculative_ngram_threshold` (start 1, incremented per predicted token) | **1, rising** | Depth-proportional evidence bar rather than a probability floor: the n-th predicted token must be supported by an n-higher occurrence count in the n-gram cache |
| LMDeploy | none in the speculative path | — | No probability gate exists; `--speculative-num-draft-tokens` default 1 is the depth. The nearest confidence threshold in the CLI is `--dllm-confidence-threshold` **default 0.85**, but its help text scopes it to diffusion-LLM unmasking ("The confidence threshold for dllm"), not to speculative decoding |
| MLC-LLM | none | — | `EngineConfig` / `--speculative-mode` / `--overrides` expose only `spec_draft_length` (0 = adaptive) and `spec_tree_width` (1); there is no confidence or probability floor to set |
| **Strata / MAGMA v2 (ours)** | `--spec-min-p` | **0.7 standing, 0.5 candidate** (task brief; no public URL) | Our own measurements: 0.5 raises single-stream decode 8–11 % and lowers "acceptance rate" 91 % → 87 %. No comparable project in this survey ships a floor that high as a default; the only floor above zero at all is ExLlamaV2's 0.25, and the highest value anyone argues for in public is llama.cpp's 0.8 — argued for on the explicit grounds that acceptance may fall while tokens/window and TPS rise |

**Reading (all inference).** The four projects split cleanly into two groups, and the split is not about
the value of the floor but about *which number is allowed to be called a regression*:

1. **Ratio-published group** (llama.cpp, LMDeploy, MLC-LLM, and ExLlamaV2's `accuracy`): the acceptance
   ratio is reported next to a length/counter quantity, both derived from the same raw counters, and no
   project states a numeric acceptance floor that a change may not cross. MLC-LLM's `accept_len` and
   LMDeploy's `mean_accept_length` are the headline; the ratio is the diagnostic that says where the
   chain dies.
2. **The one project that treats the ratio as the objective** does so only by *name*, not by policy:
   ExLlamaV2 calls it `accuracy` and calls the other number `efficiency`, and both are returned by the
   same function.

Two consequences for the 0.7 → 0.5 decision, stated as inference:

- The numeric floors are not transferable between projects because the gated quantity differs: our
  `--spec-min-p` gates *extending a verify window*, llama.cpp's `p_min` gates *adding the next draft
  token* on `cur_p->data[0].p` (top-1 sampler probability), ExLlamaV2's 0.25 gates the same thing on a
  greedy draft draw, and llama.cpp's DSpark variant gates on a confidence head that predicts acceptance
  rather than on a token probability. A 0.7 floor in one design is not a 0.7 floor in another.
- Every project that reports both numbers reports them per draft position, and every one of them derives
  both from raw counters (`#gen tokens` / `#acc tokens`, `num_draft_tokens` / `num_accepted_tokens` /
  `num_drafts`, `draft_count[]` / `accept_count[]`). None of them needs an operator to decide in advance
  which of the two is "the" metric — the artifacts answer that after the run. Our per-request lines
  ("drafts accepted N of M", "tokens/window", "ms/window") contain the same three raw quantities but are
  not aggregated per position, so the 0.5 arm's 87 % cannot currently be read as "the chain dies at
  position k more often" versus "the chain is longer and banks more per window".
