# Web digest: GPU clock governance and LLM inference (2026-11-09)

Question set: (1) pin-vs-range semantics of `-lgc`/`-lmc` on Blackwell/Ada, burst behavior; (2) cross-domain coupling; (3) memory-clock DVFS vs inference; (4) `clocks_event_reasons` 0x400; (5) production locked-clock practice (MLPerf, TensorRT, clouds); (6) GSP-RM clock-request latencies. Grades: A = official doc fetched verbatim; B = NVIDIA-forum/staff text fetched verbatim; C = community/search-level, unfetched or secondary.

## 1. `-lgc`/`-lmc` documented semantics: both are ranges; a pin is the degenerate range min=max

- [nvidia-smi manual](https://docs.nvidia.com/deploy/nvidia-smi/index.html) (A, fetched): `-lgc` takes a `<min,max>` pair that "defines the range of desired locked GPU clock speed in MHz" and produces the "**closest desired locked GPU clock speed**" — the driver negotiates to the value; it is not a per-microsecond guarantee. Single value = both min and max (= pin). "Supported on Volta+. Requires root." Two lock modes: mode 0 (default) "provides the highest possible frequency accuracies supported"; **mode 1 uses "close loop controllers to achieve frequency accuracies with improved perf per watt"** — the only documented quantization/feedback mechanism inside the lock path. `-lmc` mirrors this for memory (not supported on Hopper; `--lock-memory-clocks-deferred` exists instead — works on GB202). `-ac` (application clocks) is deprecated: "will be removed in a future CUDA release. Please use -lmc ... and -lgc", yet MLPerf still uses `-ac` (see 5).
- [NVML `nvmlDeviceSetGpuLockedClocks`](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceCommands.html) (A, search-level quote): "Set clocks that device will lock to, **running at either the specified minGpuClockMHz or maxGpuClockMHz, or somewhere in between**." Documented semantics are a band the DVFS engine owns; `nvidia-smi` docs state locks "supercede application clocks and takes effect regardless if an app is running."
- Boost within a range lock stays DVFS-owned: [Spheron throttling measurements](https://www.spheron.network/blog/sustained-load-gpu-throttling-we-measured-the-hidden-clock-t) (C) found range-locking more deterministic than floating but boost/thermal margins still govern; [cfregly/ai-performance-engineering appendix](https://github.com/cfregly/ai-performance-engineering/blob/main/docs/appendix.md) (C): "By default, GPUs use auto boost, which is usually optimal, but fixed clocks can avoid any transient downclocking"; memory-bound workloads "plateau well below max and can run at 80-90% without losing throughput." → **v4/v5 range policy = documented-legal boost delegation; v2 pin = documented-legal forced floor at ceiling.** Neither is flagged as unsupported on GeForce; the observed 2830-2955 MHz sustained decode under v2 pin (3135 requested) is consistent with "closest desired" semantics — the driver lands below the pin, not at it.
- Short-burst (1-15 ms) behavior: no public microbenchmark of burst clocks vs sustained under range locks. Nearest evidence (B, fetched): NVIDIA's njuffa in [ramp-down thread](https://forums.developer.nvidia.com/t/very-fast-ramp-down-from-high-to-low-clock-speeds-leading-to-increased-time-repeatedly-ramping-up/165974): "When I run with very short kernels, sufficiently spaced apart, my GPU seems to operate at **about half the highest available clock rate**", and "the automatic GPU power management has **no user-settable knobs**." → gap named: burst-clock telemetry at kHz rate is the only way to close this; nobody has published it.
- Hard caps override everything: Robert Crovella (staff, B, fetched [RTX 5090 headless thread](https://forums.developer.nvidia.com/t/how-to-force-lock-sm-and-memory-clocks-on-rtx-5090-headless-linux/348794)): "Consumer GPUs often do not give the same level of control... it's not possible to make any sort of clock adjustments on any NVIDIA GPU that would **violate the GPU's attempt to protect itself or stay within its power budget. The GPU clock control algorithms will take over**." Same thread: a 5090 user reports `-lgc`/`-lmc` "failed or did not lock the clocks as expected" headless even with persistenced running.
- Documented pin failure on Blackwell datacenter: NVIDIA MLPerf v5.0 [closed/NVIDIA/scripts/set_clocks.sh](https://github.com/mlcommons/inference_results_v5.0/blob/main/closed/NVIDIA/scripts/set_clocks.sh) (A, fetched verbatim): `# nvidia-smi -lgc 1965" ### This way doesn't work on GB200-NVL. https://nvbugspro.nvidia.com/bug/5069775` — NVIDIA fell back to `-rgc` + `-ac $MAX_MEM_CLOCK,$MAX_GPU_CLOCK` (the deprecated path) to pin max clocks. Same script replicated across HPE/Dell/Lenovo/Google/Fujitsu/ASUSTeK/Lambda submissions. → **on Blackwell, `-lgc` pinning has a real, NVIDIA-worked-around failure class; `-ac` max-clock pairing remains the MLPerf-validated fallback.**

## 2. Cross-domain coupling (our MEM-pin → SM 2004 @ 61 W)

- No official document describes one domain's pin degrading the other. What exists:
  - Power-budget precedence (Crovella quote above, B): any combined SM+MEM request is re-arbitrated against the power/perf policy "regardless of the GPU or the commands or tools used."
  - Application clocks are natively a (MEM, graphics) pair (`-ac mem,gfx`; P2000 example in the ramp-down thread: only "MEM 3504, SM 1721" pairs accepted, B) — the RM models the two domains jointly, not independently.
  - Ada field evidence that user clock policy rewrites attribution: [0x400 thread](https://forums.developer.nvidia.com/t/nvidia-report-false-thermal-protection-from-nvapi-gpu-getperfdecreaseinfo/388207) (B, fetched): "a clock lock (`nvidia-smi -lgc`) or a flattened V/F curve makes the API report `API_TRIGGERED` **all the time**" — pins are visible to the perf manager as a first-class limiter state.
  - Below-OS governance exists on Blackwell-family: [DGX Spark GB10 721 MHz thread](https://forums.developer.nvidia.com/t/dgx-spark-gb10-gpu-clock-pinned-at-721-mhz-under-full-load-no-throttling-not-liftable-via-nvidia-smi/376039) (B, fetched): SM pinned at 721/3003 MHz, 96% util, "Clock Event Reasons: all Not Active", power limits N/A, `-lgc` no effect; NVIDIA staff confirmed "a real clock constraint, not a telemetry artifact"; fixed only by AC unplug 30-60 s ([EC-latch writeup](https://github.com/ShiningMeUp/dgx-spark-gpu-underclock-fix), C: "GB10 的 DVFS 决策在 EC/固件层完成，位于 OS 之下" — DVFS decisions live in EC/firmware below the OS and can latch; one reporter's case survived 8 h unplugged).
- Verdict for our case (C-hypothesis, flagged): the MEM-only pin holding SM at 2004 @ 61 W matches no documented `-lmc` behavior; the two documented mechanisms it resembles are (a) joint power/perf arbitration and (b) a below-OS perf-policy latch that `nvidia-smi` cannot see or clear. 61 W at 2004 MHz is 10x below the 575 W cap, so power-cap precedence does NOT explain it — an EC/firmware-side state is the better fit. Probe: `-rgc` + `-rmc` + full power drain vs re-pin, with `clocks_event_reasons` and board-limit telemetry at 2 ms sampling (same method as the 0x400 thread).

## 3. Memory-clock DVFS and inference: decode is bandwidth-bound; the 7001 idle tier is normal

- RTX 5090 memory states: stock 14001 MHz = 28 Gbps GDDR7; idle half-rate 7001 MHz ([nvidia-tuning-toolkit](https://github.com/daimonionnn/nvidia-tuning-toolkit), C, tested on MSI 5090 / driver 580.126.09; [GeForce forums idle-mem thread](https://www.nvidia.com/en-us/geforce/forums/game-ready-drivers/13/579571/), C). → "with no engine, mem clock drops to 7001" is the standard two-tier P-state model, not an anomaly; every engine start re-raises it.
- Measured power/clock sensitivity of decode vs prefill (community, C): [3090 power sweep](https://openclawdc.com/blog/undervolt-gpu-24-7-local-agent): 250 W → 31.7 tok/s vs 350 W → 32.0 tok/s (1%), 200 W → 20.6 tok/s (knee collapse); [r/LocalLLaMA 3090 tuning](https://www.reddit.com/r/LocalLLaMA/comments/1egvoqj/rtx3090_power_tuning_results_on_llm_vision_tts): 250-300 W ≈ full speed; [4090 phase power](https://gigagpu.com/rtx-4090-24gb-llama-3-8b-benchmark): ~400 W prefill (compute-bound) vs ~360 W batch decode. Prefill punishes caps; VRAM-resident decode barely notices SM/power cuts because it is DRAM-channel-bound.
- **Gap named:** no public A/B of mem-clock 7001 vs 14001 on GDDR7/50-series decode exists (searched; nothing). Extrapolation chain only: decode tok/s ceiling ∝ effective bandwidth, so a 2x mem downclock should halve the VRAM-resident decode ceiling — consistent with why the v2 best-numbers regime pinned MEM 14001 during processing. For our hybrid MoE lane (weights streamed over PCIe), mem clock does not touch the transfer leg; it moves only the VRAM-resident portion + L2 residency — second-order there.
- 14001 = "14001 MHz" is nvidia-smi's data-rate convention (28 Gbps / 2); community OC headroom on 5090 is normally +1000-3000 MHz effective via offsets (LACT/nvidia-settings Coolbits path — [nvidia-tuning-toolkit notes LACT cannot do clock offsets via CLI](https://github.com/daimonionnn/nvidia-tuning-toolkit), C), while `-lmc` pins operate inside the stock supported set.

## 4. `clocks_event_reasons` 0x400 = "Reliability" — a V/F-margin limiter, not an event; do not fight it

- NVML docs (A, fetched [NvmlClocksEventReasons](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlClocksEventReasons.html)): `nvmlClocksEventReasonReliability` — "**The reliability policy is currently limiting the GPU clocks**"; sibling `nvmlClocksEventReasonBoardLimit` — "The board limit (operating) policy is currently limiting the GPU clocks." Hex values are not printed on the doc page; the nvidia-smi manual adds the two newer flags 'Board Limit' and 'Reliability Violation' (A via search).
- Field-measured behavior on Ada (B, fetched, [0x400 thread](https://forums.developer.nvidia.com/t/nvidia-report-false-thermal-protection-from-nvapi-gpu-getperfdecreaseinfo/388207), water-cooled RTX 4090, driver 621.14, 2026): NVML reasons = `0x0000000000000400 Reliability (nvidia-smi)` in 100% of 5152 samples at ~2 ms cadence while graphics clock held a constant 2820 MHz; every thermal/power slowdown bit and counter = 0; core 36-53 C. NVAPI `GetPerfDecreaseInfo` misread the same state as THERMAL_PROTECTION in 10-30 ms bursts (median 15.5 ms, ~3.75 bursts/s). Rate scales with proximity to the top of the stock V/F curve: 2820 MHz @ 1.05 V → 6.2% of samples; -400 MHz offset → 0.8%; V/F flattened at 950 mV → 0.4%. Locking clocks or flattening the curve switches NVAPI to `API_TRIGGERED` permanently.
- Reading for GB202 serving: 0x400 active while sustaining 2830-2955 MHz decode = the driver's reliability policy is holding a margin below the absolute top V/F operating point; it is a standing limiter, not a throttle event (clock does not drop in the Ada measurements). Fighting it via hard pins converts the attribution to user-defined-clock states and bypasses the V/F guard the silicon was binned with; the Ada data shows the guard's cost is a few percent of frequency, not burst-level throttling. Undocumented on GB202 specifically — same-family inference, flagged C.

## 5. Production practice: MLPerf locks to MAX clocks (via `-ac`), TensorRT locks for determinism, vLLM/SGLang do not require it

- MLPerf closed-division NVIDIA practice (A, fetched verbatim, [set_clocks.sh](https://github.com/mlcommons/inference_results_v5.0/blob/main/closed/NVIDIA/scripts/set_clocks.sh)): read max clocks from `nvidia-smi -q -d CLOCK`, then `sudo nvidia-smi -rgc; sudo nvidia-smi -ac $MAX_MEM_CLOCK,$MAX_GPU_CLOCK` — i.e. **pin both domains at their max**, using the deprecated-but-working `-ac` pair because `-lgc` broke on GB200-NVL (nvbug 5069775). Historical verbatim: Inspur T4x8 v0.7 [README](https://github.com/mlcommons/inference_results_v0.7/blob/main/closed/Inspur/README.md): "please lock the clock at the max frequency by `sudo nvidia-smi -lgc 1590,1590`"; Jetson submissions use MAXN mode + max locks ([inference_results_v3.1 NVIDIA Jetson README](https://github.com/mlcommons/inference_results_v3.1/blob/main/closed/NVIDIA/README_Jetson.md), C). **Capability truth, verified by grep:** the frequently quoted MLPerf rule "clocks must be locked to the base frequency" is NOT present verbatim in the current surfaces checked — [submission_rules.adoc](https://github.com/mlcommons/policies/blob/master/submission_rules.adoc), [inference_rules.adoc](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc), [submission guide](https://docs.mlcommons.org/inference/submission), [power doc](https://docs.mlcommons.org/inference/power), [system-info](https://docs.mlcommons.org/inference/system-info) (all fetched, none contain a clock-locking requirement; `accelerator_frequency` is an auto-detected inventory field). The lock practice lives in submission scripts, not a retrievable rule sentence. Search-level hits asserting the phrase (e.g. first-pass search summaries) could not be confirmed at source — treat the "locked to base" wording as unverified folklore.
- TensorRT performance guide (A, fetched [benchmarking.html](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)): "you can lock the clock at a specific frequency by calling the `sudo nvidia-smi -lgc <freq>` command"; unlock with `-rgc`; enumerate with `-q -d SUPPORTED_CLOCKS`. Why: "Running TensorRT workloads with floating clocks or with throttling taking place can lead to **more non-determinism in tactic selections**"; locked clocks give "deterministic tactic selections and consistent performance measurements" at the cost that "average performance with locked clocks **will not be as good as when the clock is floating**"; "no definite recommendation" between the two. Monitor with `nvidia-smi dmon -s pcu` during runs. TRT-LLM backend README ships `sudo nvidia-smi -lgc 1410,1410` ([tensorrtllm_backend](https://github.com/triton-inference-server/tensorrtllm_backend/blob/main/README.md), A-code).
- [SetStablePowerState blog](https://developer.nvidia.com/blog/advanced-api-performance-setstablepowerstate) (A, fetched): DX12 stable-power-state "**does not lock the memory clock**"; "Don't rely solely on the SetStablePowerState function when profiling... makes the results less comparable than when the appropriate clocks are **locked with nvidia-smi**" (`--lock-gpu-clocks` + `--lock-memory-clocks`, reset after). → NVIDIA's own benchmark doctrine = lock BOTH domains.
- vLLM/SGLang: no clock-lock requirement in vLLM docs or `benchmarks/README.md` (grep, A-code) or SGLang (code search, empty). Bench methodology papers use it anyway ([arXiv:2505.11329](https://arxiv.org/html/2505.11329): `nvidia-smi --lock-gpu-clocks=tdp,tdp`, C). Persistence-mode doctrine (A, manual): `-pm` is immediate, "does not persist across reboots"; `-lgc` likewise does not survive reboot ([gb10-clock-cap](https://github.com/agjs/gb10-clock-cap/blob/main/AGENTS.md), C: "nvidia-smi -lgc does not survive reboot and persistence mode does not preserve it") — which is exactly the niche a systemd governor fills; no vendor ships one.
- Cloud practice: no evidence of pinned clocks in shared cloud offerings; OpenReview paper notes B200 servers could not be locked because it needs root (C, search-level).

## 6. GSP-RM: clock requests are RPCs (function 76, GSP_RM_CONTROL); no documented 12 ms quantization

- [GSP README](https://download.nvidia.com/XFree86/Linux-x86_64/565.57.01/README/gsp.html) (A, fetched): GSP "offload[s] GPU initialization and management tasks"; NVIDIA claims "lower latency access to GPU hardware internals"; default on Turing+; `NVreg_EnableGpuFirmware=0` disables on supported drivers. No latency numbers, no clock-path detail documented.
- Clock/perf queries and controls traverse `GSP_RM_CONTROL` RPCs: [open-gpu-kernel-modules #1239](https://github.com/NVIDIA/open-gpu-kernel-modules/issues/1239) (A-issue, fetched; GB203, driver 610.43.02): a read-only `nvidia-smi -q -d SUPPORTED_CLOCKS` can page-fault the GSP task (Xid 120), then every clock RPC times out with `Xid 119: Timeout after **6 s** of waiting for RPC response... GSP_RM_CONTROL`, heartbeat timeout 5200 ms, host unrecoverable until power cycle. → documents (a) clock controls are GSP RPC round trips, (b) the RPC timeout floor in the failure path is seconds, (c) GSP perf state can wedge on Blackwell.
- Measured microsecond-level GSP clock-request round-trip costs: none published. Nearest data points (B, fetched): staff statement that GPU power-saving artifacts are "in the milliseconds range"; the Ada 0x400/NVAPI thread's bursts at 10-30 ms with median inter-burst 141 ms at 2 ms sampling. **Named gap:** a 12 ms GSP-side quantization is neither documented nor refuted anywhere; the 12.27 ms vs 0.5 ms GPU-reach alternation matches the driver/EC perf-decision cadence magnitude, not any documented RPC floor. Probe that would close it: nvml clock + `clocks_event_reasons` sampling at ≥1 kHz across decode windows, correlated with the reach-wait timestamps, plus one A/B with `NVreg_EnableGpuFirmware=0` where the driver supports it.

## 7. Verdicts against our policies

| Our policy | Documented analogue | Verdict |
| --- | --- | --- |
| v2 pin SM 3135 + MEM 14001, demote on quiet | MLPerf `-ac` max-clock pin; TensorRT `-lgc` determinism pin; "closest desired" landing 2830-2955 vs 3135 requested | Legal, MLPerf-shaped. Pin-at-max is what MLPerf does; the demote-to-idle tail is our own addition (matches njuffa "no user-settable knobs" — nobody else keeps clocks up) |
| v4/v5 range locks 1800-3135 / 7001-14001 | Exact documented `-lgc`/`-lmc` semantics ("somewhere in between"), DVFS owns boost | The intended use of the API; best case is v2-equivalent ceiling, worst case DVFS parks low on short bursts (njuffa half-clock observation) |
| MEM-only pin → SM 2004 @ 61 W | No documented analogue; nearest = joint-domain `-ac` pairs + below-OS EC latch class (GB10) | Unexplained by power-cap precedence (61 W << 575 W). Treat as firmware perf-policy state; needs the -rgc/-rmc + power-drain A/B |
| 0x400 Reliability during sustained serving | `nvmlClocksEventReasonReliability` "reliability policy is currently limiting the GPU clocks"; Ada: clock undropped, few-percent V/F margin | Do not fight. It is the guard that permits the sustained 2830-2955 regime; pinning converts it to API_TRIGGERED/user-clock attribution |
| 12.27 vs 0.5 ms reach-wait alternation | No documented quantization; millisecond-range power artifacts (staff); 10-30 ms perf-decrease burst cadence on Ada | Open. kHz-rate telemetry A/B is the executable probe; GSP-off A/B secondary |
