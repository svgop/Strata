# KV tiering + persistence digest (2026-11-06) — the policy shape, the granularity answer, and closing the restart gap beyond the parked tail

Question: what tiering/eviction policy, what reuse granularity, and what persistence format fit THIS rig — one operator, 1–6 streams, 76-request sessions, 93.9% intra-session reuse, 150–261K contexts, 48 GiB parked cache, slot files already draining at exit — where production (LMCache, Mooncake, vLLM, SGLang) converged, and what full KV persistence across engine restarts takes from here? Companion to `2026-11-05-serve-tail2.md` (owns serve-layer tail latency); this digest owns the KV hierarchy and the park/drain/restore lifecycle.

## 0. Standing state verified in this tree (the facts every finding prices against)

- **The tier stack exists, four deep.** (1) VRAM resident window: `--kv-resident 32768` cells per QSA layer (config; the F-22b law: a depth lever, a floor, not a free slot source — SVG-CUSTOM.md:971, the 20480 arm regressed and was reverted); (2) the whole K/V in pinned host RAM (generate.cpp:910-912); (3) parked conversation images in host RAM — `--conversation-cache-mib 49152`, 24 slots, min-tokens 200 (config; `ConversationCache`, generate.cpp:9626-9628); (4) drained slot files on disk (`STRATA_CONV_SLOT_DIR=/home/svg/LLM/data/conversation-slots`, launch-custom-iq3s-8081.sh:33; drain at exit → `slot-<serial>.bin`, restore newest-first at boot, generate.cpp:13199-13304).
- **KV byte arithmetic.** `--kv int8` = 1,056 B/cell (k + v + fp16 scales per 64 values + pooled indexer row), k8v4 = 816, help text generate.cpp:904-909; a cell is per (token × QSA layer), so one token = 12 × 1,056 = **12,672 B ≈ 12.4 KiB**; a 261,144-token conversation = **3.24 GiB of KV**, + ~118 MiB GDN running state (:1776) + ~1 MiB tokens ≈ **3.4 GiB per max-length parked image**. 48 GiB admits ~14 max-length conversations; 24 slots over-admits by slot count.
- **Reuse is conversation-scoped and token-exact inside a session.** A request resumes at the deepest matching state: live tokens first, then checkpoints, then idle batch slots, then parked images (`resume` selection, generate.cpp:13965-14026; `borrows` mounts a parked checkpoint prefix for a NEW conversation while the parked one stays — conversation_snapshot.hpp:119-124). Checkpoints copy only the non-rewindable running state (~118 MiB); positional cells below stay in the session (generate.cpp:1768-1779).
- **The 32,768 fallback is chunk quantization, not a residency effect.** `prompt_cache_every` default = 16,384 (generate.cpp:826), but periodic checkpoints evaluate per prefill chunk (:10174, `done >= pp_next_check` then `pp_next_check = done + every` :10197) and the chunk is `auto:32768` — so checkpoints land only at 32,768-token boundaries. In-session checkpoint coverage = 6 × 32,768 = 196,608 tokens + the 2,048 root (:800, :831).
- **The disk slot carries exactly ONE checkpoint** — the deepest (`session_checkpoints_to_save`, conversation_file.cpp:1120-1124) — plus the full live KV, tokens and running state (`session_save_peak_bytes`, conversation_file.cpp:1138-1145). A restart resumes token-exact only if the client re-sends the parked tokens verbatim; any re-render drift falls back to that deepest checkpoint, i.e. granularity-bound. T66's own round-trip measured it: "drain 2 → restore 2 → **65/138 prefix reuse**" (launch-custom-iq3s-8081.sh:33) — restart resumes are NOT exact by default; the checkpoint fallback is load-bearing.
- **Validity keys are already production-shaped.** `SessionFileIdentity = {model, config}` hashes (conversation_file.hpp:25-27): model = head/tail fingerprint of every resolved weight input (native shards, dense, head, embedding, PLE, pack files, expert source, MTP; generate.cpp:9636-9665); config = engine version + backend + **kv format** + max_context + kv_resident + mtp_window + KV rotation + full rope config + control-vector digest + 22 numerics switches (generate.cpp:9667-9697). Read path validates identity + per-session read limits (geometry, layer carve, max tokens, running-state and KV part sizes) BEFORE allocating, and admits against the RAM floor (generate.cpp:13230-13256; conversation_snapshot.hpp:52-57).
- **Observed slot dir right now: zero live slots, two orphan temps** (`.slot-14.bin.a6f3456adafb5110.tmp` 112 MB, Nov 5; `.slot-2.bin.a27c34d4598c053b.tmp` 128 MiB, Nov 4). The temp name is dot-prefixed by construction (conversation_file.cpp:113, `"." + leaf + hex + ".tmp"`), and both cleanups match the prefix `"slot-"` (generate.cpp:13213-13215, :13297-13298) — **dot-prefixed orphans are never removed**: small leak, and hard evidence that interrupted/killed exits lose the drain in practice.
- **Banked negative that frames the compression question**: parked-state LZ4-class compression is bit-exact but ~1.01× on int8 KV; structure-aware coding is the owed form (F-276, SVG-CUSTOM-FEATURES.md:81-83).

## 1. Findings

### F1. Production hit-rate policy shape converges on hash-chained blocks + LRU (+ admission by measured reuse at fleet scale) — at OUR scale the hit-rate ceiling is the return rate, not capacity or policy

Mechanisms, with numbers: [Mooncake](https://arxiv.org/html/2407.00079v5) (fetched): KV paged in **512-token blocks**, each block's key = hash of its tokens **concatenated with the previous block's hash** (§6.1); eviction left to LRU/LFU/request-characteristic choice, and on their 23,608-request trace **LRU beat LFU and LengthAware** (§4.2); hit ratio rises **34% at 1K blocks → 55% at 50K blocks, then plateaus** (Table 1) — i.e. capacity stops buying hit rate; skew is extreme ("over 50% of cache blocks remaining unused", others hit tens of thousands of times, Fig. 6); the theoretical reuse ceiling on their workload is **~55%, up to 90% in one chat-shaped service** (§9). [vLLM](https://docs.vllm.ai/en/latest/design/prefix_caching.html) (fetched): full blocks only, block hash = `hash(parent hash, block tokens, extras)` (sha256 default, xxhash option), LRU free-queue eviction of refcount-0 blocks, freed blocks re-inserted in reverse so the last block (least likely reused) evicts first. [SGLang RadixAttention](https://arxiv.org/html/2312.07104v2) (fetched): token-granularity radix pages, **LRU evicting unreferenced leaves first**, longest-shared-prefix-first admission ≈ DFS-optimal; benchmark hit rates **50–99%**, production Chatbot Arena **52.4%/74.1%**, tree management overhead **<0.3%**. [LMCache](https://docs.lmcache.ai/mp/l2_storage/index.html) (fetched): L1 (host RAM or GDS-NVMe) + durable L2; store/prefetch controllers; watermark eviction (trigger 0.8, ratio 0.2 per cycle; LRU, ARC, or per-salt IsolatedLRU); prefetch bounded by a 0.5-of-L1 in-flight watermark.

Ours: with 24 slots and 48 GiB against a working set of ~6 live + ~14 parkable long conversations, capacity misses are rare; the hit-rate ceiling is the **conversation-return rate itself (93.9% given)** — Mooncake's plateau shape says more cache and smarter eviction both buy ≈0 here. Per-conversation economics are scale-free: stored bytes (12,672 B/token) and re-prefill seconds (1/6,300 s per token) are both linear in tokens → **every conversation costs ~13.1 s of re-prefill per GiB stored**, so size-weighted eviction (greedy-dual-size class) has no signal to work with; recency and expected-return are the only discriminative terms. Predicted hit-rate delta of ANY eviction-policy upgrade on this rig: **+0.0–0.3 pt**; the tail-latency deltas (F2/F3) dominate. Confidence: high on production mechanisms (fetched), high on the scale-law translation (arithmetic above), medium on the +0.0–0.3 (needs the counter of R0 to confirm).

### F2. Granularity: production's blocks are 16–512 tokens and vLLM's own guidance moved COARSER, not finer — our honest answer is that "block granularity" is the wrong knob; CHECKPOINT SPACING is ours, and 32,768 → 8,192 is nearly free

Production choices and measured tradeoffs: vLLM 16-token blocks (search-level default; [design doc](https://docs.vllm.ai/en/latest/design/prefix_caching.html) fetched — full blocks only, and the [stable features doc](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching.html) now ships `--prefix-match-unit` defaulting to the GCD of block sizes with **"64 is a reasonable starting point"**); SGLang token-level radix with `--page-size` default 1, 16 used for agent-heavy deployments (search-level); Mooncake 512-token blocks (fetched §6.1); LMCache storage chunks sized by bytes, sweet spot **~4 MB per chunk** (RESP docs fetched: below ~2 MB per-key overhead dominates, above ~4 MB allocation/window costs do; Llama-3.1-8B BF16 ≈ 128 KB/token → ~32 tokens ≈ 4 MB). Finer granularity buys match depth at the cost of per-key metadata/hash maintenance; production sits at 16–512 tokens because fleet workloads (Mooncake: 23.6K requests/hour, 720:1 input:output) match thousands of distinct prefixes.

Ours: intra-session resume is token-exact (live match, §0) — no granularity term at all. The granularity-bound cases are exactly three, all checkpoint-bound: (a) rewind after a client edit (resume from deepest checkpoint ≤ divergence), (b) restart with re-render drift (T66's 65/138), (c) cross-conversation borrow depth. At spacing g the wasted re-read is mean g/2, worst g: **g=32,768 → 2.6 s mean / 5.2 s worst; g=8,192 → 0.65 s mean / 1.3 s worst** (at 6.3K tok/s). Cost of 8,192: checkpoints copy only the 118 MiB running state ≈ 2–3 ms each (the measured park D2H family is 50–63 ms for a whole session, SVG-CUSTOM-FEATURES.md:57-59); a 261K read takes 32 saves ≈ **80 ms added to a 41.5 s read (+0.19%)**; host RAM for checkpoints is unchanged at `prompt_cache=6` (6 × 118 MiB); the mid-chunk placement machinery exists (`resume_plan`/`PromptPlan` segments a read for BYIELD parks and periodic checkpoints, generate.cpp:10004-10006). Coverage shrinks 196,608 → 49,152 tokens of rewind depth — acceptable if tail edits dominate, measurable first. Confidence: high on mechanism and costs (code-anchored arithmetic); the event frequency is unmeasured — that is R0's job and P1's falsifier.

### F3. The restart gap is write-through + lazy restore, not a new format — drain-at-exit loses to crashes (proven on disk today), and eager boot restore is O(all slots)

Today's lifecycle: park → host RAM only; disk touched once at clean exit; boot restores newest-first, synchronously, before the serve loop (generate.cpp:13304). Three failures fall out: (a) **crash or kill loses every parked conversation** — the two orphan temps in §0 are interrupted drains; (b) **boot pays Σ(all slots)** — 24 × ~4 s for 261K-class slots ≈ up to ~96 s before first admission (only the RAM preflight bounds it); (c) the restore lands at boot whether or not any conversation ever returns. Production anchor points: [LMCache's MP mode](https://docs.lmcache.ai/) (fetched homepage) sells exactly this decoupling — cache "will not be lost even if the inference engine crashes", durable L2 written continuously behind the engine; [CacheGen Appendix E](https://arxiv.org/html/2310.07240v3) (fetched) prices KV storage at scale (≈$0.05/month for an 8.5K-token context if >150 reuses/month) — trivially economical here; and SGLang's HiCache L3 tier measured **96.8–98% multi-turn hit rates with 145.5K effective input tok/s vs 9.4K L1-only** on DeepSeek-V4-Flash ([LMSYS unified-radix-cache blog, 2026-08-11](https://lmsys.org/blog/2026-08-11-unified-radix-cache/), fetched) — a third tier in front of compute pays at fleet scale, and its L1/L2/L3 split is the same shape as our VRAM/pinned-RAM/slot-disk stack. Confidence: high on the failure modes (observed on disk), high on the fix being lifecycle-only (format already fits; §0).

### F4. Compression of the on-disk form: priced out now; the production evidence class is aimed at fp16-over-network, and our own negative is banked

[CacheGen](https://arxiv.org/html/2310.07240v3) (fetched): anchor-delta encoding (groups of 10 tokens), layer-wise quantization, per-channel-layer arithmetic coding (−53% bitstream); **3.7–4.3× smaller than quantized KV**, 200 ms offline encode, TTFT 2.7–4.3× vs text re-prefill **at network bandwidths (≤3 Gbps)**, quality <2% accuracy / <0.1 perplexity. [CacheBlend](https://arxiv.org/html/2405.16444v2) (fetched): non-prefix reuse of multiple chunks with RoPE re-rotation + **15% (5–18%) selective recompute of high-KV-deviation tokens** recovers full-prefill quality (≤0.002 F1/Rouge-L), TTFT 4.1–6.6× vs full recompute at 512-token chunks. Ours: the KV is already int8 (2× over fp16 before any codec), the transfer is a local NVMe read (~4 s for 3.4 GiB), and the tree's own honored negative measured LZ4-class at **~1.01× on int8 KV** (F-276). CacheGen's 3.7–4.3× would put a 261K slot at ~1.7 GiB and ~2 s — saving ~2 s on an event class that P2/P3 make rare, at the cost of encode CPU on the park path and a second on-disk format version. Priced out standing; revisit only if slot restore ever dominates a live path. Confidence: high (fetched numbers + banked negative).

### F5. The hybrid-architecture precedent validates our checkpoint shape and names the one eviction upgrade worth considering: session-aware retention

[LMSYS unified radix cache](https://lmsys.org/blog/2026-08-11-unified-radix-cache/) (fetched, 2026-08-11 — the freshest hybrid source): full-attention KV stays valid across the whole matched prefix, but **"a recurrent state is valid only at an exact prefix checkpoint"** — exactly our QSA-cells-plus-GDN-checkpoint structure; their fix separates shared prefix identity from per-component reuse validity (FULL/SWA/MAMBA TreeComponents; Kimi-K3 = FULL+MAMBA(KDA)) and restores recurrent checkpoints into a private slot before mutation (our `borrows` semantics). Their eviction upgrade is **session-aware eviction**: attach a session_id after successful requests, order eviction candidates by reference/session depth — "change eviction order rather than pinning memory" — measured **2.9–16.6% lower TTFT on SWE-bench** multi-turn and device hit-ratio 42%→51% at batch 128 on DeepSeek-V4-Pro, i.e. a **48–64-client** regime. At 1–6 streams the transfer case shrinks by two orders; Mooncake's trace says LRU is the right default; SGLang's leaf-LRU and vLLM's free-queue are the same family. Ours: keep LRU-oldest (already in `evict_oldest`), add the counter, and only if evict-then-return recurs, protect by conversation depth (turns ≥ threshold), never by size (F1's 13.1 s/GiB identity makes size-weighting inert). Confidence: high on the shape validation; medium-high that the upgrade is priced out here (counter decides).

## 2. The design for THIS rig

Policy in one line: **keep the conversation-scoped exact-reuse model, drop checkpoint spacing 4×, make disk a write-through tier instead of an exit hook, and make boot lazy.** Extend the existing skeleton — do not replace it; session-file v1 + identity + read-limits preflight is already the production shape (§0).

### P0 — Instrument the reuse lifecycle first (co-requisite of P1/P3/P4)

- **Change**: decompose every request's resume into one of `exact_live | checkpoint_depth(n) | borrow_depth(n) | zero` and export counters + histograms: `resume_kind`, `checkpoint_depth_tokens` (the tail re-read length), `evicted_then_returned` (return within 24 h of eviction), `slot_restore_seconds`, `slot_drain_seconds`, `park_write_seconds` (serve/server.py observe sites already receive engine REUSED/DONE lines; the engine side already logs `parked=%zu bytes=%zu evictions=%zu ... reused_kv_bytes=%zu`, generate.cpp:9882).
- **Predicted**: zero perf effect; converts P1/P4 from arithmetic to measured event counts.
- **Falsifier**: n/a (measurement). Accept if /metrics grows the series with no wall change.

### P1 — Drop the effective checkpoint spacing 32,768 → 8,192 (P1 = one config value + mid-chunk checkpoint placement the plan machinery already supports)

- **Change**: `--prompt-cache-every 8192`; extend the prefill segment plan so a periodic checkpoint lands every 8,192 tokens INSIDE a 32,768 chunk (read_part boundaries; the same plan already places BYIELD parks mid-read, generate.cpp:10004-10006). Keep `prompt_cache=6` (coverage 49,152 tokens) and root 2,048; arm `--prompt-cache-tail` so the newest boundary nearest the tail is always present.
- **Predicted**: rewind/re-render/borrow tails drop mean 2.6 s → 0.65 s per event, worst 5.2 s → 1.3 s (F2); checkpoint-save overhead +80 ms per 261K read (+0.19%, inside drift); TTFT@262K unchanged within the +4% floor.
- **Floors/falsifier**: prefill marginal rate must stay ≥6K tok/s solo (bank 6,925 fresh); TTFT@262K +>4% → revert; P0 shows <5 checkpoint-resume events/day over a week → the change is noise, revert (needle priced, law 15). If P0 later shows deep rewinds (>49K), raise `--prompt-cache` to 10–12 (1.2–1.4 GiB host RAM per session set) instead of finer spacing.

### P2 — Park-time write-through (crash-safe persistence; drain-at-exit becomes the fallback, not the only path)

- **Change**: when a conversation is parked (the `ConversationCache::put` path, including the elastic park), write its slot file immediately — same session-file v1 bytes, same identity, tmp+rename discipline already in conversation_file.cpp:462-489 — throttled to one write at a time, in true idle (the park itself is idle-time). At exit, keep the drain only for entries parked-but-not-yet-written. Fix the orphan-temp hygiene: match the dot-prefixed temp form (or clean any `*.tmp` older than a boot) in both cleanup loops (generate.cpp:13213-13215, :13296-13298). Cap the slot dir at `conversation-cache-mib` (48 GiB), evicting lowest-serial first, mirroring `evict_oldest`.
- **Predicted**: kill -9 / power loss now loses only the turns since the last park instead of the whole cache; park cost grows by ~4 s per 261K write in idle (measured restore class, T66); disk steady-state = the parked set ≤ 48 GiB (today: 0 live, 240 MB orphans). NVMe wear is turn-boundary-paced (parks per hour, not per second).
- **Floors/falsifier**: (a) round-trip kill-test — park a 261K conversation, `kill -9`, relaunch, confirm restore + prefix reuse (the T66 protocol); (b) promote/demote bands (2.2–8 ms map, 2.0–2.8 ms unmap) must not move — the write never runs on the request path; (c) /metrics `slot_drain_seconds` at exit drops toward the unwritten-set only; (d) dir size stays under cap with the alarm armed.

### P3 — Lazy slot restore (boot non-blocking; restore on touch, off the control lines)

- **Change**: `session_restore()` (generate.cpp:13206-13262) reads only each file's header — identity + size fields, preflight via the existing read-limits path (verify the KV section offset allows a header-only probe before relying on cheap probes; a bounded leading-block read is the fallback) — and returns. Full restore happens on first touch of that conversation (the returning-request path calls the same restore under the RAM admit), optionally prefetched in background newest-first when the engine is idle ≥N seconds after boot. The restore must run off the `ctl` lines with progress beats (park-style, generate.cpp:9719-9727) — a 4 s read must never hold the ~113 ms admission window's lock (SV-8 discipline, prior digest F5).
- **Predicted**: boot-to-first-admission loses the Σ(all-slots) penalty (≈31–96 s at full occupancy) and gains ~0 standing; the first touch of a parked 261K conversation pays ~4 s instead of 0 (eager) — still 10.7× under the 42.7 s re-read floor; total restore work after a restart = only what returns (in practice 1–2 conversations, not 24).
- **Floors/falsifier**: boot-to-first-admission within +4% of a no-slot boot; first-return TTFT for a parked 261K conversation ≤5 s; if P0 ever shows ALL slots touched after every restart, lazy ≈ eager (wash) — keep lazy anyway for the boot path's independence from disk latency.

### P4 — Session-depth-guarded eviction, counter-gated (default stays LRU-oldest)

- **Change**: only if P0's `evicted_then_returned` fires ≥1/week: in `evict_oldest`, skip conversations with turns ≥ a threshold (e.g. 32) while any shallower entry exists ("change eviction order rather than pinning", LMSYS 2026-08). Never size-weight (F1: all conversations cost the same 13.1 s/GiB).
- **Predicted**: one saved eviction-return of a 261K conversation = one avoided 42.7 s re-read; hit-rate move ≤ +0.3 pt (F1).
- **Falsifier**: the counter IS the falsifier — below threshold, do not build (the policy has no event to act on).

### P5 — Cross-session sharing stays with `borrows`; no radix tree, no block hashing

- **Position**: token-level radix indexing (SGLang) or hash-chained blocks (vLLM/Mooncake/LMCache) buy cross-REQUEST dedup at fleet scale. Our cross-session mass is (a) system/harness prefixes of ~2–4K tokens → 0.3–0.6 s per cold start, ~25–50 MB per parked copy × 24 slots ≈ 0.6–1.2 GiB of dedup against 48 GiB; (b) whole-corpus sharing — already exact via `borrows` (conversation_snapshot.hpp:119-124). Add a one-week P0 measurement of cross-conversation prefix overlap before ever revisiting.

### The interactions that bite (mandate item 4)

- **KV form is per-engine and the identity already keys it**: `c.kv` sits in the config fingerprint next to rope, cvec, mtp_window, kv_resident and 22 switches (generate.cpp:9667-9697) — q4_0 / k8v4 / int8 / `STRATA_KV_ROT` each hash differently, and `session_file_read` refuses a foreign file before allocation. Rule: a config-hash miss refuses, never reinterprets — serving numerics-wrong context is worse than any 42.7 s re-read. The only identity gaps worth closing are operational: engine_version is IN the hash (every rebuild invalidates slots — correct, keep it), and there is no marker distinguishing "restored from disk" images for telemetry (add one in P0, not in the format).
- **Multi-slot eviction at restart**: today the eager restore stops at `conversation_cache_slots` or the RAM floor and DELETES the files it could not take (generate.cpp:13233, :13252-13256) — under lazy restore (P3) the files must survive on disk until touched or cap-evicted (P2), so the boot path stops being the deletion authority.
- **Disk budget**: slot ≈ 12.9 KiB/token all-in (12,672 KV + running state + tokens amortized); 261K ≈ 3.4 GiB; the dir mirror is bounded by the 48 GiB RAM budget only if P2's cap lands — otherwise write-through makes the dir an unbounded mirror of everything ever parked. Observed orphan leak: 240 MB and growing per interrupted drain until the hygiene fix lands.
- **Do not touch `--kv-resident`**: the 96.5% VRAM-hit window is the F-22b floor law; this digest's changes are all host/disk-side and leave the resident window alone.

## 3. What NOT to do (and the numbers that close each door)

- **No block hashing / radix tree for this rig.** 6 streams × 76-request sessions vs Mooncake's 23.6K requests/hour; intra-session reuse is already token-exact; the marginal cross-session cases are P5's 0.3–0.6 s. Metadata machinery buys no hit rate here (F1 plateau logic).
- **No CacheGen/LZ4 compression of int8 KV on disk.** Banked negative ~1.01× (F-276); CacheGen's 3.7–4.3× targets fp16-over-WAN; 2 s saved on an event class P2/P3 make rare, against encode CPU on the park path and a format fork (F4).
- **No per-step KV write-through** (LMCache layer-wise store during decode). Our park points already coincide with reuse boundaries; per-step writes at 12.4 KiB/token ≈ **76 MB/s of NVMe during prefill** for zero reuse P2 does not already capture.
- **No value-based admission (Mooncake-style predicted hit rate).** One operator's reuse is deterministic; admission already exists (min-tokens 200, RAM floor, byte budget, superseded-drop :9740). Instrument first (P0); the policy has no event to act on until `evicted_then_returned` says otherwise.
- **No eager all-slot restore, and no restore ON the admission lines.** The first wastes 31–96 s of every boot (P3); the second repeats SV-8's lock-held-I/O class on a 4 s read.
- **No checkpoint on every chunk boundary without the P0 counter** — if checkpoint-resume events are <5/day, P1's +0.19% prefill tax and the coverage shrink buy nothing measurable (law 15).
- **No weaker validity key, ever.** Weights head/tail fingerprint + config (kv format, rope, cvec, switches) is the minimum; a slot that passes a weaker key is silent context corruption.

## 4. Boundary of the conclusion

Every predicted delta is priced from measured constants (6.3K tok/s, 42.7 s @261K, ~4 s slot read, 50–63 ms park D2H, 118 MiB checkpoints) and fetched production numbers; the unmeasured terms are event frequencies (checkpoint resumes/day, evict-then-return/week, returns-after-restart) — P0 closes those before P1/P4 adopt. The production evidence is fleet-shaped (48–64 clients, 720:1 I:O, TP4/TP8); the translation to one operator is arithmetic, not measurement, and the digest's falsifiers are the instrument. If slot restore ever lands on a live path (e.g. restore-on-touch while another stream decodes), re-price P3's idle-prefetch arm before trusting the 4 s figure — it was measured on a boot-idle engine.
