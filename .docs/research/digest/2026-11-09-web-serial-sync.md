# 2026-11-09 — Serial-decode device→host sync: the 12-vs-8 ms question

## Verdict

The 12.27 ms serial-lane wait is not a flag-propagation cost (that class is µs). It is **host-side exposure**: in a single-stream per-window ring, every wait fully serializes host↔device (GPU idles during host work, host idles during GPU work), so any host wake/schedule/launch jitter lands in the wait bucket at full magnitude. Batched lanes overlap that same jitter behind GPU compute — 0.5-0.7 ms is the jitter, 12 ms is jitter × no-overlap × wake-quantization. Day-scale 12↔8 ms swings at identical graphics clocks match four documented mechanisms: CPU preemption of the polling thread (measured 15.3 ms-class penalties), scheduler-tick quantization (250 Hz = 4 ms steps), memory-clock DVFS state (documented +11-45% latency shifts with unchanged GPU clock), and GSP-firmware channel scheduling variance.

## 1. Serial decode latency anatomy (documented numbers)

- **Kernel launch: ~3-5 µs typical, up to ~25 µs** depending on grid/system; hundreds of tiny decode kernels burn ms in launch alone. [NVIDIA forum 258228](https://forums.developer.nvidia.com/t/advantage-of-cuda-graphs/258228) (C) · [Modal GPU glossary](https://modal.com/gpu-glossary/host-software/cuda-graph) (B) · [ICPP'19 poster](https://www.hpcs.cs.tsukuba.ac.jp/icpp2019/data/posters/Poster17-moc.pdf) (B).
- **Graph launch: ~2 µs regardless of kernel count** vs ~3-8 µs *per kernel* individually — NVIDIA's own GTC/OLCF material. [OLCF CUDA Graphs deck](https://www.olcf.ornl.gov/wp-content/uploads/2021/10/013_CUDA_Graphs.pdf) (A) · [PyTorch blog](https://pytorch.org/blog/accelerating-pytorch-with-cuda-graphs) (A).
- **llama.cpp upstream graphs: batch-size-1 only, best case 1.2x** (Llama-7B on H100), plus "~10% further improvement" possible from CPU-side prep/sampling. Capture is gated by a `use_cuda_graph` condition in `ggml/src/ggml-cuda/ggml-cuda.cu` that requires single-device full-offload-compatible graphs — partial offload forces per-layer rings, confirming our zero-doorbell constraint. [NVIDIA blog](https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs/) (A) · [issue #6763 / PR #6766](https://github.com/ggml-org/llama.cpp/issues/6763) (A).
- **Wait-mode taxonomy is documented, not folklore:** `cudaDeviceScheduleSpin` = busy-wait (lowest wake latency); `cudaDeviceScheduleYield` = release CPU between polls; `cudaDeviceScheduleBlockingSync` / `cudaEventBlockingSync` = sleep on an OS primitive — wake latency rides the scheduler tick. [CUDA runtime API, cudaDeviceFlags](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__DEVICE.html) (A) · canonical SO answer [11953722](https://stackoverflow.com/questions/11953722/how-to-reduce-cuda-synchronize-latency-delay) (C, snippet-verified).
- **Device→host flag visibility:** `__threadfence_system()` is the documented ordering primitive for device writes visible to host pollers (A: [C++ extensions guide](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)); round trip is ~1-10 µs over PCIe in forum/blog microbenchmarks (C: [NVIDIA forum 14645](https://forums.developer.nvidia.com/t/synchronizing-mapped-memory-use-between-host-and-device-while-kernel-is-running/14645/15), [Lei Mao](https://leimao.github.io/blog/CUDA-Zero-Copy-Mapped-Memory)). Polling write-combined host memory is a documented footgun — host reads of WC memory are slow (C). **Gap: no vendor-published µs figure for flag write→host-poll visibility.** Device-side wait without host round-trip exists as `cuStreamWaitValue32` (A: [CUDA driver API, stream memops](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__STREAM.html)).
- **Scheduling overhead can dominate serial decode:** vLLM's CPU scheduler measured at **>50% of total inference time** on small models; biggest costs are input-tensor building and detokenization, not the scheduling algorithm. [MLSys/WuKlab study](https://mlsys.wuklab.io/posts/scheduling_overhead) (B).

## 2. Mechanisms that produce a 12↔8 ms day-scale shift at identical graphics clocks

Ranked by fit to our signature (multi-ms, varies by day, identical `nvidia-smi` clocks):

1. **CPU preemption of the host poll/launch thread.** eBPF study on a live GPU inference process: median preemption penalty per affected launch pair **15.3 ms** (0.1% of pairs — enough to poison every window in a serial lane); CPU noisy neighbor cost **-8.8%** throughput; combined CPU+net+disk neighbors **-20.5%**; `taskset`+`nice` cut context switches 96.3% and recovered **+7.6%** tok/s. Same-box behavior changing day-to-day with background daemons is exactly this signature. [eunomia.dev eBPF study, 2026-05](https://eunomia.dev/blog/2026/05/24/measuring-cpu-noise-in-gpu-inference-with-ebpf/) (C, instrumented).
2. **Scheduler-tick quantization (CONFIG_HZ).** Any wait that ever sleeps (yield loop, blocking sync, timer slack) quantizes wake to the tick — **HZ=250 = 4 ms steps**; a serial lane that takes 2-3 tick-quantized wakes per window lands at 8-12 ms. Documented kernel behavior: `nohz_full` stops the tick when one runnable task remains; isolated cores still take a timer IRQ roughly every other second. [RHEL RT docs](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux_for_real_time/8/html/optimizing_rhel_8_for_real_time_for_low_latency_operation/assembly_isolating-cpus-using-tuned-profiles-realtime_optimizing-rhel8-for-real-time-for-low-latency-operation) (A) · [rigtorp low-latency guide](https://rigtorp.se/low-latency-guide) (C) · [LWN hrtimer slack](https://lwn.net/Articles/484162) (A).
3. **Memory-clock DVFS state, decoupled from SM clock.** Instrumented DVFS study (Jetson EMC, the only paper found isolating memory clock): locked-point shifts move decode-proxy median latency **+11.7%…+44.8%**, an L2-resident kernel runs **8.3× slower at the memory-clock floor with GPU clock unchanged**, and frequency actuation lag is **ms-scale (EMC p95 ≤ 9.7 ms)** — a governor decision lands *after* the next window. On discrete GPUs, aggressive idle ramp-down with repeated ramp-up is a documented forum complaint; fix = persistence mode + locked application clocks. [arXiv 2606.16106](https://arxiv.org/html/2606.16106v2) (B) · [NVIDIA forum 165974](https://forums.developer.nvidia.com/t/very-fast-ramp-down-from-high-to-low-clock-speeds-leading-to-increased-time-repeatedly-ramping-up/165974) (C) · corroborating: [3090 dropping to idle clocks during token generation](https://www.reddit.com/r/LocalLLM/comments/1wdc7dx/gpu_drops_to_idle_clocks_during_token_generation) (D). Lesson: "identical graphics clocks" does not prove identical *memory* clocks — verify with NVML per-clock readback, not one counter.
4. **GSP firmware channel scheduling.** Default on Turing+; the vendor claim is *lower* latency ("lower latency access to GPU hardware internals"), but multiple community reports attribute multi-frame stutter/scheduling regressions to it, resolved by `NVreg_EnableGpuFirmware=0`. No compute-decoder-specific measurement found — treat as a hypothesis with an A/B test design, not a verdict. [Driver README ch.43](https://download.nvidia.com/XFree86/Linux-x86_64/565.57.01/README/gsp.html) (A) · [forum 311127](https://forums.developer.nvidia.com/t/stutering-and-low-fps-scrolling-in-browsers-on-wayland-when-gsp-firmware-is-enabled/311127) (C/D).
5. **SM-clock ramp on short serial bursts** (sub-window GPU idles let the governor drop boost). Doc-tier: NVIDIA's ramp-down thread above; our 233 t/s-best-day vs 12 ms-window variance is consistent with boost residency differences. (C/D)
6. **Explicitly weak evidence:** RCU stalls and driver interrupt coalescing surfaced only as soft-IRQ noise measurements (TIMER softirq avg 2.4 µs, max 30.1 µs — an order too small to explain 4 ms alone) [eunomia] (C). Keep RCU in mind for stall-style multi-100 ms events, not 4 ms quanta.

## 3. What the best stacks do for the serial low-batch case

- **TensorRT-LLM:** capture CUDA graphs for decode, then **pad every batch size up to the nearest captured graph** (`use_cuda_graph`, `cuda_graph_batch_sizes`, `cuda_graph_padding_enabled` — graphs "only created for the batch sizes in `cuda_graph_batch_sizes`") so a single-stream lane never replays an uncaptured shape; latency builds additionally use `low_latency_gemm_plugin` (CUTLASS latency-kernels) and `MAX_BATCH_SIZE=1`. The padding trick is exactly the fix for "shape changes force re-capture" — one fixed set of whole-window graphs + padding, not per-layer rings. [TRT-LLM API ref v0.21](https://nvidia.github.io/TensorRT-LLM/0.21.0/llm-api/reference.html) (A) · [issue #6294](https://github.com/NVIDIA/TensorRT-LLM/issues/6294) (A) · [Modal latency guide](https://modal.com/docs/examples/trtllm_latency) (B).
- **vLLM v1:** engine-core process runs the scheduler as a **documented busy loop**; async scheduling overlaps output processing with GPU execution. Known failure mode matches our anatomy: the busy loop is CPU-starvation-sensitive and decode gaps appear when it loses its core. [arch overview](https://docs.vllm.ai/en/latest/design/arch_overview) (A) · [forum: scheduler starves under background load](https://discuss.vllm.ai/t/throughput-drops-and-increased-ttft-when-running-background-automation-executors/2597) (C).
- **SGLang:** overlap scheduler prepares batch N+1 metadata during batch N's GPU compute; Nsight traces show "no single idle time on the GPU" — the design our serial lane lacks. [LMSYS v0.4 blog](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4) (A/B) · [failure case when overlap breaks](https://github.com/sgl-project/sglang/issues/19347) (A).
- **CPU-offload lineage — the actual implementations:** FlexGen zig-zag block schedule: "overlap the weights load of the next layer, cache/activation load of the next batch … and the computation of the current batch," multiple CUDA streams + CPU threads, six independent logical threads in the inner loop ([arXiv 2303.06865](https://arxiv.org/html/2303.06865), B, ICML'23). DeepSpeed ZeRO-Inference: layer prefetching overlaps fetch of layer i+1 with compute of layer i — and honestly documents that **CPU-offload prefetch gave zero gain at short sequences** because compute can't hide fetch ([deepspeed.ai](https://www.deepspeed.ai/2022/09/09/zero-inference.html), A). KTransformers (SOSP'25): routed experts on CPU NUMA, **GPU defers/moves ahead** instead of waiting per expert; CPU expert compute overlaps subsequent GPU attention — the only offload stack with a published deferral ring. [paper](https://dl.acm.org/doi/10.1145/3731569.3764843) (B) · [SGLang integration](https://www.lmsys.org/blog/2025-10-22-KTransformers) (A).
- **Host isolation:** `isolcpus`/`nohz_full` + IRQ affinity + SCHED_FIFO for the polling thread is the standard fix class; measured +7.6% under load, 15-20% projected for shared servers [eunomia] (C).

## 4. Map to our case

- 12.27/14 ms wait in the serial lane = full-duplex serialization: the doorbell spin is *waiting for work the host could have pre-issued*. The batched lane's 0.5-0.7 ms is the true flag+launch jitter; the serial lane adds wake quantization and launch-path preemption on top, uncompressed.
- 12.27 ≈ 3 × 4 ms (HZ=250 quanta) and 15.3 ms measured preemption penalties are both in-band: poller got descheduled or its wait path slept. A pure spin (never `sched_yield`, never blocking sync, default timer slack bypassed via busy read) on an isolated core should collapse the wait toward the batched-lane number.
- Day variance at "identical clocks": verify memory clock via NVML across days before blaming GSP; then A/B `NVreg_EnableGpuFirmware=0`.
- Structural fix used by every A-grade stack: **whole-window graph + padding + CPU run-ahead** (launch window N+1 before consuming window N's doorbell), or a deferral ring (KTransformers) so the GPU never drains. Partial offload does not force per-layer host waits — it forces per-layer *rings*; the wait bucket shrinks to zero only when ring depth ≥ 1 ahead.

## Ten-line report

1. Flag-propagation µs myth: device→host mapped-flag visibility is 1-10 µs (PCIe) — a 12 ms wait is host scheduling, not wire latency. (A/C)
2. Mechanism 1 — poller preemption: 15.3 ms median penalty per preempted launch pair; CPU neighbors cost 8.8%, combined 20.5%. (C, instrumented)
3. Mechanism 2 — tick quantization: any sleeping wait wakes on CONFIG_HZ ticks; HZ=250 = 4 ms steps; 2-3 quanta/window = our 8-12 ms band. (A)
4. Mechanism 3 — memory-clock DVFS independent of SM clock: +11.7-44.8% latency between locked points; 8.3× at the floor with GPU clock unchanged; ms-scale actuation lag. (B)
5. Mechanism 4 — GSP firmware scheduling: default on Turing+, vendor claims lower latency, community reports multi-frame regressions fixed by `NVreg_EnableGpuFirmware=0`; A/B it. (A/C)
6. Best-stack fix — TRT-LLM: decode CUDA graphs + `cuda_graph_padding_enabled` pads batch sizes to captured shapes; graphs never re-capture mid-lane. (A)
7. Best-stack fix — vLLM v1/SGLang: scheduler as documented busy loop; batch N+1 prepared during batch N's compute; Nsight shows zero GPU idle; both measurably degrade when the busy loop loses its CPU. (A/B/C)
8. Best-stack offload fix — FlexGen/ZeRO-Inference overlap fetch(i+1) with compute(i) via multi-stream multi-thread rings; ZeRO admits CPU prefetch gains ~0 at short sequences — the honest baseline for our lane. (A/B)
9. Best-stack offload fix — KTransformers deferral ring: GPU moves ahead, CPU experts overlap later GPU attention; only published design with per-layer host work hidden behind GPU windows. (B)
10. Host prescription: pure-spin doorbell on `isolcpus`/`nohz_full` + SCHED_FIFO core, clocks locked (`-lgc`/`-lmc` + persistence mode) and verified via NVML, CPU run-ahead depth ≥ 1, padding-captured per-T graphs.
