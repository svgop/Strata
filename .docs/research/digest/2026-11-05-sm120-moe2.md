# sm_120 small-M MoE kernel frontier — evidence digest (2026-11-05)

## 1. Question

Which kernel mechanisms with PUBLIC MEASUREMENTS on Blackwell actually transfer to our sizes — grouped GEMM at M≤8, host-streamed routed experts, fused attention at 262K context — and which are large-M or wrong-silicon stories wearing a Blackwell label?

Headline: **at M≤8 the entire production stack converges on one law — weight bytes are the clock, kernels are judged by achieved GB/s and launch/glue overhead, not FLOPS.** Every flagship Blackwell GEMM machine (DeepGEMM, FlashMLA, TRT-LLM tcgen05 paths, CUTLASS TMA-WS collectives) is either not built for sm_120 or measured to LOSE at M≤32; the measured winners at our sizes are W4A16-class dequant-on-the-fly kernels with small tiles, persistent launches, and fused glue — plus, for dsv41, the KV-byte cut, which remains the single strongest lever on the box.

## 2. Findings by mandate area

### 2.1 DeepGEMM on Blackwell — DEAD as code, ALIVE as a design spec

Provenance: https://github.com/deepseek-ai/DeepGEMM (README fetched 2026-11-05); issues #20, #136 via search snippets of the repo.

- **Architectures: SM90 and SM100 only.** README requirements name "NVIDIA SM90 or SM100 architecture GPU". No sm_120, no consumer mention. Portability is not a recompile: the SM90 path is wgmma-based and the SM100 path is tcgen05/TMEM-based — sm_120 has neither (banked; re-confirmed by Colfax below). Porting = full MMA-layer rewrite, not a build fix.
- **Grouped variants:** contiguous grouped (M-axis grouped; prefill/training; M-block-aligned segments) and **masked grouped** (per-expert bounded-M shape + `masked_m` tensor; explicitly "for the inference decoding phase when CUDA graph is enabled and the CPU does not know how many tokens each expert receives" — i.e., the decode design pattern: per-expert M upper bound, graph-compatible, compute-only-selected).
- **JIT:** everything compiles at runtime per shape (DeepJIT; `DG_PRINT_CONFIGS` dumps the per-shape config table; 2025-07-20 added a low-CPU-overhead JIT C++ module). No CUDA toolkit compile at install; CUDA ≥12.9 required.
- **Measured sweet spots:** headline 1550 TFLOPS FP8 on H800. **No public M≤64 numbers on the README; no M≤8 measurement anywhere fetched.** Their own benchmark caveat (issue #136): masked-grouped GEMM results **fluctuate up to 20%** with the random `masked_m` seed — a benchmark-noise law that independently validates our interleave protocol for any grouped-GEMM leg. Issue #20: `masked_m=0` groups produce NaNs — an expert-skip footgun for exactly our tiny-M shape.
- Grade: measured-public on sm_90/sm_100; **verdict for us: DEAD as code** (wrong silicon, wrong M regime, rewrite-class port), **TRANSFER as design**: per-expert bounded-M + mask + graph-compat is the correct grouped-GEMM interface for a tiny-M decode path if we ever grow one.

### 2.2 FlashMLA / MLA-class decode — DEAD as code; the KV layout table is the transferable artifact

Provenance: https://github.com/deepseek-ai/FlashMLA (README fetched 2026-11-05); https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog15_Optimizing_DeepSeek_V32_on_NVIDIA_Blackwell_GPUs.html (fetched).

- **Architectures: SM100/SM103 only; Hopper support REMOVED in the 2026.09.30 release.** No sm_120. Decode additionally **requires FP8 or FP4 KV cache — bf16 KV decode is not supported at all** in current FlashMLA.
- **The KV layouts (the artifact to copy):** head_dim 512 (V4.1): FP8 = **528 B/token** (512 e4m3 + 16 e8m0 scales, one scale per 32 values); FP4 = **288 B/token** (512 e2m1 in 256 B + 32 e4m3 scales, one per 16 values). This is production's answer to "how do you quantize MLA KV and still dequantize in-kernel": block scales inside the token record, dequant in the attention kernel, no pre-dequant pass.
- **Measured:** B200 (CUDA 13.3): sparse-MLA decode up to **1024 TFLOPS** (FP4 KV); fused qnorm+RoPE+attention+RoPE+FP8-cast single kernel 950 TFLOPS decode; older H800-class FP8 sparse decode 410 TFLOPS. No per-token latency at bs=1-8 published in the README; no context-length sweeps.
- **TRT-LLM's V3.2 blog (B200)** adds the decode-kernel details that transfer: sparse MLA decode runs **MQA-mode for MTP** (all verify rows in one pass); DeepGEMM MQA kernel gained **+10% from larger MMA tiles** and **paged-KV block sizes where 64 divides block**; sparse rows gathered with **TMALDG.Gather4**; a **"fast path" for N≤2048 with its own separate CUDA graph**; B200 batch=1 MTP-3 TP4 measured **276.2 tps/user, TPOT 3.23 ms** at 8K/1K.
- For our sm_120 box the runnable MLA-class kernels are FlashInfer's: **v0.6.14 DeepSeek-class sparse MLA (d_qk 512/576) on SM120/121; v0.7.0 DeepSeek-V4 sparse MLA with NVFP4 KV on RTX 5090/PRO 6000 (backend="cake", top-k 192/256); v0.7.2 V4.1 mixed FP8/FP4 cache decode** — i.e., the exact model class of our dsv41 engine already has a shipping sm_120 kernel family to copy layouts and scheduling from (https://flashinfer.ai/releases, fetched).
- Grade: measured-public on sm_100/sm_103 + transfer argument for the layouts; sm_120 code existence measured-public via FlashInfer release notes (numbers not yet published per-kernel). **Verdict: TRANSFER the KV layout + MQA-verify + fast-path-graph structure; do NOT port FlashMLA itself.**

### 2.3 vLLM / SGLang fused-MoE on sm_120 — the strongest measured warning on the board

Provenance: https://github.com/vllm-project/vllm/issues/48732 (fetched); https://github.com/vllm-project/vllm/issues/36095 (fetched); https://flashinfer.ai/releases (fetched); https://github.com/flashinfer-ai/flashinfer/issues/2577 (fetched).

- **Untuned sm_120 Triton fused-MoE is 3-6× off at decode.** vLLM #48732 (opened 2026-07-15, open): Qwen3-Omni-30B-A3B (128 experts, N=768) on 8×RTX 5090, TP4, vLLM 0.11.2 with default configs: **0.41 req/s, mean ITL 178.8 ms** vs **SGLang 0.5.15 on identical hardware: 0.74 req/s, ITL 27-52 ms**. The gap is decode ITL, not prefill. There are **no RTX 5090 fused-MoE tuning configs for any dtype in-tree** (#36095); the only consumer-Blackwell configs are RTX PRO 6000 fp8_w8a8.
- **What tuned small-M configs look like on sm_120** (RTX PRO 6000 data in #48732): batch key "1": `BLOCK_SIZE_M=16, BLOCK_SIZE_N=128, BLOCK_SIZE_K=64, GROUP_SIZE_M=16, num_warps=8, num_stages=5`; keys 4/64/128: `BLOCK_M=16, N=32, K=64, GROUP_M=1, warps=4, stages=3-4`; key 16: `BLOCK_M=32, N=64, K=64, warps=4, stages=3`. **BLOCK_M floor is 16 everywhere; never 8** — the Triton `tl.dot` minimum, and consistent with CUTLASS's smallest shipped M-tile of 32.
- **Two measured cautionary tails in the same issue:** (a) a *small-key-only* tuned config (keys 1-256) **regressed bs=32 throughput −11.2%** — tune the full batch curve or nothing (this is our incline law, independently rediscovered); (b) a 9-key config on PRO 6000 landed within noise of defaults (+0.5% @bs32, −0.8% @bs1) — tuning pays only where defaults are missing or badly transplanted, which is exactly the 5090 situation.
- **At equal bit-width, kernel choice is worth 1.8×:** #36095 measured on 2×5090, Qwen3.5-35B-A3B 4-bit: compressed-tensors AWQ via Marlin-MoE **~87 t/s** vs GPTQ-Int4 via `moe_wna16` **~47 t/s** and `gptq_marlin` **~48 t/s** — same nominal bpw, dequant-scale layout and kernel path decide.
- **FlashInfer is the fastest-moving sm_120 MoE stack** (releases page, fetched): v0.6.16 unified MoE API "SM120/SM121 B12x NVFP4 and W4A16 backends"; v0.6.17 SM12x W4A16 gained **persistent launches + a tensor-core decode path for small batches + shape-stable route packing (no recompile when batch size changes)**; v0.7.1 measured **W4A16 runs a Qwen3.8-Flash-Next MoE layer 1.36× faster than Marlin at one token** (DGX Spark, sm_121 — same arch family); v0.7.3 (2026-11-04, yesterday) shipped the **Frost low-latency MoE** (cuDNN backend) covering BF16/FP8/MXFP8/NVFP4 grouped GEMM **on SM120** with a MoELayer low-latency path Ampere→SM120.
- **NVFP4-on-sm_120 was shipping garbage until July 2026** (#2577, closed fixed): FlashInfer 0.6.3 mm_fp4 on SM120 returned all zeros across cutlass/cudnn backends; root cause was `nvfp4_quantize` **silently corrupting scale factors when global_scale is not float32** (fixed 0.6.13, PR #3497). Same issue records **CUTLASS TMA-WS grouped-GEMM init failures on SM120 — "SMEM tile configs assuming B200-class hardware"** (TRT-LLM #11368) — the 228 KiB vs 99 KiB smem cliff striking in production. And on the same silicon, **Marlin W4A16 (50.5 t/s) beat the NVFP4 CUTLASS path (26-41 t/s)** on a Qwen3.5-397B-A17B-NVFP4 4×PRO 6000 rig, with **MTP=2 costing Marlin −22% t/s** (verify rows are not free even on a fully-resident card).
- Grade: measured-public on sm_120 (multiple independent rigs). **Verdict: TRANSFER the config discipline + W4A16/persistent-kernel class; treat NVFP4 MoE GEMM as quality/risk-gated, not speed-adopted on sm_120.**

### 2.4 TensorRT-LLM Blackwell MoE — tcgen05 shipped only on sm_100/103; the measured small-M table is the transfer

Provenance: https://nvidia.github.io/TensorRT-LLM/blogs/tech_blog/blog24_MoE_as_Dense_GEMM.html (fetched); blog1 "Pushing Latency Boundaries" (fetched, note the URL is `blog1_` not `blog01_`); FlashInfer #2577 for the "trtllm backend explicitly `BackendSupportedError` on SM120" line.

- **Where tcgen05 shipped:** MoE-as-dense-GEMM (DENSEGEMM) is "NVIDIA Blackwell only — SM100/SM103"; the trtllm MoE backend refuses SM120 **by design**. Consumer sm_120 is served by the separate TensorRT-RTX line (banked). **No wgmma fallback exists on sm_120 either** — sm_120 kernels are mma.sync (Ampere-lineage) + optional TMA/PDL/CLC (Colfax, below).
- **Measured M-sweep (B200 TP8, DeepSeek-V3 shape: 256 experts, top-8, hidden 7168, NVFP4):** DENSEGEMM-vs-grouped per-MoE-module latency: **M=1: 0.18× (grouped 5.5× faster), M=8: 0.41× (grouped 2.4× faster), M=16: 0.60×, M=32: 0.81×, M=64: 1.01×, M=128: 1.12× (dense wins), crossover ~M=224-256, loses again ≥272.** Roofline: **memory-bound below M≈280-312; the dense path pays ~145 µs fixed loading ALL 256 experts' weights regardless of M.** This is the cleanest public confirmation that at our M (1-8 verify rows spread over ~4-10 experts), load-only-selected-experts is worth 2.4-5.5× over any dense transformation.
- **Measured per-mechanism price list at decode** (blog1, B200, DeepSeek-R1, 67→368 TPS/user progression, each step measured): multi-stream shared/sparse-expert overlap **+9%**; MLA kernel optimization **+9.6%**; TopK kernel **+5%**; Fuse_A_GEMM (gates+up fused — shipped specifically because it wins **when num_tokens < 16**) **+6%**; MTP3 **+76%**; PDL **+3%** (168→173); RMSNorm fusion + multi-stream **+7%**; CUTLASS grouped-GEMM optimization **+12%**; sparse-experts-as-GEMMs **+5.5%**; Fuse_A_GEMM+Router_GEMM **+13.7%**; vboost clock lock **+2.8%**. Router-GEMM fusion "improves when num_tokens ≤ 30". CUDA graphs were in the BASELINE (not a line item).
- Grade: measured-public on sm_100 (B200) + transfer argument (the M-regime physics are identical; sm_120 lacks only the tcgen05 throughput multiplier, which is irrelevant when memory-bound). **Verdict: the small-M table TRANSFERS verbatim; the tcgen05 machinery does not exist for us.**

### 2.5 CUTLASS 4.x sm_120 grouped GEMM — builders exist, tuned only down to M-tile 32

Provenance: https://raw.githubusercontent.com/NVIDIA/cutlass/main/CHANGELOG.md (fetched); Colfax NVFP4 sm12x tutorial https://research.colfax-intl.com/cutlass-tutorial-nvfp4-blockscaled-gemm-on-nvidia-rtx-pro-blackwell-gpus-sm12x/ (fetched).

- **What exists for sm_120 (by version):** 3.9.0 — blockscaled dense+sparse collective mainloops (`sm120_blockscaled_mma_tma.hpp`), NVFP4 grouped GEMM example 79d, full EVT epilogues; 4.0 — SM120 blockwise dense GEMM; 4.2.0 — example 92 MoE low-latency grouped GEMM is **SM100-only**, CLC-scheduler memory-fence fix in the SM120 pingpong kernel; 4.4.2 — SM120f NVFP4/MX grouped GEMM exposed in the profiler; 4.5.0 — **128×32×K and 128×64×K tiles for SM120 blockscaled builders (+30% on SM121 kernels)**; 4.6.0 — **ptr-array TMA collective for FP8 grouped GEMM on SM120/121 (`MainloopSm120ArrayTmaWarpSpecialized`, MoE expert-dispatch use case) + tileN=8/16 for SM120 blockscale kernels**; 4.8.0 — Operator API `cutlass.kernels`.
- **The sm_120 programming model, confirmed by the Colfax tutorial (RTX PRO 6000 Server, CUDA 13.2):** warp-level `mma.sync` from registers; **NO tcgen05/TMEM**; available: TMA, PDL, **CLC (Cluster Launch Control) persistent scheduling** — the sm_120 substitute for cluster-based persistent schedulers — and warp-group register re-allocation on sm120a/sm120f. Their kernel: CTA tile 128×128×128, NVFP4 MMA atom 16×8×64, 256 threads; reaches ~60% of FP4 peak at large square shapes; **grouped GEMM and M≤16 are not covered or measured**; the 2k×2k case loses to wave quantization (256 CTAs over 188 SMs).
- **Small-M reality:** smallest M-tile shipped is 32; tileN 8/16 exist but no tileM 8/16. At M≤8 an M-tile of 32 pads ≥4× — harmless for bandwidth-bound weights, but it means CUTLASS builders are not where a tiny-M decode kernel comes from; the Marlin / FlashInfer-W4A16 / Triton-BLOCK_M=16 class owns that regime (2.3).
- Grade: measured-public existence on sm_120 (changelog + tutorial); **no public tiny-M measurements**. **Verdict: correct tool for a FUTURE fp8/NVFP4 grouped path at M≥32 (never our decode shape); for M≤8 use the GEMV/persistent class. Pin ≥4.6.0.**

### 2.6 Mechanisms, priced individually for the decode loop

- **PDL (programmatic dependent launch).** Measured e2e +3% as one step of the B200 latency campaign (blog1: 168→173 TPS); LMSYS Ling-3.0-flash on Blackwell chained it across six kernels with producer-independent load hoisting and proved bitwise-neutrality (banked, sm_120-class evidence); llama.cpp's all-kernels PDL PR was rejected as marginal (banked counter). **Combo-only verdict stands: PDL on the 5-6 hottest dependent pairs + hoisted weight/KV loads; never alone.** sm_120 supports PDL (Colfax).
- **cp.async.bulk / TMA for weight streaming from pinned host memory — DEAD on mechanism.** PTX `cp.async.bulk` operands are the `global`/`shared::cta`/`shared::cluster` state spaces only; **host/system memory is not an operand state space** — pinned memory is reachable only as mapped zero-copy through generic addressing, with no TMA-engine benefit over plain loads (PTX ISA / CCCL cp_async_bulk docs; CUDA guide §async-copies; NVIDIA forum — all via search, 2026-11-05). TMA's engine drives GDDR streams. On our rig the routed-expert lane is the CPU reading DRAM anyway — a GPU load instruction cannot accelerate CPU DRAM reads. Double mismatch; do not revisit.
- **TMA multicast — DEAD on sm_120.** Multicast requires CTA clusters (SonicMoE's B300 design is explicitly "2CTA MMA with TMA-multicast B tiles", https://tridao.me/blog/2026/sonicmoe-blackwell, fetched); sm_120 has no clusters (banked; Colfax documents CLC as the replacement, not clusters).
- **Cluster launch for small tiles — DEAD** (no clusters; same source line as above).
- **CLC persistent scheduling — the live sm_120 replacement.** Available on sm_12x (Colfax); FlashInfer's SM12x W4A16 path ships "persistent launches" (v0.6.17). This is the mechanism behind our queued persistent GDN megakernel / FlashInfer-style persistent MoE tier kernel. No standalone public number; graded via its shipping host kernels (1.36× W4A16 result).
- **L2 persistence (`cudaAccessPolicyWindow`).** **No public LLM-decode measurement exists** (search 2026-11-05: NVIDIA docs + Lei Mao walkthrough + Veitner 2025 + PyTorch #101489). Veitner's measured finding: persistence pays only when streaming and persistent data actively compete for L2; PyTorch saw no measurable gain on A6000. Our 5090 has **96 MB L2** (TechPowerUp GB202 spec) and Qwen has a measured **93.5% expert-hit concentration** — the mechanism plausibly fits (pin top hot-expert weight ranges while expert GEMV streams past), but this is **speculation grade with a cheap counter-gated falsifier**.
- **`__ldg` / L2 policy hints (`createpolicy`).** No public decode numbers found; at most noise-level on bandwidth-bound GEMV where every byte is read once. SKIP unless a reuse-measurement shows otherwise.

### 2.7 Weight-format interaction: dequant-on-the-fly vs pre-dequanted hot copies

- **At decode M-regimes everything is memory-bound, so bpw IS the currency:** TRT-LLM blog24 roofline — memory-bound below M≈280, crossover M≈336 (measured); the 145 µs fixed all-expert load at M≤32 (measured); SonicMoE's arithmetic-intensity analysis for fine-grained MoE (memory-bound regime, fetched).
- **At equal bpw, kernel quality dominates: 1.8×** (Marlin-AWQ vs GPTQ paths, #36095, measured on 5090s) and **1.36×** (FlashInfer W4A16 vs Marlin at 1 token, measured sm_121). At unequal bpw, fewer bytes wins even against faster silicon paths: **Marlin W4A16 beat NVFP4-CUTLASS on a PRO 6000 rig** (50.5 vs 26-41 t/s, #2577 measured).
- **For OUR two surfaces:** (a) dsv41 host lane at the 46-50 GB/s ceiling — an FP8 pre-dequanted hot copy of 1.75-2.31 bpw experts is **2.3-4.6× more bytes**; strictly DEAD (this is the banked shadow-quant falsification, now with the mechanism priced from the production roofline). (b) Qwen VRAM tier at 1.79 TB/s — IQ3_S dequant-on-the-fly already reads 2.3× fewer bytes than an FP8 copy; the tier GEMV is latency/launch-shaped at M≤8, not compute-bound, so pre-dequant buys nothing and costs VRAM against the slot economy. DEAD both surfaces. The only pre-dequant that ever pays is at M≥~300 (TRT-LLM crossover) — a regime we never enter.
- The FP4 nuance worth banking: NVFP4 (4.25 bpw effective) is **more** bytes than IQ3_S (~3.44 bpw) — the FP4 tensor-core path is not a byte win for this box anywhere; its only legitimate role is where TC throughput matters (never at M≤8, where even Marlin's cuda-core path is at bandwidth).

## 3. Ranked shortlist for THIS rig

Ranked by expected effect × (1/cost) × risk-adjustment. Lane terms (46-50 GB/s dsv41; qwen shadow-tier DRAM) are untouched by every item — all effects land on the GPU term, glue, or slack. Adoption bar stays ≥+4% average with a named falsifier, interleave protocol, cross-engine change order.

**1. FP8 KV cache for dsv41 MLA, FlashMLA-layout (per-32-group e8m0 scales, in-kernel dequant), MQA-mode verify rows.**
- Expected on our terms: attention GPU term 5.4 ms at 262K scales with KV bytes; 528 vs 1152 B/token ≈ 2.2× byte cut → attention → ~2.8-3.4 ms → **dsv41 round 16 ms → ~13.8-14.4 ms = +11-16% t/s** (banks ~52 → ~58-60 t/s class). Lane GB/s unchanged.
- Kernel shape: keep the existing paged table; store per-token 512-dim e4m3 + 16×e8m0 (scale every 32 values) inline in the KV record (FlashMLA V4.1 layout); dequant inside the attention kernel after the LDG; verify rows as one MQA pass (MTP semantics); keep block sizes multiple of 64 (TRT-LLM MQA-kernel constraint); attention math BF16 accumulate, KV path FP8.
- nvcc-13.2 risk register R1/R2 apply: golden parity + acceptance canary (M3b) before adoption; verify `cvt.rn.bf16x2`-class conversion emission with cuobjdump on the first build (FlashMLA itself flags 13.2 as the recommended floor — we meet it; verify, don't assume).
- Falsifier: DS4_ATTN_SPLIT telemetry attention-ms at 262K must drop ≥25% with acceptance unchanged; long-context quality spot-check at 262K before/after. If the attention term does not move ≥25%, the term was not KV-byte-bound → kill and bank.

**2. Glue-fusion pass + PDL combo on the hottest dependent pairs (both engines).**
- Expected: qwen — fuse 10-14 of the ~48 doorbell round-trips (router/accept/sampling/combine microkernels; LMSYS census: glue ≈ GEMM time) + PDL-chain 5-6 pairs → window 14 → 12.5-13 ms → **+8-13% on all three qwen banks (232/222/315 → ~253-265 / ~243-254 / ~345-356 class)**. dsv41 — the 25% attention launch tax: blog1's PDL step alone was +3%; with Fuse_A_GEMM-class fusions (their gate+up fusion ships precisely because it wins at num_tokens<16) expect **+4-8% dsv41 round**.
- Kernel shape: no new tiles — fuse adjacent elementwise/reduction pairs into the producer kernel epilogues; PDL with `cudaGridDependencySynchronize()` before consumption and producer-independent loads (gate weights, KV prefetch) hoisted above the wait; `launch_dependents` early-trigger gated to decode shapes (LMSYS gated M≤512; our M is 1-8, always inside the gate).
- nvcc-13.2 risk register R3: PDL intrinsics are stable since 12.0-class toolchains; still A/A-verify bitwise neutrality per pair (LMSYS proved it is achievable; make it the gate).
- Falsifier: WSTAT doorbell-count telemetry must show the round-trip drop; interleave 3v3 with kill line <+4% any lane; revert per-pair.

**3. sm_120 small-M tier-GEMV shape discipline (qwen VRAM expert tier) — profile-gated.**
- Expected: qwen tier GEMV is MMVQ-lineage; if profiling shows <70% of the 1.79 TB/s roofline during tier reads, retuning to the measured sm_120 small-M shape class buys **+2-5% window**; if ≥85% roofline, DEAD — bank the profile.
- Kernel shape (from 2.3 measured configs): `BLOCK_M=16` floor (never 8), `BLOCK_N=32-64`, `BLOCK_K=64`, `GROUP_M=1`, `num_warps=4`, `num_stages=3-4` at M≤8; or adopt the FlashInfer W4A16-class design: persistent CLC-scheduled kernel, shape-stable route packing so batch 1-8 changes never recompile, tensor-core decode path optional at M≥16. Dequant stays on-the-fly (2.7). Tune the FULL batch curve 1→12 in one pass (the −11.2% bs=32 regression in #48732 is the same trap as our incline law).
- nvcc-13.2 risk register R4/R5: any Triton-generated path pins triton ≥3.6 (sm_120 MLIR crash class); any new intrinsic path gets the banked nvcc-13.2 verify step (compile, cuobjdump-inspect, golden parity).
- Falsifier: the profile itself (achieved GB/s of tier GEMV during a 6-row conc window) decides before any code; then interleave with kill line.

**4. Conditional-node round-graph for dsv41 (banked queued item — this round adds the vendor price list).**
- Expected: +8-10% dsv41 round (banked pricing; graphs touch slack + 3 host syncs, never the lane). New supporting evidence: TRT-LLM ships CUDA graphs in the decode BASELINE plus a separate captured fast-path graph for short sequences (blog15); their entire 5.5× campaign assumed graphs as ground truth.
- Kernel shape: layer WHILE-loop + eos-exit + per-round retry as conditional nodes; keep cooperative groups out of node bodies (doc restriction); bounded memory-pool threshold alongside (banked).
- Falsifier: unchanged from banked entry (slack telemetry; 3-sync count per round).

**5. L2 persistence pilot for qwen hot experts — speculation grade, one afternoon, counter-gated.**
- Expected: +1-3% qwen window GPU term at best; plausibly zero (PyTorch null precedent).
- Kernel shape: `cudaAccessPolicyWindow` on the top-K hot expert weight ranges (hitRatio 0.3-0.5, set-aside ≤32 MB of the 96 MB — never more, KV and tier streams must keep streaming room per the Veitner competition condition); env-gated, revert = unset.
- Falsifier: L2 hit/miss counters during conc windows, ON vs OFF, plus interleave; zero delta closes the line permanently.

**6. NVFP4 KV for dsv41 as the follow-on to #1 (288 B/token FlashMLA FP4 layout; FlashInfer cake ships it on 5090 silicon since v0.7.2).**
- Expected: additional ~−0.8-1.2 ms attention → ~+5-7% dsv41 round on top of #1. Only after #1 lands; quality recalibration at 262K is the gate; scale-dtype law (R2) mandatory.

Banked rows now provenance-complete, not re-ranked: ragged-Q per-row verify (FlashInfer XQA SM120 v0.6.16 + per-T captured graphs); W4A16 re-bake of GPU-resident dense weights (Marlin sm_120 works since vLLM v0.12; quality-gated class — dsv41 shared-expert Q5_K re-bake priced quality-traded in T56, same gate applies).

## 4. What NOT to do (falsified + killed this round)

Standing falsifications — never re-propose: W12 GDN_SPLIT gfx-derived splits; SMT lane threads (−20%); TF32/TC_QT scorers; DS4_AHEAD prefetch (−8.4%); fine-grained expert routing; PDL ALONE (combo form only); tcgen05/FA4 on sm_120 (absent); tree-verify topk>1 (lane cost dominates); gate-mass adaptive-k on DS (top-4 routing measured FLAT); hugepages; shadow-quant FP8 hot copies (2.3-4.6× more bytes at the proven ceiling); Machete W4A8 (wgmma-only, and sm_120 has no wgmma); CPU attention on this box (eats the lane).

Killed THIS round with sources — do not re-propose without a re-open condition:

- **DeepGEMM (port or borrow)** — sm_90/sm_100 only; both paths (wgmma, tcgen05) absent on sm_120; no public M≤64 measurements; port = MMA-layer rewrite. Re-open condition: DeepGEMM ships an mma.sync sm_120 backend.
- **FlashMLA as code** — SM100/103 only, Hopper dropped, decode requires FP8/FP4 KV. Re-open condition: same as above. (Its layouts are the thing to copy — see shortlist #1.)
- **TRT-LLM MoE backend / DENSEGEMM on sm_120** — unsupported by design (`BackendSupportedError`); measured 5.5×/2.4× SLOWER than grouped at M=1/8 even on its home silicon.
- **TMA multicast / cluster launch** — no CTA clusters on sm_120 (CLC is the substitute).
- **cp.async.bulk/TMA from pinned host memory** — no sysmem state space in the instruction; plus the lane is CPU-side on this box.
- **NVFP4 MoE as the sm_120 speed path** — measured losing to Marlin W4A16 on PRO 6000 rigs; silent-corruption history (R2); more bytes than IQ3_S on every surface we own. Shelf variant only, quality-gated, never byte-justified.
- **Small-key-only Triton/shape retunes** — measured −11.2% off-key regression (#48732); full batch curve or nothing (our incline law, independently rediscovered).
- **CUTLASS sm_120 builders as a tiny-M decode kernel source** — smallest M-tile 32, no tiny-M tuning, TMA-WS smem configs assume B200 (228 KiB vs our 99 KiB — production init failures). Legitimate only for a future M≥32 FP8 grouped path (prefill-side), pinned ≥4.6.0.

## nvcc-13.2 risk register (standing entries for every kernel touched above)

- **R1 — smem cliff:** any collective/kernel ported from SM100-class code must assert shared-mem ≤99 KiB at compile time; production TMA-WS grouped-GEMM init failures on SM120 exist precisely from this (FlashInfer #2577 → TRT-LLM #11368).
- **R2 — scale-dtype silent corruption:** FP8/FP4 scale factors must be asserted float32 (or the exact packed UE8M0/e8m0 layout) at the API boundary; the FP4 garbage-output incident shipped silently for months (PR #3497).
- **R3 — toolchain verification step:** every new intrinsic path (PDL griddepcontrol, cp.async.bulk if ever used GDDR-side, cvt.rn.bf16x2) gets: compile with 13.2 → cuobjdump/ptxas verbose inspection → golden parity → A/A interleave. Banked law: nvcc 13.2 has miscompiled new intrinsic paths for us before.
- **R4 — arch-suffix behavior:** sm_120a-only features (warp-group register re-allocation) require `-arch=sm_120a` emission — verify the flag actually reaches nvcc and parity-test A/A (banked trap: arch_defaults arms tables never consulted on CUDA builds).
- **R5 — grouped-shape benchmark noise:** masked/grouped GEMM measurements fluctuate up to ±20% with routing seeds (DeepGEMM #136) — interleave protocol is mandatory, single-boot numbers are rumors (law 1).
