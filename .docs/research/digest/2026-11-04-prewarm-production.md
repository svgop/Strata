# Prewarm as a server-start feature — production digest

Question: how do production stacks implement warmup as a first-class boot feature? Per system: (a) what is warmed, (b) readiness ordering, (c) config surface, (d) failure policy, (e) keep-warm/idle, (f) bypass + cost accounting. Strata context: Qwen lane boots a 41.63 GiB complement pin that drops the page cache (madvise DONTNEED) — page-cache warm must run AFTER pin; DS lane measures 16.6 tok/s cold vs 36.8 warm; 262k-ctx cold re-read costs 42.7 s.

## vLLM — warmup is an init stage, gated by a READY handshake

- Boot order (source, `vllm/v1/engine/core.py` EngineCore.__init__ → _initialize_kv_caches): model load → `get_kv_cache_specs()` → `determine_available_memory()` (memory-profiling dummy forward, `profile_run(randomize_inputs=...)`) → `initialize_from_config(kv_cache_configs)` (allocate KV cache) → `compile_or_warm_up_model()`. Comment: "Profiles the peak memory usage of the model to determine how much memory can be allocated for kv cache."
- `compile_or_warm_up_model` (source, `vllm/v1/worker/gpu_worker.py`): (1) `_dummy_run(size)` for each compile/warmup size not covered by capture sizes, largest first; (2) `kernel_warmup(self)` — kernel-level warm hook; (3) CUDA graph capture `capture_model()` inside `_get_cudagraph_capture_context()` (skipped when enforce-eager); (4) `_dummy_sampler_run(hidden_states)` sized to max_num_reqs×max_num_batched_tokens — "preallocate memory buffer for logits and other sampling related tensors of max possible shape to avoid memory fragmentation issue"; (5) `freeze_gc_heap()`. Returns `compilation_times` — the stack DOES account for warmup cost.
- Profiling bypass exists but is partial: preset `kv_cache_memory_bytes` logs "skipped memory profiling. This does not respect the gpu_memory_utilization config" — yet "a profile run still executes so the model compiles for max_num_batched_tokens". Memory-assert "Error in memory profiling." aborts init — failed warmup = server never READY.
- Readiness: EngineCoreProc performs a ZMQ handshake — sends HELLO, waits for init (HANDSHAKE_TIMEOUT_MINS = 5), sends `{"status": "READY"}`; `run_server_worker` nests `serve_http` INSIDE the engine context, so HTTP serves only after the full init (incl. capture + warmup) completes. `/health` (`vllm/entrypoints/serve/instrumentator/health.py`) is LIVENESS only: `await client.check_health()` → 200, or `EngineDeadError` → 503. There is no separate /ready — gating is structural (server can't be up before warmup finishes).
- DP note: `VLLM_RANDOMIZE_DP_DUMMY_INPUTS` + dp>1 → dummy inputs randomized so data-dependent branches are exercised during warmup.
- Keep-warm/idle: no idle unload. Sleep mode instead (`docs/features/sleep_mode.md`): `--enable-sleep-mode` (+ `VLLM_SERVER_DEV_MODE=1` for the endpoints); `POST /sleep?level=1` offloads weights to CPU and discards KV ("The content of KV cache is forgotten"), level 2 discards both; `POST /wake_up` restores "without full model reload", supports `tags=["weights"|"kv_cache"]`; `is_sleeping` true until all components awake. CUDA-graph memory "stays on the GPU while asleep" unless `sleep_mode_offload_cudagraph=True` — costs "about 3% decode latency at batch size 1"; NCCL comm buffers suspendable via `enable_nccl_comm_suspend=True` (needs NCCL 2.29.7+). `--sleep-preserve-parameter-names` keeps named weights (e.g. `'draft.*'`) through level-2 sleep — directly relevant to a drafter.
- Bypass: `--enforce-eager` (no capture, faster boot, slower decode); capture sizes trimmed via `compilation_config` (see [[w11-cold-scout]]: buckets, ~50 ms/graph, maintainer rejection of lazy capture).
- Grade: verified-from-source (gpu_worker.py, core.py, health.py raw) + docs.
- https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/v1/worker/gpu_worker.py ; https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/v1/engine/core.py ; https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/entrypoints/serve/instrumentator/health.py ; https://github.com/vllm-project/vllm/blob/main/docs/features/sleep_mode.md ; https://docs.vllm.ai/en/stable/design/cuda_graphs.html

## SGLang — the most literal "warmup before ready" server feature

- Default warmup request (source, `python/sglang/srt/entrypoints/http_server.py` `_wait_and_warmup` / `_execute_server_warmup`): poll `GET /model_info` up to 120× until 200, then send per DP rank a generation request with `"text": "The capital city of France is"`, `"max_new_tokens": 8`, `"temperature": 0` (VLMs: `/v1/chat/completions` with a base64 PNG + "Describe the image."; encoders: `/encode`). Warms tokenizer/detokenizer + full generate path end-to-end.
- Readiness machine: warmup thread is started in the FastAPI lifespan BEFORE uvicorn yields (port listening during warmup); `ServerStatus.Up` is set ONLY after warmup succeeds; then logs "The server is fired up and ready to roll!" and `_freeze_gc_after_server_warmup()`. `/ready` returns `tokenizer_manager.is_ready()`; `/health_generate` sends a real 1-token generation (`input_ids=[0]`, `max_new_tokens=1`, temp 0) with timeout `SGLANG_HEALTH_CHECK_TIMEOUT` (default 20 s) — a deep probe, vs plain `/health`.
- Failure policy: any warmup exception → `kill_process_tree(os.getpid())`. Poll timeout → kill_process_tree. Hard fail-closed boot.
- Config surface: `--skip-server-warmup` (default False; "If set, skip warmup"); `--warmups` (default None): "Specify custom warmup functions (csv) to run before server starts ... will run the functions warmup_name1 and warmup_name2 specified in warmup.py". The registry (source, `python/sglang/srt/entrypoints/warmup.py`) is the best model of a declarative warmup spec: `whisper_autodetect` — silent WAV request with two `"regex"`-constrained samples to PRE-COMPILE xgrammar FSMs ("first compile takes ~15-20 s"); `voice_chat` — 511 random-token requests of growing length to "warm the fused_moe triton kernels"; `prefill_shapes` — power-of-2 prefill sizes 64→32K (+ page-aligned midpoints), max_new_tokens 1, temp 0, warms fused_moe + attention-extend kernels. Timeout envs: `SGLANG_WARMUP_TIMEOUT` (600 s; 1800 s for PD disaggregation).
- Diffusion CLI adds `--warmup-mode`: `off` | default (request priming) | `synthetic` (full synthetic server warmup) — a three-level warmup dial.
- Known warmup defects (cautionary): warmup thread requested `0.0.0.0` when host is 0.0.0.0 (issue #9814); dual-stack IPv6 broke start, workaround `--skip-server-warmup` (issue #18201). Warmup-by-self-HTTP couples readiness to socket/bind details — an in-process warmup avoids this class.
- Keep-warm/idle: none; RadixCache retains prefix KV indefinitely (prefix caching IS the keep-warm for shared prefixes). No idle unload.
- Capture phase (see [[w11-cold-scout]]): cuda-graph capture at boot before serving; breakable prefill graphs; torch.compile dominates prep time.
- Grade: verified-from-source (http_server.py, warmup.py raw; server_arguments docs).
- https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/entrypoints/http_server.py ; https://raw.githubusercontent.com/sgl-project/sglang/main/python/sglang/srt/entrypoints/warmup.py ; https://docs.sglang.io/advanced_features/server_arguments.html ; https://github.com/sgl-project/sglang/issues/9814 ; https://github.com/sgl-project/sglang/issues/18201 ; https://lmsysorg.mintlify.app/docs/sglang-diffusion/api/cli

## Triton Inference Server (+ TensorRT-LLM backend) — the canonical warmup-as-config schema

- Doc semantics (user_guide/model_configuration.html): "When the ModelWarmup property is defined in a model configuration, Triton will not show the model as being ready for inference until model warmup has completed." And: "The settings define a series of inference requests that Triton will create to warm-up each model instance. A model instance will be served only if it completes the requests successfully." Motivation: backend init "is deferred until the model receives its first inference request" — first requests are much slower. Warmup runs per model instance, once at load; config re-poll reloads re-run it ("it will cause Triton to be less responsive to model update").
- Exact schema (proto, `triton-inference-server/common/protobuf/model_config.proto`, message ModelWarmup): `name` (string, sample name used in logs), `batch_size` (uint32 >= 1; "If batch_size > 1, the 'inputs' ... will be duplicated to match the batch size"), `inputs` (map<string, Input> — "warmup meta data associated with every model input, including control tensors"), `count` (uint32, iterations; "Default value is 0 which indicates that this sample will be used only once"; sequence-model caveat documented). `Input`: `data_type`, `dims` ("not including the batch dimension"), and a oneof: `zero_data` (bool — "the value will not be checked, instead, zero data will be used as long as the field is set"), `random_data` (bool; STRING inputs fall back to zero_data), `input_data_file` (binary raw row-major file in a `warmup/` subdirectory of the model dir; TYPE_STRING elements = 4-byte length + bytes). Multiple `model_warmup [ {...}, {...} ]` entries = a warmup sequence.
- Failure policy — strongest in industry: QA test `qa/L0_warmup/test.sh` builds a `failing_infer` model with warmup and asserts the SERVER FAILS TO START (`run_server` expects PID 0 → "*** Expect fail to start ***"), with log "failed to run warmup sample 'zero sample': An Error Occurred;". Success logs: "is running warmup sample '<name>'" and "... for iteration N" for count>1.
- Cost accounting: the same QA test TIMES the first inference of warmup-on vs warmup-off models back to back — warmup cost is measured as a boot-time/first-inference delta, an explicit test fixture.
- TensorRT-LLM backend specifics: build-time layerwise kernel tuning + timing cache (`model.cache`) reuses autotune results across builds (see [[w11-cold-scout]]); runtime `cuda_graph_batch_sizes` capture runs warm-up iterations BEFORE capture — "kernel autotuning during CUDA graph warm-up". Triton model_warmup is the generic wrapper that fires these at load.
- Keep-warm/idle: models stay loaded; `--model-control-mode` explicit/poll governs reloads; no idle unload concept.
- Bypass: simply don't define `model_warmup` — "By default, no model warmup is done"; "the effect of warming up models varies depending on the framework backend".
- Grade: verified-from-source (proto raw + docs + QA test.sh raw).
- https://raw.githubusercontent.com/triton-inference-server/common/main/protobuf/model_config.proto ; https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/model_configuration.html ; https://raw.githubusercontent.com/triton-inference-server/server/main/qa/L0_warmup/test.sh

## llama.cpp llama-server — one dummy decode, default-on

- What runs (source, `common/common.cpp` `common_init_from_params`, `if (params.warmup)`): decode BOS+EOS (falls back to token 0 "some models (e.g. T5) don't have a BOS token"), truncated to `n_batch`; encoder models encode + decode one decoder-start token; batch via `common_batch_get_one`, with zero-filled dummy embeddings/states (`common_batch_set_zero_state`). Then: `llama_memory_clear(llama_get_memory(lctx), true); llama_synchronize(lctx); llama_perf_context_reset(lctx);` and samplers reset "to reset RNG state after warmup to the seeded state". Log: "warming up the model with an empty run - please wait ... (--no-warmup to disable)". Effect: every weight tensor touched once (DRAM/NVMe pages + CUDA buffers), one full eager compute pass.
- MoE caveat — our exact hazard: issue #11163 — warmup "didn't work for MoE models": dense tensors warmed into OS cache, expert tensors NOT touched by the tiny decode. A 1-8 token warmup does not visit a 512-expert tier.
- Readiness: HTTP listener starts BEFORE model load finishes (serves /health during load), then load runs, then `is_ready.store(true)` — inference stays 503 until load+warmup done. Blocking gate, structurally.
- Config: `--warmup`/`--no-warmup` (default enabled); no count control — "it's always 0 or 1" (discussion #19713 proposes `--warmup-count`, not implemented).
- Failure: warmup OOM possible on memory-maxed boxes (community reports; `--no-warmup` is the escape). No dedicated failed-warmup state.
- Keep-warm/idle: none — weights stay mapped; the OS page cache is the residency policy.
- Grade: verified-from-source (common.cpp raw) + issues.
- https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.cpp ; https://manpages.debian.org/unstable/llama.cpp-tools/llama-server.1.en.html ; https://github.com/ggml-org/llama.cpp/issues/11163 ; https://github.com/ggml-org/llama.cpp/discussions/19713

## Ollama — keep_alive is the whole keep-warm contract; warmup inherited from llama-server

- Current architecture: "runner: Remove CGO engines, use llama-server exclusively for GGML models (#16031)" (commit 9db4bdba) — Ollama now drives llama.cpp's `llama-server`, whose `--warmup` (default ON) performs the dummy decode above. The historical Go runner had NO warmup of its own (verified: zero "warmup" matches in `llama/runner/runner.go` @ v0.5.7).
- Load path: model loads synchronously on demand — an empty generate/chat request loads ("If an empty prompt is provided, the model will be loaded into memory", done_reason "load"); FAQ: "you can preload a model by sending the Ollama server an empty request" / `ollama run model ""`. First real request after load pays context allocation + any first-call JIT the underlying runtime still owes.
- Keep-warm/idle (docs.ollama.com/faq + docs/api.md): keep_alive default "5m"; per-request values: duration ("10m", "24h"), seconds, "any negative number which will keep the model loaded in memory (e.g. -1)", "'0' which will unload the model immediately after generating a response"; `OLLAMA_KEEP_ALIVE` env, request param overrides env; `ollama ps` shows UNTIL; `ollama stop` unloads; `OLLAMA_MAX_LOADED_MODELS` / `OLLAMA_NUM_PARALLEL` govern concurrency. This is the only clean production CONTRACT for idle residency.
- Reload cost after idle unload = full cold load; third-party measurement (secondary, unverified): ~11.4 s cold vs ~0.9 s warm first-token under default 5 m unload.
- Failure: load failures surface as request errors; server stays up.
- Grade: verified-from-source (commit, faq, api.md, v0.5.7 runner.go) + secondary for numbers.
- https://github.com/ollama/ollama/commit/9db4bdba ; https://docs.ollama.com/faq ; https://raw.githubusercontent.com/ollama/ollama/main/docs/api.md ; https://raw.githubusercontent.com/ollama/ollama/v0.5.7/llama/runner/runner.go ; https://dev.to/ji_ai/ollama-keepalive-my-model-reloaded-214-times-in-one-day-il4

## LMDeploy — registry-driven kernel warmup at engine init

- PyTorch engine (source, `lmdeploy/pytorch/engine/executor/base.py` ExecutorBase.init()): build model → build GraphRunner ("Building GraphRunner and warmup ops") → build cache engine → `logger.info('Warming up model.')` → `self.warmup()`. `misc_config.empty_init` short-circuits: "Skip building KV cache and warming up model during empty init" — an explicit cold-boot escape hatch.
- WarmupManager (source, `lmdeploy/pytorch/backends/cuda/warmup_manager.py`): a singleton REGISTRY — kernels/op modules register callables via `manager[key] = func`; `warmup(WarmupMeta(max_num_tokens, max_batch_size, dtype, model_config))` runs all registered funcs in random order behind a rank-0 tqdm. Ops self-declare their warmup; the engine just fires the registry at init.
- TurboMind engine: no engine-level warmup found in `serve/core/async_engine.py`; docstring notes a manual constraint — "When using pytorch backend with dp > 1, all dp_rank should receive at least one request before it can start processing (warmup)".
- Readiness: api_server starts after engine build returns, so warmup is a boot gate; failure surfaces as init exception (server fails to start).
- Keep-warm/idle: none documented. Sleep/wakeup exists (`sleep()`, `wakeup(tags)`, `empty_init`) mirroring vLLM's shape.
- Grade: verified-from-source (executor/base.py, warmup_manager.py, async_engine.py raw).
- https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/engine/executor/base.py ; https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/pytorch/backends/cuda/warmup_manager.py ; https://raw.githubusercontent.com/InternLM/lmdeploy/main/lmdeploy/serve/core/async_engine.py

## MLC-LLM — verified negative: no server warmup feature

- Zero "warmup" in `serve/engine.py` and `serve/engine_base.py` (source). ## TorchServe / Ray Serve — load-gated readiness, no warmup primitive (TorchServe); init-chain gating (Ray)

- TorchServe has NO model warmup feature (source: configuration.md contains zero warmup mentions). Config surface: `model_store` + `load_models` (all | MAR files | names) to preload at start; `default_startup_timeout` bounds worker init — a worker exceeding it "is considered unresponsive and will be restarted". Readiness (`inference_api.html`): `/ping` returns 200 `"Healthy"` when "the number of active workers is equal or larger than the configured minWorkers", 500 unhealthy below it; worker states WORKER_STARTED / WORKER_MODEL_LOADED / WORKER_STOPPED; `maxRetryTimeoutInSec` (default 5 min) bounds dead-worker recovery. Project notice: "no longer actively maintained". Warmup here = preload-then-wait-for-minWorkers.
- Ray Serve LLM documents the full init chain it waits on before a replica takes traffic: node provisioning → image → "importing large libraries (such as vLLM)" → model load → "Torch compile ... enabled by default" → "vLLM runs some inference on the model to determine the amount of available memory it can dedicate to the KV cache" → "vLLM captures the CUDA graphs for different input sizes ahead of time" → Warmup: "Initialize KV cache, run model inference". Config levers are all load-side (`model_source`, `HF_HUB_ENABLE_HF_TRANSFER`, `load_format: runai_streamer[_sharded]`, compile `cache_dir` restore via CloudDownloader, CallbackBase init hooks); no explicit warmup knobs.
- Grade: verified-from-docs (both pages fetched); TorchServe config.md verified negative.

## The CUDA-level boot layer every stack walks

- Allocator pools: PyTorch's caching allocator holds freed blocks to "speed up memory allocations ... without device synchronizations"; `PYTORCH_CUDA_ALLOC_CONF backend:cudaMallocAsync` switches to CUDA's async allocator with its own pool; `expandable_segments:True` exists precisely because batch-size changes leave "unusable free slices ... this pattern might repeat 50+ times creating many slivers" — one growing segment fixes reuse. `garbage_collection_threshold` avoids "expensive sync-and-reclaim-all". First-iteration cost = pool growth via (slow) cudaMalloc; pre-sizing the pool at boot removes it. (docs.pytorch.org/docs/2.15/notes/cuda.html)
- Graph capture pre-warm: same doc — "Before capture, warm up the workload to be captured by running a few eager iterations", and graph allocations come from "a graph-private memory pool" reserved across replays. This is WHY capture happens after dummy runs in vLLM/LMDeploy/TensorRT-LLM.
- Driver JIT cache: fat-binary PTX is JIT-compiled by the driver at first kernel launch, cached on disk (`~/.nv/ComputeCache` on Linux) — `CUDA_CACHE_DISABLE` (default 0), `CUDA_CACHE_PATH`, `CUDA_CACHE_MAXSIZE` default 1 GiB (max 4 GiB) since CUDA 12.2 (was 256 MiB). A warm boot with a warm JIT cache skips first-launch compile stalls. (NVIDIA programming-guide env appendix + CUDA Pro Tip blog)
- Triton kernels + autotune: `@triton.autotune(configs, key=['M','N','K'])` — "an auto-tuning key whose change in values will trigger evaluation of all the provided configs" — i.e., every NEW shape key pays a benchmark sweep at first call; compiled kernels persist in the on-disk Triton cache (`TRITON_CACHE_DIR` knob, `python/triton/knobs.py`). SGLang's `prefill_shapes`/`voice_chat` warmups exist to trigger exactly these sweeps pre-traffic. (tutorial 03 + knobs.py)
- cuBLAS/cuDNN first-touch: handle creation + workspace allocation happen lazily on first GEMM/conv — covered implicitly by every stack's dummy run; vLLM exposes it as the explicit `kernel_warmup()` stage inside `compile_or_warm_up_model`.
- Grade: verified-from-docs/source (PyTorch notes, Triton tutorial/knobs, NVIDIA blog/docs).
- https://docs.pytorch.org/docs/2.15/notes/cuda.html ; https://triton-lang.org/main/getting-started/tutorials/03-matrix-multiplication.html ; https://raw.githubusercontent.com/triton-lang/triton/main/python/triton/knobs.py ; https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html ; https://developer.nvidia.com/blog/cuda-pro-tip-understand-fat-binaries-jit-caching

## Mechanisms that transfer to Strata — ranked by expected value

1. **Page-cache-bound decode (DS lane 16.6→36.8 tok/s; 42.7 s @ 262k re-read).** No production stack warms the page cache as a feature — because none of them evict it. Strata's complement pin (madvise DONTNEED) is the outlier that creates the need. Two validated shapes transfer: (a) llama.cpp's "touch every weight tensor once" dummy pass — but issue #11163 proves a tiny decode MISSES MoE expert tensors, so the warm must read the expert tier explicitly (our `dd`-to-/dev/null equivalent, in-process); (b) Ollama's keep_alive contract applied to the DS lane: don't evict what costs 42.7 s to re-read — a residency policy (`keep_alive: -1` analog) beats any re-warm. Rank: highest value; warm-after-pin ordering is a Strata-specific constraint no peer faces (vLLM's analogue is weights already resident after load; our pin runs after).
2. **Declarative warmup config schema.** Merge Triton's `model_warmup` (name, batch_size, count, inputs{zero|random|file}) with SGLang's `--warmups` named-function registry (xgrammar FSM pre-compile; growing-length MoE-kernel sweeps; power-of-2 prefill ladder 64→32K). For Strata: config = list of named warmup specs — {prompt chunk, full-window prefill, one decode, one spec/dspark draft step} — each with payload source and repeat count, engine-tagged (qwen|ds). Triton's `input_data_file` maps to feeding real-shaped tensors to the drafter; `count` covers the multi-step spec chain.
3. **Readiness state machine.** Convergent industry design: HTTP listens EARLY (SGLang lifespan thread, llama.cpp pre-load listener, TorchServe ping-during-load), a distinct `/ready` flips only after warmup completes (SGLang `ServerStatus.Up`, Triton "not ready until warmup completed"), `/health` stays LIVENESS-only (vLLM check_health → 503 on dead; SGLang `/health_generate` as the deep probe with a timeout). Adopt exactly this split: `/ready` = warmup-gated, `/health` = cheap liveness, and make the ready payload carry per-stage warmup timings — vLLM already returns `compilation_times`; Triton's QA test times warmup-vs-off; no stack exposes timings over HTTP yet (cheap differentiator for boot QC).
4. **Failure policy: fail-closed with an escape hatch.** Spectrum observed: Triton aborts the whole server on warmup failure (strongest); SGLang kill_process_tree on warmup exception or poll timeout; vLLM init exceptions mean never-READY; TorchServe restarts the worker with a timeout; llama.cpp/Ollama just expose --no-warmup. For a local single-tenant server: abort the lane's boot (exit non-zero) with per-stage timeout (SGLANG_WARMUP_TIMEOUT shape; PD default 1800 s suggests 3× base), plus `--skip-warmup` / `empty_init` (LMDeploy's exact flag name) as the escape.
5. **Lazy graph captures.** vLLM's verdict stands ([[w11-cold-scout]]): capture at boot inside the warmup stage, never lazily at request time — RFC #20098 died to a maintainer "strong no" (OOM unpredictability + perf dips). LMDeploy's GraphRunner-build-before-warmup ordering and TensorRT-LLM's "warm-up iterations BEFORE capture" (autotuning during graph warm-up) define the micro-order: eager dummy → capture → verify.
6. **Keep-warm/idle for the two-lane swap.** vLLM sleep levels map cleanly onto Strata's park/promote: level 1 = weights to CPU, KV dropped, wake "without full model reload"; `tags=["weights","kv_cache"]` partial wake; `--sleep-preserve-parameter-names 'draft.*'` preserves a drafter through level-2 sleep; keeping CUDA graphs resident during sleep costs "about 3% decode latency at bs=1" — quantified trade for our idle-swap storm (96 swaps/round, [[w11-cold-scout]]). Ollama's keep_alive default-5m/-1/0 + per-request override is the UX contract to copy.
7. **MoE-specific warmup coverage is a peer-proven requirement.** SGLang ships growing-length fused_moe sweeps and a prefill-shape ladder BECAUSE first-call autotune + lazy kernels hit MoE hardest; llama.cpp's warmup missed experts entirely. Strata's in-engine warmup must visit ≥ top-k experts across the shape ladder, not one decode step.
8. **CUDA-level boot hygiene** (lower rank: mostly free once warmup stage exists): eager dummy iterations before capture (PyTorch doc prescription), allocator pool pre-growth (expandable_segments for changing batch windows), Triton `TRITON_CACHE_DIR` + driver `CUDA_CACHE_*` JIT cache kept warm across reboots (re-run of the warmup stage hits the on-disk caches — second boot is cheap; measure the delta).
