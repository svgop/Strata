# Host-device latency architecture for the hybrid decode loop — evidence digest

Question: how do production and frontier systems remove the host↔device protocol class — doorbell round-trips, per-layer host syncs, per-turn payload re-ship — and what does each mechanism cost, who ships it, and does it fit sm_120/12 GB? Companion digest `2026-11-04-sm120-kernel-advances.md` owns graph-feature API maturity (conditional nodes TRANSFER, device-launch standalone DEAD, PDL combos, stream priorities DEAD); this digest extends the protocol/measurement half and does not re-litigate those verdicts.

## Measured per-round-trip cost floor (the currency everything is priced in)

- Kernel launch submission: 1.8-1.9 µs CPU-side for a length-1 graph/launch; a 2000-kernel graph costs 209 µs under CUDA 11.8 (multiple doorbell writes, submission cycles alternate host-RAM push and remote GPU-memory TLP writes) vs **5.9 µs near-constant under CUDA 13.0 with always exactly ONE doorbell write**. Command-stream anatomy: pushbuffer (host RAM) + GPFIFO (GPU VRAM) + USERD GP_Put + doorbell MMIO register via BAR0 (https://arxiv.org/html/2604.26889v1 — reverse-engineered closed driver, CUDA 11.8 vs 13.0 chain graphs of 1-2000 kernels). This is the amortization proof: one graph replay = one doorbell, so 48 per-layer doorbells collapse to 1 by putting the loop inside the graph.
- Bare cudaLaunchKernel: 3-7 µs (https://arxiv.org/html/2604.17861v1); ~5 µs wave-of-null-kernels methodology (https://forums.developer.nvidia.com/t/any-way-to-measure-the-latency-of-a-kernel-launch/221413); ~10 µs per launch folk number incl. API path (https://modal.com/gpu-glossary/perf/overhead); overhead decomposition CPU-side vs device-side (https://www.hpcs.cs.tsukuba.ac.jp/icpp2019/data/posters/Poster17-moc.pdf).
- Doorbell round-trip visibility on PCIe5-class parts: spin-kernel polling a mapped pinned flag with `__ldcg` + `__nanosleep(100)` measures a **~1-2 µs poll round trip** (https://arxiv.org/html/2512.16056v2 — PCIe5 x16 host-GPU study, RTX-class parts). Small cudaMemcpyAsync fixed overhead is a different, larger beast: ~35 µs (70 µs display-attached) measured on the classic forum thread (https://forums.developer.nvidia.com/t/pci-express-latency-and-how-to-decrease-it/20629); pinned-flag direct read/write avoids the cudaMemcpy API path entirely.
- Copy-engine facts from the driver study: inline DMA via compute engine ~24 ns startup, saturates ~17.5 GiB/s, rejected above ~31 KiB; copy-engine DMA ~500 ns startup saturating ~1 MiB (https://arxiv.org/html/2604.26889v1). A per-layer 4-8 byte doorbell via memop write, not via memcpy, is the right primitive.
- Pricing Engine A: 48 RTs × (1-2 µs PCIe visibility + ~2-7 µs launch submission + host-loop gap, serialized with draft launch/finish) ≈ **0.5-2 ms pure protocol cost per 9-16 ms window** before counting parse/format of ~0.6-1.5 MB text ids. Engine B: 3 syncs/round sit in the ~4 ms slack; removing their host-side cost attacks slack, never the 7.3 ms lane.

## 1. Device-driven orchestration (graph contains the layer loop)

- Mechanism (carried from companion digest, extended): conditional nodes (CUDA 12.8 IF/ELSE/SWITCH/WHILE, https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes) put the per-layer loop and eos/accept early-exit inside one replay; device graph launch (`cudaGraphInstantiateFlagDeviceLaunch`, CUDA 12.0+, https://developer.nvidia.com/blog/enabling-dynamic-control-flow-in-cuda-graphs-with-device-graph-launch) reports device-side launch latency "more than 2x lower than host launch" and constant across topology; constraint: one pending launch + one self-relaunch (tail-launch) at a time.
- NEW production evidence (who ships it): still **no public inference engine** ships conditional nodes or device launch — vLLM/TRT-LLM/SGLang use torch-style whole-capture graphs; closest 2026 artifact is xMIx (arXiv 2607.22595), a vLLM serving-time intervention platform whose device-computed predicate gates nested execution "conceptually aligned with CUDA conditional nodes", integrated with vLLM continuous batching + graph capture at **+1.3% mean ITL / +2.6% TTFT overhead** vs +510% ITL for eager-hook baseline (https://arxiv.org/html/2607.22595v1). Adopters remain HPC/graphics; ROCm parity still open.
- NEW driver-level evidence for why the loop-in-graph form wins on CUDA 13.x: single-doorbell submission (see cost floor above) — the whole verify window becomes 1 doorbell + 5.9 µs submission regardless of layer count.
- Capture limits, stated precisely: (a) stream capture bakes memcpy SIZE — variable-size H2D cannot be replayed at a different length; update the node via `cudaGraphExecMemcpyNodeSetParams` or capture max size and let a device scalar carry the true count (https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html). (b) capture permits only copies involving device or pinned device-mapped memory; pinned-memory ALLOCATION APIs remain forbidden in all capture modes (https://docs.nvidia.com/dl-cuda-graph/cuda-graph-basics/constraints.html). (c) a pinned RING read by kernels through its device mapping is the compatible pattern — allocation happens outside capture, the ring pointer is baked, contents flow (GPUOS ships exactly this; https://arxiv.org/html/2604.17861v1).
- 12 GB fit: graph metadata ~10 MB per captured graph (TRT-LLM measured; https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/blogs/tech_blog/blog20_Tuning_CUDA_Graph_Batch_Sizes_for_Higher_Output_Throughput.md — 49 graphs ≈ 260 MB, 259 graphs ≈ 2.6-4.9 GB, capture 10.8→25.9 s). Lazy per-cohort shape graphs are exactly the memory shape that eats the 1.2 GB headroom; ONE window-graph per cohort-family + param patching (§3) caps the count.
- Verdict: TRANSFER — highest-leverage item, Engine A first (48→1), Engine B second (3 syncs→0 host-side; the graph cannot touch the lane wait).

## 2. Command-ring protocols (device polls work; DPDK/NVMe completion model)

- Mechanism: persistent kernel (one block per SM) never exits; host writes 64-128 B descriptors into a lock-free SPSC ring in device-mapped memory, store-release on a commit field = doorbell; device warps load-acquire the cursor, claim atomically, dispatch via device function-pointer table, resume polling (https://arxiv.org/html/2604.17861v1 — GPUOS, UCSC/UW/Berkeley, open source https://github.com/Multi-V-VM/GPUOS).
- Measured: descriptor submission **<100 ns vs 3-7 µs per cudaLaunchKernel (30-70x)**; per-op 8→3.1 µs; attention decode per-token 140→16 µs; CUDA-graph comparison 6.2x on stable shapes degrading to 2.1x under shape variation while the ring stays consistent; **tested on RTX 5090 and GB10 (CUDA 13.0)** — consumer-Blackwell evidence, closest cousin to sm_120 in the literature; costs: ~2-4% of threads held resident, ring contention past ~64 producer threads, NVRTC/injection machinery.
- Maturity: research system, no production adopter; the production analog is the SGLang RFC replacing ZMQ host-side channels with bounded MPSC + "userspace rings carrying payload" (https://github.com/sgl-project/sglang/issues/23206) — elite stacks accept rings as the destination pattern, but on the HOST side for now.
- Grid-constant / kernel-parameter updates without relaunch: `cudaGraphExecKernelNodeSetParams` patches a node's args in-place on the instantiated exec ("minimal cost"; end-to-end 433 ms vs 580 ms recapture-then-update vs 706 ms no-graph on A100; https://developer.nvidia.com/blog/constructing-cuda-graphs-with-dynamic-parameters; guide: https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html). Device-side param-update APIs (kill the host copy entirely) are compiler-research stage (https://arxiv.org/html/2503.19779v2).
- Fit: the ring REPLACES the doorbell only if a persistent consumer exists; with graphs already covering the window, the ring's job shrinks to the boundary: command word + token ring in pinned memory consumed by the graph's first node, completion counter written by the last. sm_120: no tcgen05/clusters needed; 2-4% resident threads is affordable at 12 GB decode occupancy.
- Verdict: WATCH as a full persistent megakernel (no production shipper; conflicts with graph path), TRANSFER as the boundary ring (§4/§5).

## 3. Fixed-buffer graph discipline + per-token param patching (kill lazy recapture)

- Mechanism: llama.cpp (production, batch-1 default-on): reuse ONE instantiated graph; per-token KV-shift parameter changes are found node-wise and "manually replaced" before launch; structural growth recaptures only when needed; `cudaGraphExecUpdate` patches instead of re-instantiating (https://developer.nvidia.com/blog/optimizing-llama-cpp-ai-inference-with-cuda-graphs; merge at +5-18% token-gen https://www.reddit.com/r/LocalLLaMA/comments/1cnfkl3/cuda_graph_support_merged_into_llamacpp_5_18). NVIDIA engineering write-up confirms measured up to 1.2x on Llama-7B H100, graphs "restricted to batch size 1", residual bottleneck = CPU-side gaps (graph prep + sampling) between tokens.
- TRT-LLM counterpoint on graph-set bloat: padding to captured batch sizes wastes compute (gaps up to 1024 slots), denser sets cost 2.4x capture time and GBs of metadata (blog20 above). Lesson for 12 GB: few graphs + param patching, not many graphs.
- Fit: replaces Engine A's lazy per-cohort capture — shapes vary per verify window, but token-count variation is a scalar, not topology. sm_120: plain graph APIs, no version risk beyond 13.4 validation.
- Verdict: TRANSFER (pairs with §1; the two together are the "breakable graphs" queued item).

## 4. Completion paths (doorbell alternatives, ranked)

- Mapped pinned flag + host spin: ~1-2 µs RT measured; zero CUDA API calls in steady state (https://arxiv.org/html/2512.16056v2). The window's completion = one counter increment in pinned memory by the graph's last node; host reads it once per window. Cheapest per-event path. sm_120: universal.
- Stream memops: `cuStreamWriteValue32/WaitValue32` and `cuStreamBatchMemOp` enqueue wait/write/flush as stream items — doorbell semantics without a kernel launch; CUDA 13.1 adds 64-bit atomic reductions to batch ops (https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__MEMOP.html; https://docs.nvidia.com/cuda/archive/13.1.2/cuda-driver-api/group__CUDA__MEMOP.html; pattern write-ups: https://www.cudahandbook.com/book/ch6/stream-memory-operations; https://github.com/NVIDIA/cuda-python/issues/2364). Use BatchMemOp to emit N completion words in ONE host-visible call.
- cudaEventRecord/Query: ~1-10 µs per API call with driver overhead and yield jitter unless busy-poll; fine as a secondary tick, not per-layer (https://forums.developer.nvidia.com/t/overhead-of-cudaeventrecord-cudalaunchkernelexc-in-multithreading/300769).
- cudaLaunchHostFunc: callbacks run on a single driver worker thread, serialized across streams, OS-schedulable, no ordering guarantees — field-measured **12 ms tail** from callback-finish to stream-continue on A100/H100 with two streams (https://forums.developer.nvidia.com/t/culaunchhostfunc-overhead-latency-usage-cpu-gpu-signaling/327066). Never per-layer. Acceptable only as idle-wake: last-node host func → write(eventfd) → epoll, once per window/round, not per token.
- Stream priorities: DEAD for this box (companion digest; single latency stream).
- Batched completions: every elite engine reports per-STEP, never per-layer — SGLang emits one output batch per step with future-token resolution (https://www.lmsys.org/blog/2024-12-04-sglang-v0-4); TRT-LLM one graph result per IFB step; GPUOS one commit per descriptor. Engine A's 48 completions/window is the anti-pattern to delete.
- Verdict: TRANSFER — per-window mapped-flag counter + BatchMemOp doorbell; host-func demoted to idle wake only.

## 5. Serialization elimination at the boundary (the text-line protocol)

- vLLM V1 (production): isolated EngineCore loop; API↔core via ZMQ async IPC (https://docs.vllm.ai/en/latest/design/arch_overview); workers cache request state and receive only **incremental diffs**; Persistent Batch caches input tensors/metadata and applies per-step diffs with NumPy (credited to LMDeploy); goal stated as near-zero CPU overhead — motivated by GPU forward "as low as ~5 ms" on small models (https://developers.redhat.com/articles/2025/01/28/vllm-v1-a-major-upgrade-vllms-core-architecture). This is the exact "stop re-shipping state; ship deltas" protocol.
- Shared-memory rings (Python↔engine, production): `vllm.distributed.device_communicators.shm_broadcast.MessageQueue` — shared-memory ring buffer, writer broadcasts handle to readers, fixed chunk count (https://docs.vllm.ai/en/v0.11.2/api/vllm/distributed/device_communicators/shm_broadcast); newer single-writer/multi-reader ring object storage (https://docs.vllm.ai/en/stable/api/vllm/distributed/device_communicators/shm_object_storage). Known failure mode is a bound lesson: hardcoded `max_chunks=10` ring deadlocks when a reader stalls (https://github.com/vllm-project/vllm-ascend/issues/9405) — size the ring ≥ worst-case producer burst.
- SGLang (production): TokenizerManager↔Scheduler via ZMQ+msgpack; overlap scheduler runs the CPU scheduler one batch ahead and hides it inside GPU compute — Nsight shows no GPU idle over 5 consecutive decode steps; 1.1x end-to-end; motivating citation "unoptimized engine can spend as much as half its time on CPU overhead" (https://www.lmsys.org/blog/2024-12-04-sglang-v0-4). The stack's own RFC admits ZMQ is now the residual and proposes userspace rings (https://github.com/sgl-project/sglang/issues/23206).
- llama.cpp (production): single-process C++ engine — no per-step IPC at all; ids enter once per request, per-step deltas are one sampled token patched into graph params (§3). Binary wire protocol exists only for REMOTE backends: ggml RPC over TCP, structed opcode+buffer messages (https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md; wire-protocol internals dissected at https://retr0.blog/blog/llama-rpc-rce — note unauthenticated, RCE-history: treat as LAN-only design).
- Engine A fix, stated: pinned int32 ring (ids) + control struct (base offset, delta len, gen counter, draft/verify mode) + completion counter; per turn write ONLY new tokens (≤ kVerifyMaxT-scale, hundreds of bytes) + 8-16 B control; device-side zero-copy reads through the mapping; kill GEN/BGEN text framing entirely. Wire cost drops from ~0.6-1.5 MB + per-line parse to ~1 KB; the Python-side format/parse (ms-scale at 100K lines) disappears. Recovery estimate: ~0.1-1 ms per turn plus jitter variance removal; the biggest single win after §1.
- Verdict: TRANSFER — zero CUDA-version risk, pure protocol work, evidence-backed by three production stacks.
