## 0. Verification of the prior researcher's headline claim

- SpecPilot is REAL and matches the claim: arXiv 2611.02501, "SpecPilot: Autonomous Algorithm Discovery and Systems Optimization for Speculative Decoding", submitted 2026-11-02. UC Berkeley / Princeton / Stanford / NVIDIA. Code Apache-2.0 at https://github.com/StargazerX0/SpecPilot, project page https://stargazerx0.github.io/specpilot-project-page/, HTML full text https://arxiv.org/html/2611.02501v1.
- Claimed numbers verified verbatim: "raises the speedup over AR from stock's 4.46x to 10.87x with one request, and from 1.94x to 3.93x with batching" (abstract).
- Correction to the claim's framing: the headline 10.87x was measured on an RTX PRO 6000 Blackwell **96 GB** workstation card (sm_120, 1.51 TB/s measured), NOT a 12 GB consumer 5070. Target is Qwen3.8-27B, a dense-weight hybrid (GDN in 48 of 64 layers, attention elsewhere) in **BF16**, with 512-expert MoE layers NOT covered by their mechanisms (their W12 encode touches dense MLP, GDN in_proj, qkv_proj only — see §2a). Repo pins: torch 2.13 + CUDA 13.0, SGLang v0.5.20 frozen base, sm_120a-only kernels for the PRO 6000 finals. https://github.com/StargazerX0/SpecPilot (README.md:48-62, 203-204)
- Repo reproduces from fresh clone: 2.25x [2.18, 2.32] over stock on the flagship setting (README.md:70-76). The released artifact is six complete engines (stock tree + per-setting `files/` overlays), not just scripts.

## 1. SpecPilot framing and cost model (the part worth stealing regardless)

- Speedup model: `S(N) = tau(N) / c(N)`, `c(N) = T_step(N) / T_AR`; tau = tokens accepted verifying N rows. Ceiling per round = `(tau_best/tau) * (T_prof/T_floor) * (T_step/T_prof)` — tau factor (better tree), kernel factor (profiled time vs byte floors: max(FLOP time at 60% peak dense, byte time at 90% peak BW)), overhead factor (unprofiled time). Largest factor directs each round. (Paper §3.1, Eq. 3-4.)
- Measured gap facts that transfer to any engine: single-request GEMM time grew only 17.88→18.58 ms from 1→64 rows (weight-stream-dominated); weight reads = 80% of the 23.61 ms step after round 1; stock DFlash2 chain accepts tau=4.25 of an oracle 6.42@8-positions / 8.20@16-positions (exact replay on recorded lattices). With batching, stock speedup halves (FP8 27B: 3.40x@1 → 1.89x@24). (§3.1)
- Promotion rule: paired runs on two GPUs, promote only if gain's 95% lower bound > 1% + 2x stock-vs-stock noise (<0.1% single-request). Sealed final on unseen requests + token forcing (§3.2-3.3).
- Token forcing (losslessness test that task accuracy cannot replace): teacher-forced scorer feeds system outputs through the target on the stock engine, FP32 LM head. Mismatch = token differs from scorer argmax; margin = log-prob gap. Stock mismatches 0.72% of tokens (near-ties from kernel rounding; delta threshold set from AR-vs-stock first divergences, rounded up to 1/8). Reject rules: rate rule (+0.5 points at 95% conf) or event rule (binomial test on large-margin events, margin > 2*delta, unexplained by audit). Faulty system (logit bias 2 on every 7th vocab id after 2048 tokens) passes accuracy (-1.6 pts, CI overlaps lossless -0.3) but fails token forcing (2.0-2.4% vs 0.72%). (§3.3, §6.2, Fig. 2c/4)
- Relevance to us: this is a cheap, engine-agnostic quality gate — stronger than MMLU spot-checks for verify-path changes; we can implement the scorer against our own stock engine in an afternoon.

## 2. The four discovered mechanisms (paper §4 + code read)

### 2a. W12 — lossless 12-bit weight format (code: `settings/*/files/python/sglang/kernels/ops/gemm/specpilot_d5_w12.py` H100, `specpilot_d2_w12.py` sm_120)

Format (verified in `_encode_rows()`, d5_w12.py:1044-1080):
- Per output channel (row) n: pick the 16-binade window [E_n-15, E_n] covering the most weights (256-bin histogram via scatter_add + cumsum, ties → highest window; zeros/denormals always escape).
- In-window weight e = E_n-15+c, c in [0,15]: store sign(1) + c(4) + mantissa(7) = 12 bits, in TWO planes: low-byte plane `[c0 m6..m0]` (8 bits) + nibble plane `[s c3 c2 c1]` (4 bits) = 1.5 B/weight.
- Kernel reconstructs bf16 bits `[s 0111 c3c2c1 | c0 m6..m0]` and multiplies the fp32 accumulator by `scale[n] = 2^(E_n-127)` — the window trick makes the exponent free.
- Escapes (out-of-window, zeros, denormals): decode as placeholder 2^-15; a per-row CSR list (rp/col/val) corrects exactly in the GEMM: `acc += x*w_true - x*2^-15` (both products exact in fp32; encode asserts `n_inexact == 0` — d5_w12.py:1118-1124). Escape rate < 1.3e-4 of weights (App. E); max escapes in a row tracked.
- Load-time check: every encoded tensor decodes bit-for-bit against the checkpoint (`_check_roundtrip` → `torch.equal`), engine raises otherwise (d5_w12.py:1290-1327). 12.013-12.020 bits/weight across eight dense models, six families; Qwen3.8-27B converted layers 44.67→33.58 GB.

Nested 8-bit view (the TLV payload) — same file, `decode_n<QM>()` (d5_w12.py:177-202) and record layout comment (line 9-16):
- Per (128-row tile, 64-k chunk): a 12 KB record = Q region [8 warps][1 KB] (one byte per weight `[c0 m6 m5 m4 | s c3 c2 c1]`, wgmma-A-fragment lane order) + B region [8 warps][512 B] (`[m3..m0]` nibbles).
- Exact GEMM streams the whole 12 KB; the Q pass (`q_pass()` context manager + `_QPASS` global read at call time, so CUDA graphs captured inside the context replay the Q kernels — line 1236-1256) streams ONLY the Q regions: 1 B/weight, with the dropped mantissa bits set to their midpoint (`lo = (q & 0xF0F0F0F0) | 0x08080808`), and only escapes ABOVE the row window (|w~| >= 2) corrected exactly; below-window escapes keep the placeholder 1.0625*2^-15. Top-1 agreement with the exact pass: 98.7% of 104k teacher-forced positions (App. C, Table A5).
- Zero extra memory: the Q view is the first 8 KB of each 12 KB record. No second model copy.

GEMM kernel (the reason the format pays):
- Persistent stream-K, H100: wgmma m64nNTk16 bf16, A-operand decoded IN REGISTERS from the planes — `decode()` uses `(n*17 & 0x87) | 0x38` byte-splat + 2 `__byte_perm` + 1 `__byte_perm` per A register ≈ 3.3 ops/register (d5_w12.py:139-158); producer warp TMA (bulk 1-D for planes, 2-D SW128 for activations, 5-stage mbarrier ring); 2 escape warps (double-buffered smem corrections); deterministic split-K (contributors publish fp32 partials with red.release, k=0-segment owner reduces in segment order — bit-determinism for fixed P); fused SiLU(gate)*up epilogue; PDL (programmatic dependent launch, first ring stages issued before griddepcontrol.wait). sm_120 port (`specpilot_d2_w12.py:1-31`): NO wgmma on Blackwell consumer — 8 consumer warps decode straight into `mma.sync m16n8k16` A fragments, swap-AB (weight rows as M=16 side, tokens as N=8 via ldmatrix.x4), cp.async.bulk 12 KB records, 2-3 stage ring.
- Measured kernel wins: beats cuBLAS on every Qwen3.8-27B projection 1.19-1.47x at 1 row, 1.17-1.35x at 32 rows (H100); on PRO 6000 1.18-1.68x up to 32 rows, flat in rows while cuBLAS slows from 8 rows on (§6.3, App. E). W12 alone (no speculation) speeds AR decoding 1.19-1.28x@1, 1.13-1.20x@32; KV pool grows 2.0-2.5x from the freed memory.
- Certified LM head: INT8 copy with per-row Cauchy-Schwarz bound discards tokens that provably cannot be argmax; survivors rescored exactly in BF16; argmax never changes. 878→482 us on H100; on PRO 6000 slower than BF16 (2598 vs 1750 us) so W12 LM head used there (§4.1).
- Closed directions (App. F): 11-bit weights 3x slower decode; 7-bit nested Q view -3.8%; 6-bit -17.5% (each eighth of Q-view bytes removed costs ~0.01 top-1 agreement, "twice what the saved time bought back"); W12 GEMM bound by decode + SM issue rate, not bandwidth.

**Verdict for our engine:** the W12 FORMAT does not port. It is a lossless recode of BF16 at 12.01 bits. Our experts are IQ3_S-class (~3.x bits, lossy, already decoded): a "W12 view over IQ3_S packs" is a category error — W12 preserves bits the pack no longer has; re-encoding IQ3_S values into 12-bit records costs 3.4-4x the lane bytes at identical (3-bit) quality, on a CPU lane already at 93-100% of the DRAM ceiling. Hard no for the expert lane; also no for 12 GB VRAM (12-bit GPU-resident weights would blow the budget that IQ3_S tiers exist to protect). What ports: (i) the certified-argmax screen pattern for our LM head; (ii) the kernel pattern (decode-in-registers, deterministic split-K, PDL, escape-CSR) as a template for our activation-GEMV family; (iii) if we ever carry a BF16/FP8-resident subset (e.g., attention+GDN projections), W12-style 12-bit records for exactly that subset with the nested Q view is the only form of "12-bit view" that is coherent.

### 2b. Best-first tree verification on a hybrid GDN target (code: `specpilot_tree.py`, `specpilot_tree_gdn.py`, `specpilot_d8_gdn.py`)

Tree build (`specpilot_tree.py:1-115`):
- Replaces the drafter's single greedy selector walk with the best-first N-1 nodes chosen from the drafter's per-slot top-K candidate lattice, edge score = path-conditional `log_softmax(score[b, slot, parent_cand, :] / T)`; `SPECPILOT_D3M_CALIB=1` swaps in calibrated edge scores `(1-B) log p + B log q[slot, rank, bin]` from a constant precomputed table (`specpilot_d3m_calib_table.py`) without per-row renormalization.
- Layout: node 0 = root = previous bonus; parents precede children; siblings carry distinct tokens of one slot; "the verify width stays N = block_size, so every block-sized buffer of the engine (KV reservation, verify CUDA graph, GDN intermediate snapshots) is reused unchanged" — i.e., the tree costs ZERO extra verify rows vs the stock chain of the same block size.
- Paper: drafting 16 positions (twice trained block) into a 32-node tree, "more nodes than drafted positions" = wide tree; edge-scored-by-parent beats DDTree's marginal scores; on the same 8-position lattice best-first raises tau 4.25→5.38@32 nodes, →5.85@16-position draft, 6.25@63 nodes; at 16 nodes it matches EAGLE-2-style top-4 (5.03 vs 5.02) and beats Sequoia (4.71) (§6.4, Fig. 10). DSpark's Markov head (Eq. 1: `l_s(y) = base_s(y) + <W1[x_{s-1}], W2[y]>`) plugs into the same builder — "DSpark lattice" (§4.2). Concurrent PCTree (arXiv 2608.02123) builds trees from the same Markov head.

Snapshot-free GDN verify — THE piece for our 36 GDN layers (code: `specpilot_tree_gdn.py`):
- Stock cost: one fp32 state snapshot per verified node per layer = `HV*K*V*4 B` = 3 MiB/node/layer (module docstring, line 4-5); snapshots unshareable across branches (TreeWY §2 confirms vLLM+SGLang both do this).
- SpecPilot stores NO per-node state. Verify writes each node's COMMIT INPUTS: L2-normalized k (fp32), raw v, gate g, beta — ~33 KiB/node/layer (~90x smaller than a snapshot). The commit replays the accepted path from the UNCHANGED committed state with the same arithmetic, so the committed state equals the state verify used for the accepted leaf; per-node outputs equal the sequential recurrence along the root path (docstring lines 6-9).
- Three Triton kernels (all graph-capturable at fixed per-cohort shapes):
  1. `_gdn_tree_paths_kernel` (lines 27-129): one program per (leaf, V-block, head); reconstructs the leaf's root path by walking `parent_ptr`, loads committed state tile into registers (`b_h [BK,BV] fp32`), applies the gated delta rule sequentially down the path (gated softplus, L2-norm q/k, `b_h *= exp(g); b_v -= (b_h*b_k).sum(); b_v *= beta; b_h += k⊗v; o = (b_h*q).sum()`), writes o and the commit inputs. Interior nodes are covered by the leaf programs that pass through them — "every program that covers a node writes identical values."
  2. `_gdn_tree_wy_kernel` (lines 131-267, SPECPILOT_K_GDN_WY=1): TreeWY-form whole-tree solve on tensor cores. Builds the strict-ancestor matrix by parent-pointer hops (MAXD static bound), computes cumulative gate sums `gam`, forms `X = diag(beta) * Lr`, `Lr[t,s] = Anc[t,s] * e^(gam_t-gam_s) * (kn_s . kn_t)` strictly lower triangular in topological order; solves `(I+X)^-1 rhs` by the nilpotent Neumann product `(I-X)(I+X^2)(I+X^4)(I+X^8)` (+X^16 factor when depth >= 16 possible), all `tl.dot(input_precision="tf32x3")`; fp32 state split `hi+mid+lo` bf16 (24 significand bits exact) so `tl.dot(kb, h)` products are exact. One program per (request, head, V-block) instead of per leaf. Paper: within one BF16 ulp of the path kernel (§4.2). Promoted at 1.030x (App. B Table A3).
  3. `_gdn_tree_commit_kernel` (lines 369-460): grid (NV, bs, L*HV) — replays the accepted path into ALL 36 (their 48) GDN layers in ONE launch, reading stored kn/v/g/beta, writing `temporal` state. Commit launch width knob SPECPILOT_K_COMMIT_BV=8 in the final config.
- Accept logic: greedy tree accept (`specpilot_tree.py:19-24` docstring): longest root path where child token == target argmax at parent, plus bonus; permutes the reserved req_to_token block so the accepted path occupies positions seq_len+d.

**Verdict for our engine:** DIRECT PORT. Our verify-half/commit-half split exists because we snapshot the 113 MB recurrent state. This mechanism removes the snapshot entirely: verify reads state read-only, stores ~33 KiB/node/layer of commit inputs, one commit kernel replays the accepted path across all 36 layers in one launch. Scratch for T=8: 8 nodes * 36 layers * ~33 KiB ≈ 9.5 MB — trivial on 12 GB vs the 113 MB snapshot save+restore. Eliminates the split's serialization (today it caps effective window or doubles step count) and is the prerequisite for any tree work. Their kernels are Triton, proven on sm_120 (PRO 6000 finals), gated delta rule parametrized exactly like Qwen3-family GDN (A_log, a, dt_bias, softplus).

### 2c. TLV — two-level verification (code: `specpilot_d8_tlv.py`, `specpilot_d5_w12.q_pass`)

- One scheduler step = Q-step + exact step (module docstring lines 3-11 + paper §4.3):
  1. Q-step: draft + tree build + tree verify with the target's QUANTIZED VIEW (the d8q graph variant; W12 linears read only the nested 8-bit Q regions via `q_pass()`). Greedy tree accept WITHOUT commit (no recurrent-state scatter, no seq-len publish). Q's accepted path = chain C; Q's bonus = anchor of the next draft.
  2. Exact step: second draft anchored at Q's bonus, its best-first subtree truncated to `N - |C|` nodes, attached below the chain by `compose_chain_tree()` (d8_tlv.py:99-139 — chain nodes 0..C-1, subtree re-rooted at chain node C-1, ancestor mask assembled on device). ONE exact pass verifies the combined 32-node tree, accepts, commits as usual.
- Lossless because ONLY the exact pass accepts tokens; the chain merely proposes, like any draft. Q-step needs no state rollback (it never commits), which is why the no-commit property matters.
- Measured (App. C): one TLV cycle ≈ 30 ms on the final H100 system — two drafts 1.05 ms each, Q pass 11.5 ms (0.77x of exact), exact pass 14.9 ms, glue 1.6 ms; tau per exact pass 6.16 → 11.67. Tokens/s 270 (round 2) → 416 (round 3). TLV was the round-3 promotion at 1.037x paired (App. B).
- Regime dependence: TLV gained single-request everywhere; LOST 13% batched on BF16 27B (Q pass 0.80-0.88 of a step; cycle must accept ~2x to break even) (§6.5). Q-view bits: 8-bit nested view works; INT6/INT8 scaled copies used on PRO 6000 and DSpark (D3_QCOPY: separate g128 scaled INT6 copy at M<=32); 7-bit nested -3.8%, 6-bit -17.5%.

**Verdict for our engine:** does NOT port in their form. Their Q pass works because a high-precision parent (BF16 W12) exists and the 8-bit child is free (nested). Our production weights ARE the low-precision copy — we have no higher-precision parent to nest views into; a full-model Q pass would just be our normal pass. The transferable IDEA: if we ever add a low-cost pre-verify gate, only the exact pass may commit, and the pre-verify must be memory-free (nested view) — any separate low-precision expert copy is 12 GB-VRAM and lane-bytes negative.

### 2d. Batched serving mechanisms (paper §4.4, §6.5; batch setting READMEs)

- Shared node budget: fixed node budget per step shared across requests, top nodes by path log-probability; prefix-closedness of best-first trees makes each request's share a valid tree. Sized to a PLATEAU of the target GEMM cost (192 nodes at 24 requests sits flat until the next tile). Beats equal-size per-request trees by 6-14% accepted tokens (DSpark).
- Per-request drafter block: 16/12/8 positions per request chosen on-GPU from recent acceptance + draft confidence; tree depth capped to match; keeps drafter GEMM inside its 256-row plateau. +1.040x.
- Prompt admission: new prompt rows enter the verify step so one weight stream serves both — only when the scheduler would otherwise hold the prompt back (+3.5% at 24 requests); admitting every short prompt LOST. 384-token chains FP8, 128-row segments sharing projection/MLP GEMMs BF16.
- Failures to record: 24-node trees -14.9% batched FP8; 24-position block -9.9% BF16 batched; TLV -13% BF16 batched. Mechanisms that spend verify rows help single-request, hurt batching.
- Batch finals: FP8 27B+DFlash2 3.90x AR (stock 2.02x), +DSpark 3.93x (stock 1.94x); ragged draft trees with tiered verify budget, FP8 GEMM routing, warp-specialized FP8 GEMMs, fused GDN paths, snapshot-free GDN tree verify (batch setting README + config).

**Verdict for our engine:** our regime is single-request local; the batched mechanisms are not our lane, EXCEPT the shared-budget principle generalized: rows are spendable currency, and the row budget should sit on a flat stretch of OUR activation-GEMV cost curve (which we know: 8-column family).

## 3. Rest of the tree/verify family (recent weeks, HF feed + arXiv)

- TreeWY — Speculative Verification for Gated DeltaNet Hybrids (arXiv 2608.20961v2, 2026-10-22). https://arxiv.org/abs/2608.20961 https://arxiv.org/html/2608.20961v2
  - Same problem, independent derivation: stock vLLM+SGLang keep one fp32 state snapshot per draft position (N+1 blocks/layer/sequence; unshareable across branches → "a wide, high-acceptance tree becomes memory-infeasible").
  - Method: gated delta rule as tree-structured WY/UT transform. Pseudo-value rewrite `S_t = alpha_t S_{t-1} + v~_t k_t^T` with `v~_t = beta_t (v_t - alpha_t S_{t-1} k_t)`; DFS pre-order node layout gives strictly-lower-triangular `G[t,i] = (g_t/g_i)(k_t^T k_i)[i<t]`; ONE triangular solve `(I + diag(beta) G) V~ = R` verifies the whole tree; commit reconstructs only the accepted state `S_a = g_a S_0 + sum_{i<=a} (g_a/g_i) v~_i k_i^T`. Stores V~ = O(N*d_v): "a 128x smaller object per head" — turns N+1 state blocks into 1, chain or tree.

## 4. 12-bit weight formats besides W12

- NyoomFloat12 / NF12 (ICLR 2026): lossless FIXED-LENGTH 12-bit format for BF16 weights; the contribution is exactly the fixed-length decode that DFloat11's variable-length Huffman kills GEMM throughput with. Closest published relative of W12 (W12 = 12.01 bits fixed + register decode + nested view). https://www.alphaxiv.org/abs/2610.nyoomfloat12 https://iclr.cc/virtual/2026/10013421
- DFloat11 (NeurIPS 2025, arXiv 2504.11651): lossless ~11-bit Huffman over BF16; bit-identical outputs; decode-before-GEMM; SpecPilot measures it 4.8-6.7x SLOWER than cuBLAS on H100 (§7). Code: https://github.com/LeanModels/DFloat11
- ZipNN (IBM, IEEE CLOUD 2025): lossless entropy coding for storage/transfer, decode before GEMM. https://research.ibm.com/blog/Zip-NN-AI-compression
- ZipServ (ASPLOS 2026): hardware-aware lossless compression fused for inference, strongest on GDDR GPUs (~29% decompressed-read speedup); code https://github.com/HPMLL/ZipServ_ASPLOS26; paper https://www.cse.ust.hk/~weiwa/papers/zipserv-asplos26.pdf
- Unweight (Cloudflare TR Cf-TR-2026.04.v1): lossless MLP weight compression program; SpecPilot: does not consistently beat cuBLAS on HBM GPUs. https://research.cloudflare.com/papers/unweight-2026.pdf
- SpecPilot's own claim: "first lossless format whose GEMM beats cuBLAS on H100" (§7) — i.e., W12/NF12-class fixed-length + in-register decode is the current frontier; variable-length entropy coding is settled as a dead end for GEMM-resident weights.
- Kernel support on sm_120: W12's PRO 6000 build is `mma.sync m16n8k16` + `ldmatrix.x4` + `cp.async.bulk` + byte_perm/LOP3 register decode (see §2a) — all available on our sm_120. No int4x2 tricks needed (W12 is byte/nibble-plane aligned, not 4-bit). The nibble-plane assembly uses `*17 & 0x87 | 0x38` byte-splat + byte_perm — same lop3/PRMT family as our IQ4_NL tab16() (see digest w9 §1) — evidence the decode idioms transfer to our existing register-decode codebase. NO released code evaluates 12-bit-vs-IQ3_S quality because W12 is lossless vs BF16 — quality comparison is undefined/moot: W12 == BF16 exactly; IQ3_S is a different (lossy) point on the byte curve.
- 12-bit view over our IQ3_S packs: NOT COHERENT as a lossless construct (the pack has already discarded the bits). The only two coherent constructions: (a) W12 records over weights we hold at BF16/FP8 (GPU-resident dense projections — a small share of our bytes), optionally with the nested 8-bit Q view; (b) a nested view over our own MTP/lookup drafter weights (tiny) to enable a SpecPilot-shaped pre-verify of chains — zero extra memory, lossless if only the exact pass commits.

## 6. Portability matrix to our engine (48L: 12 QSA + 36 GDN, 512-expert top-10 MoE, VRAM+CPU hybrid experts, MTP + lookup drafter, T=1..8 @ 8-column activation family, RTX 5070 12 GB sm_120, CUDA 13.4, 262K ctx, CPU lane at 93-100% DRAM ceiling)

PORTS (ordered by expected value):
1. Snapshot-free GDN verify + replay commit (§2b): removes our verify-half/commit-half split. Saves 2x113 MB state save/restore traffic per verify step (~0.34 ms at nominal BW, plus graph/doorbell overhead of the split) and unblocks full-T single-pass verify and any later tree. Kernels are Triton, gated-delta-rule, proven on sm_120 in this repo. Commit inputs ~33 KiB/node/layer ≈ 9.5 MB scratch at T=8 x 36 layers. Note TreeWY's chain mode is the graph-capturable form; our per-cohort graphs make tree masks viable where vLLM's global graphs were not — but keep chain-mode first.
2. Best-first accept over the lookup drafter's EXISTING candidates at FIXED row budget T (§2b): zero new verify rows, zero GEMV widening (tree maps into the same T slots), zero expert-lane change beyond token substitution. Their replay numbers (tau 4.25→5.38 on the same lattice) bound our expected gain; our lookup drafter's per-position top-k is exactly their lattice. Accept/commit is a CPU-side build + device gather; graph-compatible at fixed shapes.
3. Calibrated edge scores (constant table from recorded lattices — `specpilot_d3m_calib_table.py` pattern): cheap acceptance lift on the same tree.
4. Token-forcing gate (§1): teacher-forced scorer vs our stock engine; adopt as the quality gate beside MMLU/mimic for every verify-path change.
5. Ceiling cost model (§1) re-expressed in our terms (tau factor / lane-bytes factor / overhead factor): ranks our next moves with byte floors, matching our measured-terms discipline.
6. Certified-argmax LM head screen (§2a): INT8/FP8 copy + per-row bound, survivors rescored exactly; helps our logits pass (vocab-sized GEMV is bytes-bound too); lossless by construction.
7. W12 pattern (not format) for our dense-projection GEMV/GEMM kernels if we hold any BF16/FP8-resident linears; decode-in-registers + PDL + deterministic split-K idioms transfer (§4).

DOES NOT PORT (named boundaries):
- W12 as our weight format: 12.01 bits vs our ~3.x-bit packs = 3.4-4x lane bytes on a lane at 93-100% DRAM ceiling; VRAM-negative on 12 GB; quality argument moot (lossless vs BF16 is not comparable to IQ3_S's point on the byte curve). A "12-bit view over IQ3_S" is not a coherent construct (§4).
- TLV full-model Q pass: requires a high-precision parent to nest the cheap view into; we have none for the experts; any separate low-precision expert copy is VRAM+bytes negative (§2c).
- Wide trees (N=32, more rows than drafted positions): 4x our widest 8-column activation family (static-assert wall) AND expert-set expansion on a saturated lane (DraftExpert trade, §3). Headroom to T=12 (proven) is the maximum sane row budget; WY-kernel economics only appear at N>=16 anyway.
- Their absolute numbers: dense-hybrid 27B BF16 on 80-96 GB HBM cards; our 12 GB / 512-expert / CPU-lane geometry is a different deployment — their own thesis says no optimization transfers unexamined.

## 7. Execution-ready adoption plan (our engine)

Order and expected effect (all in our measured terms; gate every step on the token-forcing scorer + MMLU/mimic):
1. **GDN snapshot-free verify** (path kernel + one-launch replay commit, Triton, per-cohort shapes): kill verify-half/commit-half. Expected: -0.3..-0.5 ms GPU per verify step at T>=2, window no longer split (effective acceptance x window up without any drafter change); lane bytes unchanged.
2. **Best-first accept at fixed T** over lookup-drafter candidates (+ calibrated edge table): tau up toward oracle; rows/experts unchanged. Expected: tau +10..30% on mimic set; GPU ms neutral (same row count); CPU build cost ~us-scale.
3. **Certified LM-head screen** + cost-model ceiling harness (byte floors per kernel class; recompute each change).
4. **Optional T=9..12 probe** with the SAME path/commit kernels (they are row-count agnostic): only if step 1-2 leave the activation GEMV and lane bytes with measured headroom; WY kernel only matters at N>=16 — skip.
Risks: (i) QSA attention needs a tree-mask variant within T rows (their PRO 6000 used Triton attention for this; ours is a small kernel change, graph shape static); (ii) doorbell/graph capture: Q-mode-style context switching is NOT needed (no TLV), but accept-path permutation must stay graph-safe (their req_to_token block permutation is the reference); (iii) Triton-on-sm_120 compile maturity (their repo pins torch 2.13/CUDA 13.0; we are on 13.4 — check the w9 nvcc sm_120 miscompile note applies to any byte-pointer decode we port); (iv) tree token substitution changes the expert union per step — measure lane bytes directly, expect small delta from routing overlap, gate on the 93-100% ceiling never exceeding 100%.
