# Prewarm digest — academic + kernel/GPU mechanics (2026-11-04)

Boundary note on kernel versions: man7 pages document behavior through the 6.x series. The mechanics below (fadvise, madvise incl. `MADV_POPULATE_*` 5.14+, `MADV_COLD` 5.4+, mincore, MAP_POPULATE, read_ahead_kb) are long-stable ABIs. Kernel 7.2 continuity is assumed, not proven — smoke-test each syscall once before depending on it (one `madvise`/`mincore` call each; residency delta confirmed via `mincore` closes that loop).

## A) Academic literature

### A.1 The six named systems

**ServerlessLLM** — [arXiv:2401.14351](https://arxiv.org/abs/2401.14351), [OSDI'24 PDF](https://www.usenix.org/system/files/osdi24-fu.pdf). Locality-enhanced serverless inference; cold-start dominated by checkpoint loading.
- Mechanism (fetched from [arXiv HTML v2](https://arxiv.org/html/2401.14351v2)): loading-optimized checkpoint format — tensors grouped by target GPU into partitions for sequential chunk reads; data-only binary files + separate tensor-index (name → GPU id, offset, size); **16 MB bulk-read chunks read with O_DIRECT** (deliberately avoiding mmap — safetensors' mmap path suffers **~112K page faults on cold LLaMA-2-7B load**); chunks land in a pinned-host pool then DMA to GPU; multi-thread I/O per tier, pipelined across tiers with task queues; inference process only sets pointers.
- Numbers: **3.6–8.2× faster than PyTorch, 3.6–4.7× faster than safetensors** (8.2×/4.7× at LLaMA-2-70B). Optimization multipliers on RAID-0 NVMe (~12 GB/s): bulk reading 1.2×, direct IO 2.1×, multi-thread 2.3×, pinned memory 1.4×, pipeline 1.5× (multiplicative). End-to-end: OPT-6.7B startup **0.8 s** vs RayServe 12.1 s; OPT-30B 7.5 s vs 213 s.
- Infra: full system wants a cluster (locality scheduler), but the checkpoint-format layer is **single-server applicable** — NVMe + host RAM + one GPU is exactly its fast path.

**Splitwise** — [arXiv:2311.18677](https://arxiv.org/abs/2311.18677), ISCA'24. Phase-splitting prefill (compute-bound) from decode (memory-bandwidth-bound) onto separate machine classes; **1.4× throughput, 20% lower cost**. Infra: ≥2 GPU pools — **not applicable on one GPU**. Takeaway only: the two phases stress different resources, which is why warm-decode cares about DRAM residency while cold-prefill cares about weight-load bandwidth.

**DistServe** — [arXiv:2401.09670](https://arxiv.org/abs/2401.09670), [OSDI'24 PDF](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf). Prefill/decode disaggregation with a goodput metric (SLO-attaining queries/GPU/s); **7.4× goodput** or 2.4–6.4× more queries under strict TTFT/TPOT SLOs. Infra: separate GPUs — **not applicable**; takeaway: TTFT and TPOT have separate optimizers, so a prewarm design should separate "first request" cost from "steady decode" cost.

**Mooncake** — [arXiv:2407.00079](https://arxiv.org/abs/2407.00079), FAST'25 ([USENIX](https://www.usenix.org/conference/fast25/presentation/qin)). KVCache-centric disaggregation for Kimi: prefill/decode clusters + CPU/DRAM/SSD pooled into a global KV cache tier ("trading more storage for less computation"); up to **75% more throughput** under SLO. Infra: cluster — **not applicable**; the transferable idea is the tiered KV pool — the machine already mirrors it (pinned DRAM complement, VRAM KV slots).

**Preble** — [arXiv:2407.00023](https://arxiv.org/html/2407.00023v2), [code](https://github.com/WukLab/preble). Distributed prompt/prefix scheduling; E2 algorithm co-optimizes KV-state reuse and load balance; **1.5–14.5× throughput** on shared-prefix workloads. Infra: distributed — scheduler part **not applicable**; the prefix-reuse mechanism itself is single-box applicable via vLLM APC/SGLang radix-cache-style boot prefill (see §3, item 6).

**CacheGen** — [arXiv:2310.07240](https://arxiv.org/abs/2310.07240), SIGCOMM'24 ([ACM](https://dl.acm.org/doi/10.1145/3651890.3672274)). KV-cache compression: custom tensor encoder exploiting layer/sequence-wise distribution similarity + tailored quantization → **3.5–4.3× smaller KV bitstream**, streamable (decode starts before full fetch). Designed for network transfer; single-box relevance is compression of precomputed KV for canned long contexts (a 262K-token context's KV compressed ~4× could sit in DRAM instead of re-prefilling).

### A.2 What is real since 2025

- **HydraServe** — [arXiv:2502.15524](https://arxiv.org/pdf/2502.15524). Proactive model distribution to servers ahead of requests + overlapping cold-start stages (weight load, runtime init) inside a worker; **1.7–4.7× cold-start reduction**. Infra: cluster distribution — not applicable; the *stage-overlap* idea is applicable (warm page cache on one thread while CUDA init runs on another).
- **λScale / FaaScale** — [arXiv:2502.09922](https://arxiv.org/abs/2502.09922) (MLSys'26 version [PDF](https://www.ruichuan.org/papers/faascale-mlsys26.pdf)). Extends ServerlessLLM's loading-optimized checkpoint to *inference state* (KV + model state) for fast scale; up to **5× tail-latency improvement, 31.3% cost reduction**. Cluster infra — not applicable.
- **KVShare** — [arXiv:2503.16525](https://tldr.takara.ai/p/2503.16525). KV sharing of identical prefixes + selective recomputation for similar ones. Single-box applicable when clients share prompt templates.
- **IMPRESS** — [FAST'25](https://www.usenix.org/system/files/fast25-chen-weijian-impress.pdf). Importance-ranked multi-tier prefix-KV storage; documents that disk I/O to fetch reused prefixes can **negate** the TTFT gain of reuse → tiers must be pre-warmed by importance. Directly matches the 262K-token cold re-read (42.7 s) problem.
- **FlashServe** — [ACM DL](https://dl.acm.org/doi/full/10.1145/3795154.3795363), Dec 2025. Predictive pre-warming of serving pods before traffic spikes; scheduling-layer, single-box takeaway is only "run prewarm on a trigger/predictor, not always."
- **Breaking the Ice: cold-start decomposition of vLLM** — [arXiv:2606.07362](https://arxiv.org/html/2606.07362). Startup split into six stages; **weight loading is only ~7–10% of total startup** and startup is **mostly CPU-bound** (better GPU barely helps); torch.compile cache adds 11–21 s when disabled; **CUDA graph capture 0.33 s at 3 batch shapes → 1.8 s at 60 shapes** (linear in shape count, PCC=0.99); loader bake-off: CoreWeave Tensorizer reaches 53–60% of safetensors' load time, Run:ai Model Streamer moderate gains. This paper is the price list for the GPU-side boot bundle.
- **Run:ai Model Streamer** — NVIDIA/Run:ai, Sep 2025 blog: streaming weights NVMe→GPU with I/O overlapped with H2D copies; the industrial version of ServerlessLLM's pipelined loader.
- **InstantInfer** — [arXiv:2607.18957](https://arxiv.org/html/2607.18957v1): communicating-finite-state-machine loading pipeline, **7.2× cold-start speedup**. Cluster pipeline; not applicable.
- Negative result (honest boundary): searches for additional dedicated single-server "page-cache prewarm for local LLM serving" papers (ColdServe/SiloServe/ServerlessRing) found nothing — this niche is owned by practitioner tooling (vmtouch, dd, io_uring warmers) plus the checkpoint-format line above.

**Infra filter:** Splitwise, DistServe, Mooncake, Preble-scheduler, HydraServe-distribution, λScale all require multi-GPU/cluster state. On one GPU + one NVMe + host RAM, the surviving academic mechanisms are: (1) ServerlessLLM's loading format (O_DIRECT + chunked + threads + pinned staging), (2) prefix-KV reuse + prewarm (Preble/KVShare/IMPRESS), (3) KV compression for canned contexts (CacheGen), (4) startup stage decomposition + overlap (Breaking the Ice / HydraServe).

## B) Kernel/OS + GPU mechanics

### B.1 Page-cache control

| Mechanism | Behavior | Since | Source |
|---|---|---|---|

| `posix_fadvise(WILLNEED)` | **non-blocking** read of region into page cache; kernel may shrink the read under VM pressure — self-limiting under memory stress | long-stable | [fadvise(2)](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html) |
| `posix_fadvise(NOREUSE)` | documented but **historically a no-op** in Linux (see comment in `mm/fadvise.c`) | no-op | [linux/mm/fadvise.c](https://github.com/torvalds/linux/blob/master/mm/fadvise.c) |
| `posix_fadvise(DONTNEED)` | drops clean cached pages; does **not** prevent re-caching on next read | long-stable | [fadvise(2)](https://man7.org/linux/man-pages/man2/posix_fadvise.2.html), [Marsching](https://sebastian.marsching.com/blog/archives/161-Design-flaws-of-the-Linux-page-cache.html) |

| `madvise(MADV_COLD)` / `(MADV_PAGEOUT)` | deactivate (reclaim-candidate) / actively reclaim (swap or writeback) | 5.4 | [madvise(2)](https://man7.org/linux/man-pages/man2/madvise.2.html) |

Note on the observed Qwen complement behavior: the documented semantics say MADV_DONTNEED on a file-backed mapping drops the mapping's PTEs while page-cache pages *may persist*; a genuine page-cache drop alongside a 41.63 GiB pin is consistent with (a) private/CoW pages being freed, or (b) plain reclaim pressure — pinned RSS competes with cache for the same RAM. Either way the sequencing constraint stands: warm **after** the pin.

### B.2 Readahead and NVMe behavior

- `read_ahead_kb` (default 128 KiB) only governs the **page-cache readahead path**; typical sequential-NVMe tuning raises it to 1–4 MiB ([RHEL perf guide](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/performance_tuning_guide/sect-red_hat_enterprise_linux-performance_tuning_guide-storage_and_file_systems-configuration_tools), [HPE recommends 4 MiB + raised max_sectors_kb for large sequential reads](https://community.hpe.com/t5/array-performance-and-data/how-to-improve-low-sequential-read-performance-for-large-files/td-p/6982872)).
- **O_DIRECT bypasses readahead entirely** — for a direct-read warmer, tune block size and queue depth instead ([OneUptime 2026 guide](https://oneuptime.com/blog/post/2026-03-02-how-to-configure-readahead-settings-for-disk-performance-on-ubuntu/view)).
- A sequential ~110 GB buffered re-read: the kernel grows the readahead window on confirmed sequentiality, so a single-threaded dd at bs=8M runs at effective queue depth ≈1–2 — it **cannot saturate NVMe internal parallelism**. Queue depth is the first-order knob for NVMe throughput ([Haas et al., VLDB 2023 — "What Modern NVMe Storage Can Do"](https://dl.acm.org/doi/pdf/10.14778/3598581.3598584)); io_uring with in-flight parallel reads saturates NVMe where mmap/single-stream FileChannel does not ([Lucene #14655 benchmarks](https://github.com/apache/lucene/issues/14655)).
- ServerlessLLM's measured single-NVMe-tier multipliers are the reference for warmer design: bulk-read 1.2×, **O_DIRECT 2.1×, multi-thread 2.3×**, pinned 1.4×, pipeline 1.5× ([arXiv:2401.14351](https://arxiv.org/html/2401.14351v2)).

### B.3 Prefetch tooling

- **io_uring buffered reads** (`IORING_OP_READ` without O_DIRECT) populate the page cache while running at high queue depth — the natural native-server warmer primitive ([Qdrant io_uring guide](https://qdrant.tech/articles/io_uring), [Rishab Joshi, Optimizing NVMe with io_uring](https://www.rishabjoshi.com/post/optimizing-nvme-storage-systems-with-io_uring)); io_uring for DBMS page-loading integration studied in [arXiv:2512.04859](https://arxiv.org/html/2512.04859v1).
- **vmtouch/fincore/mincore** give the residency truth source (§B.1) — a readiness gate should consume this, not a sleep timer.
- **systemd ReadAhead: does not exist.** Removed upstream starting v217 (Sept 2014 "readahead: wipe out" patch, [systemd-devel](https://lists.freedesktop.org/archives/systemd-devel/2014-September/023394.html)); fully gone by v230 ([Debian bug 776485](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=776485)). Named boundary: nothing to enable on Fedora; roll the warmer as a native server feature or a one-shot systemd oneshot unit.

### B.4 Hugepages / THP

- TLB math for this box: a 110 GB store mapped at 4 KiB = **~28.2M pages**. Zen 4/5 L2 STLB holds ~2–3K entries for 4 KiB pages → ~8–12 MiB of coverage; a tens-of-GB working set at 49.5 GB/s walks page tables constantly beyond that coverage. At 2 MiB pages the same store is **56,320 entries** — 512× fewer TLB fills (their `vm.nr_hugepages≈56320` figure is exactly this arithmetic). Sources: [kernel THP admin guide](https://docs.kernel.org/admin-guide/mm/transhuge.html) (THP reduces TLB misses; khugepaged compaction can stall — many inference stacks run THP=madvise or off), [THP TLB-pressure explainer](https://www.abhik.ai/concepts/systems/transparent-huge-pages), [hugepages-for-LLM profiling guide](https://adgstudios.co.za/blog/linux-hugepages-thp-tlb-misses-gpu-llm-workloads).
- Explicit hugetlbfs: `vm.nr_hugepages=56320` reserves ~110 GiB **up front, unusable by anything else** — on a dual-channel box already hosting a 41.63 GiB pin + DS expert RAM copies, this is infeasible. Priced dead (§3).
- THP=madvising the anon expert pools (DS RAM copies) is the cheap experiment: 512× fewer walks against the measured 49.5 GB/s ceiling; risk is khugepaged stall during the copy — apply THP before serving starts, not during.
- First-touch NUMA: single-socket AM5 → one NUMA node, no placement choice exists. No action.

### B.5 CUDA boot costs

- **Persistence mode**: without it the driver re-initializes per job boundary; `nvidia-persistenced` keeps the driver resident ([NVIDIA Driver Persistence docs](https://docs.nvidia.com/deploy/driver-persistence/persistence-daemon.html)) — a running systemd clock-lock service that talks to the driver effectively provides this; verify `nvidia-smi -q | grep Persistence` once.
- **Module load / JIT**: `CUDA_MODULE_LOADING` — lazy mode introduced CUDA 11.7, **default on Linux since CUDA 12.2, all platforms since 12.3** ([CUDA Programming Guide, lazy loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html)): context creation is cheap but the **first call of each kernel pays its module load**. `EAGER` front-loads everything at context creation. First launch can be ~7× slower than subsequent (community measurement: [r/CUDA](https://www.reddit.com/r/CUDA/comments/1n6rk27/first_kernel_launch_takes_7x_longer_than)); PTX→SASS JIT applies only when no prebuilt SASS matches the arch — sm_120 Blackwell kernels must ship sm_120 SASS or pay JIT every boot (check with `cuobjdump --list-elf` on the engine's cubins).
- **cuBLAS handle + first GEMM**: handle creation and per-shape algorithm heuristics run on first use — standard mitigation is dummy GEMMs at every serving shape ([NVIDIA forums, "Why warm-up?"](https://forums.developer.nvidia.com/t/why-warm-up/48565)).
- **cudaMallocAsync pool**: first pool growth performs physical allocation + VA mapping (expensive); **release threshold defaults to 0** — freed blocks return to the OS, so each growth spike re-pays the cost. Fix: `cudaMemPoolSetAttribute(pool, CU_MEMPOOL_ATTR_RELEASE_THRESHOLD, ≥peak)` and/or allocate the peak-sized buffer once at boot ([CUDA Runtime docs](https://docs.nvidia.com/cuda/archive/11.0/cuda-runtime-api/group__CUDART__MEMORY.html), [NVIDIA forum thread on release-threshold stalls](https://forums.developer.nvidia.com/t/gpu-stalls-due-to-stream-synchronization-even-when-idle/191761), [PyTorch discuss — pre-grow largest size first](https://discuss.pytorch.org/t/how-to-achieve-const-memory-cost-for-capturing-cudagraph-with-multiple-batch-sizes/203786)).
- **CUDA graph capture as warmup**: capture cost scales with shape count — 0.33 s at 3 shapes → 1.8 s at 60 shapes, linear ([arXiv:2606.07362](https://arxiv.org/html/2606.07362)). The machine captures lazily per cohort batch shape → **first request per new shape pays capture**. Pre-capturing all cohort shapes at boot converts that to boot time.
- **Clock lock interaction**: `nvidia-smi -lgc` pins **SM/core clocks only — memory clocks are a separate knob** (`-lmc` / `-ac "mem,core"`). Locked SM clocks remove compute DVFS ramp, but **memory-clock DVFS ramp, cold caches/TLB, and lazy module loads still make the first pass slower** — a warmup sweep remains valuable, and locking memory clocks too (`-lmc`) removes the remaining ramp ([NVIDIA forum — 50-series latency](https://forums.developer.nvidia.com/t/seconds-of-latency-on-50-series-gpu/362978), [clock visibility](https://forums.developer.nvidia.com/t/is-nvidia-hiding-locked-gpu-clock-or-am-i-missing-something-how-to-see-locked-gpu-memory-clocks/280966), [ONNX Runtime #23101 — locked clocks still slow on first runs](https://github.com/microsoft/onnxruntime/issues/23101)). Verify with `nvidia-smi -q -d CLOCK`; watch HW Slowdown reasons that override locks ([Microway guide](https://www.microway.com/hpc-tech-tips/nvidia-smi_control-your-gpus)).
- **MPS**: merges contexts for *multi-process* GPU sharing; a single Python HTTP server process gains nothing. Not applicable unless workers are split into subprocesses.

## 3) Priced for our box

Scored on: (1) boot→warm-decode time, (2) first-request latency, (3) steady-state cost (must be 0), (4) memory-pressure risk (page cache shares RAM with the 41.63 GiB pin + DS expert copies — capping matters). Targets: DS 16.6→36.8 tok/s cold/warm delta; 42.7 s cold 262K re-read; Qwen cache-drop ordering constraint.

Capping policy (applies to #1/#3): warm in decode-priority order (hot cohorts first), verify with mincore per file, and stop/hold when `MemAvailable` drops below a floor sized to the working set delta. WILLNEED gives a soft cap for free (kernel throttles under pressure); the io_uring path needs an explicit in-flight-bytes cap because it fills the cache as fast as the NVMe allows.
