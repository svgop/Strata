# Crash forensics digest (2026-11-04): CUDA/CPU idle-corruption hunt

Case tie-ins are marked **CASE** throughout. The falsified/known list (not OOM, not T18 dispatch, bit-check passes) is respected: nothing below re-proposes those.

## 1. CUDA-aware sanitizers in 2025-26 — practical limits on a 12 GB consumer card

### 1.1 What each compute-sanitizer tool actually covers (official docs, fetched)
[Compute Sanitizer docs](https://docs.nvidia.com/compute-sanitizer/ComputeSanitizer/index.html) (fetched).

- **memcheck**: OOB + misaligned device accesses, hardware exceptions, malloc/free errors, CUDA API errors, leaks. Lightest tool; the other three are heavier.
- **racecheck**: **shared-memory (on-chip) hazards only** — "only supports detecting accesses to on-chip shared memory". Dead-end for host-thread races.
- **initcheck**: uninitialized device global memory reads. **synccheck**: invalid synchronization-primitive usage.
- **None of the four cover host-side threading** — host API calls are tracked only for API errors/leaks. **CASE**: our corruptor is plausibly a host-side race; compute-sanitizer is structurally blind to it. Its value here is ruling the GPU side in/out, nothing more.
- Hard limit for this engine: **"Memcheck padding doesn't support `cudaHostRegister` or virtual memory management APIs."** The 37.58 GiB registered pinned complement gets **no redzones, no padding** from memcheck — an OOB write into it from a kernel is invisible to the tool. Only our own mprotect/canary layer (§4) covers that region.
- Memory footprint: error detection with dynamic parallelism "requires significantly more memory on the device"; in constrained environments memcheck "may fail to initialize with an internal out of memory error". On a 12 GB card near-full VRAM, memcheck routinely makes the target OOM before running ([forum: consumes too much GPU memory](https://forums.developer.nvidia.com/t/compute-sanitizer-consumes-too-much-gpu-memory-causing-it-unusable/229644), search-level; [forum: not a drop-in replacement](https://forums.developer.nvidia.com/t/compute-sanitizer-not-quite-a-drop-in-replacement-of-cuda-memcheck/225877/7), search-level). **CASE**: run memcheck only on a shrunk config (small cohort shape, subset of graphs), never the production shape.
- Overhead: memcheck typically ~4x kernel slowdown, racecheck/initcheck/synccheck 10-50x ([Vi-HPS slides](https://www.vi-hps.org/cms/upload/material/tw41/Nsight_Compute-sanitizer.pdf), search-level). [cuCatch paper (ACM)](https://dl.acm.org/doi/pdf/10.1145/3591225): compute-sanitizer is "the only commercial GPU memory-safety tool" but with "large performance and memory overheads" (search-level).
- Useful knobs (fetched): `--report-api-errors all` (default `extended` hides `cudaErrorNotReady` — for an idle-polling engine that exclusion matters), `--leak-check full` (host backtraces, needs `-rdynamic`), `--force-blocking-launches` and `--force-synchronization-limit` (reduce hangs, lose per-thread error precision — "only the first thread to hit an error in a kernel will be reported"), `--launch-timeout`, `--kill`.
- Graphs: partial support (memory nodes added 2023.1; **device graphs unsupported** per release notes, search-level via [release notes](https://www.scribd.com/document/789188818/ReleaseNotes)); a known indefinite-hang bug with graphs + memcpy without an intervening `cudaDeviceSynchronize` ([forum 250745](https://forums.developer.nvidia.com/t/compute-sanitizer-hangs-indefinitely-while-cuda-memcheck-works-as-is/250745), search-level). Known false positives tracking stream-ordered/pinned allocations ([CUDA.jl #3347](https://github.com/JuliaGPU/CUDA.jl/issues/3347), search-level).
- Sanitizer coredump support since CUDA 11.6 (fetched docs) — pairs with §3.6.

### 1.2 Compile-time instrumentation — the 2025-26 step change
[NVIDIA blog, Dec 2025](https://developer.nvidia.com/blog/better-bug-detection-how-compile-time-instrumentation-for-compute-sanitizer-enhances-memory-safety) (fetched) | [nvcc docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html) (flag `-fdevice-sanitize=memcheck`, added CUDA 12.6, search-level).

- CUDA 13.1+ (we are on 13.4): compile kernels with `-fdevice-sanitize=memcheck` (+`-lineinfo`, avoid `-G`), then run under compute-sanitizer. Overhead "in some cases, nearly an order of magnitude lower" than binary instrumentation.
- It catches what runtime instrumentation misses: **overruns that land in an adjacent, validly allocated object** — fat pointers bound to the originating allocation. The blog notes the same blind spot exists in GCC/Clang ASan.
- Limits: register-pressure launch failures ("too many resources requested for launch" → `__launch_bounds__`), HMM allocations unsupported, UB can produce false positives, recompilation required.
- **CASE**: this is the one compute-sanitizer mode worth a real run here — it covers graph-replayed kernels reading stale pointers into the pool region, at tolerable overhead, on sm_120.

### 1.3 ASan / TSan combos with CUDA — what works, what storms
- nvcc passes unknown flags to the **host** compiler: `-fsanitize=address` works for host code only; device code has no ASan ([nvcc docs](https://docs.nvidia.com/cuda/cuda-compiler-driver-nvcc/index.html), search-level). GPU-side checking = compute-sanitizer only.
- Combining: HPE [sanitizers4hpc](https://cpe.ext.hpe.com/docs/24.07/debugging-tools/sanitizers4hpc/guides/user_guide.html) officially orchestrates ASan-equivalent + compute-sanitizer for CUDA programs (search-level); in practice compute-sanitizer's dynamic-instrumentation "ports" can conflict with other sanitizer runtimes ([forum: no attachable process](https://forums.developer.nvidia.com/t/compute-sanitizer-no-attachable-process-error/298362), search-level). Safe pattern: **separate runs** — ASan build alone for idle soak; compute-sanitizer alone on a shrunk config. Never both in one process.
- ASan blind spot that matters here: ASan shadow memory has no idea about `cudaHostRegister`'d regions — writes into the pinned complement from GPU or from pool threads are untracked unless the region is poisoned manually (`__asan_poison_memory_region`) or fenced with mprotect guard pages (§4.1).
- TSan: documented false-positive storms from CUDA internals — extended-lambda host-side code ([forum 244908](https://forums.developer.nvidia.com/t/prevent-false-positives-for-thread-sanitizer-in-extended-lambda-implementation/244908)), and data races **inside libcuda.so.1** on kernel launches from multiple threads ([forum, Oct 2026](https://forums.developer.nvidia.com/t/threadsanitizer-reports-a-data-race-inside-libcuda-so-1-when-two-threads-launch-the-same-kernel-on-the-per-thread-default-stream-struct-argument-by-v/386479)). Mitigation: instrument ALL our host code, suppress only driver/runtime frames (`race:libcuda.so`, `race:libcudart`); PyTorch confirms TSan is "clunky" until every dependency is instrumented ([pytorch #167970](https://github.com/pytorch/pytorch/issues/167970)). TSan on the CPU pool threads + reload path is viable but expects a tuning day.

## 2. Heisenbug classes that pass load and strike idle

### 2.1 cudaGraphExec lifetime — destroy/update vs in-flight execution
- `cudaGraphExecDestroy` does **not** implicitly synchronize; destroying an exec while still executing is unsafe ([CUDA runtime graph docs](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__GRAPH.html); [forum: do we need to synchronize before cudaGraphExecDestroy](https://forums.developer.nvidia.com/t/do-we-need-to-synchronize-before-calling-cudagraphexecdestroy/336458), search-level). Launching a device graph **while an update is applied** is documented undefined behavior ([CUDA programming guide — graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)).
- Graph node parameters are **frozen at capture/instantiate**: pointers captured in `kernelParams` refer to the pointed-to memory, not a copy of it — free/reuse the buffer and every replay dereferences a dangling pointer ([forum 112518](https://forums.developer.nvidia.com/t/cudagraph-kernel-node-copy-questiont/112518); [PegaInfer walkthrough](https://susun-blog.com/blog/pegainfer-4-cuda-graph-part2), search-level). PyTorch's answer is a single memory pool across all graph captures so captured pointers stay valid ([CUDA graphs trees](https://dev-discuss.pytorch.org/t/understanding-cudagraph-trees/1967)).
- Wild catches: SGLang capture-time segfaults in long-running servers ([#6496](https://github.com/sgl-project/sglang/issues/6496)), intermittent segfault after hours of normal operation ([#15444](https://github.com/sgl-project/sglang/issues/15444), Dec 2025), cudnn-frontend graph-plan retention SIGSEGV ([#1486](https://github.com/NVIDIA/cudnn-frontend/issues/1486), Oct 2026), llama.cpp disabling graphs after `cudaGraphExecUpdate` consecutive-update counter issues ([PR #7302](https://app.semanticdiff.com/gh/ggerganov/llama.cpp/pull/7302/overview)).
- **CASE fit**: our engine re-captures graphs per cohort shape and idles/reloads; a graph exec destroyed (or its captured input/output pointers freed) at unload while a tail wave still runs = exactly "passes load, strikes late". The idle unload/reload path is suspect #1.

### 2.2 Event/stream destruction races
- Destroy semantics are deferred: `cudaEventDestroy`/`cudaStreamDestroy` mark for deletion; actual free happens after pending work drains. Destroying while work is still recorded, or an event still referenced by a stream, is the use-after-free pattern ([SO: should events/streams always be destroyed](https://stackoverflow.com/questions/10920290/should-cuda-events-and-streams-always-be-destroyed); [programming guide — asynchronous execution](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)).
- **CASE fit**: speculative decode + per-cohort graphs means event churn; a polling thread calling `cudaEventQuery` on a just-freed event faults inside the driver, not in our frames — matching a faulting frame that lands somewhere meaningless.

### 2.3 Pinned-memory registration races + MADV/pinned interplay
- `cudaHostRegister` is documented to misbehave when called concurrently from multiple host threads ([forum 296497](https://forums.developer.nvidia.com/t/cudahostregister-on-multiple-threads/296497), 2024); edge cases with non-standard allocations ([forum 294999](https://forums.developer.nvidia.com/t/strange-behaviour-of-cudahostregister/294999)).
- Freeing/unregistering pinned memory with in-flight async copies = classic UAF; requires stream sync first ([SO: cudaFreeHost matching allocation semantics](https://stackoverflow.com/questions/8591577/does-cudafreehost-care-what-device-is-active-when-cudamallochost-is-used-to-allo); [aussieai advanced CUDA bugs](http://www.aussieai.com/book/cuda-debug-12-advanced-bugs), search-level). After any sticky device error, free/unregister calls fail until `cudaDeviceReset` ([SO 6153035](https://stackoverflow.com/questions/6153035/cuda-fails-when-freeing-memory-after-kernel-execution-error)).
- Pinned memory mechanics: page-locked pages live in normal host RAM with reserved page-table entries; DMA uses the driver's mapping of the **physical** pages ([Lei Mao: page table for page-locked host memory](https://leimao.github.io/blog/Page-Locked-Host-Memory-Page-Table)). CPU `mprotect` bits are CPU-MMU-only — a GPU DMA can still write a `PROT_NONE` page unless the IOMMU rejects the transaction (see §4.1).
- **CASE fit**: the 37.58 GiB complement is registered at startup (static), so the race surface is the *reload path*: unregister/re-register or complement realloc while expert-pool threads still hold pointers into it. Any mlock limit flake at re-registration silently degrades to unpinned (bit-check still passes — consistent with our falsified list).

### 2.4 Page-locked memory + fork/exec interactions
- CUDA is unsupported across `fork()` after context init: pinned registrations and context state belong to the parent; children touching CUDA resources SIGSEGV; `exec()` clears runtime state but inherited mappings of page-locked memory can still fault ([forum: pinned shared memory across fork](https://forums.developer.nvidia.com/t/how-to-make-host-pinned-shared-memory-across-process-fork-2/36195); [forum: crash in cudaMemcpy after fork/wait](https://forums.developer.nvidia.com/t/crash-in-cudamemcpy-after-fork-and-wait-for-a-child-process/173197); [PyTorch DDP SIGSEGV via bad shared-mapping](https://discuss.pytorch.org/t/how-to-fix-a-sigsegv-in-pytorch-when-using-distributed-training-e-g-ddp/113518)).
- **CASE fit**: the Python parent restarts the engine. If the parent ever forks a CUDA-initialized helper (telemetry, probing), the child inherits a page-locked mapping clone; child exit re-walks those VMA clone entries in the parent's context via mm references — a known SIGSEGV-at-idle shape. Verify the parent never forks post-CUDA-init except `fork+exec` of a fresh engine.

### 2.5 Deferred/sticky errors — corruption attributed late
- Kernel faults are deferred: they surface at the next synchronization point, attributed to an unrelated API call ([SO 76787504](https://stackoverflow.com/questions/76787504/at-which-points-are-asynchronous-cuda-errors-synchronized-to-host); [Lei Mao: proper CUDA error checking](https://leimao.github.io/blog/Proper-CUDA-Error-Checking); [RAPIDS cudf #3514](https://github.com/rapidsai/cudf/issues/3514)). Sticky errors poison the context; `cudaDeviceSynchronize` returns previously-occurring async errors ([forum: sticky-ness](https://forums.developer.nvidia.com/t/cuda-errors-determine-sticky-ness/271625)).
- **CASE fit**: a device fault at the END of a load window can kill the context; the host process then SIGSEGVs inside the driver minutes later at idle when the next deferred call lands. Check `journalctl -k` for **Xid** at the previous activity window: Xid 13/31 = usually workload bugs ([NVIDIA Xid docs](https://docs.nvidia.com/deploy/xid-errors/latest/index.html); [CoreWeave](https://docs.coreweave.com/support/cks/articles/what-do-gpu-xid-error-codes-mean); [field guide](https://www.abhik.ai/articles/nvidia-xid-errors)).

### 2.6 Host callback threads
- `cudaLaunchHostFunc` callbacks execute on a **driver-internal thread**, must not call CUDA APIs, block, or sync ([runtime API docs](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__EXECUTION.html); [SO 75145603](https://stackoverflow.com/questions/75145603/catching-an-exception-thrown-from-a-callback-in-cudalaunchhostfunc)). Known deadlock/crash class around driver callback thread + host locks ([cuda-python #2058](https://github.com/NVIDIA/cuda-python/issues/2058)).
- **CASE fit**: a callback firing during idle drain, running pool logic that assumes pool-thread context, writes a descriptor through a stale pointer → next dispatch's vtable/function-pointer jump = PC in data.

### 2.7 The closest published analog: corruption on the IPC/doorbell path, not CUDA
[vLLM #35104](https://github.com/vllm-project/vllm/issues/35104) (fetched, through Aug 2026).

- Symptoms: workers died spontaneously after idle periods **10 min–9 h**; stable under continuous load; a keepalive request every 5 min prevented all idle crashes. Final crash site: `shm_broadcast.py` `memory_fence()` — the `threading.Lock`'s **C-level `_thread.lock` descriptor corrupted**. Root cause hypothesis: runtime C-extension loading (JIT/autotune/compile) corrupting the CPython method descriptor. Fix: replace the lock barrier with `sched_yield()` ([PR #40303](https://github.com/vllm-project/vllm/pull/40303)); MTBF went from ~5.5 h to 96+ h soak clean.
- **CASE fit**: this is our symptom family exactly — passes load, strikes idle, control-flow corruption (corrupted function-pointer-ish object), on the **front-door/IPC path**, cured by a keepalive that keeps the idle path from executing. Lesson: instrument and stress the doorbell/line-protocol drain path as a first-class suspect, and use a keepalive as a cheap discriminator (does MTBF explode?).

### 2.8 Fatbin PC symbolization — decoding our core
- Fatbins are embedded in a **`.nv_fatbin`** data section (plus `__nv_module_id`) of the host ELF — it is **data, not executable code** ([stealthium: inside CUDA fatbins](https://stealthium.io/blog/fatbins-cuda-gpu-binary-formats-part-1); [how CUDA binaries work](https://www.thesoftwarefrontier.com/p/how-cuda-binaries-actually-work); [nvfatbin docs](https://docs.nvidia.com/cuda/nvfatbin/index.html)).
- A faulting RIP that symbolizes into `.nv_fatbin` is therefore one of: (a) **jump through a corrupted function pointer / return address into a data section** (control-flow corruption — the corruptor overwrote a pointer used by an indirect call); (b) a gdb nearest-symbol artifact when RIP is in an unmapped/anon page adjacent to that section. Discriminator: check whether the RIP page's PT_LOAD in the core has the execute bit and whether RIP+0 disassembles coherently.
- The second thread sitting at an anonymous mapping is consistent with a CUDA driver-internal thread (driver threads have anon stacks) or a thread whose PC was smashed into anon memory. Pull its NT_PRSTATUS registers and compare against the core's map list (§3).

## 3. Core forensics at scale (30-100 GB truncated cores)

### 3.1 What survives truncation
- ELF **notes come first**: `NT_PRSTATUS` per thread carries registers — survives truncation; `readelf -n core` extracts them ([unix.SE 155389](https://unix.stackexchange.com/questions/155389/can-anything-useful-be-done-with-a-truncated-core), search-level — fetch 403'd; summary consistent across sources). Thread stacks often survive even when heap/anon regions are cut off; `bt N` works where full `bt` hits unreadable memory.
- A 2 GB truncation case produced incomplete backtraces and failed memory-mapping reconstruction ([HPE case](https://support.hpe.com/hpesc/public/docDisplay?docId=sf000111734en_us), search-level) — expect exactly that shape on a 28.8 GB slice of a ~120 GB VA process.

### 3.2 Tooling for huge cores
- `eu-stack --core <file>` unwinds **all threads by default**, needs no executable/debuginfo setup, and is much faster than gdb on big cores — Percona adopted it in pt-pmp for exactly that ([Percona blog, Jun 2024](https://www.percona.com/blog/eu-stack-support-and-other-improvements-in-pt-pmp-of-percona-toolkit)).
- gdb: `gdb -batch -ex "thread apply all bt" ./engine core` ([SO 18391808](https://stackoverflow.com/questions/18391808/how-do-i-get-the-backtrace-for-all-the-threads-in-gdb)); `info proc mappings`, `info registers` on whatever survived. High-quality symbolization path: debuginfod ([GNOME blog](https://blogs.gnome.org/mcatanzaro/2021/09/18/creating-quality-backtraces-for-crash-reports)).

### 3.3 systemd-coredump truncation mechanics
- systemd-coredump **≤ v250 truncates 64-bit cores at 2 GB by default** (`ProcessSizeMax`/`ExternalSizeMax`); fix via `/etc/systemd/coredump.conf.d/*.conf` overrides + `daemon-reload` ([IBM Lessons from the Field #27](https://community.ibm.com/community/user/wasdevops/blogs/kevin-grigorenko1/2023/03/20/lessons-from-the-field-27-avoiding-core-dump-trunc), fetched). Our 28.8 GB core = limits raised but still capping — check `coredumpctl info` for the truncated flag and current `ProcessSizeMax`/`ExternalSizeMax`/`KeepFree` values; a full-state core of this engine needs ~headroom for the pinned complement + anon, or a shrink policy (§3.4).
- `coredumpctl` workflow reference ([OneUptime guide, Mar 2026](https://oneuptime.com/blog/post/2026-03-02-how-to-use-systemd-coredump-for-crash-analysis-on-ubuntu/view), search-level).

### 3.4 Shaping future cores: coredump_filter + MADV_DONTDUMP
[core(5)](https://man7.org/linux/man-pages/man5/core.5.html) (fetched).

- `/proc/PID/coredump_filter` bits: 0 anon-private, 1 anon-shared, 2 file-private, 3 file-shared, 4 ELF headers, 5 private-huge, 6 shared-huge, 7/8 DAX. Default dump mask = bits 0+1+4+5 = `0x33`. The value **is preserved across execve** and inherited by fork — set it in a wrapper: `echo 0x31 > /proc/self/coredump_filter; exec ./engine` (drop bit 1 to exclude anon-shared if the driver's scratch arenas dominate; keep 4 for symbolization).
- `madvise(2)` `MADV_DONTDUMP` excludes arbitrary VA ranges — call it on the 78 GB mmap'd store (file-backed content is recoverable from the file, dumping it is pure waste) and on any retired arena. `MADV_DODUMP` re-includes. Keep the pinned complement and the pool heaps dumpable.
- RLIMIT_CORE is **ignored when the core is piped** (systemd-coredump path) — with a pipe, size control lives entirely in coredump_filter + MADV_DONTDUMP + systemd `ProcessSizeMax`. `core_pipe_limit=0` (default) means the collector may not read `/proc/<pid>` before reaping — relevant if the watcher wants to grab `/proc/PID/maps` at crash time.
- For CUDA host processes the filter governs CPU-side memory; the GPU-side capture is separate (§3.6).

### 3.5 PR_SET_DUMPABLE and watchers
- `PR_SET_DUMPABLE=0` disables core dumps entirely (and chowns /proc entries) — **do not set it** on the engine; it is the off-switch, not a shaper ([prctl(2)](https://man7.org/linux/man-pages/man2/prctl.2.html), stable reference). A watcher/parent can pre-open `/proc/<engine-pid>/maps`, `/proc/<pid>/smaps` snapshots each minute at idle so the pre-crash map layout is on disk even if the core truncates.
- eBPF class: `bpftrace`/`execsnoop`-style observers are cheap and safe to leave running — trace `mmap`/`munmap`/`mprotect`/`madvise`/`fork`/`clone` by the engine + parent to catch an unload/reload mapping event at crash time ([bpftrace](https://bpftrace.org); [Brendan Gregg eBPF overview](https://www.brendangregg.com/ebpf.html)).

### 3.6 GPU-side state capture
- `CUDA_ENABLE_COREDUMP_ON_EXCEPTION=1` (+ `CUDA_COREDUMP_FILE` pattern) makes the runtime write a GPU core (`.nvcudmp`) on device faults; open with `cuda-gdb` (`info cuda kernels`, `cuda thread`) ([cuda-gdb 13.4 docs](https://docs.nvidia.com/cuda/cuda-gdb/index.html); [vLLM blog: CUDA core dump debugging, Aug 2025](https://vllm.ai/blog/2025-08-11-cuda-debugging)). Known to sometimes not generate ([forum 341420](https://forums.developer.nvidia.com/t/cuda-coredumps-not-being-generated/341420), search-level) — treat absence as uninformative. If a sticky Xid precedes the host SIGSEGV, this captures the device-side killer while the host core cannot.

## 4. Watchdog/instrumentation that catches the corruptor BEFORE the fault

### 4.1 mprotect guard pages around the pinned complement
- Mechanism: place a `PROT_NONE` page after each critical buffer; any CPU-side overflow write faults instantly with a stack naming the writer. Classic hardening technique (Electric Fence lineage; [guard pages overview](https://www.deepwatch.com/glossary/guard-pages); [StackGuard canaries, USENIX](https://www.usenix.org/legacy/publications/library/proceedings/sec98/full_papers/cowan/cowan.pdf)).
- Feasibility on registered memory: `mprotect` changes CPU PTE bits only; the pages stay locked and the driver's DMA mapping is untouched ([Lei Mao: page-locked page tables](https://leimao.github.io/blog/Page-Locked-Host-Memory-Page-Table)). So guard pages catch **CPU-side** writes into the complement — our likeliest corruptor — without breaking CUDA.
- Boundary: guard pages do **not** catch GPU DMA writes (device transactions bypass CPU page tables; enforcement lives in the IOMMU). A GPU-origin OOB write shows up instead as IOMMU/DMAR faults in `journalctl -k` if the IOMMU is enabled, or not at all on consumer setups ([pinned memory + DMA overview](https://www.abhik.ai/concepts/language-internals/pytorch-pin-memory), search-level). Enable IOMMU before the soak to close this blind spot.

### 4.2 Poisoning and canaries
- `MALLOC_PERTURB_=<byte>` (glibc) fills freed memory with a byte pattern and fresh allocations with its complement — turns silent reuse-into-stale into immediate wrong-values ([malloc(3)](https://man7.org/linux/man-pages/man3/malloc.3.html), stable reference). Near-zero cost; first line.
- Explicit free-list poisoning + epoch tags on the pool's job descriptors (the fixed T18 bug's neighborhood): write a generation counter into each descriptor; a 5-second idle-time sweeper thread checksums the descriptor array and logs which descriptor/epoch changed without a dispatch. This converts "corruptor strikes idle" into a timestamped first-touch event, hours before SIGSEGV.
- Allocator-level: tcmalloc/jemalloc debug modes offer guard/quarantine semantics if the engine's allocator is swappable (jemalloc `--enable-debug` / `MALLOC_CONF=abort:true,junk:true` pattern; [guard-page heap debugging overview](https://www.deepwatch.com/glossary/guard-pages)).

### 4.3 Live watchpoints on the hot structures
- gdb hardware watchpoints on the doorbell word / next-job index / epoch (`watch -l *(uint64_t*)&ring.head`): at idle the engine is quiescent, so a hardware watchpoint costs nothing and catches the exact writer instruction + full stack ([gdb manual — Set Watchpoints](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Set-Watchpoints.html), stable reference). Best used attached from the parent at last-request-completion, armed for the idle window.

### 4.4 Health-probe thread + protocol-side watchers
- Periodic probe from a dedicated thread at idle: `cudaGetLastError()` + `cudaStreamQuery` on a dedicated probe stream + a trivial probe kernel + `cudaMemGetInfo`. Any sticky context damage surfaces at the probe with a timestamp instead of corrupting a deferred call ([sticky-error class, §2.5](https://forums.developer.nvidia.com/t/cuda-errors-determine-sticky-ness/271625)).
- Doorbell/protocol side: epoll error-edge (`EPOLLHUP|EPOLLERR`) and an epoll-driven watchdog on the protocol pipe; log every line-protocol write with epoch+length; a length-tag mismatch on read = corruptor caught in the act of a buffer overrun on the wire path (vLLM #35104's fence-corruption analog, §2.7).
- Xid watcher: `journalctl -k -f` filtered to NVRM/Xid in the parent; record Xid + timestamp alongside engine state ([Xid docs](https://docs.nvidia.com/deploy/xid-errors/latest/index.html)).
- `CUDA_LAUNCH_BLOCKING=1` linearizes launches — recommended in CUDA debugging practice to convert deferred faults into immediate, correctly-attributed ones ([HPC Admin Tech CUDA pitfalls](https://www.hpcadmintech.com/wp-content/uploads/2016/03/Carlo_Nardone_presentation.pdf), search-level; [PyTorch guidance](https://discuss.pytorch.org/t/how-to-fix-cuda-error-device-side-assert-triggered-error/137553)). Slow but honest; run a soak in this mode as a discriminator between device-fault-at-idle vs host-only corruption.

## 5. Determinism tools

### 5.1 rr on CUDA — verified dead end in 2025-26
[rr issue #2173](https://github.com/rr-debugger/rr/issues/2173) (fetched).

- `rr record` on any CUDA binary fails at `cuInit()` (`CUDA_ERROR_NO_DEVICE` assertion). Maintainer (2018): rr "doesn't understand [the driver's] communication between userspace and kernel space/hardware"; ioctls touch memory "not referred to by any of the args" (maleadt). Last activity **Sep 2024**: with NVIDIA's open kernel driver documenting ioctls, it "might be worth investigating" — still open, no support shipped through 2026. No workarounds found in the thread.
- Verdict for this engine: **not usable** — the pinned complement, graphs, and driver worker threads all ride unsupported ioctls/mappings. Commercial TTD (Undo) claims long-running-process recording generally but CUDA support is unverified here (search-level only) — do not budget for it without a trial.

### 5.2 What replaces record-replay here
- The engine is its own replay: every dispatch already passes the doorbell. Log (epoch, cohort shape, dispatch kind, descriptor hash) per dispatch + a forced idle-drain → unload → re-capture cycle in a loop (idle-hammer harness). If MTBF collapses from ~hourly to minutes, the reload path owns the corruptor. This is the deterministic-substitute that costs hours, not weeks, and needs no kernel support.
- Keepalive discriminator (vLLM #35104 pattern, §2.7): 1-line request every 120-300 s. Crashes stop → idle-path trigger confirmed; crashes continue → corruptor rides async driver work and idleness is coincidence.
