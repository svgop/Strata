# Web digest — hugepage/THP regressions and what fixed them

## Verdict (read this first)

1. **A large boot-reserved hugetlb pool is a *capacity* tax on every workload, documented as expected behavior — not a kernel bug.** Reserved pool pages leave the buddy allocator, are excluded from `MemFree`/`MemAvailable`, cannot back page cache, and cannot be reclaimed or swapped ([kernel hugetlb doc](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html), [man7 proc_meminfo](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html), A). Red Hat states the reservation "effectively reduces the amount of memory available to the system" and "prevents it from properly using its full memory capacity" (B). **No source frames this as a defect; the documented fix is exactly what we did — release the pool.** Our case matches documented design behavior, not a 7.2.x regression (no 7.2.x mm throughput regression found anywhere; documented absence, section 5).
2. **The page-class (TLB) upside is small; the capacity downside is large.** Measured hugepage/THP wins: 0-3% typical, ~10% best, 12% for a page-table-bound DB at 200 connections ([nelhage](https://blog.nelhage.com/post/transparent-hugepages/), A; [ClickHouse](https://clickhouse.com/blog/huge-pages-clickhouse-managed-postgres), B). Losses from THP=always on the *same* box: "Several applications have seen 30% performance degradations or worse" (A). A 10-25% box-wide tax from a 58%-of-RAM pool sits far outside any TLB-effect band and squarely inside the capacity-loss band.
3. **MoE expert streaming is page-cache-headroom-bound, and pinning the expert slabs is measured NEGATIVE — even when done for the engine's own benefit.** vllm.cpp staged ~70 GiB routed-expert slabs into a non-evictable pool: same-binary median-of-3, **19.43 → 18.76 tok/s (0.966x)**, because the grouped-MoE kernels are dequant/latency-bound (~19-24% of peak BW, residency can't help them) while the pinned pool **cut unified reclaimable headroom ~103 → ~30 GiB** (A, [vllm.cpp BENCHMARKS.md](https://github.com/localai-org/vllm.cpp/blob/main/docs/BENCHMARKS.md)). A 106 GiB boot-reserved pool carved from the same RAM is the same move with worse economics: no kernel-side benefit for the consumer, full page-cache loss for everything else.

**Mechanism for our case (best fit, A-grade analogues):** 106 GiB pool = ~58% of RAM removed from page cache on a box where both engines stream 40-80 GiB of mmap'd expert weights through that cache. Cache floor collapses → eviction/reload churn and kswapd pressure on every process, plus earlier watermark crossings (hugetlb is out of `MemAvailable`, so reclaim begins at the same absolute watermarks with ~half the reclaimable pool). Release restores — exactly our observation. Residual 206-221 vs 233 solo is host-state aging, owned by the other digests.

**Boundary:** no public incident report states "reserved pool slowed *unrelated* workloads by N%" with numbers. The effect is documented as capacity accounting (vendor docs) and inferred headroom mechanics, not as a bug tracker entry. Our measurement is therefore the strongest direct datapoint found.

## 2. Mechanism chain (kernel-doc grounded)

1. `nr_hugepages` carve-out at boot takes contiguous 2 MiB blocks out of the buddy allocator into the persistent pool; pool pages are unmovable, unswappable, uncacheable ([hugetlbpage doc](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html), A).
2. `MemAvailable` = MemFree + reclaimable page cache + SReclaimable − reserves; pool pages never appear ([man7](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html), A).
3. Watermarks (min/low/high) are per-zone constants scaled by `watermark_scale_factor`; reclaim (kswapd) wakes at low watermark and scans *page cache* first ([kernel sysctl vm doc](https://docs.kernel.org/admin-guide/sysctl/vm.html), [SUSE tuning](https://documentation.suse.com/sles/12-SP5/html/SLES-all/cha-tuning-memory.html), [Oracle: anticipating memory needs](https://blogs.oracle.com/linux/anticipating-your-memory-needs), A/B).
4. With ~58% of RAM outside the reclaimable set, the same absolute watermarks are reached with ~half the file-cache cushion → kswapd active earlier and longer; direct reclaim (allocation slowpath) is the documented throughput-killer ([kernel-internals: running out of memory](https://kernel-internals.org/mm/oom), B).
5. mmap-streamed MoE weights re-fault through a now-starved cache → page-fault storms and repeated disk reads, documented for exactly this access pattern ([NVIDIA forum: slow mmap on DGX Spark, ~60 GiB paged in page-by-page](https://forums.developer.nvidia.com/t/very-slow-mmap-on-dgx-spark-that-affects-model-loading-questions-to-nvidia/349886), [carteakey: llama.cpp mmap default](https://carteakey.dev/blog/local-inference/local-llm-optimization), B/C).
6. **Unmovable-pool fragmentation:** the pool itself, reserved at boot, does NOT fragment the remaining zones (it is carved before fragmentation, which is why docs recommend boot-time reservation). The fragmentation risk class is *runtime* pool growth and wrong-migration-type fallbacks: Johannes Weiner's finding that fallback allocations cause fragmentation persisting "until the system reboots"; kswapd/kcompactd taught to build page-block-sized free chunks ([LWN, Mar 2025: huge page allocation](https://lwn.net/Articles/1014220/), A). `MIGRATE_MOVABLE` vs `MIGRATE_UNMOVABLE` pageblock mechanics and page-stealing: ([PingCAP fragmentation deep-dive](https://www.pingcap.com/blog/linux-kernel-vs-memory-fragmentation-1), [syst3mfailure page allocator](https://syst3mfailure.io/linux-page-allocator), B).

## 3. THP / khugepaged regressions — documented cases + what fixed them

The single best war-story compendium: [kernel-internals: mm performance regressions](https://kernel-internals.org/mm/war-stories-regressions) (B, carries commit hashes).

| Case | Degradation | Mechanism | Fix |
|---|---|---|---|
| THP `defrag=always` (v2.6.38→~4.x) | Redis/PG/MySQL/Java: sub-ms requests took **tens of ms**; appeared only after hours of uptime (fragmentation-state dependent) | synchronous compaction **inline in the page-fault path**; one 2 MiB THP fault could scan/migrate "hundreds of megabytes" | defrag modes; `defer` in v4.6 (commit `444eb2a449ef`) moves compaction to khugepaged; operators run `defer+madvise` or `never`; diagnose via `compact_stall`/`compact_fail` in `/proc/vmstat` |
| khugepaged CPU storms | container hosts/CI: **1-5% of a core** periodically, mmap_lock read contention with faults | scans every THP VMA each cycle; `max_ptes_none=511` → repeated failed collapses of "almost collapsible" regions | `scan_sleep_millisecs`, `pages_to_scan`, `max_ptes_none=0`; later kernels skip unchanged VMAs; per-cgroup THP control |
| Automatic NUMA balancing (v3.13) | HPC/numactl-tuned and shared-memory workloads | TLB-shootdown IPI storms (up to all CPUs), page-table lock contention, shared-page thrash | `kernel.numa_balancing=0` + scan tunables; `numa_pages_migrated` in vmstat |
| Swap readahead window swings | any swapping system | over/under-prefetch by workload shape | adaptive window; `vm.page_cluster` (0 for NVMe/random) |

Primary write-ups:
- nelhage (A): THP benefit "up to about a 10% performance improvement", **0-3% typical**; 512x memory bloat via khugepaged; forced 2 MiB→4 KiB splits before fast ops = long pauses; **"Several applications have seen 30% performance degradations or worse with THP enabled"**; fix = `transparent_hugepage=madvise`. Go needed a runtime workaround ([golang/go#8832](https://github.com/golang/go/issues/8832)).
- Vendor disable-THP guidance: [MongoDB](https://www.mongodb.com/docs/manual/tutorial/transparent-huge-pages) (A, vendor doc), [Redis/IBM](https://ibm.github.io/event-automation/es/es_2019.2.1/troubleshooting/redis-latency-transparent-huge-pages) (B) — COW fork amplification 4 KiB→2 MiB.
- MariaDB ships `PR_SET_THP_DISABLE` because THP harmed it (A, [LWN Aug 2025](https://lwn.net/Articles/1032199/)); same article covers the 2025 control-state additions (`PR_THP_DISABLE_EXCEPT_ADVISED`, per-size mTHP sysfs, BPF order-selection proposal).
- PostgreSQL: "THP is not recommended for PostgreSQL on Linux"; oversizing reservations "can also drive a system into an out-of-memory situation" ([Cybertec](https://www.cybertec-postgresql.com/en/huge-pages-postgresql/), B).

**Relevance to our box:** we ran stock THP with a `MADV_HUGEPAGE`-mapped engine; none of these paths require a hugetlb pool, and our tax survived identical THP settings with the pool released → the pool's capacity term, not THP machinery, carried the regression.

## 4. Large-folio / mTHP regressions 2024-2026 (the modern cliff class)

- mTHP swap-out: 64K mTHP swap went from a **14% regression to a 46% improvement** vs 4K after swap-out-without-splitting landed ([LKML Apr 2024](https://lkml.org/lkml/2024/4/8/1131), A); order-0 swap allocator fragmentation concerns in the common case ([LKML Jun 2024](https://lkml.org/lkml/2024/6/19/409), A).
- mTHP landed in 6.10; per-size tuning and benchmark history: ([LWN mTHP](https://lwn.net/Articles/954094), A; [LPC 2024 benchmarks](https://lpc.events/event/18/contributions/1721/attachments/1577/3281/mTHP_LPC2024.pdf), A).
- 2025 swap-cache rework ("swap table") improving folio-lock throughput ([LWN May 2025](https://lwn.net/Articles/1021301), A).
- 2025 control-layer work motivated by "use of huge pages can make some workloads slower as the result of internal memory fragmentation, so the THP feature is often disabled" ([LWN 1032199](https://lwn.net/Articles/1032199/), A).

**Lesson:** every large-folio regression of the era was an *allocator/reclaim path* regression fixed by patches or knobs — none were fixed by reserving more memory.

## 5. Kernel-version cliffs 2025-2026 (incl. documented absence for 7.2.x)

- **Documented absence:** no Fedora Bugzilla/LKML report found of a 7.2.x mm/hugepages throughput regression. Searches surface only: a Fedora + Tuned-PPD governor regression fixed in a newer kernel ([Phoronix, Aug 2026](https://www.phoronix.com/news/Fedora-Tuned-PPD-Perf-Fix), B); an early-7.0.0 Fedora testing regression thread ([discussion.fedoraproject.org](https://discussion.fedoraproject.org/t/resolved-early-kernel-7-0-0-testing-shows-massive-regression/187900) — direct fetch timed out, unverified content); F45 shipped kernel 7.2 Nov 3, 2026 ([Fedora Magazine](https://fedoramagazine.org/announcing-fedora-linux-45), A).
- Linux 7.4 core MM pull (rc2) is **correctness, not throughput**: huge PMD/PUD refcount/TLB-flush bugs, shmem/memfd data loss, GUP fixes — mostly reported by Anthropic ([Phoronix](https://www.phoronix.com/news/Linux-7.4-Core-MM-Nasty-Fixes), B).
- 7.2.7 Fedora advisory exists (security/critical fixes) ([linuxsecurity.com](https://linuxsecurity.com/advisories/fedora/fedora-45-kernel-2026-4c098c462e), B).

**Read:** our regression tracks a configuration state (pool armed), not a kernel-version cliff. The 7.2.12→7.2.15 delta is unrelated on current evidence.

## 6. Opposite evidence — pools that helped, and how they were sized

| Deployment | Measured result | Pool sizing | Grade |
|---|---|---|---|
| ClickHouse Managed PostgreSQL (r7i.4xlarge) | pgbench select-only, 100 clients: **373,083 → 418,087 TPS (12%)** with 2 MiB pages; page tables **6.12 GB → 111 MB** at 200 conns | "A quarter of the machine's memory", mirroring `shared_buffers` = 25% of RAM; reserved before start after cache flush + compaction; overcommit tuned against the **remaining 75%** | B (production operator, numbers given) |
| PostgreSQL generally | huge pages only for shared_buffers; compute exactly with `postgres -C shared_memory_size_in_huge_pages` (PG 15+); `huge_pages=on` pins, `try` "silently falls back to 4KB pages" | pool = shared memory need (+segment overhead ~750 MB on a 32 GB cache), never a fraction of total RAM | A/B ([PG docs](https://www.postgresql.org/docs/current/runtime-config-resource.html), [Cybertec](https://www.cybertec-postgresql.com/en/huge-pages-postgresql/), [Stack Harbor](https://stackharbor.com/en/knowledge-base/postgres-huge-pages-shared-buffers)) |
| SGLang | `--enable-thp` (MADV_HUGEPAGE on KV pool) — opt-in per-process, no reserved pool; docs lag the flag ([server args](https://sgl-project.github.io/advanced_features/server_arguments.html), [repo](https://github.com/sgl-project/sglang)) | none — THP madvise, not hugetlb pool | B |
| vllm.cpp | residency levers help only **bandwidth-bound** kernels (dense Q8_0 tower: ~20% per-launch gain, 63% of DRAM peak); residency is measured **NEGATIVE** on dequant/latency-bound grouped-MoE kernels | pin only what a bandwidth-bound consumer proves; never pin what the page cache is serving | A |
| Oxla (OLAP, Redpanda write-up) | rationale (TLB reach, one fewer walk per miss); **no published numbers**; notes `glibc.malloc.hugetlb=2` degrades when the pool runs out | pool via sysfs; OOM possible "when not enough memory is available outside huge pages pools" | B ([redpanda.com/blog/oxla](https://www.redpanda.com/blog/oxla-using-huge-pages-in-linux-applications)) |

**The uniform doctrine: pool = measured consumer demand, reserved at boot, sized to leave the streaming cache intact.** Nobody in the evidence set reserves 50-60% of RAM. The "<25%" pattern traces to `shared_buffers = 25% of RAM` ([PG docs](https://www.postgresql.org/docs/current/runtime-config-resource.html)) mirrored by ClickHouse's quarter-of-memory pool.

## 7. Sizing/arming doctrine that avoids the tax

1. **Pool = worst concurrent consumer draw, measured.** Not model size, not box size. Large `HugePages_Free` at steady state = oversize = pure page-cache loss (Red Hat, Cybertec; B).
2. **Keep the streaming cache whole.** Budget: `MemAvailable_after_reservation ≥ working_set + watermark headroom`. On a page-cache-streaming box (our MoE case), leave ≥40-50% of RAM outside the pool; ClickHouse tunes overcommit against the remaining 75% for a 25% pool (B).
3. **Boot-reserve only.** Runtime `nr_hugepages` growth runs compaction against a fragmented buddy allocator; boot carving is the documented reliable path ([hugetlbpage doc](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html), A; [RHEL 7 tuning](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/7/html/performance_tuning_guide/sect-red_hat_enterprise_linux-performance_tuning_guide-memory-configuring-huge-pages), B).
4. **THP stays `madvise` on any shared box.** `always` carries documented 30%+ degradations and fault-path compaction stalls; per-engine opt-in (SGLang `--enable-thp`) gets the upside without taxing others (A).
5. **Diagnostics before arming a pool:** `compact_stall`/`compact_fail`, `pgscan/pgsteal`, kswapd CPU, `thp_collapse_alloc_failed` in `/proc/vmstat`; `MemAvailable` floor; `HugePages_Free` vs `Total` (A/B).
6. **An unused pool is a live tax — release it.** `nr_hugepages=0` is the documented remedy and matched our observed recovery (A for the mechanism; our measurement for the magnitude).
7. **Do not pin what the page cache is serving.** Residency/pool levers pay only for bandwidth-bound kernels; dequant/latency-bound MoE kernels gain nothing and pay the headroom cost (A, vllm.cpp).
