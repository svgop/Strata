# sm_120 kernel advances for the hybrid decode loop — evidence digest

Question: which CUDA 12.8-13.x features and kernel families have REAL sm_120 production users with numbers, and which of them attack the GPU term (7.2 ms / attention 25% launch tax / 9-16 ms window) or the slack (syncs, launch, gaps) — given the lane is DRAM-bound at 49.5 GB/s and untouchable by GPU kernels. Box: RTX 5070 12 GB, 262K context leaves ~1.2 GB free, CUDA 13.4 toolchain. Falsified and standing (do not re-propose): tcgen05 on sm_120 (status re-verified below), FA4, PDL ALONE, TF32 TC scorer, DS4_AHEAD prefetch, SMT lanes, CUDA-graph-everything for DS (+10-15% not 3.75×). Queued (extended, not duplicated): conditional graph nodes for DS round-graph, micro-group expert pipelining over PCIe, L2 persistence window, FP8 KV for DS, persistent megakernel for the 36 GDN layers.

## tcgen05 re-verification (standing falsification, now source-verified)

- tcgen05 (5th-gen tensor cores, tensor-memory based) exists ONLY on datacenter Blackwell sm_100/sm_10x. Consumer Blackwell sm_120 — including the `sm_120a` arch-specific suffix — has NO tcgen05 path; the programming model is register-based `mma.sync` (`mma.sync.aligned.m16n8k16` lineage). Sources: https://github.com/NVIDIA/cuda-rust/issues/1194 ; https://gau-nernst.github.io/tcgen05/ ; https://github.com/modular/modular/issues/5707 (MAX fails to build on sm_120 because kernels assume tcgen05); https://forums.developer.nvidia.com/t/dearest-cutlass-team-when-the-hell-are-you-going-to-properly-fix-tcgen05-fp4-support-for-dgx-spark-gb10-sm121/359598
- Second sm_120 constraint confirmed alongside: NO CTA clusters on sm_120 (Colfax's NVFP4 sm_120 GEMM works around both; https://research.colfax-intl.com/cutlass-tutorial-nvfp4-blockscaled-gemm-on-nvidia-rtx-pro-blackwell-gpus-sm12x), and only ~99 KiB shared memory vs 228 KiB on SM100 — ported datacenter kernels break on smem sizing (https://forums.developer.nvidia.com/t/psa-state-of-fp4-nvfp4-support-for-dgx-spark-in-vllm/353069).
- Verdict unchanged: DEAD. Any kernel candidate must be mma.sync-based, ≤99 KiB smem, cluster-free.

## 1. CUDA 12.8-13.x features on consumer Blackwell — maturity + users

### Conditional graph nodes (cudaGraphConditionalHandle)
- Mechanism: device-written boolean/scalar decides IF/ELSE/SWITCH/WHILE branches INSIDE one graph replay; no host round-trip. Introduced 12.4; CUDA 12.8 added ELSE and SWITCH and is the version NVIDIA documents as the full feature set (https://developer.nvidia.com/blog/dynamic-control-flow-in-cuda-graphs-with-conditional-nodes).
- Body-node restrictions (same source): kernels (NO cooperative/CDP inside), empty, child graphs, memset, memcpy, nested conditionals; all nodes in one context.
- Maturity: API-complete since 12.8; NO public inference engine ships it yet (vLLM/SGLang use torch-style whole-capture graphs instead; nothing in TRT-LLM release notes). Adopters are HPC/graphics. ROCm parity still open (https://github.com/ROCm/hip/issues/3905) — proof it is considered production-grade API surface, but young.
- Fit: directly targets the DS 3-host-syncs/round and the queued round-graph: layer loop + early-exit-on-eos + per-round retry all expressible as a WHILE/IF inside one replay. Graphs don't touch the lane wait (already re-priced) — this removes the HOST side of the syncs, not the lane.
- Verdict: TRANSFER (slack term). Highest-leverage queued item, now with confirmed 12.8 semantics. Engineering cost: high-ish (manual node construction, no torch help), risk: medium (young API; validate node-count limits per graph on 13.4 first).

### Device graph launch (cudaGraphLaunch from device)
- Mechanism: graph launched from running device code (cudaGraphInstantiateFlagDeviceLaunch; introduced CUDA 12.0; device-launched graphs must be launched from within a device context/kernel; https://developer.nvidia.com/blog/enabling-dynamic-control-flow-in-cuda-graphs-with-device-graph-launch ; https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html ; https://stackoverflow.com/questions/79789225/executing-a-cuda-graph-from-a-cuda-kernel).
- Maturity: API stable, adopters rare (kernel-scheduling research, not inference stacks).
- Fit: overlaps conditional nodes; conditional nodes alone cover the DS round loop. Device launch adds nothing for us unless a persistent kernel must CHAIN rounds — exactly the queued GDN megakernel territory, not a separate feature.
- Verdict: DEAD as a standalone item (covered by conditional nodes / persistent kernel).

### PDL combos (PDL + graphs, PDL + load-hoisting) — NOT "PDL alone"
- Mechanism: secondary kernel launches while primary runs; `cudaGridDependencySynchronize()` before consuming; producer-independent loads hoisted BEFORE the wait; `cudaTriggerProgrammaticLaunchCompletion()`/`griddepcontrol.launch_dependents` early-trigger. Hopper+ feature, works on sm_120 (mma.sync kernels, no tcgen05 dependency).
- Production users with numbers:
  - LMSYS Ling-3.0-flash spec decode on Blackwell (2026-08-21): PDL chains THREE paths (MoE main, router, KDA) across SIX converted kernels; the load-hoist trick matters — "producer-independent loads go before the wait" (2.6 MB gate-weight cold read overlaps producer tail); early-trigger `launch_dependents` moved to right after producer's own wait, gated to M≤512 because at prefill shapes early release steals SMs. Measured: router gate matvec 7 µs hot vs 11 µs cold; draft-extend graph fix alone took NEXTN 288 tok/s/3.33 ms TPOT → 526 tok/s/1.76 ms; final tuned 606 tok/s/1.53 ms; their DSpark draft reached 1120 tok/s, accept 9.95. Bitwise-neutral verified (GDC on/off 4/4 identical). https://www.lmsys.org/blog/2026-08-21-ling3-flash-spec-decode-blackwell
  - vLLM × HPC-Ops (2026-07-06): PDL-chained stages erase inter-kernel bubbles in attention/MoE backends. https://vllm.ai/blog/2026-07-06-vllm-hpc-ops
  - FlashInfer: `enable_pdl` constructor arg on Blackwell kernels (release PRs); FlashInfer paper reports 29-69% inter-token latency cuts vs compiler backends (multiple mechanisms). https://flashinfer.ai/releases
  - Counter-evidence: llama.cpp PR #15480 (PDL on ALL kernels) was NEVER merged — maintainer: "speedup seems to be largest when running very small models on very fast GPUs", marginal gain for a lot of code; disabled when external BLAS kernels present (https://github.com/ggml-org/llama.cpp/issues/15479).
- Fit: our falsified verdict was PDL ALONE. The production pattern is PDL+graphs+load-hoist per kernel pair. Attention is 25% launch tax on DS — if ~1.8 ms of that is inter-kernel gaps inside the attention sequence, PDL-chaining the attention pipeline is the mechanism that attacks exactly those gaps. sm_120 evidence is the LMSYS work (Blackwell, spec decode, same shape family as ours).
- Verdict: TRANSFER, conditional on the combo form (graphs already running; PDL on the 5-6 hottest DEPENDENT pairs; hoist weight/KV-prefetch loads above the gdc_wait). Cost: medium (per-kernel audit), risk: low (bitwise-neutral when accumulation order unchanged — LMSYS proved).

### Green contexts (SM partitioning)
- Mechanism: in-process SM subsets via cuCtxCreate with resource descriptors; CC 9.0+ (sm_120 qualifies mechanically); H100-documented granularity min 8 SMs/multiples of 8. https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/green-contexts.html
- Maturity: zero inference adopters; academic partitioning studies note split/merge is cumbersome and there is NO memory-bandwidth QoS (https://hal.science/hal-05788038v1/document ; https://www.cs.unc.edu/~jbakita/ecrts25.pdf).
- Fit: our problem is not SM contention — the lane wait is a HOST-side wait; a reserved SM slice for a poller kernel does not speed the DRAM lane.
- Verdict: DEAD.

### Stream priorities
- Mechanism: `cudaStreamCreateWithPriority`; affects ORDER of pending concurrent launches only; no preemption of running kernels; typically 2 levels (https://forums.developer.nvidia.com/t/how-high-priority-stream-preemption/78183 ; https://arxiv.org/html/2401.16529v1).
- Fit: single-process box, one latency-critical stream already; nothing to deprioritize.
- Verdict: DEAD.

### Memory pool release-threshold tuning (steady-state zero-alloc)
- Mechanism: `cudaMemPoolSetAttribute(pool, cudaMemPoolReleaseThreshold, UINT64_MAX)` on a cudaMallocAsync pool → freed blocks reused, never returned to OS; removes alloc-triggered page ops/syncs at steady state. https://developer.nvidia.com/blog/using-cuda-stream-ordered-memory-allocator-part-1 ; https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/stream-ordered-memory-allocation.html
- Production: RMM/torch (`PYTORCH_CUDA_ALLOC_CONF=backend:cudaMallocAsync`), vLLM's cumem allocator (https://docs.vllm.ai/en/stable/api/vllm/device_allocator/cumem). Battle-tested pattern.
- Fit: DS engine runs NO graphs and 3 host syncs/round — if any per-round alloc touches a non-caching path, this is pure slack removal. CAUTION: 1.2 GB free — a never-release pool must be bounded (set threshold ~256 MB, not UINT64_MAX, so the pool cannot eat KV headroom). torch native caching allocator already gives zero-alloc steady state for torch-owned tensors; this pays only for engine-owned cudaMallocAsync or cudaMalloc-free paths.
- Verdict: TRANSFER, small and cheap (bounded threshold; one afternoon) — insurance against alloc-jitter in the ~4 ms slack.

### cudaMemAdvise / cudaMemPrefetchAsync for pinned host reads
- Mechanism check: both APIs apply to MANAGED (unified) memory only. Pinned host memory (cudaHostAlloc/cudaHostRegister) is already zero-copy-optimal; there is nothing for these APIs to do on it (https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html ; https://www.olcf.ornl.gov/wp-content/uploads/2019/06/06_Managed_Memory.pdf).
- Fit: the lane reads weights from host DRAM at 49.5 GB/s (proven ceiling); GPU-side memory hints cannot move that term, and migrating managed memory over PCIe would make it WORSE.
- Verdict: DEAD (mechanism mismatch).

### Batched memcpy — cudaMemcpyBatchAsync (NEW in CUDA 12.8)
- Mechanism: submit many copies in one call, amortizing per-call CPU/driver overhead; 3D variant; requires a NAMED stream (default stream → "invalid argument"); does NOT aggregate D2D into one transfer. https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-host-programming.html ; https://github.com/rapidsai/rmm/issues/2509 ; https://forums.developer.nvidia.com/t/cudamemcpybatchasync-cannot-aggregate-d2d-copy-operations/353401
- Production: RMM adopted it (same issue) for allocator copies; no inference-engine usage notes yet.
- Fit: feeds the QUEUED micro-group expert pipelining — per-cohort H2D/D2H activation+result swaps collapse from N calls to 1; PCIe transfers still cost the same bytes, only the HOST overhead shrinks.
- Verdict: TRANSFER, small (supports the queued pipelining item; do not expect byte-speed change).

## 2. Attention kernels for sm_120 consumer

### FlashAttention-3/4 status on sm_120
- FA4: does NOT run on consumer Blackwell (sm_120); tracking issue confirms blockers — no FP8 KV support and block-sparsity explicitly asserted OFF on SM 12.0 (https://github.com/Dao-AILab/flash-attention/issues/2307 ; https://github.com/Dao-AILab/flash-attention/issues/2860 ; guide: https://www.spheron.network/blog/flashattention-4-blackwell-gpu-cloud-guide). FA3 was Hopper-shaped (wgmma) and is not the sm_120 path either.
- What IS speed-of-light on sm_120 prefill: plain Ampere-style mma.sync m16n8k16 + cp.async + ldmatrix.x4 + smem swizzle reaches 197.7/209.5 TFLOPS (94.4% SOL) BF16 on RTX 5090 — and PyTorch's CuDNN SDPA backend already hits 97.2% SOL (203.6 TFLOPS), i.e. the ATTENTION-PREFILL term is closed by stock software (https://gau-nernst.github.io/fa-5090/). Author explicitly skips TMA on sm_120 ("supports cp.async.bulk, but I don't use it here") and notes consumer smem is "modest" — the 99 KiB constraint again.
- Verdict: FA4 DEAD (re-confirmed). Prefill attention needs nothing custom.

### FlexAttention
- Paged-KV FlexAttention exists as a paper with L4 (Ada) numbers, latency growing ~linearly (~2×) with context; no sm_120 production path, no decode numbers vs FlashInfer. https://arxiv.org/html/2506.07311v1
- Verdict: DEAD for this box (no production sm_120 evidence; decode metric absent).

### SageAttention (FP8 QK^T PV) / SageAttention3 FP4
- SageAttention2 on RTX 5090: 560 TOPS, ~2.7× vs FA2 kernel-level; sm_120 supported in the official repo; end-to-end real-workload gains 20-37% (video generation = prefill-dominated). SageAttention3 FP4: paper claims 1038 TOPS (~5× vs FA); real-measured gap much smaller in practice per issue #378. Quality: near-lossless per-block FP8 with per-block scales; FP4 shows visible quality deltas in some workloads. https://github.com/thu-ml/SageAttention ; https://github.com/thu-ml/SageAttention/issues/378 ; community: https://www.reddit.com/r/StableDiffusion/ (Sage 2.1 ~37% faster than FA 2.7 on 5090, Windows)
- Fit: decode at 262K is KV-BYTES-bound, not QK^V-compute-bound; Sage's wins concentrate in the prefill/long-Q regime. For DECODE the relevant quantization is of K/V cache (below), not QK^T math.
- Verdict: DEAD for decode loop (keep on the shelf for the 262K PREFILL pass only, where 20-37% is real).

### Paged/combined decode attention — FlashInfer XQA on SM120 (the one that matters)
- FlashInfer ships an XQA decode kernel family for Blackwell RTX / SM120-121 (TRT-LLM lineage), used with attention sinks and sliding window; v0.6.16 (2026-07-31) added RAGGED Q + per-row sliding-window masking FOR SPECULATIVE DECODE on SM120/121 — "causal/non-causal draft-block masks, letting each request verify a different draft-token count". https://docs.flashinfer.ai/api/attention.html ; https://flashinfer.ai/releases
- This is the first-class spec-decode decode-attention kernel for CONSUMER Blackwell: one kernel, variable rows per request, no padding-to-cap.
- KV read bytes at 262K:
  - NVFP4 KV cache decode kernels are SM120-EXCLUSIVE (they exist on consumer Blackwell before datacenter paths for some shapes) — FlashInfer QA nvfp4-KV decode confirmed working on RTX 5090 sm_120 (https://github.com/vllm-project/vllm/issues/49011); DeepSeek-V4 NVFP4 sparse-MLA decode ("cake" backend) on RTX 5090/RTX PRO 6000 shipped v0.7.2 (2026-10-15); NVFP4 KV halves KV footprint vs FP8 KV (https://developer.nvidia.com/blog/optimizing-inference-for-long-context-and-large-batch-sizes-with-nvfp4-kv-cache).
  - FP8 KV state-of-the-art in vLLM (2026-04-22): FP8 KV is "most compelling for long-context, decode-heavy serving where KV-cache traffic dominates bandwidth"; halving KV bytes roughly halves that traffic term (https://vllm.ai/blog/2026-04-22-fp8-kvcache ; measured comparisons: https://blog.squeezebits.com/vllm-vs-tensorrtllm-8-kv-cache-quantization-35079).
- Launch tax: graphs already own the launch term; the remaining attack on attention is BYTES (KV quant) and gaps (PDL combo above). Community existence proof of the full recipe — NVFP4 weights + NVFP4 KV + MTP + 262K context on one RTX 5090 (https://www.reddit.com/r/Vllm/comments/1vu6vo3/my_rtx_5090_vllm_recipe_nvfp4_weights_nvfp4_kv/ — thread not fetchable, treat as unverified-but-precise anecdote).
- Fit: 262K KV at fp16 is the dominant device-memory consumer on 12 GB; FP8 KV frees ~half the KV bytes → directly buys back context headroom from the 1.2 GB free floor AND cuts the attention GPU term proportionally to KV bytes. FP4 KV doubles that again where FlashInfer's SM120-exclusive kernels cover our shape.
- Verdict: TRANSFER — the strongest single kernel-side lever for BOTH engines' GPU term at 262K. Cost: medium (FlashInfer integration or kernel lift), risk: quality recalibration at 262K required (measure before/after on long-context tasks; FP8 KV is the low-risk step, FP4 KV the follow-on).

## 3. Speculative-decode kernel support

### EAGLE-3 verify machinery in production
- vLLM + SGLang ship EAGLE-3/MTP in production: Red Hat measured up to 2.5× with vLLM EAGLE-3 (https://developers.redhat.com/articles/2025/07/01/fly-eagle3-fly-faster-inference-vllm-speculative-decoding); MLX-LM discussion reports 3.3-6.5× on CUDA EAGLE-3 because tree verify is "nearly free" at these shapes (https://github.com/ml-explore/mlx-lm/discussions/890). TRT-LLM enumerates the draft/verify kernel zoo (https://nvidia.github.io/TensorRT-LLM/advanced/speculative-decoding.html).
- Verify kernels: SGLang's `sgl_kernel` carries `verify_tree_greedy`, `build_tree_kernel_efficient`, `tree_speculative_sampling_target_only` — the tree-accept kernels; overhead concentrates in (a) verify running at padded batch×(draft+1) shapes and (b) tree state indexed by tree path (LMSYS restricted their compact spec cache to topk=1 chains for exactly this reason — trees "would have to be indexed by tree path"). https://lmsys.org/blog/2026-08-21-ling3-flash-spec-decode-blackwell
- SGLang draft runners: EAGLE draft / draft-extend / frozen-KV MTP each get their OWN CUDA-graph runner built on the decode runner (https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph); draft-capture improvements tracked at https://github.com/sgl-project/sglang/issues/10088.
- The LMSYS draft-extend graph FIX is the direct precedent for our "draft launch/finish serialized" symptom: one captured graph for the draft-extend stage took the whole spec loop from 288 → 526 tok/s (1.82×) before any other change.

### Verify-batch kernels that keep an 8-12 row window efficient
- FlashInfer XQA ragged-Q per-row draft masking (SM120/121, v0.6.16+) is purpose-built: each request verifies its own draft count in one kernel; no padding to kVerifyMaxT. Combined with the proven 8→12 headroom, the window can ride acceptance instead of a fixed cap.
- Chain vs tree: LMSYS chose topk=1 chains because tree state indexing contaminates the KV/state path; chain verify over T=1..12 stays a plain batched decode kernel (our MMVQ 8-column family already prices this).
- Adaptive draft length: scheduling-level, not kernel-level — Cohere DSD keeps a per-(batch-size,K) goodput table from offline profiling, captures CUDA graphs for EVERY valid K so runtime K changes still hit a captured graph, measured +23% vs fixed-K at BS 128/256 (large-batch regime; at low BS it matches fixed-K) and notes MoE optimal-K is non-monotonic because verify loads extra experts (https://cohere.com/blog/hardware-aware-dynamic-speculative-decoding). Newer: Nightjar (learned per-step length, https://arxiv.org/html/2512.22420v2), Learning-to-Draft RL policies (ICLR 2026, https://proceedings.iclr.cc/paper_files/paper/2026/file/34345e243156da67605d4b63d71c8d98-Paper-Conference.pdf), vLLM RFC #48202 per-request proposal lengths (https://github.com/vllm-project/vllm/issues/48202); SGLang ships acceptance-driven adaptive length. None change kernels; all need multi-K graph coverage to avoid capture misses.
- Fit: Qwen engine window 9-16 ms at T=1-6, cap 8 with proven headroom to 12: (1) ragged-Q verify removes dead rows when acceptance collapses; (2) capture verify graphs for T=1..12 (12 shapes, small graphs) and pick T per recent acceptance — the DSD pattern at bs=1 simplifies to a goodput curve over T.
- Verdict: TRANSFER (window term). Two moves: adopt ragged per-row verify kernel semantics; capture per-T graphs. Tree-verify machinery stays DEAD for us — the lane's expert-dispatch cost dominates any tree topk>1 win, and chain verify keeps state handling trivial (LMSYS precedent).

### Draft-target weight sharing
- Nothing new beyond what vLLM/SGLang do (draft head folded into target graph; NEXTN-style shared layers). LMSYS's DSpark result (1120 tok/s, accept 9.95, block draft) shows the ceiling is in the DRAFT MODEL quality, not kernel sharing — a modeling lever, not a kernel one.
- Verdict: DEAD for kernel engineering (owned by model/draft-training choices).

## 4. Weight-path kernels

### W4A16 Marlin-class on sm_120 — WORKS now
- Marlin kernels compile and run on sm_120: vLLM v0.12.0 enabled NVFP4-on-SM120 via Marlin support (PR #24722); earlier stacks fell back to Marlin-W4A16 on RTX 5090 with a "no native FP4" warning (https://github.com/vllm-project/vllm/issues/47749 ; backend-selection fallback history: https://github.com/vllm-project/vllm/issues/31085). Community confirmation thread: https://www.reddit.com/r/LocalLLaMA/comments/1pe4xm4/vllm_v0120_supports_nvfp4_for_sm120_rtx_50xx_and
- Newer and faster than Marlin at bs=1: FlashInfer v0.7.1 CuTe-DSL NVFP4 W4A16 MoE/GEMM backends on SM12x — "W4A16 decode 1.36× faster than Marlin at one token" (DGX Spark measurement, same arch class); v0.6.17 gave SM12x W4A16 a TENSOR-CORE decode path for small batches (previously CUDA-core GEMV). https://flashinfer.ai/releases
- W4A8: Machete is DEAD on sm_120 by construction — it is wgmma/Hopper-only (https://developers.redhat.com/articles/2024/10/14/introducing-machete-mixed-input-gemm-kernel ; https://github.com/vllm-project/vllm/issues/35439: CUTLASS/Machete W4A8 need new kernels on Blackwell). Blackwell-native W4A8 replacement exists for MoE on SM120: FlashInfer W4A8 MegaMoE (v0.7.2, PR #4632, expert-parallel workstation MoE).
- NVFP4/MXFP4 on CONSUMER Blackwell: hardware FP4 tensor cores exist on sm_120 (unlike Hopper); software is now real: CUTLASS NVFP4 block-scaled tutorial for SM12x (https://research.colfax-intl.com/cutlass-tutorial-nvfp4-blockscaled-gemm-on-nvidia-rtx-pro-blackwell-gpus-sm12x), TransformerEngine NVFP4 fixed across RTX 50 line (https://github.com/NVIDIA/TransformerEngine/issues/2956), cuBLASLt block-scaled FP4 (`CUDA_R_4F_E2M1` + `CUBLASLT_MATMUL_MATRIX_SCALE_VEC16_UE4M3`) documented in cuBLAS 12.9+/13.x (https://developer.nvidia.com/blog/boosting-matrix-multiplication-speed-and-flexibility-with-nvidia-cublas-12-9 ; https://docs.nvidia.com/cuda/cublas/index.html ; version-minimums: https://github.com/nvidia/cudalibrarysamples/issues/310). Caveats: smem-limited kernels and TMA-WS grouped-GEMM tactics crash on sm_120a in some paths (vLLM PSA above) — use sm_120-native kernels, not sm_100 ports.
- Fit: our GPU-resident weights (attention + shared experts + router/dense) quantized W4A16/NVFP4 cut their GEMV bytes ~2-4× AND free VRAM against the 1.2 GB floor. The lane (CPU experts) is untouched — no kernel can help it.
- Verdict: TRANSFER, moderate (GPU term bytes + VRAM headroom). Cost: medium; risk: quantization quality on the GPU-resident stack (W4A16 Marlin is the safe step; NVFP4 CuTe the fast step).

### cuBLASLt for skinny GEMV (N=1-6) — wrong tool
- Evidence: cuBLASLt heuristics are tuned for tensor-core-friendly N; for GEMV-like decode shapes the production stacks (llama.cpp vec-dot/MMVQ, vLLM custom GEMV, TRT-LLM) all ship CUSTOM kernels instead; hand-written batched kernels beating cuBLAS on edge shapes is documented behavior (https://discourse.julialang.org/t/slow-matrix-multiplication-in-cublas-gemm-strided-batched-with-complexf64/132826); RL-generated kernels (CUDA-L2) beat cuBLAS/cuBLASLt by up to 22% on ordinary GEMM — heuristics are not a ceiling (https://arxiv.org/html/2512.02551v4). cuBLASLt FP4 also carries shape/alignment constraints (K multiples, block-scale layouts) unfriendly to N=1-6.
- Fit: our activation-GEMV family is already custom (MMVQ lineage, 8-column by design); cuBLASLt adds nothing for N=1-6; the byte lever is W4 quantization of whatever weights sit GPU-side.
- Verdict: DEAD as a replacement (keep custom GEMV; revisit cuBLASLt only if a shared-expert GEMM grows N beyond ~32 where TC paths pay).

## 5. Occupancy/latency mechanics for many-small-kernel chains

- Launch overhead baseline: ~2-10 µs per kernel launch (driver-dependent); graphs collapse N launches into one (~µs) + cheaper per-node dispatch; when kernels are tens of µs, launch overhead is 7-10% of wall (https://susun-blog.com/blog/pegainfer-3-cuda-graph ; https://arxiv.org/html/2501.09398v1 ; https://forums.developer.nvidia.com/t/launch-of-many-small-kernels-10x-slower-compared-to-one-kernel/350194). Graphs are not universally faster (https://stackoverflow.com/questions/78648536/) — capture must cover the actual dependency chain.
- The 48-doorbell chain is the textbook case for FUSION FIRST, graphs second: SGLang's replay data is flat across a 32× prompt-length range — "signature of launch overhead, not compute" — and their BCG replay beat torch.compile piecewise by ~17% precisely by removing per-segment dispatch (https://www.lmsys.org/blog/2026-08-17-advanced-cuda-graph).
- Breakable CUDA Graph (BCG) — NEW mechanism directly relevant to hybrid loops: capture WITH eager breaks at marked ops; eager output lands in a persistent boundary buffer whose device address was fixed at capture; the next captured segment reads it. This is exactly the shape of "graph runs GPU layers, host runs the lane in between": the lane handoff becomes an eager break inside one logical graph instead of a host sync tearing the graph apart. Shipped: SGLang PR #19102 (Feb 2026), default prefill strategy by v0.5.15; standalone library https://github.com/meta-pytorch/breakable-cuda-graphs; boundary-buffer trick credited to vLLM PR #9724.
- Persistent megakernel: Mirage MPK compiles whole-model inference into ONE persistent kernel with NVSHMEM barriers — 1.2-2.1× latency reduction, OSDI '26 (https://github.com/mirage-project/mirage ; https://arxiv.org/abs/2512.22219 ; https://zhihaojia.medium.com/compiling-llms-into-a-megakernel-a-path-to-low-latency-inference-cf7840913c17). Multi-GPU/cluster focus; the transferable invariant for us is the queued GDN persistent kernel: static task graph, resident threads, intra-kernel barriers replace 36 launches + their syncs.
- Fusion boundaries (LMSYS production census, Blackwell spec decode): per-NEXTN-step time split — MoE grouped GEMM 1215 µs, router/activation/glue 1127 µs (as much as the GEMM!), all-reduce 951 µs, dense GEMM 918 µs — GLUE is half the budget; they fused moe_align onto the pair axis, SwiGLU into the up-GEMM epilogue, and replaced an inductor combine with a Triton reduction joined to the PDL chain. Their host-pin removal alone was ~485 µs/step. https://www.lmsys.org/blog/2026-08-21-ling3-flash-spec-decode-blackwell
- `__grid_constant__` / grid-constant params: zero-risk hygiene for small kernels (parameter space instead of smem, compiler-visible strides); no standalone perf evidence needed — it is standard practice in CUTLASS/FlashInfer kernels.
- Cooperative groups: NOT usable inside conditional-node bodies (NVIDIA doc), and our use case (grid sync across the layer chain) is precisely what conditional graphs/persistent kernels replace.
- Fit: Qwen's 48 doorbell round-trips/verify-window: (a) fuse glue (router/accept/sampling microkernels) into neighbors — the LMSYS census says glue ≈ GEMM time; (b) BCG-style eager breaks for the lane handoff; (c) persistent kernel for the fixed-state GDN layers (queued) removes 36 launches from the chain.
- Verdict: TRANSFER (window + launch tax). Fusion-first is the cheapest per-byte of latency; BCG is the structural mechanism that lets graphs and host lanes coexist.
