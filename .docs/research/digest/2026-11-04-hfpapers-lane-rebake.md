# Lane + re-bake enablers — CPU kernel frontier and re-bake specs, 2026-11-04

## A. CPU-side memory-bound kernel frontier

### A1. Non-temporal loads for read-once lanes — our falsification CONFIRMED externally — SKIP (closed)
- (a) Mechanism: MOVNTDQA-class NT loads bypass cache for streaming reads. Question: does any source show NT loads helping PURE read streams from normal WB DRAM?
- (b) Evidence: NT loads are architecturally available only for write-combining (UC/WC) memory, not userspace WB RAM — "non-temporal loads are available only for write-combine memory … mostly reserved to … memory mapped devices and typically not available in the userspace"; conclusion in source: "non-temporal loads are not useful" (https://johnnysswlab.com/frugal-programming-saving-memory-subsystem-bandwidth ; https://stackoverflow.com/questions/37070/what-is-the-meaning-of-non-temporal-memory-accesses-in-x86 ; https://www.nic.uoregon.edu/~khuck/ts/acumem-report/manual_html/ch05s03.html). NT STORES (avoiding RFO) are the half that works; irrelevant to our read-only lane.
- (c) The nearest live alternative is NT prefetch (`_mm_prefetch(addr, _MM_HINT_NTA)` / locality-0): normal load path, line marked LRU-first-evicted. It controls cache pollution, it does not raise DRAM throughput; at 78 GB store / 96 MB L3 everything we touch is read-once already, so pollution control is a non-problem and the extra prefetch instructions only add bus traffic.
- (d) Verdict: **SKIP — falsification stands, no contradicting source found for pure WB loads.** No paper 2025-2026 contradicts. Queue closed.

### A2. Prefetch-distance tuning for streaming reads — no 2025-2026 result; lane already saturated — SKIP (cheap residual probe only)
- (a) Mechanism: software prefetch at distance D ahead of a linear read stream, tuned to DRAM latency × bandwidth.
- (b) Evidence status: targeted search found NO 2025-2026 paper tuning prefetch distance for DRAM-bound CPU GEMV (closest: prefetch-degree heuristics for heterogeneous memory, https://dl.acm.org/doi/fullHtml/10.1145/3695794.3695800; survey, https://arxiv.org/html/2606.09955v1; timeliness bound for HW prefetch, https://dada.cs.washington.edu/research/tr/2002/06/UW-CSE-02-06-03.pdf; greedy prefetch wastes bandwidth, https://users.ece.cmu.edu/~omutlu/bandwidth_lds_hpca09.pdf). Engineering consensus: for pure linear streams, Zen's stride/HW prefetchers plus the OOO window of 16 workers already saturate DRAM — software prefetch helps latency-bound single-thread or pointer-chasing, not a lane measured at 93-100% of its ceiling.
- (c) Quality cost: none (runtime only).
- (d) Verdict: **SKIP as a direction.** Our 93-100%-of-ceiling measurement IS the prefetch verdict: there is no unused bandwidth for a longer prefetch runway to harvest. Keep at most one 20-line A/B probe (MADV/hint on vs off) at next kernel-touch, then close.

### A3. TLB behavior for 78-109 GB stores at 49.5 GB/s — file-backed THP works in 2026 kernels IF the file is 2 MiB-aligned — TRANSFER (new layout spec, zero RAM cost)
This is the section that changes what we bake. Three independent sources pin the kernel mechanics:

- **madvise(2) rules for file-backed THP** (https://man7.org/linux/man-pages/man2/madvise.2.html): since Linux 5.4, khugepaged can collapse file-backed (page-cache) pages under MADV_HUGEPAGE, but only on hugepage-aligned boundaries, only if the mapping is hugepage-aligned WITHIN THE FILE, and (non-tmpfs) the file must not be open for write and the mapping executable. Real-world negative control: a memmap2 user set `Advice::HugePage` on a model-file mmap, saw the `hg` smaps flag, and NO huge pages ever materialized — the file was not 2 MiB-aligned at segment boundaries (https://github.com/RazrFalcon/memmap2-rs/issues/162, Jan 2026). Alignment-in-file is the binding constraint, not the madvise call.
- **UMLoad, arXiv 2611.04253** (https://arxiv.org/abs/2611.04253, full text https://arxiv.org/html/2611.04253 — NOT in the sibling digests; new find): proves the positive case at inference scale. They rewrite weight files offline ("Padding" + "Reorder") so every GPU-consumed range is 2 MiB-aligned, rely on OS THP for the page cache, and get 96.41-99.94% huge-page mapping coverage on Linux 6.16.9 / 6.8.12. Measured: WITHOUT alignment, 4 KiB fallback regresses decode time-between-tokens 1.3-10.3% (Intel 1.3-4.5%, AMD 3.4-10.3%); WITH alignment, decode stays within 0.1% (Intel) / 0.6% (AMD) of the copy-backed baseline. Padding costs 1.07-5.13% file growth, read at load, never transferred. Platforms: Core Ultra 9 185H (89.6 GB/s), Ryzen AI 9 HX 370 (120 GB/s), Jetson AGX Orin (204.8 GB/s). Load-time cuts 36.6-71.9% vs vanilla.
- **MADV_COLLAPSE** (6.1+) works eagerly on private anon, shmem, AND regular file-backed pages, even when global THP is `never`/`madvise` (https://www.kernel.org/doc/Documentation/admin-guide/mm/transhuge.html ; https://lwn.net/Articles/887753). Known bug: -EINVAL on file-backed collapse when pages are dirty — fix patch series landed Dec 2025 (https://patchew.org/linux/20251215084615.5283-3-shivankg@amd.com). Fedora 45 kernel 7.2.12 (our host) contains all of it.
- **Explicit hugetlbfs datapoint** (https://github.com/ggml-org/llama.cpp/issues/12444, Mar 2025): MAP_HUGETLB on a 377 GB DS-R1 store gave 10x LOAD speedup on a 1.5 TB server — load-time, not steady-state decode; matches our RAM-budget price-out. No steady-state number claimed.
- TLB math: 78 GB at 4 KiB pages ≈ 20M PTEs vs Zen5 L2 dTLB ~2K entries (data-TLB sizes unpublished in C&C; https://chipsandcheese.com/p/amds-ryzen-9950x-zen-5-on-desktop) → page walks interleave with every 2 MB of streamed weights; at 2 MiB pages the same store is ~39K mappings and each walk covers 512× more bytes.
- (d) Verdict: **TRANSFER — new baking-time invariant: every tensor segment (and every quant block boundary we want independent) 2 MiB-aligned in the GGUF/container, then MADV_HUGEPAGE + optional MADV_COLLAPSE on the mmap.** Zero RAM cost (PTE compression only), so it does not collide with the hugetlbfs price-out. It upgrades the queued "MADV_HUGEPAGE on anon pool" probe into a two-arm probe: arm 1 anon pool (khugepaged path, RAM-copied engines), arm 2 file-backed mmap store with 2 MiB-aligned re-bake (needs a re-quant or a repacking pass with padding ≤5%). Expected lane effect: not bytes but walk-free streaming — UMLoad's 1.3-10.3% decode regression when absent bounds the upside on the mmap engine (our 748B RAM-copied engine should see less; the 78 GB mmap lane the most).

### A4. Row locality / same-expert-across-tokens grouping — evidence + two mechanisms — TRANSFER (scheduling only)
- (a) Mechanism: group decode work by expert before dispatch so each worker streams one expert's weight rows contiguously (and warms its LUT/scales once) instead of interleaving experts across tokens.
- (b) Evidence:
  - **KTransformers (SOSP '25)**, https://madsys.cs.tsinghua.edu.cn/publication/ktransformers-unleashing-the-full-potential-of-cpu/gpu-hybrid-inference-for-moe-models/SOSP25-chen.pdf — the CPU-lane reference paper of the year. Relevant pieces: AMX kernel splits expert weights into tasks in a lightweight task queue with dynamic work-stealing (beats static OpenMP split under expert load imbalance; 1.83x prefill); tasks are CO-SCHEDULED BY TARGET EXPERT to maximize cache hits, gate/up/down fused into two batches; expert-deferring (defer non-top-2 experts' compute across the layer boundary onto CPU during next GPU attention) lifted CPU utilization 74%→100% and decode +33-45% on DS-V3 (dual Xeon 8452Y, 1 TB DDR5/socket, MLC 220 GB/s intra-socket, A100/4080 GPUs). Their NUMA result: matrix-splitting every expert across sockets + reduce-scatter beats whole-expert-per-socket placement, 1.63x decode — dual-socket only; our AM5 is UMA, so this is context, not a lever.
  - **Expert-locality statistics** (llama.cpp issue #20757, https://github.com/ggml-org/llama.cpp/issues/20757): routing is concentrated (Gini ≈ 0.76, "44% expert overlap between consecutive tokens", ~15-20% of experts absorb ~80% of tokens on some models; concentration is model-dependent — Qwen-Coder-style models concentrate, gpt-oss is flat); cumulative-LFU simulation on Qwen3-30B-A3B: 88 experts/layer ≈ 98.8% hit rate. llama.cpp has since MERGED a hot-expert GPU cache (`--moe-cache-mib`) + an expert slot-pool RFC track (#24528, https://github.com/ggml-org/llama.cpp/discussions/24528; #28248, https://github.com/ggml-org/llama.cpp/discussions/28248).
- (c) Quality cost: none (bit-exact reordering of the same math).
- (d) Verdict: **TRANSFER — sort the pool's dispatch queue by expert id (within-token and across the small batch window) before threading.** Bytes unchanged; the gain is L2/L3 row reuse and one-time LUT/scale warmup per expert per layer. Expected effect is second-order (our batch-1 lane reads each expert's rows exactly once anyway); it compounds with any future batch>1 / speculative window where the trace shows consecutive-token overlap ~44%. Measurable on our side: expert-profile telemetry already gives the concentration stats to predict per-window savings before coding.

### A5. Zen4/Zen5 >95%-of-theoretical-peak GEMV — no external paper does it; our lane is at published state of the art — negative result (binding-law confirmation)
- Calibration numbers found: Zen 4 streaming ≈ 76% of theoretical DDR5 (https://chipsandcheese.com/p/amds-zen-4-part-2-memory-subsystem-and-conclusion); KTransformers 220 GB/s measured vs 307 GB/s theoretical on 8-channel Xeon (72%); community decode bandwidth on desktop llama.cpp typically 50-70% of theoretical (https://github.com/ggml-org/llama.cpp/issues/26484 proposes a bandwidth metric because nobody measures it); Zen 5 desktop: per-CCD Infinity Fabric caps 64 GB/s read (32 B/cycle @ 2 GHz), DDR5-6000 dual-channel = 96 GB/s theoretical, latency ~70 ns, "closer to Fabric limits than Zen 4" (https://chipsandcheese.com/p/amds-ryzen-9950x-zen-5-on-desktop; DDR5 scaling curve flattens past 6000-7200, https://www.techpowerup.com/review/ddr5-memory-performance-scaling-with-amd-zen-5).
- **No 2025-2026 source shows real GEMV above ~95% of theoretical DDR peak on Zen4/Zen5.** Everything published sits at 50-76% of theoretical. Our lane at 93-100% of a PROVEN 49.5 GB/s practical ceiling is above the published state of the art; the ceiling itself (≈52% of 96 GB/s nominal) is machine-real, and the sweep found no kernel trick that moves the DRAM-side ceiling itself on AM5.
- (d) Verdict: **The lane law survives adversarial reading: only FEWER BYTES (Section B) or walk/row locality (A3/A4) remain.** No CPU-kernel paper of 2025-2026 offers a fourth lever for a saturated read-once lane.

## B. Re-bake pipeline enablers — full-text specs (verified from paper bodies + repos)

### B1. PuzzleMoE (2511.04805) — exact algorithm, released code, 3-bit quality — TRANSFER (closest to runnable NOW)
Full text: https://arxiv.org/html/2511.04805 · HF: https://huggingface.co/papers/2511.04805 · Code VERIFIED: https://github.com/Supercomputing-System-AI-Lab/PuzzleMoE (Apache-2.0; `scripts/experts_merging.py` single entry point incl. `--real_merge` bit-packing; `triton_kernel.py` fused dual-expert GEMM with on-the-fly mask/sign decode; modeling patches for Mixtral / Qwen3-30B-A3B / Qwen1.5-MoE / DS-MoE-16B).
- (a) Mechanism — pairwise dual-mask merge, exact equations:
  1. Pair experts (default RANDOM pairing; evolutionary search grouping adds almost nothing, Table 7). k≥3 rejected: 2^k−1 mask choices explode and 3-expert encoding needs 5 bits > 3 spare exponent bits.
  2. Similarity mask: symmetric percent difference Δ = ‖|W_i|−|W_j|‖ / (|W_i|+|W_j|); M_sim = 1{Δ ≤ τ_sim}, τ_sim = 0.4 fixed for all models/tasks (best range 0.3-0.5, Fig 5). Sign-safe by design: magnitudes only, signs stored separately. Paper derives the closed-form null model (half-normal ratio → arctan formula, Appendix B.2) — for σ1≈σ2 experts, τ=0.4 keeps a predictable fraction, so the mask is DATA-FREE.
  3. Saliency mask: Wanda-style A_i = |W_i| ⊙ ‖X_i‖₂ per expert on ONE forward pass of 128 samples × 2048 tokens (C4 default; Table 5 shows C4 vs MATH calibration moves nothing — task-agnostic). M_i^sal = 1{A_i ≥ A_j}, complementary.
  4. Merged weight: W_merged = M_sim ⊙ (|W_i|+|W_j|)/2 + (1−M_sim) ⊙ (M_i^sal ⊙ |W_i| + M_j^sal ⊙ |W_j|). Store W_merged, masks M_i = M_i^sal ∨ M_sim, M_j, signs S_i, S_j.
  5. Inference reconstructs Ŵ_i = (−1)^{S_i} ⊙ M_i ⊙ W_merged — i.e. signs RE-APPLIED at read time, exactly as summarized in our queue.
  6. Bit-pack: BF16 exponents of expert weights sit in [112,128] → shift by 112 into 5 bits, freeing 3 exponent bits to carry {mask_i, mask_j, sign} per element; zero ppl cost (Table 1). Decode Algorithm 1: mask bit at bit (13−expert_pos), sign at (15−expert_pos), exponent rebuild `exp = (W & 0x0F80) + (112<<7)`.
- (b) Numbers: 2 min to compress Mixtral-8x7B on 2×A100 (DS-MoE 10 min; 45x faster than D2's SVD pipeline). Accuracy at 50% expert reduction: Mixtral 72.6% avg (best of all methods; +16.7% MMLU over prior), DS-MoE −0.5%, Qwen1.5-MoE −0.5%, Qwen3-30B-A3B −1.4%. 1.28x inference speedup (Mixtral), 1.19x (Qwen3).
- (c) Quality at 3-bit merged (our regime): merge-then-quantize = symmetric group-128 quant on W_merged; avg bitwidth formula (2 sign + 1.58 ternary-mask + 3 quant + 0.125 scale)/2 = **3.35 bpw at 80% compression**, Mixtral −1.7%, DS-MoE −1.0% vs full (Fig 5b, Table 10, Appendix B.3.1). At 50% sparsity, PuzzleMoE+3-bit ≈ NAEE-25%+AWQ-4-bit.
- (d) Verdict: **TRANSFER — the only re-bake enabler with runnable released code today, and the merge→requant shape maps 1:1 onto a ggml re-bake: dequant our IQ packs → merge pairs (similarity mask data-free; saliency mask from OUR 1,615-window trace routed-activation norms — strictly in-domain, which 2610.41366's §6.4 shows matters more than any operator choice) → requant merged experts to IQ3_S with trace-imatrix.** Expected lane effect: merged experts halve that pair's lane bytes → bytes scale with merge ratio; at 25% merge ≈ −12% lane bytes for the merged layers. Caveats for our pack: (i) their saliency/calibration numbers are BF16-checkpoint experiments — on already-IQ1_M/IQ2/IQ3 packs the merge baseline carries existing quant error, so expect their −0.5-1.4% to roughly add to existing pack error; bake a 1-layer pilot first; (ii) the bit-packed exponent trick is GPU-format — irrelevant to ggml, drop it, keep masks+signs as sidecar tensors (≤0.5 bpw on merged pairs at IQ3 rates); (iii) merge with REAP-style router-row deletion decision, not random pairing, if we want the pruning-merging hybrid — but keep M_sim τ=0.4 and the sign-reapply law untouched.

### B2. Channel-selection reader (2610.37386) — sketch, top-k statistic, recovery, pack format — TRANSFER (biggest byte cut; CPU port required)
Full text: https://arxiv.org/html/2610.37386 (sibling digests hold the verdict; this is the build spec). Code VERIFIED: https://github.com/AidenGeunGeun/calibration-free-moe (Apache-2.0; `reader/sketch.py` resident ternary sketch, `reader/progressive.py` Triton screen+select+recover+read-accounting, vLLM 0.29.0 patches, baselines, contract tests). Triton/CUDA only — CPU port of screen + top-k is ours to write (scalar-friendly: ternary MACs + one exact top-k over ≤ (tokens×k_experts×channels)).
- (a) Mechanism, offline build (bake-time, per layer):
  1. Rotate each gate row g_j and up row v_j with randomized Hadamard R in 128-coordinate blocks (outlier flattening; orthogonal → activations unchanged: (Rg_j)ᵀ(Rx) = g_jᵀx).
  2. Store each 128-block of Rg_j, Rv_j as ternary codes {−1,0,1} + one FP16 scale + block mean-squared error ρ_b. 256 B BF16 → ~30 B: sketch ≈ 7% of the BF16 checkpoint (gate+up only), recovery map +0.5%.
  3. Precompute per-channel down norms ‖d_j‖; TRANSPOSE every down projection D_e so column j becomes a row (kept-channel reads contiguous — this IS the selected-channels-first layout).
- (b) Runtime per token per layer: rotate x once → sketch GEMV gives ĝ_j, v̂_j estimates; partial screen at low budgets reads ternary codes only at the 80 largest-|Rx| coordinates per 128-block (fixed 80/128 chosen once on OLMoE dev data, reused everywhere). Score in OUTPUT units so channels compete ACROSS the token's experts: s_j = w_j·‖d_j‖·|φ(ĝ_j)·v̂_j|; exact top-k across all candidates (e.g. 6,144 for Qwen3-30B; one expert may get many channels, another none). Kept channels load full weights; skipped channels recovered by rank-32 map: ŷ = Σ_{K} w_j d_j a_j + U Σ_{S} w_j b_j p_j, where U = top-32 left singular vectors of the layer's stacked down columns, b_j = Uᵀd_j (precomputed), p_j = φ(ĝ_j)v̂_j reused from the screen. From 28.7% reads up: full sketch + Gauss-Hermite error-aware score s_j (Appendix G).
- (c) Numbers + quality: reads 12.8% / 17.8% / 28.7% of routed-expert bytes (sector-exact accounting, GPU-profiler-verified 18.3% vs 17.8% counted); accuracy 94.5-98.1% of full model at 17.8% (Qwen3-Thinking, Gemma 4, Qwen3.5); MoE block 1.60-1.90x batch-1 vs OPTIMIZED vLLM (whose kernels stream at 83-88% of achievable BW — a strong baseline), whole model up to 1.88x. Works on quantized checkpoints (GPTQ-4: KL 0.045 @ 18.9% reads; AWQ-3: KL 0.075 @ 19.7%) — but the sketch+recovery overhead grows to ~34% of BF16 routed bytes on a 4-bit store / ~20% on 3-bit (Table 3 discussion).
- Pack format for selected-channels-first on OUR store (derived from their load-time transforms, no paper figure needed): per expert, permute gate/up rows and down columns by a fixed channel order (the sketch's coordinate order); store {sketch codes+scale+ρ_b (2-bit-class), permuted IQ gate/up blocks, transposed IQ down, per-channel ‖d_j‖} — so a selected channel's gate row, up row, and down column are each ONE contiguous extent; unselected extents are never touched. Bytes moved per token ≈ sketch + k-of-N channel extents + U,b_j ≈ 17.8% of today's routed bytes + ~7% resident overhead on the BF16-equivalent store (~5.5 GB on 78 GB).
- (d) Verdict: **TRANSFER — the largest byte cut on the table (−82% routed reads at 94.5-98.1% quality), and the only mechanism that beats the lane law rather than riding it.** Two gates before a bake: (1) CPU port of screen+top-k must fit in the 49.5 GB/s budget's compute slack (our lane saturates DRAM with 16 workers — the ternary screen is ~2-bit MACs, likely fine, but it is a MEASURED unknown, not a given); (2) accuracy transfer to IQ1_M/IQ2/IQ3_S packs is unproven (paper is BF16 + GPTQ-3/4; our sketch would be built from dequantized weights, adding one source of screen noise). Pilot: one layer, one budget, KL-vs-full on our 1,615-window trace. interacts with B1/B3: REAP or merge shrink the candidate set first; channel-selection then cuts reads inside survivors.

### B3. Replacement-operator law (2610.41366) — trained-scale gate rule + tilt fill, exact spec — TRANSFER (zero-cost guardrail + REAP companion)
Full text: https://arxiv.org/html/2610.41366 (sibling digests hold the verdict; this is the build spec). Code: NOT released (Appendix G.5: "Code, masks and fitted operators are not yet public"). MoNE's code (the rank-0 base) IS public and reproduced to ≤0.32 pts by the paper.
- (a) Trained-scale rule, exact equations. Rerouting survivors after pruning has two gate scales; use the one the router was TRAINED with:
  - Softmax routers trained WITHOUT top-k renormalization (OLMoE, DSv2-Lite): keep g_j^keep = p_j (raw softmax probs; top-k sums ≪ 1). Renormalizing g_j^renorm = p_j/(1−P_pruned) costs **0.8-8.5 points** at every ratio (worst: DSv2-Lite 75% −8.47), lowers ranking AUC 0.03-0.14 on two-choice tasks, and FLIPS whether rerouting beats MoNE's constant.
  - Routers trained WITH renormalization (Granite: renorm +2.08 at 50%; Moonlight: +1.68 at 50%, +1.60 at 75%): renormalize over the SELECTED SURVIVORS — that is the trained scale.
  - **Our engines: Qwen3-MoE / DeepSeek-family routers are softmax-top-k WITH renormalized gates (norm_top_k_prob=True class) → trained scale = renormalize over survivors = what REAP-style code already does.** The paper's cost lands on the OTHER convention — so for us this is a verification item (one config grep), not a change. For any non-renorm router we ever bake (OLMoE-class), keep-scale rerouting needs the PRUNED experts' router rows retained at bake time (d values each) — a checkpoint-schema requirement; note vLLM compressed-tensors grew a REAP-style pruned + MoNE-style novice checkpoint schema in Oct 2026 (llm-compressor PR 3343 / compressed-tensors PR 938, cited in the paper).
- (b) Tilt fill (tilted novice), exact spec: for each pruned expert i with routed calibration tokens Ω_i, replace MoNE's constant with N_i(x) = μ_i + U_i·clip(V_i·x − φ̄_i, ±c_i):
  - Fit: rank-r reduced-rank ridge regression of E_i(x) on x, closed form from STREAMED float64 sufficient statistics (count, means, C_xx, C_xy; unweighted by gates), ridge λ·diag(C_xx) with λ=10⁻², Cholesky L of the ridged Gram, full-rank solution A, SVD of LᵀA → keep top-r: V_i = Σ_r Q_rᵀL⁻¹ (r×d), U_i = W_r (d×r). r=32 default.
  - φ̄_i = V_i·x̄_i folds the input mean away (nothing of dim d stored beyond μ_i); clip c_i = 4σ of projected features (touches ~0.01% of values).
  - Params per pruned expert: 2rd + 2r (≈1.2-1.8% of the pruned model at 50%). Experts with ≤4r routed calibration tokens fall back to the constant.
  - Fit budget: needs 1,000 sequences × 4,096 tokens (100 sequences → gain unstable ±2.5 pts across slices; §B.5). We have 1,615 windows + expert-profile telemetry — need routed-token coverage per candidate-pruned expert; experts below the 4r floor keep the constant.
- (c) Numbers: tilt beats MoNE's constant +3.45 (OLMoE 50%), +1.37 (Moonlight 50%), +2.80/+3.27 at 75%, stable ≤0.20 pts across calibration draws; rank-8 keeps 82% of the gain at a quarter of the params on OLMoE; at 75% cuts OLMoE WikiText ppl 1434→172 vs rerouting's 1280. Survives GPTQ 4- and 3-bit quantization in 11 of 12 settings (interaction ≤0.16 pts) — rerouting's gain ERODES under quantization in 11 of 12 (mechanism, untested: rerouting pushes every slot through quantized experts; tilt/constant slots stay 16-bit). The tilt keeps 2/3-3/4 of MoNE's batch-32 prefill saving; rerouting keeps almost none (5-7% at batch 32; order reverses at batch 1 — launch-bound).
- Quality-cost boundary from their evaluation section (binds our bake too): at 25% pruning MoNE constants keep 92-97% of multiple-choice but 5-65% of GSM8K and 0-17% of code under general-text calibration; in-domain masks rescue generation (GSM8K-calibrated 25% mask keeps 97-100% of dense GSM8K). Calibration DOMAIN moves the mask 4-9× more than resampling. → our re-bake masks and tilt fits must come from the 1,615-window trace (in-domain by construction), NOT generic C4/wiki text.
- (d) Verdict: **TRANSFER — (1) trained-scale check is a free guardrail wired into the queued REAP re-bake; (2) tilt fill is the accuracy-floor upgrade on top of REAP constants, implementable in ~200 lines from the spec above (no code release; MoNE repo is the rank-0 scaffold); (3) under 3-bit requant, prefer tilt/constant slots over rerouting whenever slots must run through quantized weights — the paper's only quantization-robust operators.**

### B4. Which re-bake is closest to runnable on OUR mixed IQ1_M/IQ2/IQ3 packs
- Ranking: **PuzzleMoE (runnable today, released code, merge→requant is our native shape) > tilt fill + trained-scale (spec-complete, ~200 lines, rides the queued REAP bake, calibration = our trace) > channel-selection reader (biggest win, two measured-unknown gates: CPU port cost, IQ-pack screen accuracy).**
- Calibration data for all three: the 1,615-window trace + expert-profile telemetry. Specifically: (i) PuzzleMoE saliency masks → per-expert routed-activation norms ‖X_i‖₂ from the trace (128 samples × 2048 tokens equivalent; our windows already exceed the paper's calibration volume); (ii) similarity mask → data-free (τ_sim = 0.4); (iii) tilt fits → routed (x, E_i(x)) pairs per candidate-pruned expert, ≥4r tokens floor, 1,000-sequence-class volume — subsample the trace to fit, hold out windows for KL check; (iv) channel-selection → nothing at bake (data-free), only the pilot KL evaluation uses the trace. Domain warning from B3 applies: do not substitute generic text for the trace anywhere a mask or fit touches it.
